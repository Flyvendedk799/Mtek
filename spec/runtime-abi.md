# Program Format and Browser Runtime Contract (v0.1)

- Repository path: `spec/runtime-abi.md`
- Status: Normative for v0.1. Runtime ABI version **1**, manifest schema version **1**.
- Implemented by: `crates/mtek-compiler/src/emit_js/`, `src/package/` (compiler side); `packages/runtime-web/` (runtime side).
- Depends on: `spec/gpu-layout.md`, `spec/scenes.md`, `spec/materials.md`, `spec/diagnostics.md`.

---

## 1. Responsibilities

| Compiler emits | Runtime owns |
|---|---|
| executable logic as JavaScript (initialisers, handlers, binding evaluators, layout writers, pure/cpu functions) | device and canvas, the frame loop and scheduler, input, transforms, resources and their lifetime, rendering, asset loading, physics adapter loading, hot reload, diagnostics delivery |
| declarative data as JSON (manifest: structure, layouts, shaders, assets, capabilities, symbols, spans) | interpreting the manifest's *data* — never interpreting program *logic* from JSON (blueprint §2.2) |
| WGSL modules and their span maps | creating shader modules and pipelines, capturing their validation errors |

## 2. Build output

`mtek build` writes (blueprint §5.3):

```
dist/
  index.html                       # minimal page: canvas + bootstrap module (§6.5)
  app.js                           # the program module (§3)
  app.js.map                       # Source Map v3: app.js -> .mtek sources
  app.d.ts                         # host-facing declarations (§6.4)
  runtime.d.ts                     # declarations of the runtime host API, referenced by app.d.ts
  runtime.<h16>.js                 # the runtime bundle (ESM), content-addressed
  program.manifest.json            # the manifest (§5)
  shaders/<h16>.wgsl               # one per material (and probe shaders in test builds)
  shaders/<h16>.mtek-map.json      # WGSL span map (§5.4)
  assets/<h16>.<ext>               # packaged assets (spec/assets.md)
  physics/<h16>.js                 # only if the program uses physics (spec/physics.md)
```

- `<h16>` is the first 16 lowercase hex digits of the SHA-256 of the file's bytes; the manifest records the full 64-digit hash.
- `index.html`, `app.js`, `app.d.ts`, `runtime.d.ts` and `program.manifest.json` have fixed names so hosts can reference them.
- **Reproducibility.** Two builds of the same inputs with the same compiler produce byte-identical `dist/` trees (no timestamps, absolute paths, random ids, or hash-map iteration order in outputs). A test enforces this (`spec/testing.md` §7).
- **Replace on success** (not atomic): the build writes into the sibling directory `<out_dir>.tmp-<buildId>/`; only if everything succeeded it renames the existing `<out_dir>` to `<out_dir>.old-<buildId>`, renames the temporary directory to `<out_dir>`, then deletes the `.old` directory (Windows cannot rename onto an existing directory, hence the three steps). A failed build deletes its temporary directory and leaves the previous output untouched.

## 3. The program module (`app.js`)

An ES module with this exact export surface (ABI 1):

```js
// Generated by mtek 0.1.0 for language 0.1 — do not edit.
import * as rt from "./runtime.3f9c0a1b2c3d4e5f.js";
export { mountMtek } from "./runtime.3f9c0a1b2c3d4e5f.js";

export const abi = 1;
export const baseUrl = new URL("./", import.meta.url);
export const manifestUrl = new URL("./program.manifest.json", import.meta.url);

export const writers = {   // keyed by layout id (spec/gpu-layout.md §5); writer functions themselves are module-private
  "builtin:frame":               { all: w_builtin_MtekFrame,  fields: { /* … */ } },
  "builtin:object":              { all: w_builtin_MtekObject, fields: { /* … */ } },
  "material:src/main.mtek::Pulse": { all: w_1f3a9c2e_Pulse,     fields: { tint: w_1f3a9c2e_Pulse_tint, phase: w_1f3a9c2e_Pulse_phase } },
};

// Every user function (pure fn and cpu fn) takes ctx first: f_pulse(ctx, t). Keyed by symbol.
export const functions = { "src/main.mtek::pulse": f_pulse };

export const scenes = {
  Demo: {
    init,                 // (ctx) => void : state, entity state/fields, material instance values (§4.3)
    update,               // (ctx, dt) => void, or null
    fixedUpdate,          // (ctx, dt) => void, or null
    entityUpdate,         // array indexed by static entity index: (ctx, self, dt) => void, or null
    entityFixedUpdate,    // same shape
    events,               // { key_down: [{ key: "Space", owner: -1 | entityIndex, fn }], … } — declaration order;
                          // `key` is the DOM KeyboardEvent.code ("Space", "KeyA"), never the Mtek name.
                          // fn signature: (ctx, self /* entity record, or null for scene handlers */, arg /* PointerEvent | entity_ref | undefined */) => void
    bindings,             // array indexed by binding id: (ctx) => value
  },
};

export const prefabs = {
  "src/props.mtek::Crate": {
    init,                 // (ctx, self, params) => void — params: object of evaluated prefab params by name
    update,               // (ctx, self, dt) => void, or null
    fixedUpdate,          // (ctx, self, dt) => void, or null
    events,               // same shape as scene events; owner is always "self"
    bindings,             // array: (ctx, self) => value
  },
};

export default { abi, baseUrl, manifestUrl, writers, functions, scenes, prefabs };
```

Generated code imports only `rt` math/value helpers and receives everything else through the `ctx` argument (§4.2). It never touches WebGPU, the DOM, `globalThis`, `fetch`, timers, or `Math.random` directly. A lint test (`spec/testing.md` §7.3) greps emitted code for forbidden identifiers.

**Name mangling.** Every user identifier that becomes a JavaScript *binding* gets a kind prefix — `f_` functions, `l_` locals and loop variables, `a_` function/handler parameters — so no user name can collide with a JavaScript reserved word, a runtime helper or a generated helper (`w_…` writers, `rt`, `ctx`). Scene state, entity state, prefab params and fields are object *properties* and keep their original Mtek names (`ctx.s.speed`, `self.state.hits`, `self.params.origin`); property names cannot collide with reserved words.

## 4. Values and the generated-code context

### 4.1 CPU value representation

| Mtek | JavaScript | Invariant maintained by generated code and `rt` helpers |
|---|---|---|
| `f32` | `number` | always the result of `Math.fround` |
| `i32` | `number` | always `x \| 0` |
| `u32` | `number` | always `x >>> 0` |
| `bool` | `boolean` | |
| `string` | `string` | |
| `vec2` / `vec3` / `vec4` | `{x, y}` / `{x, y, z}` / `{x, y, z, w}` | components f32-rounded; **never mutated after creation** (operations create new objects) |
| `quat` | `{x, y, z, w}` | same |
| `color` | `{r, g, b, a}` | same; linear |
| `mat4` | `Float32Array(16)`, column-major | never mutated after creation |
| `struct` | plain object with the declared field names | never mutated after creation |
| `array<T, N>` | `Array` of length N | never mutated after creation |
| `entity_ref` | `{ slot: number, gen: number }` (frozen) | |

Because values are never mutated in place, sharing a reference is semantically a copy, which is what value semantics require. Assignment to a vector component (`self.position.y = 0.0`) emits construction of a new vector. Allocation cost is accepted for v0.1 and measured by the runtime benchmark before any optimisation.

`rt` exports the helpers generated code uses: `v2 v3 v4 quat color` constructors, `fround`-disciplined vector/matrix/quaternion operations (`v3add`, `v3scale`, `qmul`, `qrotate`, `m4mul`, …), integer helpers (`idiv`, `irem`, `udiv`, `urem` implementing `spec/language.md` §6.3), conversions (`f2i`, `f2u`), and every pure intrinsic of `spec/stdlib.md` §6 with WGSL-matching semantics (`round` = ties-to-even, …). These live in `packages/runtime-web/src/math/` and have their own unit tests against the conformance table. The helper names, the index from Mtek operations to helpers, the CPU results of non-portable cases and the table format are decision 0037.

### 4.2 The context object (`ctx`)

The runtime passes `ctx` to every generated function. Its shape is part of ABI 1:

| Member | Meaning |
|---|---|
| `ctx.s` | scene state object (`ctx.s.speed`). Read and write directly (`ctx.s.speed = v`). |
| `ctx.e[i]` | static entity record by index (manifest order). An **entity record** — the type of every `e`/`self` parameter in this table — has: `position`, `rotation`, `scale`, `visible` (read directly; write only through the setters below), `state` (object; read **and write directly**, e.g. `self.state.hits = v`), `params` (prefab params, read-only), `mat` (material instance: `p` = current param values, read-only; write through `setParam`), `ref` (its `entity_ref`). |
| `ctx.cam` | the active camera record: `position`, `target`, `rotation`, `projection` fields. |
| `ctx.frame` | `{ time, delta, index }` (f32/f32/u32 already converted). |
| `ctx.setTransform(e, field, value)` | `field` ∈ `"position" | "rotation" | "scale"`; validates scale (`E8090`), marks transform dirty. |
| `ctx.setVisible(e, value)` | |
| `ctx.setParam(e, name, value)` | writes the instance's mirror through the generated field writer; validates opaque colours (`E8100`). |
| `ctx.setCamera(field, value)`, `ctx.setLight(e, field, value)` | |
| `ctx.spawn(prefabId, params) → entity_ref`, `ctx.destroy(ref)`, `ctx.alive(ref)` | `spec/scenes.md` §9 |
| `ctx.body(refOrEntity)` | physics commands (`spec/physics.md` §3) |
| `ctx.random()`, `ctx.print(message, spanId)`, `ctx.isKeyDown(code)` | CPU intrinsics |
| `ctx.warn(code, spanId)` | report a mapped runtime warning (e.g. index clamping `W8030`, once per span) |

Ownership rules (`spec/scenes.md` §8) are enforced **statically**; the setters only re-validate values. Generated code passes **span ids** (indices into the manifest `spans` table) so the runtime can map any run-time diagnostic to the Mtek source.

### 4.3 Initialisation

`scenes.X.init(ctx)` runs once with a `ctx` whose state objects are pre-created with every declared key set to its zero value. It executes the initialisation order of `spec/scenes.md` §11 as straight-line generated code (state initialisers, entity params/state/fields, material instance values written through the writers). Then the runtime evaluates all bindings once, propagates transforms, creates physics bodies, and loads startup resources.

## 5. The manifest (`program.manifest.json`)

JSON, UTF-8, keys in a fixed order, schema version 1. A JSON Schema for it is checked in as `spec/manifest.schema.json` and the runtime validates the manifest against a compiled form of that schema before using it.

```json
{
  "manifestSchema": 1,
  "runtimeAbi": 1,
  "languageVersion": "0.1",
  "compilerVersion": "0.1.0-dev",
  "buildId": "<sha256 of build identity, §5.3>",
  "targetProfile": "webgpu-core-2026",
  "requiredCapabilities": { "features": [], "limits": {}, "wgslLanguageFeatures": [] },
  "subsystems": { "physics": false },
  "runtimeConfig": { "fixedStep": 0.016666668, "maxCatchUpSteps": 4, "maxFrameDelta": 0.1, "maxEntities": 16384, "pauseWhenHidden": true },
  "entryScene": "Demo",
  "sources": [ { "id": 0, "path": "src/main.mtek", "sha256": "…" } ],
  "spans": [ { "file": 0, "start": 412, "end": 431, "startLine": 18, "startColumn": 16, "endLine": 18, "endColumn": 35 } ],
  "symbols": [ { "id": "src/main.mtek::Demo.Cube", "kind": "entity", "span": 3 } ],
  "layouts": [ /* layout records, spec/gpu-layout.md §5 */ ],
  "shaders": [ { "hash": "…", "url": "shaders/1a2b….wgsl", "map": "shaders/1a2b….mtek-map.json", "material": "src/main.mtek::Pulse", "vertexEntry": "mtek_vs", "fragmentEntry": "mtek_fs", "vertexAttributes": ["position"], "surfaceInputs": [] } ],
  "materials": [ { "id": "src/main.mtek::Pulse", "layout": "material:src/main.mtek::Pulse", "shader": "…", "resources": [], "params": [ { "name": "tint", "type": "color", "span": 5 } ] } ],
  "meshes": [ { "id": "mesh:0", "kind": "box", "size": [1, 1, 1] } ],
  "assets": [],
  "scene": { /* §5.2 */ }
}
```

Every `spans` entry carries the half-open byte range into the file as stored on disk and the 1-based line and column of both ends (columns count Unicode scalar values), computed by the compiler's source manager exactly as for compiler diagnostics; the runtime copies them verbatim into the `source` of a diagnostic and never ships or reads source text (decision `spec/decisions/0019-manifest-spans-carry-line-columns.md`).

`requiredCapabilities.limits` lists only limits **above** the WebGPU defaults that the program needs (the v0.1 profile `webgpu-core-2026` is exactly the default limits, so it is `{}`); `features` lists optional WebGPU features (none in v0.1; `timestamp-query` is requested opportunistically by dev builds and never required).

### 5.1 Compatibility (blueprint §5.3)

**Order of checks.** The runtime first reads only `manifestSchema`, `runtimeAbi` and `languageVersion` (the schema types them as plain `integer`/`integer`/`string`, never as `const`, precisely so this check can run first) and rejects mismatches with `E8003`; only then does it validate the whole manifest against the schema (`E8006` on failure). An old or future program therefore always gets the accurate "incompatible program" diagnostic, never a schema error.

The runtime **rejects** a manifest whose `manifestSchema` or `runtimeAbi` it does not implement, whose `languageVersion` it does not support, or whose `requiredCapabilities` the device cannot satisfy — `mountMtek` fails with `E8003` (incompatible program) or `E8002` (device below profile), naming the mismatching field. There is no "probably compatible" path. v0.1 runtimes implement exactly `manifestSchema 1`, `runtimeAbi 1`, `languageVersion "0.1"`.

### 5.2 Scene structure

```json
"scene": {
  "name": "Demo", "symbol": "src/main.mtek::Demo",
  "fields": { "clearColor": [0.0052, 0.0070, 0.0091, 1.0], "ambientColor": [1.0, 1.0, 1.0, 1.0], "ambientIntensity": 0.0, "gravity": [0.0, -9.81, 0.0] },
  "state":    [ { "name": "speed", "type": "f32", "symbol": "src/main.mtek::Demo.speed" } ],
  "cameras":  [ { "name": "Main", "symbol": "…", "projection": "perspective", "hasTarget": true, "active": true } ],
  "entities": [ { "index": 0, "name": "Cube", "symbol": "…", "parent": null,
                  "mesh": "mesh:0", "material": { "id": "src/main.mtek::Pulse", "instance": 0 },
                  "light": null, "body": null, "collider": null,
                  "state": [], "update": true, "fixedUpdate": false } ],
  "materialInstances": [ { "index": 0, "material": "src/main.mtek::Pulse", "entity": 0,
                           "params": [ { "name": "tint", "class": "bound", "binding": 0 },
                                       { "name": "phase", "class": "bound", "binding": 1 } ], "shareable": false } ],
  "bindings": [ { "id": 0, "target": { "kind": "param", "instance": 0, "name": "tint" },
                  "deps": [ { "kind": "state", "name": "tint" } ], "order": 0, "span": 7 } ],
  "hostInputs": [ { "name": "tint", "target": { "kind": "state", "name": "tint" }, "type": "color", "codec": "color-hex-opaque" } ],
  "lights": []
}
```

- `fields` carries the **constant** scene-field values (linear colours as `[r, g, b, a]`, the result of compile-time colour conversion), so the runtime needs no code to obtain them.
- Binding **target** kinds: `{ "kind": "transform", "entity": i, "field": "position" | "rotation" | "scale" }`, `{ "kind": "visible", "entity": i }`, `{ "kind": "param", "instance": i, "name": … }`, `{ "kind": "camera", "field": "position" | "target" | "rotation" | "projection.fov_y" | "projection.height" | "projection.near" | "projection.far" }`, `{ "kind": "light", "entity": i, "field": "color" | "intensity" }`.
- Binding **dependency** kinds: `{ "kind": "state", "name": … }`, `{ "kind": "frame", "name": "time" | "delta" | "index" }`, `{ "kind": "entityField", "entity": i, "field": … }`, `{ "kind": "entityState", "entity": i, "name": … }`, `{ "kind": "param", "instance": i, "name": … }`.
- `order` is the binding's position in the topological evaluation order (phase 5).

### 5.3 Build identity

`buildId = sha256(` canonical JSON of: compiler version, language version, runtime ABI, target profile, enabled features, the sorted list of `(normalised path, sha256)` of every source and asset, and the `mtek.toml` contents `)`. Content-addressed file names make caching safe: a shader compiled for a different profile has a different `buildId` and, if its text differs, a different hash (blueprint §13).

### 5.4 WGSL span map (`shaders/<h16>.mtek-map.json`)

```json
{ "shader": "<sha256>", "entries": [ { "wgsl": { "line": 41, "colStart": 5, "colEnd": 38 }, "span": 12, "symbol": "src/main.mtek::Pulse.fragment" } ] }
```
One entry per emitted WGSL statement/expression that originates in Mtek source; generated wrapper code maps to the material declaration. Used to translate Naga errors (compile time) and `GPUCompilationInfo` messages (run time) into Mtek diagnostics.

## 6. Host API

### 6.1 Mounting

```ts
export function mountMtek<I = Record<string, unknown>>(
  canvas: HTMLCanvasElement,
  program: MtekProgram<I>,
  options?: MtekMountOptions<I>,
): Promise<MtekApp<I>>;

export interface MtekMountOptions<I = Record<string, unknown>> {
  inputs?: Partial<I>;                        // initial host inputs (validated like setInput)
  onDiagnostic?: (d: MtekDiagnostic) => void; // every runtime diagnostic, including warnings
  failureDisplay?: "overlay" | "none";        // default "overlay"
  seed?: number;                              // random() seed; default derived from time
  pauseWhenHidden?: boolean;                  // default from manifest runtimeConfig
  devicePixelRatio?: number | "auto";         // default "auto"
  test?: MtekTestOptions;                     // §10.2; omit in production
}
```

`mountMtek` resolves only when the device is ready, the manifest is accepted, every startup shader module and pipeline was created without validation error, and every startup asset is `ready`. It **rejects** with an `MtekMountError`:

```ts
export class MtekMountError extends Error {
  readonly kind: "webgpu-unavailable" | "adapter-unavailable" | "device-failed" | "incompatible-program"
               | "manifest-invalid" | "shader-failed" | "asset-failed" | "allocation-failed";
  readonly diagnostics: readonly MtekDiagnostic[];   // mapped to Mtek source where possible
}
```

**Code → kind mapping (normative):** `E8001`, `E8004` → `webgpu-unavailable`; `E8005` → `adapter-unavailable`; `E8002` and a rejected `requestDevice` (browser message as a note) → `device-failed`; `E8003` → `incompatible-program`; `E8006` → `manifest-invalid`; `E8051` → `shader-failed`; `E7030`, `E7031` → `asset-failed`; `E8063` → `allocation-failed`; `E8102` → `physics-failed` (M5).

`runtime.d.ts` is a **hand-maintained** file in `packages/runtime-web/src/runtime.d.ts` declaring exactly the public types of this section; the runtime build copies it to `packages/runtime-web/dist/runtime.d.ts`, and a test compiles a host snippet against it with `tsc --strict`. The compiler receives it alongside the bundle (`CompileOptions.runtime_declarations`, `spec/compiler-architecture.md` §4.12) and writes it into every `dist/`.

With `failureDisplay: "overlay"` the runtime also renders a readable error panel (diagnostic code, message, source location) positioned over the canvas, so a failure is never an unexplained blank page (blueprint §7.3, M1 exit gate). Capability detection uses `navigator.gpu`, `requestAdapter()` and the adapter's `features`/`limits`; browser names are never used as capability evidence.

### 6.2 The application handle

```ts
export interface MtekApp<I = Record<string, unknown>> {
  setInput<K extends keyof I & string>(name: K, value: I[K]): MtekInputResult; // queued; applied at the next frame start
  pause(): void;
  resume(): void;
  dispose(): void;                                          // synchronous release (§9.3)
  readonly state: "running" | "paused" | "recovering" | "failed" | "disposed";
  readonly debug?: MtekDebug;                               // present only when options.test is set (§10.2)
  replaceProgram?(candidate: MtekProgram<I>): Promise<{ ok: true } | { ok: false; diagnostics: readonly MtekDiagnostic[] }>;
                                                            // present only in dev builds (§11.2)
}
export type MtekInputResult =
  | { ok: true }
  | { ok: false; error: { code: string; message: string } };  // code in envelope form: "MTEK-E8040" unknown input,
                                                              // "MTEK-E8041" wrong type, "MTEK-E8100" non-opaque colour

// MtekProgram<I> is the type of the default export of app.js (§3). The type parameter only carries the
// Inputs interface for typing setInput; at run time inputs are always validated by the generated codecs.
export interface MtekProgram<I = Record<string, unknown>> {
  readonly abi: 1; readonly baseUrl: URL; readonly manifestUrl: URL;
  readonly writers: unknown; readonly functions: unknown; readonly scenes: unknown; readonly prefabs: unknown;
  readonly __inputs?: I;   // phantom, never present at run time
}
```

`setInput` never throws and never mutates live state immediately: valid values are queued and applied in phase 1 of the next frame (blueprint §5.4).

### 6.3 Host input codecs

Exposed through `mtek.toml` `[host.inputs]` (`spec/tooling.md` §3); only **scene state** of these types can be exposed (`E9020` otherwise):

| Mtek type | Codec id | Accepted JS value |
|---|---|---|
| `f32` | `f32` | finite `number` (rounded to binary32) |
| `i32` | `i32` | integer `number` in i32 range |
| `u32` | `u32` | integer `number` in u32 range |
| `bool` | `bool` | `boolean` |
| `vec2`/`vec3`/`vec4` | `vecN` | `number[]` of length N, finite |
| `color` | `color-hex` | `"#rrggbb"` or `"#rrggbbaa"` (sRGB, converted exactly as literals are) |
| `color` feeding an opaque material slot | `color-hex-opaque` | as above, alpha must be `ff` or omitted (`E8100`) |
| `string` | `string` | `string`, ≤ 64 KiB |

The compiler chooses `color-hex-opaque` when the state reaches any material `color` param through a binding.

### 6.4 Generated declarations (`app.d.ts`)

```ts
import type { MtekProgram } from "./runtime.js";   // resolves to runtime.d.ts in dist/
export interface Inputs { tint: `#${string}` }
declare const program: MtekProgram<Inputs>;
export default program;
```

`runtime.d.ts` (emitted by the runtime build and copied into every `dist/`) declares `mountMtek`, `MtekProgram<I>`, `MtekApp<I>`, `MtekMountOptions<I>`, `MtekMountError`, `MtekDiagnostic` and `MtekInputResult` exactly as in this section; `app.js` re-exports `mountMtek` from the hashed runtime file, and the `.d.ts` files describe that re-export. A test compiles a TypeScript host snippet against `app.d.ts` with `tsc --strict` (correct usage compiles, wrong usage fails) and asserts the runtime decoder accepts exactly what the declaration allows.

### 6.5 `index.html` bootstrap

```html
<style>html,body{margin:0;height:100%}canvas{display:block;width:100%;height:100%}</style>
```

## 7. The scheduler (implementation contract for `spec/scenes.md` §10)

```
onAnimationFrame(nowMs):
  if state != running: return requestNext()
  rawDelta = (lastMs === null) ? 0 : (nowMs - lastMs) / 1000; lastMs = nowMs   // first frame after mount/resume: 0
  delta    = min(rawDelta, maxFrameDelta)
  activeTime += delta                                    // f64
  phase1_input()                                         // host inputs, input transitions, input handlers
  accumulator += delta
  steps = 0
  while accumulator >= fixedStep and steps < maxCatchUpSteps:
      phase2_tick(fixedStep); accumulator -= fixedStep; steps += 1
  if accumulator >= fixedStep:
      counters.discardedSteps += floor(accumulator / fixedStep); accumulator = accumulator % fixedStep
  phase3_update(delta); phase4_flush(); phase5_bindings(); phase6_transforms(); phase7_render()
  requestNext()
```

- `pause()` sets `state = paused` and stops accumulating; `resume()` sets `lastMs = null`, so the first frame after resuming has delta 0 and the paused interval is never simulated. Visibility changes call pause/resume when `pauseWhenHidden`.
- **Manual clock (tests).** With `options.test.manualClock`, `requestAnimationFrame` is not used; `app.debug.step(n, dtSeconds)` runs `n` frames with the given delta synchronously (rendering included). This makes every behavioural test deterministic.
- All per-frame iteration uses arrays in stable instance order. Never iterate `Object.keys` of user-named objects to decide execution order.

## 8. Rendering

8.1 **Device.** `requestAdapter({ powerPreference: "high-performance" })`, then `requestDevice` with exactly the manifest's `requiredCapabilities` (features and limits), plus `timestamp-query` in **dev** builds when the adapter offers it (never required). Validation errors outside error scopes are captured through `device.onuncapturederror` and reported as `E8050` with the most specific mapping available.

8.2 **Surface.** `context.configure({ device, format: preferred, viewFormats: [preferred + "-srgb"], alphaMode: "opaque" })` where `preferred = navigator.gpu.getPreferredCanvasFormat()` (`bgra8unorm` or `rgba8unorm`). Each frame renders through `getCurrentTexture().createView({ format: preferred + "-srgb" })`, so the hardware encodes linear → sRGB (the renderer owns output encoding, blueprint §4.2). Depth: `depth24plus`, cleared to 1.0, compare `less`. The canvas backing size is `round(clientWidth × dpr) × round(clientHeight × dpr)`, recomputed on `ResizeObserver` callbacks; a zero-sized canvas skips rendering (simulation continues) and is not an error.

8.3 **Matrices (normative).** **View** (camera at `p`): with a `target` — `f = normalize(target − p)`; `up = +Y`, or `−Z` if `|dot(f, +Y)| > 1 − 1e-6`; `r = normalize(cross(f, up))`; `u = cross(r, f)`; rotation `R = columns(r, u, −f)`. Without a `target` — `R = mat4.rotation(camera.rotation)`. Then `V = transpose(R) · T(−p)` (the inverse of the camera's rigid transform). **Projection:** perspective, right-handed, looking down `-Z`, depth to `[0, 1]`, with `f = 1 / tan(fov_y / 2)`, `a = width / height`, column-major:
```
P = | f/a  0   0              0              |
    | 0    f   0              0              |
    | 0    0   far/(near−far) near·far/(near−far) |
    | 0    0   −1             0              |
```
`P` is written in mathematical (row, column) notation; stored column-major in a `Float32Array(16)` its non-zero entries are index 0 = `f/a`, 5 = `f`, 10 = `far/(near−far)`, 11 = `−1`, 14 = `near·far/(near−far)`. Orthographic with `h = height`, `w = h · a`: `x' = 2x/w`, `y' = 2y/h`, `z' = z/(near−far) + near/(near−far)`, `w' = 1` (column-major indices 0 = `2/w`, 5 = `2/h`, 10 = `1/(near−far)`, 14 = `near/(near−far)`, 15 = `1`). Both map `z = −near` to depth 0 and `z = −far` to depth 1. `view_proj = P · V`.

8.4 **Draw list.** Visible entities with a mesh, sorted by `(pipeline key, material instance, mesh)`, ties by instance order. **Compatible instancing (M4, normative definition):** entities are drawn with one instanced draw when they have the same mesh, the same pipeline key and the **same parameter block** (material instances whose params are all class `initial` and byte-identical, i.e. sharing one slot per `spec/gpu-layout.md` §8.2); per-instance model and normal matrices come from an instance vertex buffer. Any other combination is drawn individually. The `instancedDraws` and `drawCalls` counters make the path observable. Pipeline cache key = `(shader hash, vertex attribute set, color format, depth format, cull mode, topology)` (blueprint §7.2). Parameter edits never create pipelines. Frustum culling (M4) tests each entity's world-space bounding sphere against the six frustum planes; its effect is visible in counters.

8.5 **Pass sequence.** clear → opaque geometry → development overlay (dev builds) → present. No general render graph in v0.1.

The M1 context subset, setter validation during `init`, the program/structure checks at mount and the other rendering details this section leaves open are fixed in `spec/decisions/0031-runtime-scene-rendering-details.md`.

## 9. Resource lifecycle and resilience

9.1 **Registry.** Every GPU buffer, texture, sampler, shader module, pipeline and bind group, and every DOM event listener, is created through the runtime's resource registry, which counts creations, live objects and releases by kind (blueprint §7.4).

9.2 **Replacement.** A replaced resource is released after the frame in which it was last referenced has been submitted (`destroy()` is safe for submitted work). The runtime never waits for the GPU (`onSubmittedWorkDone`) on an ordinary frame.

9.3 **Dispose.** `dispose()` synchronously: stops the frame loop, removes every listener it added, destroys every buffer and texture, drops pipelines/bind groups, disposes the physics world, clears the overlay, and leaves counters at zero live objects (asserted by tests over 50 mount/dispose cycles, `spec/testing.md` §6.6).

9.4 **Device loss** ([S7]). On `device.lost` (reason other than `"destroyed"`): set `state = recovering`, pause, report `W8060`, then attempt a bounded rebuild — request a new adapter and device, recreate every GPU resource from the manifest and the retained CPU state (scene state, entity records, mirrors) — up to **3 attempts** with 250 ms, 1 s and 4 s delays. On success resume and report `W8061`; on failure set `state = failed`, show the overlay with `E8062` and stop. No infinite retry loop.

9.5 **Allocation failure.** Buffer and texture creation inside `pushErrorScope("out-of-memory")`; failure during mount rejects with `allocation-failed`; failure later (e.g. arena growth) reports `E8063` and stops the scene with the overlay rather than rendering stale data.

## 10. Counters, overlay and test control

10.1 **Counters** (per frame and cumulative): `frameTimeMs`, `cpuUpdateMs`, `renderPrepMs`, `drawCalls`, `instancedDraws`, `culledObjects`, `uploads`, `uploadBytes`, `pipelinesCreated`, `shaderModulesCreated`, `bindGroupsCreated`, `buffersAllocated`, `texturesAllocated`, live counts `liveBuffers`, `liveTextures`, `liveSamplers`, `liveShaderModules`, `livePipelines`, `liveBindGroups`, `liveListeners`, `sharedParamBlocks`, `ownedParamBlocks`, `discardedSteps`, `liveEntities`. GPU time is reported only when the `timestamp-query` feature is available and requested; otherwise the overlay says "GPU time unavailable" (blueprint §12.3 — never relabel CPU submission time as GPU time).

10.2 **Test control** (`options.test`, never in production builds of examples):
```ts
interface MtekTestOptions { manualClock?: boolean; renderTarget?: { width: number; height: number }; }
interface MtekDebug {
  step(frames: number, dtSeconds: number): void;
  readPixels(): Promise<{ width: number; height: number; format: "rgba8unorm-srgb"; data: Uint8Array }>;
  counters(): Readonly<Record<string, number>>;
  pressKey(code: string): void; releaseKey(code: string): void;      // injects input transitions
  setParam(entityName: string, param: string, value: unknown): void;  // M2 gate: change a param without `bind`
  scene(): { state: Record<string, unknown>; entities: Array<{ name: string; position: unknown; rotation: unknown }> };
}
```
With `renderTarget`, frames render into an offscreen `rgba8unorm-srgb` texture of that size (fixed format regardless of the platform's preferred canvas format); `readPixels` copies it to a buffer (`bytesPerRow` padded to 256), maps it and returns tightly packed rows.

## 11. Hot reload (development only)

11.1 **Protocol.** `mtek dev` serves `dist/` and an `/__mtek/events` Server-Sent Events stream. Each message is a single `data: <JSON>\n\n` frame (no `event:` line); the JSON objects are `{"type":"build-started"}`, `{"type":"build-failed","diagnostics":[…]}`, `{"type":"build-succeeded","buildId":"…","program":"/app.js?build=…"}`. The dev bootstrap subscribes and, on success, `import()`s the candidate program module.

11.2 **Candidate validation.** `app.replaceProgram(candidate)` (dev builds only): fetch and validate the candidate manifest (§5.1); create every *new* shader module and pipeline on the current device inside a validation error scope and await `getCompilationInfo()`; prepare new arenas/bind groups for changed layouts. If anything fails, discard the candidate, keep the running program untouched, report the mapped diagnostics (blueprint §7.5). Nothing is half-updated.

11.3 **Swap.** At the start of the next frame (before phase 1): carry state across by identity — `normalised module path :: qualified declaration name` (e.g. `src/main.mtek::Demo.speed`, `src/main.mtek::Demo.Cube`) — when the declared type is identical; reset values whose identity is new or whose type changed. Material instances keep their slot when layout id and bytes-layout are unchanged; a changed default value is applied only if the instance's param was `initial` and the source literal changed. Unchanged shader hashes reuse existing pipelines (so a colour edit creates **no** pipeline — M3 gate). If the scene's structure changed in a way that cannot be migrated (entity hierarchy changed, a body added/removed, prefab set changed), the scene restarts and the runtime reports `W8070` explaining which declaration forced the restart.

## 12. Runtime diagnostics

Runtime diagnostics use the same envelope as compiler diagnostics (`spec/diagnostics.md` §2) with codes in the `8xxx` range, source spans resolved through the manifest `spans` table (byte range and line/column range, decision 0019), and `"phase"` set to the scheduler phase where they arose. Each distinct `(code, span)` is reported once per mount unless its documentation says otherwise. They are delivered to `onDiagnostic`, to the overlay (errors only, or all in dev builds), and to `console` in dev builds.
