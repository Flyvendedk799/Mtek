# 0040. The CPU emitter: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §4.1 (numeric semantics), §5.3 (build output), §12.1 (code generation tests); `spec/compiler-architecture.md` §4.9, §4.11, §6; `spec/runtime-abi.md` §3, §4.1, §4.2; `spec/language.md` §5.6, §6, §7; `spec/testing.md` §3.1, §4.1, §4.3; decisions 0030, 0035, 0037, 0038.

## Context

Task M2-07 compiles the typed IR's functions (decision 0038) to JavaScript: the `functions` table of `app.js`, with `f32` rounding after every operation, WGSL integer semantics and clamped indexing, source maps down to expressions, and execution tests against the real runtime. The specification fixes the rules (`fr(...)`, `| 0`, `rt` helpers, `a[rt.clampIndex(i, N, spanId, ctx)]`, the `f_`/`l_`/`a_` prefixes, the literal printing rule, the `exec.json` example) but not every choice an implementation has to make: how a function name is qualified by its module, how expressions are mapped when several start at one position, where span ids come from, how the emitter finds the helper of an operation, which inline forms it uses, how a range bound is evaluated, and how the execution tests get the real bundle and a complete set of cases. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **What is emitted.** Every IR function with `cpuReachable` (decision 0038 item 6: every `cpu fn` and every function a `cpu fn` reaches; lifecycle functions and handlers join in M3), in program order (modules in load order, items in source order), as a module-private `function` after the writers, preceded by a comment with its Mtek signature and symbol. `functions` lists them by symbol in the same order, and the manifest's `symbols` gains one `function` entry per emitted function, after the materials (decision 0030 item 5's order, extended). A `fn` reached from neither domain is not emitted.
2. **Names.** A function is `f_<hash8>_<name>`, `<hash8>` being the module hash of `spec/gpu-layout.md` §5 — the same qualification as the writers (`w_<hash8>_<Name>`) and the WGSL structs, so two modules' functions of one name never collide, and a function's JavaScript name does not depend on what other modules declare. (The `f_pulse` of `spec/runtime-abi.md` §3 is the unqualified illustration.) Parameters are `a_<name>`, locals and loop variables `l_<name>`: Mtek forbids shadowing (`spec/language.md` §4.2), so a name means one local wherever it is visible, and sibling blocks that reuse a name are separate JavaScript block scopes. Compiler temporaries are `t_<n>` (numbered per function in emission order), the entry scene's initialiser stays `s_<Name>_init`. `ctx`, `rt` and `fr` are the only other identifiers; none can be produced by a prefixed user name.
3. **Module preamble.** `app.js` now always starts with `import * as rt from "./runtime.<h16>.js";`, the `mountMtek` re-export from the same file and `const fr = Math.fround;` (the import line of `spec/runtime-abi.md` §3 that decision 0030 item 3 deferred to M2). The two M1 goldens changed by these two lines only.
4. **Expressions.** Constants are their folded values in the CPU representation of `spec/runtime-abi.md` §4.1 (an `f32` printed as the shortest text that reads back, as a binary64 number, as the binary32 value; vectors and structs as object literals, `mat4` as `new Float32Array([...])`), so no constant is ever computed at run time. The scalar operators use the inline forms of decision 0037 item 3: `f32` `+ - * / %` are `fr(a op b)` (`%` too: JavaScript's remainder is exact, the rounding never changes it, and every `f32` arithmetic result is visibly rounded); unary minus of an `f32` is `-a` (exact), of an `i32` `-a | 0`; `i32` `+ -` are `(a op b) | 0` and `*` `Math.imul(a, b)`, `u32` the same followed by `>>> 0`; integer `/ %` call `rt.idiv`/`rt.irem`/`rt.udiv`/`rt.urem`. Comparisons are JavaScript's, `==`/`!=` as `===`/`!==` (scalars and `bool` only; `-0 == 0`, NaN unequal), `&&`/`||` short-circuit. Conversions: `f32(x)` of an integer `fr(x)`, `i32(x)`/`u32(x)` of an `f32` `rt.f2i`/`rt.f2u`, `u32(x)` of an `i32` `x >>> 0`, `i32(x)` of a `u32` `x | 0`, a same-type conversion its operand. Every other operation — vector, quaternion, matrix and colour operators, intrinsics, namespace functions, vector constructors — calls the `rt` helper of its callee and concrete signature (item 6), operands in source order. One component is a member read (`v.y`, `c.a`, `q.w`); a swizzle `rt.swizzle2/3/4(v, "z", "y", …)`, `.rgb` `rt.crgb(c)`. A struct literal is an object literal with the fields in declaration order (decision 0038 item 8), a field read a member read, an array literal an array literal. A descriptor literal of a registry schema is an object literal of the fields as written (nothing in this build consumes one on the CPU; completing it with registry defaults is M3's when spawn and the setters do).
5. **Indexing.** An index that folded to a constant reads directly (`a[2]`, `rt.m4col(m, 2)`): `E3030` guarantees it is in range. A run-time index is `a[rt.clampIndex(i, N, spanId, ctx)]` (`mat4`: `rt.m4col(m, rt.clampIndex(i, 4, spanId, ctx))`), `N` from the base type and `spanId` the manifest span of the index expression (`base[index]`). The packager interns those spans **after** every other span (symbols, material params, shader span maps), in emission order, so adding a function body never renumbers the spans of anything else, and the `W8030` of a call site maps to its source.
6. **The operation index.** `emit_js/rt_ops.rs` builds the compiler's copy of `RT_OPERATIONS` with the rules of `operations.ts` (decision 0037 item 2), and `STRUCTURAL_HELPERS` lists the structural exports the emitter uses. They cannot drift: the `codegen_programs` example dumps the table, and `tests/codegen/rt-operations.test.ts` requires it to equal `RT_OPERATIONS`, the structural names to be in `RT_STRUCTURAL_EXPORTS`, and every `rt.<name>` of every generated `app.js` to be a function exported by the real bundle. An operation without a helper is a compiler defect (`E9999` with the operation), never wrong code.
7. **Statements.** `let` is `const`, `var` is `let`, a block constant emits nothing (its uses are folded). An assignment to a local is `l_x = value;`; a compound assignment `p op= v` is `p = p op v` through the operator rules of item 4; a component assignment builds a new vector and assigns it to its base (`l_v = rt.v3with(l_v, "y", value);`, decision 0037's `v2with/v3with/v4with`), so values are never mutated. `if`/`else if`/`else` is one chain. `for i in a..b` is `for (let l_i = a, t_n = b; l_i < t_n; l_i++)`: the bound is evaluated once, before the first test (a constant bound is written in place, without a temporary); `for x in arr` is `for (const l_x of arr)`. `return`, `break`, `continue` and nested blocks are themselves. *Decision 0045 extends this to struct fields and array elements: a `var` written through one owns its storage and is written in place (copies keep values from aliasing), and a place read as well as written computes its run-time indices once into `t_<n>`.*
8. **Printing.** The JS AST prints operators with the parentheses JavaScript's precedence needs, plus one readability rule: an operator operand of a bitwise operator is grouped (`(a + b) | 0`). A negative literal binds like a prefix operator (`-(-1)`, `(1).x` never occur unparenthesised).
9. **Source map.** Every emitted function, statement and expression is wrapped with its span; the printer records a mapping where each starts. Mappings are sorted by generated position and, where several start at one position (`a_x >>> 0` for `u32(x)`: the conversion and `x`), the first recorded — the statement, or the outermost expression — keeps it; the dropped one is always enclosed by the one kept (a unit test checks this node by node). Columns are bytes (`app.js` is ASCII), source columns UTF-16 units, `names` stays empty.
10. **Fixtures and tests.** Two codegen fixtures with `exec.json`: `cpu_functions` (hand-written: a function per emission rule over two modules, the rows' expectations computed independently of the emitter — integer edge cases, conversions, `f32` rounding chains, clamped indexing with its warnings, component and compound assignment, structs, control flow, and four transcendental rows within 2–4 ulps or `1e-6`), and `numeric_cpu_table`, **generated** from `tests/semantics/numeric/cpu.json` by `crates/mtek-compiler/tests/codegen_cpu_table.rs` (one pure function per operation and signature, a `cpu fn reach_all` calling each once to make them CPU-reachable, and one row per table case; the test fails when the fixture is stale, `MTEK_BLESS=1` rewrites it). Their stub-bundle goldens are checked like the M1 ones. The Vitest global setup rebuilds the runtime bundle from source and builds every codegen fixture with it into `.out/programs/` (`codegen_programs` example, which also writes the typed IR); `app.test.ts` runs against those builds and requires them to equal the goldens up to the hashed runtime file name. The `exec.json` row format extends `spec/testing.md` §4.1: typed values in the notation of the CPU table (decision 0037 item 10) plus `{"array": [...]}` and `{"struct": {...}}` (plain JSON numbers and booleans are accepted as arguments), and the optional keys `id`, `note`, `tolerance` (`{"ulp": n}` and/or `{"abs": x}`), `calls` (calls with one `ctx`, default 1) and `warnings` (the codes `ctx.warn` must receive, in order); `fn` is a source name in `src/main.mtek` or a full symbol. Results are compared bit for bit (`-0` is not `0`, any NaN matches NaN, every `f32` must be a binary32 value), arguments must be left unmodified, every warning's span must be an index expression, and every emitted function except `reach_all` must be called by some row.
11. **Placement.** The CPU lowering lives in `emit_js/cpu.rs` rather than the `lowering/cpu.rs` of `spec/compiler-architecture.md` §4.9: it produces the JS AST directly and shares its value printing with the program emitter, and `lowering/` is the shader side's.

## Consequences

- No new dependency and no new diagnostic code.
- M2-10 (the M2 gate) can rely on `functions` being complete for every CPU-reachable function; the gate's own tests should add their programs as codegen fixtures with `exec.json` rows rather than new mechanisms.
- M2-12 and later work that changes `rt` changes no golden (the goldens use the stub), but the execution tests run the changed runtime: a helper whose behaviour changes fails the `numeric_cpu_table` rows exactly where `cpu.json` says.
- M3 adds lifecycle functions and handlers to the emitted set (`Roots::cpu_bodies`), assignable scene and entity places (through the `ctx` setters of `spec/runtime-abi.md` §4.2, component writes again building new vectors), and descriptor values with registry defaults; the source-map and exec mechanisms apply unchanged. Untrusted preview builds (M6) insert their loop-budget check in the counted and `for … of` loops of item 7.
- `spec/compiler-architecture.md` §4.9, §4.11 and §6 and `spec/runtime-abi.md` §3 point here.
