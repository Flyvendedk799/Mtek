# 0042. Grammar coverage and the M2 grammar freeze: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: M2 ("freeze the implemented grammar subset with positive and negative fixtures"); `spec/grammar.ebnf`, `spec/grammar-notes.md` note 4, `spec/testing.md` §3.2, `spec/compiler-architecture.md` §1; decisions 0023, 0025.

## Context

Task M2-11 asks for `tools/grammar-coverage`: a tool that proves every production of `spec/grammar.ebnf` is exercised by a positive fixture and every `[S: …]` restriction by a negative one, a test that fails when either is not the case, and a recorded freeze. M1-05 had left a test in `crates/mtek-compiler/tests/fixtures.rs` that required a file `tests/syntax/pass/<Production>.mtek` for each production: it proved that a file of that *name* parses, not that the parser builds the production from anything. The `[S: …]` annotations had no ids, so nothing could refer to them, and no fixture declared which rule it covers. The specification does not say where the tool lives, what a "hit" is for productions every expression passes through, how a fixture names a rule, or what covers a rule whose construct is not implemented yet (decision 0025's `E9010`). Those choices are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Where the tool lives.** A workspace crate at `tools/grammar-coverage` (package `mtek-grammar-coverage`, library plus the binary `grammar-coverage`), the third workspace member. It depends on `mtek-compiler` and `serde_json` (already allowed, decision 0007) and nothing else; the compiler does not depend on it. `cargo run -p mtek-grammar-coverage [REPOSITORY]` prints the report (exit status 0 when nothing is uncovered, 1 when there are problems, 2 when the corpus cannot be read); `tools/grammar-coverage/tests/coverage.rs` is the failing test, run by `cargo test --workspace`. This amends the layout of `spec/compiler-architecture.md` §1, which listed only the M6 tools under `tools/`.
2. **Hits are read off what the parser built.** Each positive fixture is lexed and parsed by `mtek-compiler` (it must have no diagnostic), and an exhaustive `match` over the tokens, the comments and the tree maps them to productions: the tree has one node type per production and one variant per alternative (`syntax/ast.rs`), so a production is hit when the parser built its node. The compiler is not instrumented: no counter, no global state, nothing that differs between debug and release builds, and a new tree variant does not compile until the tool maps it. Where the grammar is not one node per production: the precedence levels `OrExpr` … `MulExpr` are hit by a binary expression with one of their own operators and `PostfixExpr` by a call, field access or index (every expression passes through all of them, which alone does not count); `ParamList`, `ArgList` and `HandlerArgs` by a non-empty list; `ExprNoDesc` by an `if` condition or a `for` operand; `HandlerArg`'s parameter form is not `Param`. Lexical productions come from the tokens (`IdentContinue` from a name longer than one character, `IntPart`/`Exponent` from a float's text, `StringChar`/`Escape`/`Hex` from a string's or colour's text, `Whitespace` from a blank between tokens and comments, `LineComment` including `///`). Only `tests/syntax/pass/` counts, as note 4 says.
3. **Alternatives too.** Beyond note 4, every *top-level* alternative of a production (the parts separated by `|` outside parentheses, identified by their text with whitespace normalised) must be hit — `Primary`'s `'(' Expr ')'`, `Statement`'s `Block`, each keyword of `Keyword`. A production hit by one easy alternative proves little about the others. Nested alternatives and optional parts are not tracked.
4. **`Reserved` is covered by fail fixtures.** No positive fixture can contain a reserved word as a name. Each alternative of `Reserved` is hit by a fail fixture that reports `E0013` with exactly that word as its span. `tests/syntax/fail/recovery_every_reserved_word.mtek` declares a struct field for each of the 30 words; it is a `recovery_*` fixture because it holds 30 independent mistakes (the one-error-per-fixture rule of `fixtures.rs`).
5. **Rule ids.** A semantic restriction is written `[S: rule-id: text]` in a comment under the production it restricts; the id is lower-case words joined by `-`, the text must name at least one catalogue code (`E1020`, `E4020/E4021`, a range `E2030-E2034`), and `[S: <` is a placeholder in prose, not a rule. The 11 annotations of `spec/grammar.ebnf` got ids (`reserved-identifiers`, `import-specifier`, `stage-name`, `prefab-no-nested-entity`, `prefab-instance-params`, `param-only-in-prefab`, `scene-object-kind`, `bind-bindable-field`, `lifecycle-signature`, `array-type-arguments`, `simple-statement`). Two texts changed with it: `ArrayLength`'s rule now names its codes (`E3003` for type arguments on anything but `array` or `array` without them, `E3031` for an invalid length, decision 0035 item 4), and `LifecycleFn`'s mentions the at-most-one-per-body part of its range (`E5051`, `spec/scenes.md` §6). The header now says the restrictions are enforced by the lexer, parser or checker (`E0011`, `E1040`, `E4901` and `E1020` are not the checker's).
6. **How a fixture covers a rule.** A fail fixture declares `// covers: [S: rule-id]` (several entries separated by commas allowed) on a line of one of its `.mtek` files, conventionally the last line so that no expected span moves. Fixtures of `tests/syntax/fail/` count as well as those of `tests/semantics/fail/` (note 4 names only the latter, but four rules are enforced before the checker). A rule is covered when every code it names is reported by at least one fixture declaring it; a declaring fixture that reports none of the rule's codes, a declaration of an unknown id and a `// covers:` line in a positive fixture are problems too. The reported codes are read from the fixtures' expected diagnostics, which `fixtures.rs` compares exactly with the compiler's output in the same `cargo test` run.
7. **Rules of gated constructs.** Four rules check constructs this build does not implement (decision 0025): `prefab-no-nested-entity` and `prefab-instance-params` (prefabs, M5), `bind-bindable-field` (`bind`, M3), `lifecycle-signature` (lifecycle functions, M3). The tool's `GATED_RULES` table names each rule's construct; while the construct is gated, the rule is covered by a declaring fixture that reports that construct's `E9010`. The fixtures (`gate_prefab_with_nested_entity`, `gate_prefab_instance_sets_non_parameter`, `gate_bind_on_unbindable_field`, `gate_lifecycle_wrong_parameter`, `gate_lifecycle_twice`, `gate_lifecycle_unknown_name`) contain the actual violation, so when the work item that lifts a gate re-blesses them they become the rule's real tests. An entry whose construct the build implements is itself a problem: the work item must remove it, after which every code of the rule is required.
8. **The name-based test goes.** `every_production_has_a_fixture` and `the_production_list_is_the_production_list_of_the_grammar` (with their production lists) are removed from `fixtures.rs`; the tool reads the production list from the grammar and measures it. Positive fixtures keep their production names, for readers.
9. **The freeze.** The test also pins the counts — 73 productions, 116 top-level alternatives, 11 rules — so that a change to the grammar is a visible test change. `spec/grammar-notes.md` records the frozen subset, its date and the commit.

## Consequences

- `cargo test --workspace --locked` fails on any production, alternative or rule that loses its coverage; `tools/grammar-coverage/tests/coverage.rs` shows that removing a fixture that alone covers a point, or the declaration of a fixture that alone covers a code, is reported.
- Changing `spec/grammar.ebnf` after the freeze needs a decision record, fixtures for what is added, and the counts updated.
- The work items that implement prefabs (M5-01), `bind` (M3-05) and lifecycle functions (M3-02) remove their `GATED_RULES` entries and re-bless the `gate_*` fixtures listed in item 7.
- `spec/compiler-architecture.md` §1, `spec/grammar-notes.md` note 4 and `spec/testing.md` §3.2 refer to this record.
