# 0055. Frustum culling, renderer counters and the development overlay: details the specification leaves open

- Status: Accepted
- Date: 2026-10-17
- Blueprint origin: M4 (blueprint §11), task M4-07; `spec/runtime-abi.md` §§8.1, 8.3, 8.4, 8.5, 10.1, 10.2; `spec/tooling.md` §§2, 9; blueprint §12.3 (GPU time is never CPU time).
- Supersedes: nothing.

## Context

`spec/runtime-abi.md` §8.4 says frustum culling tests each entity's world-space bounding sphere against the six frustum planes and that its effect is visible in counters; §10.1 lists the counters and says GPU time is reported only with `timestamp-query`; `spec/tooling.md` §9 describes a development overlay "not present in release builds". The specification does not fix how the planes are extracted, which radius the sphere has, what exactly `culledObjects` counts, how the counters are exposed per frame and cumulatively, which keys the overlay answers to, how a runtime shipped as one bundle can have no overlay code in release builds, or how a test proves that. Every choice below is a **proposal**.

## Decision

1. **Planes.** The six planes are extracted from `view_proj = P * V` (the matrix `MtekFrame` holds, §8.3) by Gribb and Hartmann for the depth range `[0, 1]`: with the clip position `c = view_proj * (p, 1)` the volume is `-c.w <= c.x <= c.w`, `-c.w <= c.y <= c.w`, `0 <= c.z <= c.w`, and each inequality is one plane, a sum or difference of two matrix rows (left `r3 + r0`, right `r3 - r0`, bottom `r3 + r1`, top `r3 - r1`, near `r2`, far `r3 - r2`). The coefficients are normalised so that `a*x + b*y + c*z + d` is a signed distance in world units, positive inside. The same code serves the perspective and the orthographic projection. A degenerate matrix gives all-zero planes, which cull nothing.
2. **Sphere.** An entity with a mesh has the world-space bounding sphere centred at the translation of its world matrix (the built-in meshes are centred on the mesh origin), with radius `mesh bounding radius × max(|column 0|, |column 1|, |column 2|)` of the upper 3×3 of the world matrix: the largest scale of the entity including the scale it inherits from its parents. Rotation does not change the radius. The sphere is culled when its centre is further than the radius outside any one plane; a sphere that only touches a plane is kept. The test is conservative: it never culls a sphere that intersects the volume, and it can keep a sphere just outside near an edge or corner of the volume (a plane-by-plane test cannot tell), which costs a draw and never a wrong picture.
3. **Where.** The draw list of §8.4 (visible entities with a mesh, sorted, ties by instance order) is built as before and cached until visibility changes; culling filters it each frame, in order, after `view_proj` is known, so culling never reorders draws or changes which pipeline, material or mesh binding a surviving draw gets. The sphere centre and scale are kept per entity and refreshed whenever the entity's object block is written, so a culled entity's object block is still written and is correct when the entity returns. Culling creates no GPU object and uploads nothing of its own.
4. **What `culledObjects` counts.** The drawable entities (visible, with a mesh, with a material that has not failed) whose sphere is outside the frustum in the frame just drawn. Hidden entities and entities of failed materials are not "culled". A frame that draws nothing because the target has no pixels reports `drawCalls = 0` and `culledObjects = 0`. For every drawn frame, `drawCalls + culledObjects` equals the number of drawable entities (while there is no instancing: with instancing, `drawCalls` counts instanced draws and is smaller). `test.disableCulling` (a test option, §10.2) draws every drawable entity, as if culling did not exist, and leaves `culledObjects` at 0: it lets a test compare a culled frame with an unculled one.
5. **Counters.** `debug.counters()` keeps the names of §10.1. Frame-scoped counters (`frameTimeMs`, `cpuUpdateMs`, `renderPrepMs`, `drawCalls`, `instancedDraws`, `culledObjects`, and `gpuTimeMs` below) describe the last frame; resource counters (`uploads`, `uploadBytes`, `*Created`, `*Allocated`) are cumulative and the `live*` ones are current. Cumulative forms of the frame-scoped ones are `drawCallsTotal` and `culledObjectsTotal` (sums over rendered frames since the scene started; a hot reload starts a new scene). Frame timings come from the host clock, `performance.now()` (`HostEnvironment.now`), never from the scheduler's simulated time. `instancedDraws` remains 0 until instancing exists; this task does not change that.
6. **GPU time.** Development runtimes request `timestamp-query` as an optional device feature when the adapter offers it (§8.1; never required, never an error when missing). GPU time is *measured* only when the page also asked for the development overlay (`options.devOverlay`) and the device has the feature: two timestamps bracket the render pass, are resolved into a buffer and copied to a mappable buffer in the frame's command buffer, and the mapping is requested after the submit and resolved asynchronously. One measurement is in flight at a time (a frame that starts while the previous result is pending is not measured; the last completed value stands); no frame ever waits for the GPU. The value is `gpuTimeMs` in `counters()` together with `gpuTimeAvailable = 1`. When no measurement exists (release runtime, no feature, overlay not requested, or none completed yet) the key `gpuTimeMs` is **absent** and `gpuTimeAvailable` is 0: there is no placeholder number, and the overlay says "GPU time unavailable" (or "GPU time: pending" while the feature is active and the first result has not arrived). CPU timings are never shown under the name GPU time. The timer's two buffers go through the registry (they appear in `liveBuffers` and `buffersAllocated` only while the overlay is requested); its query set is destroyed on `dispose`.
7. **Two runtime flavours.** The runtime is bundled twice from the same sources (`packages/runtime-web/scripts/flavours.mjs`), differing only in the compile-time constant `__MTEK_DEV__`: `dist/runtime.js` (**release**, constant `false`) and `dist/runtime.dev.js` (**development**, `true`). Everything under `src/dev/` (the overlay, the panel text, the frame statistics, the GPU timer, the dev-tools aggregate) is reachable only through `if (__MTEK_DEV__)`, and the bundler runs with syntax minification (dead branches and constants only; names and whitespace stay as written), so the release bundle contains no byte of those modules and no reference to them. `mtek build --mode release` embeds `runtime.js`; `dev` and `test` embed `runtime.dev.js`; `preview` (M6) will use the release flavour. `CompileOptions` gains `dev_runtime_bundle` for this; when it is `None` (compiler tests, codegen goldens) every mode uses `runtime_bundle`. The CLI embeds both files or neither (`E9030`). The two files have different hashes, hence different `runtime.<h16>.js` names.
8. **Asking for the overlay.** `MtekMountOptions.devOverlay?: boolean` (default `false`): the development runtime shows the overlay and measures GPU time when it is `true`; the release runtime has no such code and ignores the option. The `index.html` of `--mode dev` mounts with `{ devOverlay: true }`; the pages of `release` and `test` mode do not mention it (test pages pass the option themselves when a test needs the overlay), so a test-mode page, which embeds the development runtime, still has no overlay and no extra listener unless it asks. `MtekTestOptions.disableCulling` is part of `runtime.d.ts`.
9. **The overlay.** A `<pre data-mtek-dev-overlay aria-hidden="true">` element in the canvas's parent, absolutely positioned in the top-left corner of the canvas, `pointer-events: none`. It is DOM, not drawn into the canvas, so it never changes the pixels of a frame or of `readPixels`, and it is not the failure overlay (`data-mtek-overlay`, `role="alert"`), which it does not replace; both can be present. It refreshes after every drawn frame while shown. Lines (`label: value`; the labels are the contract of the browser specs): `scene`, `entity` (the selected entity: name, position in the cycle `i/n`, and `file:line` of its declaration from the manifest span of its symbol, or "source unknown"), `frame time` (last frame, p50 and p95 over the last 120 frames, in ms), `cpu update` and `render prep`, `GPU time`, `draw calls` / `instanced draws` / `culled objects`, `uploads` / `upload bytes`, `created` (pipelines, shader modules, bind groups, buffers, textures), `live` (buffers, textures, samplers, shader modules, pipelines, bind groups, listeners, entities), `discarded steps`, `errors` (the latest four error diagnostics, `CODE: first line`), and a `keys` line documenting the keys. Percentiles are **nearest-rank** over the window sorted ascending: the value at 1-based rank `ceil(p/100 × n)` (for 1…120: p50 is 60, p95 is 114).
10. **Keys.** `` ` `` (`KeyboardEvent.code` `Backquote`, no Ctrl, Alt or Meta) shows or hides the panel; `Shift+`` ` selects the next entity (wrapping; ignored while hidden). The listener is on the canvas's document and goes through the resource registry, so `liveListeners` is one higher while the overlay is mounted and `dispose` removes it. `Backquote` is not a member of `Key`, so a program cannot observe or conflict with these keys.
11. **Hot reload** keeps the overlay: the entity list and scene name are refreshed from the new manifest at the swap; the frame statistics continue.

## Consequences

- The release bundle is smaller by the dev modules and is the only one whose contents `release` builds ship; the test-mode bundle used by every browser spec is the development flavour, so the specs run code that differs from release only by `src/dev/`, and the release flavour has its own browser spec (a release page mounted programmatically with `devOverlay: true` shows no overlay and still culls).
- `npm run build` of the runtime now produces `runtime.dev.js` (and its source map) next to `runtime.js`; the CLI build script requires all of `runtime.js`, `runtime.dev.js` and `runtime.d.ts` to embed the runtime.
- The runtime unit tests run as the development flavour (`vitest.config.ts` defines `__MTEK_DEV__` as `true`). `src/runtime-dts.test.ts` compiles the implementation with `src/flavour.d.ts`, which declares the constant.
- Merging with instancing (M4) only changes the identity `drawCalls + culledObjects = drawable entities`: culling is applied to entities before they are grouped into instanced draws.
