# 0065. Physics schemas and ownership checks: bodies, colliders, one pose authority, body commands and the manifest data

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M5 (blueprint §11), task M5-03; blueprint §8 (physics is a subsystem behind an adapter, one pose authority); `spec/physics.md` §§2, 3 and 8; `spec/scenes.md` §§4.1, 5, 7.1, 8.2, 8.3, 12; `spec/stdlib.md` §3.7; `spec/runtime-abi.md` §§4.2 and 5.2; `spec/diagnostics.md` (`E5062`, `E5071`–`E5073`, `E5091`, `E5120`–`E5123`, `E8101`–`E8103`); decisions 0025 (milestone gating), 0035, 0053, 0054, 0057 and 0062 (items that land before their milestone's gate), 0049 and 0051 (state, handlers, `bind` and the single-writer analysis that this record completes), 0062 (prefabs may carry physics fields) and 0063 (the backend, the physics bundle and its stand-in option).
- Supersedes: nothing. Lifts the M5 gate of the physics rows (decision 0025 item 2); fulfils the "M5-03 ORs its body check into one line in `package()`" of decision 0063 item 8.

## Context

The specification fixes the schemas of bodies and colliders, the body commands, the readable velocities and the codes of the rules; the registry already held the rows (gated `M5`), the manifest schema and the runtime's manifest types already described `body` and `collider`, and the checker's single-writer analysis already had the hooks for `E5070`. What no document fixes is how the checker finds out which entity has which body (an entity, a prefab, a static instance of an imported prefab), where each rule reports, what a body command compiles to, what the manifest says about a prefab's body, when `subsystems.physics` is true, and what stays gated. Every choice below is a **proposal** the owner may overrule.

## Decision

1. **Gating.** As decisions 0053, 0054, 0057 and 0062 did, the rows are marked implemented by the current build (`since` `M1`; `CURRENT_MILESTONE` is unchanged): the schemas `Static`, `Kinematic`, `Dynamic`, `BoxCollider`, `SphereCollider` with every field, `Entity.body`, `Entity.collider`, `Scene.gravity`, the body commands and readable body properties, the events `collision_enter`/`collision_exit` and the type `entity_ref`. Still `M5` when this record was written (lifted by task M5-02, decision 0064): `spawn`, `destroy`, `alive`, the prefab literal and a named entity or `self` used as an `entity_ref` value (`E9010` from the checker, not a registry row). The fixtures that used the physics rows as their example of a gate (`gate_builtin_schema`, `gate_builtin_type`, `gate_entity_field`, `gate_entity_field_read`, `gate_handler_collision`, `gate_scene_field`, `gate_prefab_physics_fields`) were removed (the last became the passing fixture `physics_prefab_crate`), `gate_nested_reported_once` now holds a prefab literal, and `every_gated_construct_has_a_gating_fixture` expects the prefab literal and the entity-as-value gate (`gate_entity_as_value`). `FieldDef::since` stays as an unused helper for the next gated field. `spec/stdlib-schema.json` is regenerated.
2. **Codes.** `E5120`–`E5123` and `E8101`–`E8103` are in `codes.rs`, in the catalogue of `spec/diagnostics.md` (the runtime rows say "implemented by M5-05") and in the runtime's `RUNTIME_DIAGNOSTIC_CATALOGUE`; `E8101`–`E8103` are in `NOT_YET_IMPLEMENTED` of the fixture coverage test until M5-05. The trigger columns of `E5062`, `E5071`, `E5072`, `E5080` and `E5091` say what they now report.
3. **Ranges.** Every number the adapter would otherwise refuse with a `RangeError` (decision 0063 item 4) is rejected by the compiler (`E5006`): `mass` > 0 and finite, damping and friction ≥ 0 and finite, `size` and `radius` > 0 and finite, `restitution` in 0…1, `Scene.gravity` finite (`ValueRange::finite`). Defaults are written out in the IR and the manifest.
4. **Pairing (`E5120`, `E5121`)** are two `FieldRule::Requires` of the `Entity` schema (the mechanism of `E5020`), so entities and the entity a prefab describes are checked by the same code; `Requires` gained an optional `help` for the tailored line ("add `body: Static {}` for fixed geometry"). A body or collider whose value is not a descriptor of the right category is `E3102` and nothing else (no cascade into the physics rules).
5. **What an entity has (`types/physics.rs`).** The typing pass records for each named entity and each prefab `EntityPhysics { body: Option<(BodyKind, member span)>, collider, malformed_body }` (`Typeck::entity_physics`); the summary of a prefab (`PrefabInfo::physics`) travels with it into every module that imports it, and **a static instance gets its prefab's summary** under its own declaration. Every later rule reads that one table, so an instance, an imported instance, `self` inside a prefab and a named entity are treated alike.
6. **Roots only (`E5091`).** At the `body` member of an entity declared inside another entity, and at the name of a static prefab instance (local or imported) whose prefab has a body and which is nested in an entity; the parent is a related span. A body entity may have visual children.
7. **Scale (`E5122`, `E5073`, `E5004`).** The `scale` of a `Dynamic` or `Kinematic` body that is written must fold to exactly `vec3(1.0)`; a value a prefab's `init` computes from params cannot be checked and is rejected too (the message says so). A `Static` body may have any positive scale, which is purely visual: the collider is sized by its own descriptor and the adapter takes no scale (`Pose = { position, rotation }`). For every body kind the `scale` of the entity is construction-only: an assignment is `E5073` and `scale: bind(..)` is `E5004` (as for any field that is not bindable).
8. **One pose authority (`E5071`, `E5072`).** An entity with any body (`Static`, `Dynamic` or `Kinematic`) owns `position` and `rotation`: an assignment (also `Name.position.y = ..` and `+=`, through `Name`, `self` and a static instance, in a scene, an entity or a prefab) is `E5071`, `position: bind(..)` or `rotation: bind(..)` is `E5072` (the binding is not typed further, like `E5004`). Both name the allowed operation (dynamic: `apply_impulse`, `apply_force`, `set_linear_velocity`, `teleport`; kinematic: `set_kinematic_target`, `teleport`; static: "static bodies cannot move", help: make it `Kinematic`) and carry the `body` member as a related span. Assigning a readable body property (`Name.body.linear_velocity = ..`) is `E5071` too. Reading the pose is unrestricted, also in a `bind` of another entity.
9. **Body commands and readable properties.** The forms are `X.body.command(args)` and `X.body.property` where `X` is a named entity, `self` (inside an entity or a prefab), a static prefab instance, or any expression of type `entity_ref` (a handler parameter, a local, a `state`; any other shape is claimed only when the member is a command or property, so a struct with a field called `body` is unaffected). The arguments are checked against the registry parameters (`E3002` arity, `E3001` types). For a **named** target the body kind is known: a command or property its kind does not support, or any use on an entity with no body, is `E5123` (the message names the kinds the command applies to, the related span the body, the note lists the commands of the kind); through an **`entity_ref`** nothing can be said statically and the runtime reports `E8101` and drops the command. An unknown member is `E5001` (the lists of commands and properties are in the notes), a command used as a value or a property called is `E3001`, `X.body` alone is `E3001` ("a construction-only component, not a value"), `.body` on anything else is `E3001`. A command is recorded as a `handlers_only`, CPU-domain built-in call, so the existing passes report it: `E5080` in any function (as `spawn` and `destroy`), `E5005` in a `bind`; in a state initialiser it is a unit value (`E3001`). **A binding cannot read a body property** (`E5005`, "which a binding cannot depend on", like a camera or light field): the manifest's dependency kinds (`spec/runtime-abi.md` §5.2) have no kind for it, and a velocity is not state the binding order could see. A state initialiser reads none (`E5081`). The checker's results are `CallKind::BodyCommand` and `FieldKind::BodyProperty`, each with a `BodyTarget` (`Entity(DefId)` or `Ref`).
10. **Collision events (`E5062`).** `on collision_enter`/`collision_exit` in an entity or a prefab that declares no `collider` is `E5062` at the event name (the scene host is the existing `E5060`). The check reads the same table as the other rules; the handler may come before the `collider` member.
11. **IR.** `Entity::body: Option<Body>` and `Entity::collider: Option<Collider>` (`BodyDesc`: `static`, `kinematic`, `dynamic { mass, linearDamping, angularDamping }`; `ColliderDesc`: `box { size, sensor, friction, restitution }`, `sphere { radius, sensor, friction, restitution }`; each with the origin and span of its member), serialised only when present; `SceneFields::gravity` (listed when written, like `ambient_color`); `ExprKind::BodyCommand { target, command, args }`, `ExprKind::BodyProperty { target, property }` and `BodyTarget::{ Entity { entity }, Ref { target } }`. A static instance copies the body and collider of its prefab (`ir/instantiate.rs`), and the entity indices in its copied handlers are renamed as for every other entity read. `mtek inspect --ir` prints `body = Dynamic { .. }`, `collider = BoxCollider { .. }` and `entity#1.body.apply_force(..)`. `SCENE_FIELDS`, `ENTITY_FIELDS`, `BODY_SCHEMAS` and `COLLIDER_SCHEMAS` are compared with the registry by the existing coverage tests.
12. **Generated code.** A command is `ctx.body(<target>).<camelCase command>(args)` and a property read `ctx.body(<target>).<camelCase property>`, where the target is the entity record (`self` or `ctx.e[i]`) or the lowered `entity_ref` expression (`ctx.body(a_other).applyForce(..)`): `applyImpulse`, `applyForce`, `setKinematicTarget`, `teleport`, `setLinearVelocity`, `linearVelocity`, `angularVelocity`. `spec/runtime-abi.md` §4.2 states the handle; **the runtime does not provide `ctx.body` yet** (M5-05: reading it throws the existing "this runtime build does not provide" internal error), and the golden mount test of the runtime skips the `physics` fixture until then.
13. **Manifest.** `scene.entities[i].body` and `.collider` are written from the IR with every field (`manifest_body`, `manifest_collider`, also used by M5-02 for the body data of a prefab); `scene.fields.gravity` is the scene's `gravity` (it was the registry default); the schema and the TypeScript types needed no change. **`subsystems.physics` is true when the entry scene has an entity with a body or a prefab of the program declares one** (a prefab can be spawned from any handler and spawn sites are not tracked, so an unused prefab with a body also loads physics; a refinement is v0.2), or when `force_physics_subsystem` forces it. Then `physics/<h16>.js` is written, and `E9030` reports a missing bundle (decision 0063). The option is kept for the packaging tests and for M5-05's runtime tests; it never turns physics off. A scene without bodies stays byte-identical (no golden of an existing fixture changed).
14. **Not in this record (honest scope).** The runtime side: `ctx.body`, stepping, creating bodies from the manifest, the command categories, events, `E8101`–`E8103`, loading the bundle (M5-05 to M5-07). `entity_ref` values other than parameters, locals and state of that type are M5-02's: a named entity used where an `entity_ref` is expected (`other == Floor`, `let r = Floor;`) is `E9010` ("Named entities and `self` as `entity_ref` values", planned for M5; fixture `gate_entity_as_value`) until M5-02 lands: M5-02 removes `entity_ref_value_is_gated` in `types/check.rs`, which keeps the lowering from meeting a value it cannot represent. The body commands, fields and state of a named entity by name are implemented. The body data of a prefab for `spawn` has no manifest table yet (M5-02 adds the prefab description; the functions that build it exist). A body command has no static check of the target's body kind through an `entity_ref`.
