# 0038. Functions, statements and effects: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §4.4 (GPU code is only what stages reach), §9.4 (diagnostics); `spec/language.md` §4.2, §7, §8.2–§8.4; `spec/diagnostics.md` §5.3–§5.4; `spec/compiler-architecture.md` §4.7, §4.8, §9; decisions 0025, 0026, 0028, 0035, 0036.

## Context

Task M2-02 implements `fn` and `cpu fn`, every statement, the effect levels, recursion detection and GPU reachability. The specification states the rules but not every choice an implementation has to make: which places are assignable beyond the list of §7.2, how often an effect error is reported and what its "full call chain" is, where the GPU roots come from before material stage functions exist (M2-04), how a function looks in the typed IR, and how the passes stay linear on pathological programs. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Landing.** The construct rows `fn` and `cpu fn` are marked `M1`, exactly as decision 0035 item 1 prescribes for M2 work that lands before the M2 gate. `self` outside an entity or prefab is only `E2003` (it would be wrong in every build), no longer `E9010` as well.
2. **Signatures and calls.** Every signature of a module is checked before any body, so calls type in any order. Parameter types are mandatory (the grammar); no `->` is the unit result `()`. A call of a user function — of the module or imported (decision 0036: the importer sees the exporter's signature in its own interner) — checks the arity (`E3002`, "`mix3` takes 3 arguments, but 2 were given.", the signature as a note) and each argument against its parameter (`E3001`, the message of the intrinsics). A call of a function without a result used as a value (an initialiser, an assigned value, a returned value, a condition, a loop's range or array) is `E3001` ("This call gives no value: …"). `return value;` in a unit function, `return;` in a function with a result and a returned value of another type are `E3001` with expected and actual types. Calls of user functions stay non-constant (`E3090` in constants).
3. **Statements.**
   - `let`/`var` take the declared type, or the value's (a literal alone is `i32`/`f32`); a value of another type is `E3001` at the value. A block `const` is evaluated with the module's constants (decision 0026 item 8).
   - The bounds of a range follow the operand rule of comparisons (decision 0035 item 2): a literal bound adopts the other bound's type, two literal bounds are `i32` (or `f32`, and then wrong); bounds that are not both `i32` or both `u32` are `E3001` at `a..b`. `for x in e` with `e` not an array is `E3001`. The loop variable has the bound or element type.
   - `if` conditions must be `bool` (`E3070`, no truthiness).
   - Every expression of a body is folded (§6.3: folding is mandatory wherever an expression is constant), so `E3040` and a constant index out of range (`E3030`) are reported in bodies too.
   - **Control flow.** A statement *leaves* its block if it is `return`, `break` or `continue`, a block that leaves, or an `if` with an `else` whose every branch leaves; a loop never leaves (its body may not run). `W3081` is reported once per block, at the first statement after one that leaves, spanning to the end of the block, with a related span at the leaving statement; the unreachable statements are still checked. A function with a result whose body does not always *return* is `E3080` at the closing brace of the body, with a related span at the result type.
   - `W2010`: a `var` that no assignment (plain, compound, or to one of its components) targets, at its name.
4. **Assignable places** (§7.2, strictly). In this build a place is a `var` local or a single component of a vector place. `let` locals, parameters, loop variables and constants are `E3061` with a related span at the declaration ("Cannot assign to the local 'sum': it is declared with `let`."). A struct field, an array element, a `mat4` column, a component of a `quat` or `color`, and any other expression are `E3061` too ("struct fields are not assignable places in v0.1"): the list of §7.2 does not name them, and widening it later breaks no program (the question is open on the board). A multi-component swizzle target is `E3060` only, whatever its base. A compound assignment `p op= v` types as `p op v` (a literal `v` adopts the type the operator table requires) and the result must have `p`'s type (`E3001`).
5. **The program-wide pass** (`types/effects.rs`). The checker records, per body, its calls (user functions, and built-in functions whose domain is not `both` or that only handlers may call), its range loops with non-constant bounds and its declarations of CPU-only types (`types/facts.rs`). After every module is checked, one call graph joins them, imported names resolved to the declaring module's function (`FnRef { module, def }`). The analysis records each function's level and reachability (`Analysis::effects`, an addition to the API of decision 0028 item 1).
   - **`E4001`** — one per strongly connected component of calls with a cycle (recursion in `cpu fn`s too), at the name of its first function (module load order, then declaration order), the shortest cycle from it as related spans, one per call ("The function 'is_even' calls itself: is_even → is_odd → check → is_even.").
   - **`E4002`** — at *every* call in a `fn` that needs the CPU: a call of a `cpu fn`, of a CPU-only built-in, or of a `fn` that itself needs the CPU. Every such `fn` is in error (§8.3: its body transitively requires `cpu`), so a chain `shade → turbulence → noise → sample_noise` reports each `fn`'s offending call. The related spans are the **complete call chain** from the callee down to the CPU-only operation: each further call ("'turbulence' calls 'noise' here", …), then the `cpu fn`'s declaration, or a note naming the CPU-only built-in; the chain is the shortest one (a breadth-first search), and the message carries the path ("The pure function 'shade' calls 'turbulence', which needs the CPU: shade → turbulence → noise → sample_noise.").
   - **`W4003`** — a `cpu fn` that calls no `cpu fn`, no CPU-only built-in and no `fn` that needs the CPU. (Every CPU-only built-in is M3 or later, so in this build every `cpu fn` at the end of a chain gets it.)
   - **`E5080`** — a call of a handler-only built-in (`spawn`, `destroy`) in any function, `fn` or `cpu fn`; that call is not also `E4002` or `E4012`, but it is a CPU effect for its callers and for `W4003`.
6. **GPU and CPU reachability.**
   - The GPU roots are `Roots::gpu_bodies`: material stage functions, which M2-04 checks with the same body checker and passes as `RootBody { module, label, span, facts }`. Until then, `Roots::gpu_functions` names functions to treat as called from a stage — the **test hook**: `analyze_with(root, fs, &AnalyzeOptions { gpu_root_functions: ["src/main.mtek::shade"] })`, and fixtures under `tests/semantics/gpu/` list the symbols in `gpu-roots.txt`. M2-04 replaces the hook's use; `analyze` passes no roots.
   - GPU code reaches only `fn`s (a call of a `cpu fn` is already `E4002`, or `E4040` from a stage). In every body it reaches, root bodies included: `E4010` at the `a..b` of each range loop whose bounds are not both constant expressions; `E4011` at the annotation (or name) of each parameter, result type, local, loop variable or block constant whose type has no GPU representation (`string`, the handles, enums, schema descriptors, records the registry marks CPU-only, and arrays and structs containing any of them); `E4012` at each call of a CPU-only built-in — *instead of* `E4002`, which would report the same call. The related spans name the root ("'shade' runs on the GPU (called from a stage function)") and each call of the shortest path from it.
   - CPU code is every `cpu fn` and `Roots::cpu_bodies` (lifecycle functions and handlers, M3); it reaches every function. `E4013` at each call of a GPU-only built-in in a body CPU code reaches, with the chain from the root. A `fn` reached from neither is compiled for neither domain until something reaches it.
   - `E4012`, `E4013` and `E5080` cannot be produced by a program of this build (their built-ins are M3–M5); `src/types/effects_tests.rs` checks them on registries where a built-in is implemented already or has another domain.
7. **Bounds.** Chains in related spans are cut after 256 steps (`MAX_CHAIN_STEPS`, with a note saying how many follow); a path in a message keeps its first and last 16 names. Of these diagnostics at most 200 per file are built — exactly the ones the sink keeps (`spec/compiler-architecture.md` §9) — and the rest are counted as suppressed, so a chain of 50 000 functions that all need the CPU stays linear. Every traversal (Tarjan's algorithm, the searches) uses explicit worklists.
8. **Typed IR.** A function is an item `{ kind: "function", name, symbol, effect: "pure" | "cpu", gpuReachable, cpuReachable, result, locals, body, span }`. `locals` lists parameters (first, in order), `let`/`var` locals and loop variables (in declaration order) as `{ index, name, type, kind: "param" | "let" | "var" | "loop", span }`; statements and expressions refer to them by index, because sibling blocks may reuse a name. Statements: `let`, `var`, `const` (a block constant, listed with its folded value), `assign` (`target` a place `{ kind: "local" }` or `{ kind: "component", base, index }`, `op` `=`/`+=`/…), `if` (`branches` — the `else if` chain flattened — and `else`), `forRange`, `forEach`, `return`, `break`, `continue`, `block`, `expr`. Expressions carry `type` and `span`; every constant expression is a `const` node with its folded value; otherwise `local`, `unary`, `binary`, `call` (`function` is the callee's symbol in the module that declares it), `builtin` (`sin`, `quat.axis_angle`), `construct` (vector constructors), `convert`, `components`, `field` (with its declaration index), `index`, `array`, `struct` (fields in **declaration** order, like struct values, decision 0035 item 5; the language does not fix the evaluation order of a literal's fields), `descriptor` (a registry schema, fields as written). The human form prints each statement on a line with Mtek-like expressions annotated with their types. The goldens of decision 0028 item 9 gain `functions_statements_and_calls`.

## Consequences

- M2-04 checks stage bodies with the statement checker of `types/body.rs` (generalising `function_body` to a body with given parameters and result), builds `RootBody`s from their facts and passes them to `check_program`; it reports `E4040` for a stage's call of a `cpu fn` itself.
- M2-05 lowers the IR functions with `gpuReachable` (and the stage bodies) to WGSL; M2-07 emits those with `cpuReachable`.
- M3 adds lifecycle functions and handlers as `RootBody`s of `Roots::cpu_bodies`, assignable scene and entity places, and makes `frame` reads facts if they need rules.
- `spec/compiler-architecture.md` §4.7 and §4.8 point here; §9 lists the chain bound.
