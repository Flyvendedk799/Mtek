# 0087. The params of the built-in `Unlit` and `Pbr` are read, written and bound by name like a user material's

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), the known gap that decision 0086 item 1 recorded and decision 0079 item 7 found; `spec/scenes.md` §§4.1, 8.1, 8.2, 8.4, 11; `spec/materials.md` §§4, 5, 9; `spec/runtime-abi.md` §§4, 5.2, 11.3; `spec/gpu-layout.md` §8.2; decisions 0039 (materials in the checker), 0044 (the prelude materials), 0046 (runtime materials, `setParam`), 0051 (`bind`), 0053 and 0067 (lights, update classes of fields and their hot reload), 0054 (texture and sampler params), 0057 (`Pbr`), 0059 (instancing, shared parameter blocks), 0062 and 0064 (prefabs, spawn), 0086 (the `E5001` wording this record replaces).
- Supersedes: the "known gap" of decision 0086 item 1 and its two `E5001` messages; the hot reload rule for material params of decision 0046/0059 as implemented ("imperative in the new program"), which becomes the rule of decision 0067 ("imperative in both programs"). Nothing else.

## Context

`spec/scenes.md` §4.1 and §8.1 say that the params of an entity's material instance are readable and writable by name: `Cube.material.color = #ff0000;`, `let c: color = Cube.material.color;`. The build did it for materials a program declares and for the materials of prefab instances, not for the built-in `Unlit` and `Pbr`: `Cube.material.color` was `E5001` (since decision 0086 with an honest message), so the benchmark tasks `interaction-02` to `-04` recolour their blocks with `bind`.

The reason was in the checker only. The prelude `std/materials.mtek` is compiled **after** the program's modules (decision 0044 item 1: `check.rs` asks `uses_builtin_material` of the checked modules whether to load it at all), so while a user module is checked there is no `MaterialInfo` of the prelude's `Unlit` to type an instance with; the descriptor `Unlit { … }` is typed as its registry schema (`Ty::Schema("Unlit")`, category `Material`), and `note_entity_material` recorded only `Ty::MaterialInstance`. Everything after the checker was already uniform: the IR lowers a built-in instance to the prelude's material item with the same `Param` records (`builtin_material_instance` and `material_instance` share `param`), `mark_imperative` marks any written param, the plan, the manifest, the generated `ctx.setParam` and the runtime's `World.setParam` → `MaterialStore.writeParam` know no difference between built-in and user materials, and a `bind` on a built-in param already worked end to end. Every choice below that the specification does not already make is a **proposal** the owner may overrule.

## Decision

1. **One path: the schema instance gets the param table** (proposal). The descriptor of a built-in material keeps its registry schema type; `Checker::instance_params` (`types/material.rs`), which gives the params of an instance type, now also answers for `Ty::Schema(name)` of category `Material`: the implemented fields of the schema, in schema order, with their types. `note_entity_material` records that schema type in `entity_materials` exactly as it records a user material's instance type, and `entity_builtin_materials` (decision 0086) is removed. From there `Cube.material.<param>`, `self.material.<param>`, a static prefab instance's `First.material.<param>` (through the prefab's `material_params`, also of an imported prefab), the write sites, the binding targets and dependencies, `E5070`, `E5073` and the type rules are the code that serves user materials; `descriptor_params` of the bind checks now uses `instance_params` too instead of its own copy of the schema walk. The alternative, typing the descriptor as the prelude's `MaterialInstance`, would need the prelude checked before every module (and loaded for programs without built-ins, which decision 0044 item 1 rules out) and changes every IR golden; it was not taken. The design relies on the prelude declaring the registry's params with the same names, order, types and defaults (decision 0044 item 5): `tests/unlit_shader.rs` checked it for `Unlit`; `every_prelude_material_agrees_with_its_registry_schema` now checks it for every built-in material (`Unlit`, `Pbr`).
2. **The default `Unlit {}`** (proposal, following `spec/scenes.md` §4.1: "`Unlit {}` if `mesh` is set"). An entity or prefab that declares a `mesh` and no `material` has the material instance `Unlit {}` (the IR and the runtime already created it); `note_default_material` (`types/scene_body.rs`) reads the registry's default of the entity schema's `material` field and its `default_when_set`, and records it like a written `Unlit {}`, so `Floor.material.color = c;` works. An entity with neither has no material: `E5001` "The entity 'Empty' has no material." with the note "an entity has a material when it declares `material`, or `mesh` (its material is then `Unlit {}`)". The 0086 messages ("this build does not expose its params…", "can only be bound in the descriptor") are gone.
3. **The rules are the user material's.** An unknown param is `E5001` "The material of 'Cube' has no param 'colour'." with the note listing its params (for `Pbr`: `base_color, metallic, roughness, base_color_texture, base_color_sampler`); an assignment of another type is `E3001` and a read into a local of another type `E3001`; `+=` works where the type has the operator (`Ball.material.roughness += dt;`) and is `E3010` for a colour; a write to a bound param is `E5070`, also through `self` in the prefab and on a static instance whose prefab binds it ("is bound by its prefab Lamp"); `base_color_texture` and `base_color_sampler` of `Pbr` are construction-only, `E5073` as for a user material's texture and sampler params (`spec/materials.md` §5); `Unlit` has no such param. Reading through an `entity_ref` stays `E5074` (`spec/scenes.md` §8.3).
4. **Update classes** are those of `spec/materials.md` §4 and decision 0059, unchanged in code: `imperative` when a lifecycle function or handler of the scene, of the entity or of the prefab writes the param (for a prefab's own handler, in every instance), `bound` for `bind(…)`, `resource` for textures and samplers, `initial` otherwise. An instance is `shareable` only when every param is `initial` or `resource`, so an instance a program writes never shares its parameter block (decision 0059: copy on write remains the guard for the test hook `debug.setParam`); `mtek inspect --bindings` shows the classes and the dependencies of a binding that reads a built-in param (`entity#2.material.roughness`).
5. **IR, manifest, generated code and runtime: no change.** A read is `ExprKind::InstanceParam` and `ctx.e[i].mat.p.<param>`, a write `ctx.setParam(e, "<param>", v)`; the runtime writes through the generated field writer of the material's layout into the instance's arena slot, marks it dirty only when the bytes change and uploads it in the render phase of that frame (`spec/gpu-layout.md` §8.2), exactly as for user materials. **Versions:** the manifest's shape did not change (built-in instances always had `params` with classes; only the values `imperative` now occur for them), so `manifestSchema` and `runtimeAbi` stay `1`, and the registry (`REGISTRY_VERSION`) and the context export are unchanged. No existing golden changed (item 9).
6. **Hot reload by the rule of decision 0067** (proposal; it changes the user-material path too). `migrateWorld` (`host/reload.ts`) carried every param that is `imperative` *in the new program* from the old record, whatever its class there and whatever the old material. It now carries a param exactly when it is `imperative` in **both** programs, the entity's instance has the **same material** and the param the **same declared type** (`keptParams`, for named and for spawned entities); any other param keeps what the new `init` set. This is the rule decision 0067 gave light fields and what `spec/runtime-abi.md` §11.3 says ("a changed default value is applied only if the instance's param was `initial` and the source literal changed"): before, an edit that added the first handler writing a param kept the old literal instead of applying the new one, and a material replaced by another with a param of the same name was handed the old material's value. `spec/runtime-abi.md` §11.3 states the rule.
7. **Tooling.** Completion after `Ball.material.` offers the params of the built-in material (the language server reads `entity_material`, which now answers for built-ins and the default `Unlit {}`).
8. **The benchmark is unchanged.** `interaction-02`, `-03` and `-04` bind their colours; binding stays a valid and idiomatic solution, so neither the tasks nor their references nor their fixtures change; a model that assigns the param now succeeds instead of meeting `E5001`.
9. **Fixtures and goldens.** No existing golden was re-blessed. `tests/semantics/fail/e5001_builtin_material_param_by_name` (decision 0086) kept its name and was rewritten for what stays an error: unknown params on `Unlit`, `Pbr`, the default `Unlit {}`, a static instance and `self` in a prefab, and an entity without a material. Three harnesses that had never met a texture or sampler param in a codegen golden learned that `init` does not write them (they are bound when the instance is created, decision 0054): `tests/codegen/app.test.ts` (`expectedCalls`), `packages/runtime-web/src/scene/world.test.ts` (the golden programs' `init`), and the fixture lists of `crates/mtek-compiler/tests/build.rs`, `packages/runtime-web/src/abi/abi.test.ts` and `tests/codegen/app.test.ts` gained the two new codegen fixtures.

## Fixtures and tests

- Semantic pass: `tests/semantics/pass/builtin_material_params` (read, assign and `+=` from the scene and from an entity's own handler through `self`, `Unlit` and `Pbr`, the default `Unlit {}`, reads into locals, state and a binding next to a bound param); `tests/semantics/pass/prefab_builtin_material_params` (`self.material.color` in a prefab with `Unlit` and in one with the default `Unlit {}`, static instances read and written from the scene, an imported prefab with `Pbr` and a bound param, `+=`, spawned instances).
- Semantic fail: `e5070_write_to_bound_builtin_param` (four `E5070`: own handler, scene, `self` in a prefab, static instance of a binding prefab; the unbound params beside them are accepted), `materials/e5073_assign_builtin_texture_param` (four `E5073` on the texture and sampler of `Pbr`), `e3001_builtin_param_assignment_type` (five `E3001`, one `E3010`), `e5001_builtin_material_param_by_name` (six `E5001`).
- IR goldens: `tests/codegen/ir/builtin_material_params.ir.{json,txt}`, `prefab_builtin_material_params.ir.{json,txt}` (`crates/mtek-compiler/tests/ir_goldens.rs`).
- Codegen goldens: `tests/codegen/builtin_params` and `builtin_params_edited` (the same scene with other literals and one other formula, for hot reload).
- Compiler: `crates/mtek-compiler/tests/unlit_shader.rs` (`every_prelude_material_agrees_with_its_registry_schema`); language server: `crates/mtek-cli/src/lsp/completion_tests.rs` (`members_of_a_builtin_material_are_its_params`).
- Runtime unit (`packages/runtime-web/src/host/builtin-params.test.ts`, the golden programs on the real runtime and the fake GPU): the classes in the manifest; a handler's write of the `Unlit` colour is in the instance's slot in the frame of the key press as exactly one upload of 16 bytes at that slot, and frames without a write upload nothing; `update`'s `+=` on the `Pbr` roughness reaches the block every frame and a binding reads it in the same frame, after the bound metallic it also reads; a handler copies a param into state and into another instance; hot reload keeps the two `imperative` values, applies the edited `initial` base colour and runs the new formula of the `bound` metallic on the kept state. `migrateWorld` against hand-made manifests: imperative in both keeps (a copy), `initial`/`bound` on either side takes the new `init`, another material keeps nothing.
- Browser, hardware (`tests/browser/specs/m6/builtin-params.spec.ts`, `tests/browser/fixtures/m6/builtin_params`, built into `.out/m6/` by `support/m6-fixtures.ts`): key handlers assign an `Unlit` colour and the base colour, metallic and roughness of a `Pbr` sphere, add to the roughness, and read every param back into state. The 25 pixels of the box are the bytes of the literal (within 1/255), the 16 sphere pixels the CPU oracle `shadePbr` for the assigned values within 3/255 (measured: at most 1/255 in all four frames), the materials before and after each write differ by more than four times the tolerance, and the values read back are the literals (linear binary32) and the binary32 sum.

## Consequences

- `spec/scenes.md` §4.1 (the `material` row), `spec/materials.md` §4, `spec/runtime-abi.md` §§5.2 and 11.3 point here; decision 0086 item 1 and decision 0079 item 7 say that the gap is lifted.
- A hot reload now applies an edited literal of a param that only the new program writes; nothing in the corpus relied on the old behaviour (every reload test passes unchanged).
- Not covered by a dedicated runtime test: a write of a built-in param of a **spawned** entity (the checker fixture spawns the prefabs whose handlers write `self.material.color`, and the generated code is the same `ctx.setParam(self, …)` as for a user material of a spawned entity, but no runtime or browser test runs it for a built-in).
