# 0062. Prefabs: declarations, params, static instances and the `prefabs` table: details the specification leaves open

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M5 (blueprint §11), task M5-01; `spec/scenes.md` §§4.4, 5, 8.2, 8.4, 11; `spec/runtime-abi.md` §§3, 4.2, 5; `spec/diagnostics.md` (`E5040`, `E5041`, `E5042`, `E5110`); decisions 0025 (milestone gating), 0035 (items that land before their milestone's gate), 0036 (modules), 0049 (state, handlers), 0051 (`bind`), 0053 (lights).
- Supersedes: nothing. Lifts the M5 gating of `prefab` declarations and of static prefab instances (decision 0025 item 2); dynamic instances (`spawn(Crate { .. })`), physics fields and collision events stay M5 (tasks M5-02 to M5-05).

## Context

The specification fixes what a prefab is (one entity, entity members plus `param`s), the three codes of its rules and the shape of the `prefabs` table of the program module (`init(ctx, self, params)`, `update`, `fixedUpdate`, `events`, `bindings[i](ctx, self)`). It leaves open how a prefab is checked, what an instance in another module may know of it, how a static instance becomes "a named entity whose fields and state initialise from params", what the IR and the generated code of that look like, and who sets `self.params`. Every choice below is a **proposal** the owner may overrule.

## Decision

1. **Gating.** Following decision 0035, the construct rows `Prefab` and `PrefabInstance` of `resolve/gate.rs` are marked `M1` (the build still reports M1; `CURRENT_MILESTONE` does not move). `GATED_RULES` of `tools/grammar-coverage` is empty: `prefab-no-nested-entity` (`E5040`) and `prefab-instance-params` (`E5042`) are covered by fixtures that report their codes. The `gate_prefab*` fixtures became real ones (below). What stays gated is reported as a milestone gate, not silently accepted: the `body` and `collider` fields and `on collision_enter`/`collision_exit` in a prefab body are `E9010` (planned for M5, fixture `gate_prefab_physics_fields`, the `Crate` of blueprint §3.3), and so is a **prefab literal** (`Crate { origin: p }` outside a declaration, the argument of `spawn`): `E9010` "Prefab literals … (planned for M5)" at the prefab's name (fixture `gate_prefab_literal`).
2. **The declaration** is checked once, in its own module, **before any scene** of the module (so an instance finds its prefab wherever it is written; `types/prefab.rs`). Its members are those of an entity body plus `param`: a nested `entity` is `E5040` at the nested entity's name (the prefab as related span), a `light` is `E5110` (decision 0053 item 3, unchanged: syntactic, and the light is not part of the prefab's entity), `param`s come first, then fields, constants, `state`, bindings, lifecycle functions and handlers. `self` is the one entity it describes; its fields are those of the `Entity` schema and its state those of the prefab. The prefab's name is not a value (`Crate.position` is `E3001`). A scene, an entity and a camera are not in scope: `E2003` from the resolver, which already scoped a prefab apart from the scene.
3. **Params.** `param name: T [= default];` — any type the annotation grammar gives; a default is a constant expression of the type (`E4031`, the code of decision 0039 item 3 for "invalid parameter default", now also for a prefab param; nothing refers to another param). A param is read by its bare name in field values, state initialisers, bindings, handlers and functions called from them; assigning it is `E3061` ("params are immutable construction inputs"). It is `self.params.<name>` at run time (item 9).
4. **Field values.** A value is typed and folded as a CPU root body (its calls make the functions it calls CPU-reachable, `CpuBodyKind::FieldInit`). Unlike an entity's, it may be **not constant** where it reads the prefab's params, constants or state or calls a function: the field is then *dynamic* (`CheckedField::dynamic`, a stand-in constant of the type keeps the checked prefab complete) and the prefab's `init` computes it. This is the initial-value expressions that decision 0039/0053 keep at `E9010` (M3) for entities; for prefabs they are needed by the specification's own example (`position: origin;`, `Unlit { color: tint }`). Construction-only values stay constants (`E3090`: a `mesh` over a param is rejected), a value that reads a field of the entity is `E5081` (`self.position` in an initialiser, with a note that names what a prefab's initialiser may read). In the `material` of a prefab each param is judged on its own: a param whose value reads the prefab is dynamic too (recorded per descriptor literal, `Typeck::init_params`); the instance's `bind`s are as in a scene (item 5). A dynamic `scale` cannot be range-checked before run time: `ctx.setTransform` reports `E8090`, as for a write.
5. **`bind` in a prefab** follows decision 0051 with `self` for the entity: the bindable fields of the entity and the params of its `material`; the bound expression may read `self`'s fields and state, the prefab's params, constants, functions and `frame`; purity `E5005`, type `E3102`, cycles `E5075` (reported as `self.position, self.scale`), `E5070` for an assignment from a handler of the prefab. Bindings are numbered per prefab in declaration order.
6. **Static instances** (`entity First: Crate { origin: vec3(0.0, 3.0, 0.0); }`). The body holds `name: value;` of params only. A name that is not a param, and any other member (`state`, `const`, `param`, a handler, a lifecycle function, a nested `entity`), is `E5042` with the prefab's params as a note (and the nearest as help); a required param left out is `E5041` at the instance's name, one diagnostic per param, with the param's declaration (possibly in another file) as related span; a param given twice is `E5002`; the value is checked against the param's type (`E3102`) and must be a **constant expression** (`E3090`) — the params of a static instance are construction-only values, like the fields of a scene; evaluating a run-time expression is what `spawn` (M5-02) does. A name that is not a prefab is `E3001` (`'Pair' is a struct, not a prefab`), an unknown one `E2003`. An instance may be nested in an entity (it is a child) and has no children of its own (`E5042`). `E5092` counts instances.
7. **What a scene sees of an instance.** The instance is a named entity: `First.position` etc. through the `Entity` schema, `First.bounces` (state the prefab declares, even in another module: `FieldKind::EntityState` with no state declaration of its own), `First.material.tint` (the params of the prefab's user material instance), `bind(..)` expressions over them, `E5081` in initialisers. A prefab's binding makes the instance's field bound: assigning it from the scene is `E5070`, with the `bind` in the prefab's file as related span (`First.position` is bound by its prefab Crate). All of this is read from the **prefab summary** `types::PrefabInfo` (params with defaults, state, the params of the material instance, the bound fields and params), which a module exports and `Imports::prefabs` carries to the importing module like decision 0039's `ImportedMaterial` (types are re-interned with `TyInterner::import_from`). A prefab's identity is `PrefabKey` (file and declaration), like `MaterialKey`.
8. **IR (`ir/model.rs`).** `Item::Prefab(PrefabItem)` is the IR of a **one-entity scene**: `params`, `constants`, `entity` (index 0; its symbol is the prefab's), `state`, `behaviors`, `bindings`; in every body of the prefab **entity index 0 is `self`**, and a read of a param is `ExprKind::Param` (the node of material params, which no prefab body can contain). A field or material param that `init` computes is `Source::Expr(expr)` (a third kind next to `Const` and `Bound`). An instance is an `Entity` with `prefab: Some(PrefabInstance { prefab, params })` (omitted from the serialised IR when absent, so no existing golden changed). The checker's side is `CheckedPrefab` and `CheckedEntity::instance`.
9. **Instantiation** (`ir/instantiate.rs`, after every module is lowered, since a prefab may live in a module lowered later). A static instance is made an **ordinary entity**: its position, rotation, scale, visibility, mesh and material instance are the prefab's with the instance's param values substituted for the reads (`Source::Expr` whose value became a constant is a `Const`; a `vecN(..)` of constants is folded as the checker folds it), its `state` is a copy owned by the instance (`path::Scene.First.bounces`), its lifecycle functions and handlers are copies with entity 0 renamed to the instance's index (`path::Scene.First.update`, `…on_key_down_Space`), its bindings are copies appended after the scene's (ids `n..`) and **evaluated before them** (`order`; they read only the instance, its params, constants and `frame`, while a scene binding may read what they write). `scene.state` and `scene.behaviors` stay in stable instance order. A material param the scene writes from a handler is marked `imperative` afterwards. Consequences: the resource plan, the manifest (entity entries, `state`, `update` flags, instances and bindings), `init`, the `events`, `entityUpdate` and `bindings` tables, hot reload and `mtek inspect --bindings` see ordinary entities and needed no change; the **code of a prefab's handlers is emitted once per instance** (a copy per static instance, not shared; the shared code is the `prefabs` table's, for `spawn`); the spans of the copies are the prefab's own, so a run-time diagnostic in a handler maps to the prefab's source (and the IR test that every span lies in its module's file allows the files of modules that declare prefabs).
10. **Generated code.** `app.js` has a `prefabs` entry for **every prefab of every module** (used or not), keyed by symbol, with the signatures of `spec/runtime-abi.md` §3: `init(ctx, self, params)` sets the state in declaration order and then the fields — constants as they are, expressions over `params.<name>`, bound values left to the runtime — in registry order, except that the fields of a prefab whose value is computed are set in the order of their declarations (so `random()` in two initialisers is not reordered); `update` and `fixedUpdate` (`(ctx, self, dt)` or `null`); `events` as for a scene, every `owner` the string `"self"`; `bindings[id]` is `(ctx, self) => value`. Names: `p_<hash8 of the module path>_<Name>_init`, `…_b<n>_<kind>`, `…_bd_<id>`. **Contract for the runtime (task M5-02, fulfilled by decision 0064):** the record of a prefab instance is created with `self.params` set to the same `params` object that is passed to `init`; handlers, lifecycle functions and bindings read `self.params`, `init` reads its argument. The manifest does not describe a prefab's bindings (targets, dependencies) yet; M5-02 adds what dynamic instances need. The manifest `symbols` list each prefab (`prefab`), its params (`param`) and its state (`state`).
11. **Runtime.** No change is needed for static instances (they are entities). `MtekProgramPrefab.events` is typed with the owner `"self"` (`MtekPrefabEventHandler`). Hot reload already compares the prefab names of two programs (`prefab 'x' was added/removed`); a prefab that is added or removed is a structural change.
12. **`mtek inspect --ir`** prints each prefab as an item (`prefab Crate [symbol]`, its params, its entity #0 — `self` — and its state, behaviours and bindings) and, for an instance, `instance of <prefab> { origin: …, tint: … }` before the fields; a value that `init` computes is printed as `init <expression>`. `--bindings` lists the instances' material instances like any entity's.

## Known limitations (recorded, not fixed here)

- The params of a static instance are constant expressions (`E3090`); a scene-state-dependent value needs `spawn` (M5-02) or a handler.
- Handler code is duplicated per static instance (item 9).
- A prefab's `body`, `collider` and collision events are gated until M5-03; `spawn`/`destroy` of prefabs, the runtime side of `prefabs[symbol]` and the manifest description of a prefab's bindings are M5-02.
- A prefab's `visible`/`scale` expressions are evaluated once at `init`; a changing value uses `bind`.
