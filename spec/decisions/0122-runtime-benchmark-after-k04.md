# 0122. The runtime benchmark after K-04: a second run, a generated comparison, what moved and what did not

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: §12.3, M7; `spec/ai-and-benchmarks.md` section 7; decisions 0095 to 0099 (method, first results), 0119 to 0121 (the changes), 0123 (what was not done).
- Supersedes: nothing. `report.md`, `summary.json` and `raw/20261019T052132Z/` are unchanged.

## Context

K-04 asked that each change be measured with the frozen runtime benchmark before it is kept, that the new raw results go to a new run id with the first run and its report untouched, and that a second report with a before/after table be generated by the same report tool. This record states how that was done and what the numbers say. Nothing here is a speed guarantee (spec section 7; decision 0096 item 7). Statements are labelled **observation** (measured), **decision**.

## Decision

1. **Decision: a new run, a second report, the first untouched.** `raw/20261019T150753Z/` is a complete run (all three implementations of all seven workloads, the same protocol, the frozen definitions `eb4cc942...`, the commit `135e43a7...` with a clean tree, taken with `run.ts --publish --prepare` under the machine's GPU lock, then `retry.ts` for the passes the machine disturbed). `report-after-k04.md` and `summary-after-k04.json` are generated by `report.ts --after=20261019T150753Z --label=k04` from the two runs' raw data; section 0 is the before/after table, the rest is the report of the new run. The tool gained `--after`/`--label`, and `report.ts` without arguments now means "the first published run" (`MAIN_REPORT_RUN`) instead of "the newest", because a later run must not regenerate `report.md`; its output for the first run is byte-identical (`report.ts --check` and `tools/report.test.ts` pass, and the test now also regenerates every `report-after-*.md` from its raw runs). Nothing under `harness/`, `common/`, the workload directories or `protocol.json` changed (`freeze.ts --check` prints the recorded hash).
2. **Observation: the machine was not quiet.** Other workers' builds and test runs were using the CPU for the whole of the run: busy share of all logical CPUs before a pass, median 19 % (6 % in the first run), maximum 100 %; during a pass, mean 32 % (20 %); 67 passes started above the 30 % quiet limit after waiting; 71 attempts were disturbed and 70 passes repeated (14 in the first run). The direct-WebGPU reference moved with the machine (for example 0.150 ms in the first run and 0.080 ms in the second for the 500 colours, 0.035 and 0.045 ms for the constant scene, the same code). The p95 threshold metric is the most load-sensitive number in the report, so the comparison below is also given from an interleaved measurement that does not depend on when the runs were taken.
3. **Observation: the threshold metric (p95 frame time) of the two published runs, all seven workloads** (`report-after-k04.md`, section 0):

   | Workload | Mtek before | Mtek after | direct before / after | Mtek vs direct before | after | above 20 % |
   | --- | --- | --- | --- | --- | --- | --- |
   | Constant scene | 0.115 ms | 0.080 ms | 0.035 / 0.045 ms | +228.6 % | +77.8 % | yes |
   | 1,000 changing transforms | 1.360 ms | 1.210 ms | 0.145 / 0.150 ms | +837.9 % | +706.7 % | yes |
   | 500 changing material params | 0.670 ms | 0.570 ms | 0.150 / 0.080 ms | +346.7 % | +612.5 % | yes |
   | 2,000 repeated meshes | 0.245 ms | 0.090 ms | 0.065 / 0.050 ms | +276.9 % | +80.0 % | yes |
   | Asset-heavy startup (p95 startup) | 223.9 ms | 297.7 ms | 204.4 / 243.0 ms | +9.6 % | +22.5 % | yes (was within) |
   | 300 physics bodies | 1.830 ms | 2.175 ms | 1.320 / 1.445 ms | +38.6 % | +50.5 % | yes |
   | 50 mount/reload/dispose cycles (p95) | 23.45 ms | 25.83 ms | 10.65 / 9.355 ms | +120.1 % | +176.1 % | yes |

   **All seven workloads are above the 20 % threshold in the second run; the asset-heavy startup, which was within it, is now just above it** because every implementation's startup was 10 to 40 % slower under the load of that run (the direct reference 204 to 243 ms, three.js 329 to 357 ms; nothing in this task touches startup or the asset path), and its Mtek median moved with them (219 to 236 ms against direct 169 to 183 ms). The p95 of the two frame workloads that did not benefit from the changes, the physics scene and the mount/reload/dispose cycles, is higher in the second run for the same reason; their p50 did not move (physics 1.580 to 1.605 ms against direct 1.135 to 1.195 ms). The threshold column is a statement about one run on one loaded machine; it does not show that a change made anything slower.

5. **Observation: the interleaved comparison.** Because the two published runs were taken under different load, the Mtek side of the old and the new runtime was also measured alternately, in one process, on prepared copies of the site built from the commit before K-04 (`dfd365c`) and from the final code (the per-step lines further down are from the intermediate commits of the branch) (seven repetitions of the frozen timing pass in a fresh page each, GPU lock held per pass, the machine's load mostly 15 to 30 % during them, one pass at 56 %; minimum over the repetitions; this is a development tool, not part of the protocol, and its output is not published):

   | Workload | p50 before | p50 after | p95 before | p95 after |
   | --- | --- | --- | --- | --- |
   | Constant scene | 0.075 ms | 0.040 ms | 0.110 ms | 0.065 ms |
   | 1,000 changing transforms | 1.070 ms | 0.535 ms | 1.335 ms | 0.775 ms |
   | 500 changing material params | 0.440 ms | 0.350 ms | 0.635 ms | 0.550 ms |
   | 2,000 repeated meshes | 0.190 ms | 0.040 ms | 0.235 ms | 0.060 ms |
   | 300 physics bodies | 1.605 ms | 1.470 ms | 1.855 ms | 1.675 ms |

   The per-step contribution, in the same way (five repetitions, p50 minimum): coalescing alone: transforms 1.015 to 0.990 ms, material params 0.455 to 0.455 ms, constant scene 0.085 to 0.075 ms, repeated meshes and physics unchanged: inside the noise (decision 0119); change tracking added: constant scene 0.075 to 0.055 ms, transforms 0.990 to 0.800, material 0.455 to 0.415, repeated meshes 0.200 to 0.045, physics 1.605 to 1.610 (decision 0120); allocation-free paths added: constant 0.055 to 0.040, transforms 0.800 to 0.505, material 0.415 to 0.340, repeated 0.045 to 0.040, physics 1.610 to 1.495 (decision 0121). The mount/reload/dispose workload, measured the same way on the two builds (two alternating runs each, the runner's own cycle pass): mount p50 22.5 to 18.6 / 20.5 ms, reload p50 3.6 to 3.8 ms, total p50 26.3 / 26.5 to 24.4 / 22.4 ms: not slower; the difference between the published runs is the machine.
6. **Observation: what these numbers say and do not say.** Where the old runtime did work for entities that did not change (a constant scene, 2,000 static instances) the frame cost fell close to the harness floor (0.020 ms) plus the draw encoding (2,000 repeated meshes: p50 0.190 to 0.040 ms, JavaScript allocation 157 KiB to 2.7 KiB; the direct reference 0.020 to 0.025 ms and 0.5 KiB). Where every entity changes every frame the cost fell by 30 to 50 % but is still several times the direct reference's: most of the 0.525 ms update of the 1,000 changing transforms is the evaluation of 2,000 generated bindings (the largest entries of a profile of the final code are `evaluate`, `qaxisAngle` and `sin`: the compiler's code and the values it builds, decision 0121 item 7), and the 500 individual draws spend most of theirs in 1,500 calls into the browser to encode them (a profile of the final code: `encode` 190 ms of 500 ms over the timing run). The 300 physics bodies are dominated by Rapier (the direct reference's p50 frame of 1.1 to 1.2 ms is almost all update, which is Rapier; Mtek's update is 1.4 to 1.5 ms of 1.6, its adapter included). None of this is a performance claim: the report must say, and does, that every workload is above the threshold in the second run.

## Consequences

- `benchmarks/results/runtime/` holds two raw runs, `report.md` for the first and `report-after-k04.md` for the second; `evidence/` and the release notes still quote only the first (decision 0104 forbids a number that is not in a linked file; the second run is not linked from them).
- A later run is taken with `run.ts --publish`, `retry.ts --run=<id>` and `report.ts --after=<id> --label=<name>`.

## Verification

- `report.ts --check` and `report.ts --after=20261019T150753Z --label=k04 --check` succeed; `tools/report.test.ts` regenerates both reports; `freeze.ts --check` equals the frozen hash; `npm run evidence:sanitize` finds no absolute path in the committed results.
- All figures above are in `report-after-k04.md` and `summary-after-k04.json` except the interleaved comparison of item 5, whose runs are not published (the script, `benchmarks/runtime/.out/ab.ts`, is a scratch tool outside the repository's tracked files); that item is evidence for the reader, not part of the reproducible report.
