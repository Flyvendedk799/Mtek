# 0079. The interaction benchmark tasks 02 to 08: what each tests, one pixel-exact geometry, fixtures derived by an oracle, timing and same-frame rules, the language and harness gaps found, and the mutation checks

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-08 (the interaction share of the full task set); blueprint §12.2; `spec/ai-and-benchmarks.md` §6 (task format, set composition, baseline fairness); decisions 0021 (task format, `set_input`, the 128 x 128 target, tolerance), 0074 (`mtek test`), 0077 (the repair harness `validate` command, `required_symbols`, NOT-RUN), 0064 and 0066 (flush points and the frame order the spawn task depends on).
- Supersedes: nothing. Adds seven tasks to `benchmarks/tasks/`; the set now has the eight interaction tasks of `spec/ai-and-benchmarks.md` §6.2 (`interaction-01` was the seed).

## Context

Section 6.2 asks for eight interaction tasks; M0 delivered one (`interaction-01`, a cube that reverses with Space). Every task needs a Mtek starter and a baseline starter, fixtures that define success for both sides, a reference solution for each side, and a Mtek side that is **verified** (compiled and run by `mtek test`, decision 0077 item 14), not predicted. The tasks of one category should test different things and must be fair: equally implementable in Mtek v0.1 and in three.js WebGPU with TypeScript event handling, with the prompt naming neither side's API. Every choice below is a **proposal** (a design choice; nothing external constrains it) unless it states a measurement.

## Decision

1. **The seven tasks.** All are `edit` tasks except `interaction-08`, which is `cold`. Budgets are those of the seed tasks (3 repairs, 4 000 output tokens, 300 s). The fixture counts are `mtek-tests/*.test.toml` files and `expect_pixel` steps.

   | Task | What the model does | What it tests | Fixtures / pixels | Required symbols |
   |---|---|---|---|---|
   | `interaction-02` | Right and Left arrows move a block one unit along a track, limited to x in [-4, 4]; at an end it is red; Enter recentres it | several key handlers; state; clamping at both ends; a derived appearance (red at an end, also after leaving it); retention (nothing moves alone) | 4 / 139 | `Demo.Handle`, `Demo.Track` |
   | `interaction-03` | A and B toggle one lamp each; Space flips both lamps *each from its own state*; Enter switches both off | independent per-entity state; flip versus set; presses of one frame all count, in arrival order (`A+Space` twice-flips A; `Enter+Space` and `Space+Enter` differ) | 4 / 242 | `Demo.LampA`, `Demo.LampB` |
   | `interaction-04` | Space starts a 1.5 s run (idle grey, running amber, done green); Space while running is ignored; Space when done returns to idle; every run counts the full 1.5 s | a three-state machine; a timer summed from frame durations; ignoring input in a state; resetting the timer | 4 / 133 | `Demo.Beacon` |

   Every edit task has one **retention fixture** that the starter passes (nothing changes without input), like the seed tasks: it detects an edit that breaks the starting picture. `interaction-08` has none (a cold starter draws nothing), so all three of its fixtures fail on the starter.
2. **One geometry for all seven: an orthographic front view in which one world unit is exactly ten pixels.** The camera is at (0, 0, 10) looking at the origin with `Orthographic { height: 12.8 }` on the 128 x 128 target, so pixel x = 64 + 10 x and pixel y = 64 - 10 y. Every shape is an unlit `Box` whose edges lie on integer pixel boundaries (sizes and positions are multiples of 0.1 and the oracle refuses a box with an edge off the grid; the one exception is the moving Runner of `interaction-08`, item 4). A pixel centre is then half a pixel from every edge, so the colour of a pixel does not depend on rasterisation rules, tessellation (there is none) or the sRGB path, and the fixtures can probe the **pixel just inside and just outside every edge**. Why not the perspective camera of the seed: there it takes a CPU projection per probe and the sample points must stay away from silhouettes; here an off-by-one in a position or a limit moves an edge by ten pixels. Measured: the Mtek runtime and the three.js baseline both reproduce the oracle's picture (item 3), so the assumption that both renderers place these edges identically held for all 1 980 probes.
3. **The fixtures are derived, not recorded.** `evidence/M6/benchmark-interaction/oracle/` holds `lib.mjs` (a flat-colour painter over the geometry of item 2 and a fixture writer) and one model per task (`interaction-0N.mjs`): the task description as a few lines of JavaScript (a state machine over the keys and inputs), no engine and no reference solution. `node oracle/interaction-0N.mjs` rewrites the task's `mtek-tests/*.test.toml`, and every expected colour in a fixture was computed there; the fixture header says so. Neither reference solution was run to obtain an expected value, and no fixture was changed after a run. The three.js references passed the first time they were run. The Mtek references did too, except that the first reference of `interaction-04` did not compile (the first gap of item 7) and was rewritten with a `bind`, after which it passed. That both sides agree with an independent model at 1 980 probes is evidence about the fixtures, the references and the renderers at once.
4. **Time.** Tasks 02, 03, 05, 06 and 07 do not depend on frame durations (frames of `0.016666668` s, the fixed step). Tasks 04 and 08 depend on summed frame durations and use frames of **`dt = 0.0625` s (1/16)**: exactly representable in binary32 and binary64, so every sum of frames is exact on both sides, and below the runtime's 0.1 s `max_frame_delta` clamp (a larger frame would be clamped on the Mtek side and not on the baseline's manual clock). The prompt of `interaction-04` says that the run does not depend on how many frames make up the 1.5 s, and the prompt of `interaction-08` defines the distance per frame as 4 times the frame's duration. **What the prompts leave open is in which frame a toggle takes effect** (the frame that applies the press may already count its own duration, or not: a handler that stores `frame.time` and an `update` that sums `dt` differ by one frame). The oracle runs both readings: `interaction-04` has checkpoints only at 21 frames or fewer after the press (still running) and 27 or more (done), the run being 24 or 25 frames long; `interaction-08` keeps a probe only where both readings agree on its colour under any shift of the picture by up to 3 pixels (one frame is 2.5 pixels). The alternate solution of item 8 that times the run with `frame.time` passes, which confirms that the fixtures do not pick one reading.
5. **Same-frame presses and host inputs.** A fixture presses several keys and then runs one frame (`press`, `press`, `step`), so the keys are applied in the order they were pressed within one frame. The three tasks that test it (03, 06, 07) were chosen because event order is a real source of bugs (a program that reads key state in `update` instead of handling the events sees at most one key per frame in a fixed order; two mutants of this kind fail exactly the same-frame fixture and nothing else, item 8). The baseline ignores a press of a key that is already down, so a frame in a fixture never contains the same key twice. **A key press and a host input are never put into the same frame**, because the two sides disagree: `spec/scenes.md` §10 step 1 applies host inputs first and key transitions second, while `startTask` (`benchmarks/baselines/support/src/task.ts`, `applyInput`) applies key transitions first and host inputs second. Fixtures of `interaction-05` always run a frame between a `set_input` and a `press`. **This is a defect of the baseline support module, reported to the orchestrator and not changed here** (it is shared): `applyInput` should apply `inputs` before `transitions`.
6. **Fairness checks, per task.** The prompts say what must happen in terms of the picture, the keys and the host input, never in terms of an API (no `key_down`, `bind`, `state`, `prefab`, `spawn`, `Orthographic`, `addEventListener`, `Scene.add`). Each baseline starter is the same scene built with the support helpers (`boxMesh`, `unlit`, `orthographicCamera`) and the starter's reusable piece is the Mtek prefab's counterpart (`createPip` in `interaction-07`). The Mtek side needs nothing the prompt does not give: the host input of `interaction-05` is a name and a type in the prompt (the model adds the `[host.inputs]` entry and the state, as in `shader-bridge-01`). What each side must do differently is part of the cost being measured: the baseline writes its own references and state variables, Mtek declares `bind`s and handlers.
7. **Language and harness gaps found.** Nothing in the language was changed; where a feature the spec lists is missing, the task is solvable by another route and the gap is recorded here.
   - **`Entity.material.param = value` on an `Unlit` instance is rejected** with `MTEK-E5001` "The entity 'Beacon' has no material." The spec (`spec/stdlib.md` §3.5, `spec/scenes.md` §8) lists the params of a material as writable, but in this build `note_entity_material` (`crates/mtek-compiler/src/types/scene_body.rs`) records only user-material instances, so a write to the `color` of a built-in `Unlit` fails, and the message is wrong in a misleading way (the entity has a material). Tasks 02, 03 and 04 recolour a block; their references **bind** the colour to state (`bind(color.linear(mix(OFF.rgb, ON.rgb, lamp_a), 1.0))`, `bind(phase_color(phase))`), which works and is idiomatic, (the alternate solutions of item 8 also bind the colour: no solution that writes an `Unlit` parameter exists in this build). A model that writes the param meets the diagnostic at its first attempt: this is the kind of finding the benchmark is for, and the harness shows it the message. Recommended follow-up (not done here): allow the write, or say in the diagnostic that built-in materials are bound, not assigned.
   - **No literal for a dead `entity_ref`.** A state of type `array<entity_ref, 5>` needs an initial value, and a reference can only be made by naming an entity (or by `spawn`, which an initialiser may not do): the reference of `interaction-07` starts as `[Rail, Rail, Rail, Rail, Rail]` with a comment, a placeholder that is never destroyed (only the first `count` entries are used). It works and it is what `tests/semantics/pass/spawn_destroy` does (`state last: entity_ref = Floor`), but it is an ergonomic gap.
   - **The baseline support module has no key-up handler, no held-key query and no fixed tick** (`TaskHost` has `onKeyDown` and `onInput`; the frame has `update` only), so **no task of this set tests `key_up`, `is_key_down`, held-key motion or `fixed_update`**, all of which Mtek supports. That part of the category is not covered; the change that would cover it is `onKeyUp(code, handler)` and `isKeyDown(code)` on `TaskHost` in `benchmarks/baselines/support/src/task.ts` (the `held` set and the `transitions` queue already contain what they need), after which a task like "move while the arrow is held" can be added. It is shared with the other task authors and was not changed here. Physics and collision tasks were not written for the same kind of reason: the baseline has no physics engine, so no fair comparison exists.
   - `expect_state` is a Mtek-only step (decision 0021 item 8), so every fixture of this set asserts pixels only; the counters and states of the Mtek side are checked only through what they draw.
   - **`on` is a keyword**, so `fn lamp_color(on: bool)` is a parse error; found when an alternate solution was written (the error is reported at the parameter, and it is the author's mistake, not a gap).
8. **The checks that the fixtures are the right ones (mutation and alternates).** `evidence/M6/benchmark-interaction/mutation/run.mjs` validates a candidate through the harness's `validate` command (parse, check, build, start, fixtures on the real browser).
   - **28 mutants** (the Mtek reference with one plausible mistake: no clamp, a limit of 5, red only at one end, Enter not recentring, Space copying a state instead of flipping it, Enter toggling, polling in `update` with a fixed key order (tasks 03 and 06), a run of 1.0 s and of 2.0 s, a restart on Space while running, a stale timer, a Done state that stays done, a limit of 5, one coordinate unclamped, Space not recentring, no cap at 8, P adding 2, R not resetting, a sixth Pip, Enter removing one Pip, an off-by-one place, a count that is not decremented, no wrap, a step of 4/60 per frame instead of 4 per second, a runner that never stops, a wrap at 5 and a stop that resets the position) **all fail** (28 of 28); each compiles, so it is the fixtures that reject it. The two polling mutants fail only the same-frame fixture.
   - **6 alternate correct solutions** (position written by the handlers and only the colour bound; bool states and a pure colour function; the run timed with `frame.time`; the marker written in `update` instead of bound; the cap as an `if` after each operation; the runner's x as bound scene state) **all pass** (6 of 6).
   The results are `mutation/mutants-results.json` and `mutation/alternates-results.json`.
9. **Status.** `mtek_side_status` is `verified` for the seven tasks, and the `// UNVERIFIED` header lines of their Mtek references are removed, as decision 0077 item 14 did for the first four. Their Mtek sources are formatted (`mtek fmt --check` is clean for every file of `interaction-01`..`08`).

## Consequences

- The set has 8 interaction tasks (7 edit, 1 cold) of the 30 of §6.2; the other categories are other tasks of M6-08. `benchmarks/README.md` (the table of tasks and the status) is updated by the orchestrator when the parts are merged.
- `benchmarks/baselines/support/test/starters.test.ts` lists the type-checked starters by name and does not yet list these seven; `tsc -b` (`npm run check`) and ESLint do cover them (the starters and references are in the `benchmarks/tsconfig.json` globs). Extending the explicit list is a shared change for the orchestrator.
- The fixtures of 04 and 08 fix the frame at 1/16 s, so a candidate is judged on a frame length that a real browser never has; this is deliberate (exact sums) and stated in the fixture headers.
- The numbers a model sees in the task prompt (1.5 s, 4 units per second, the limits) are repeated in the fixtures, which are not shown to the model; a change of a task needs a regeneration of its fixtures (`node oracle/interaction-0N.mjs`) and a new run.
