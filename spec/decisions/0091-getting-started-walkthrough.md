# 0091. The getting-started walkthrough: a document that is run, what counts as install, what is claimed and what is not

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M6 exit gate (blueprint §11): "a new user can install the toolchain, run a documented example, break it, understand the error and repair it" (task M6-11); `spec/tooling.md` §1, §4, §7; `spec/diagnostics.md` §6; `spec/runtime-abi.md` §11; decisions 0032 (CLI), 0033 (development server), 0070 (formatter), 0071 (validated suggested edits), 0076 (language server).
- Supersedes: nothing.

## Context

Every command a new user needs exists (`mtek new`, `check`, `build`, `dev`, `fmt`, `test`, `context`, `lsp`), each with tests, and no document walked a person through them. The root `README.md` still said that only `--version` existed and listed `mtek check` and `mtek dev` as "not available", so the first page a new user read was wrong. The acceptance criterion is a walkthrough test that passes from a clean environment; the risk of a walkthrough is that it drifts from the tool, so the test has to be built from the document itself, not written beside it.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **What counts as install today: building from a checkout, nothing else.** `docs/getting-started.md` says there is no registry release and no installer. Its install block is `npm ci`, `npm run build` and `cargo install --path crates/mtek-cli --locked`: the first two are the repository's documented build (the second embeds the runtime bundle into the binary, decision 0032 item 10), the third copies a release build of the same crate, with the bundle, to Cargo's bin directory. The prerequisites are the versions the repository pins (Rust 1.99.0 from `rust-toolchain.toml`, Node.js 24 from `.nvmrc`) and a Chromium with WebGPU. The `cargo install` path was run once on Windows 11 (the installed binary builds a project and prints its version); it was not run on Linux or macOS, and the document says so (macOS is stated as untested). Installing without the runtime bundle is described, with its `E9030`.
2. **What is claimed and what is not.** The document claims what the tool does on a machine with WebGPU, and for a machine without it only what was observed (the page says "Mtek could not run this program" with `MTEK-E8004` or `MTEK-E8005`; the build errors still show in the page). It does not claim support for browsers other than Chromium, for macOS, or for any editor: the sentence about editors says an integration is a separate document (the VS Code extension of M6-04 was not on `main` when this was written). It documents that the human diagnostic does **not** print the validated suggested edit (decision 0071 item 6), that the edit is in `--format json` and in the language server's quick fix, and that there is **no command that applies it**: the user edits by hand. The break and repair use `E1003` (a missing `;`), which has a validated edit.
3. **How the test extracts the document.** `crates/mtek-cli/tests/getting_started.rs` parses the Markdown fences of `docs/getting-started.md` (read at compile time with `include_str!`) and walks them in order, in an empty temporary directory, with `CARGO_BIN_EXE_mtek`:
   - ```` ```console ```` blocks: the `$ ` line is the command (`mtek ...` or `cd DIR`, plain words, no shell); the other lines are the expected output; standard output and standard error go to one file, so the order is the order a terminal shows. `exit=N` (default 0), `excerpt` (segments separated by `...`), `background` (`mtek dev`, started with `--port` of a free port), `watch` (no command: these lines must appear next in the background command's output), `runtime` (the step needs the runtime bundle).
   - ```` ```diff ```` blocks with `path=` and `role=edit|break|fix`: the lines the diff removes and keeps must occur exactly once in the file, and are replaced. The fix must restore the file as it was before the break, **and the suggested edit of the JSON report of the broken project, applied by a plain string splice, must give the same file as the documented fix**.
   - `file=PATH` blocks equal the file (the scaffolded `mtek.toml` and `src/main.mtek` shown in the document are the real ones); `files=DIR` lists the build's files; `text overlay` is the text the reload client shows, computed from the `build-failed` event the server replays to a new client (decision 0033 items 7 and 10) and compared with the document.
   - What is normalised, and nothing else: `\r\n` and colour escapes, `build` plus 16 hex digits (`<build id>`), `(N ms)` (`<n>`), the port of `127.0.0.1:` (the test cannot rely on 5173 being free), 16-hex-digit file name parts (`<hash>`). No absolute path may appear in any output (the test fails if one does), so the "temp path" needs no normalising. Exit codes, line and column numbers, counts and every word are compared as they are.
   - Also checked from the document: the versions in section 1 against `rust-toolchain.toml` and `.nvmrc` (and `package.json` `engines`), every command of the `sh install` block against `package.json` and `crates/mtek-cli/Cargo.toml` (a command nobody verifies fails the test), every relative link, the troubleshooting table's `MTEK-E9004` and port message against the real tool, and over the `mtek dev` step that `/`, `/app.js` and `/program.manifest.json` are served with the right status and content type.
4. **Rust, not TypeScript, for the walk; TypeScript for the browser half.** The walk needs the built binary, temporary directories and no browser, so it belongs with the other CLI end-to-end tests (`crates/mtek-cli/tests`) and runs in `cargo test --workspace --locked` in the `rust` CI job on Ubuntu and Windows and again, with the runtime bundle embedded, in the `node` job. The cube, hot reload and the overlay need a browser: `tests/browser/specs/m6/getting-started.spec.ts` reads the same document, takes its `edit`, `break` and `fix` diffs and its overlay block, and runs them against a real page served by `mtek dev` from a `mtek new` project: the edit widens the cube without a reload; the document's remark about state (a changed initial value of `state speed` does not reach the running scene, the cube keeps turning; a reload starts from the file) holds; the break shows exactly the documented overlay without a reload; the fix removes it without a reload. It needs a WebGPU adapter and is NOT-RUN without one (the `gpu` fixture); it runs in the hardware and software projects (the CI `browser-software` job).
5. **NOT-RUN is explicit.** A binary built without the runtime bundle (the `rust` job, a fresh checkout before `npm run build`) cannot build or serve: the walk then lists every step it did not run, prints `NOT-RUN <line>: <step>: <reason>` for each, runs the real `mtek build` once and requires it to fail with `E9030`, and asserts the list is not empty, so a missing bundle can never read as a pass; with the bundle it asserts the list is empty. So in CI the full walk (including `mtek dev`) runs in the `node` job on Ubuntu only; Windows CI runs the walk without the runtime steps. This is a limit of the CI configuration (the Windows job has no Node), not of the test.
6. **The test must be able to fail.** `the_walkthrough_rejects_a_document_that_is_not_true` runs the walk on seven mutants of the document (a wrong summary line, a wrong exit code, a changed file block, a fix that is not the inverse of the break, a changed diagnostic help line, a wrong overlay column, a wrong `build failed` line of the server) and requires each to fail at the step it is about; the browser spec was run once with the overlay column changed in the document and failed on the overlay assertion. The normaliser, the diff applier and the edit splice have unit tests with bad input.
7. **Human tester: none was available.** No human tester was available when this was written; the walkthrough has been exercised only by the scripted test, the browser spec and its author. The document's maintenance note says so. The checklist below is for the first person who can do it; their outcome is to be recorded here in a new amendment, not invented.

## Findings on the new user's path

Found while following the path, fixed where small and clearly correct, otherwise reported:

- **F1, fixed: the root `README.md` told a new user that nothing worked.** Its status paragraph said the CLI implemented only `--version`, and a table titled "Planned commands (not available)" listed `check`, `build`, `dev`, `new`, `fmt`, `test`, `context`, `grammar` and `lsp`. Both are rewritten: the status says what exists and points to `docs/getting-started.md`; the table is now "The `mtek` command" and lists the real commands (the README table is checked by nothing; the document's own commands are).
- **F2, reported, not changed: the human diagnostic does not show the suggested edit** (by decision 0071 item 6, "printing the edit in the human renderer" is a recorded follow-up). A person reading `mtek check` learns "help: end every statement ... with `;`" but not that the compiler has an exact, proven repair, nor how to get it (`--format json`, the editor). The document says so; whether the renderer should print the edit, and how a CLI user should apply one (there is no `mtek fix`), is a product decision.
- **F3, reported: there is no way to serve a release build with `mtek`.** `mtek dev` serves a development build and overwrites `dist/` with it; `mtek build` writes files that a browser will not load from a `file:` address. The document says to use any static file server and names none.
- **F4, observed and documented: hot reload does not apply an edited `state` initial value** (spec §11.3, state is carried by identity). A new user who edits `state speed` sees nothing happen. The document says so and the browser spec asserts it.
- **F5, observed, not changed: the browser console logs one `404` for `/favicon.ico`** (the browser asks, the build has none). The document says it is harmless.
- **F6, not changed: the Windows CI job never embeds the runtime**, so the `mtek build` and `mtek dev` steps of the walk run on Ubuntu (node job) and on the developer machine, not on Windows CI (item 5). Adding Node and `npm run build` to that job would close it.

Checked and fine: the template builds and is canonical for `mtek fmt --check`; the dev page's reload client shows the overlay for a failed first build and after a failed rebuild, and a successful rebuild hot-reloads without a page load (one navigation in total over an edit, a break and a fix); on a machine without WebGPU the dev page shows the runtime's own explanation and the overlay still works.

## Fixtures and tests

- Changed: `README.md` (F1, link), `spec/tooling.md` (a pointer in section 1), `spec/decisions/README.md` (this row).

## Consequences

- A change to a command's output, to the template, to the diagnostic text of `E1003`, to its suggested edit, to the dev server's lines or to the overlay breaks the walkthrough test until the document is updated, which is what makes the document trustworthy; the price is that these edits now touch two files.
- The document's `console` notation is small and specified in its maintenance note; another document can use it. A second use would be a reason to move the walker into a shared test support crate.
- The browser spec adds about 20 s to a browser run and is the only automated check of the claims about hot reload and the overlay in a real page.

## Human tester checklist

For one person who has not seen the project, on a machine with a Chromium that has WebGPU. Do not help them; write down where they hesitate.

1. Give them only the checkout and the link to `docs/getting-started.md`. Time how long installation takes and note every error and every question.
2. Did `npm ci`, `npm run build` and `cargo install ...` work as written (or did they use `target/debug/mtek`)? Was anything missing from the prerequisites (a C toolchain on Linux, for example)?
3. After `mtek new hello-mtek` and `mtek dev`: did they open the URL, and did they see a turning, pulsing cube? What did they think the panel in the corner was?
4. Did they make the cube wider by the edit, and did they understand that the page was not reloaded? Did they try changing a different value (`speed`), and was the remark about state enough?
5. After breaking the file: which of the three places did they look at first (terminal, browser, `mtek check`)? Could they say, in their own words, what was wrong and where? Did they find the fix without the document's help? Did they notice or ask for the suggested edit, and how did they expect to apply it?
6. After the repair: did they know it was repaired (the overlay left, the summary line)? Did they run `mtek build` again?
7. Did the "where to go next" section point them somewhere they wanted to go? Record the outcome here, honestly, including failures.
