# 0072. The context export: `mtek context`, what `supported` is derived from, the neighbourhood, the example library, the truncation order and the failure modes

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-05; blueprint §3.4 (one registry), §9.2 (a neighbourhood, not the whole library), §10 (never advertise planned features as supported); `spec/ai-and-benchmarks.md` §2 (the format and its rules), `spec/tooling.md` §1, `spec/stdlib.md` §1, `spec/language.md` §§1.5, 2.2, 2.3, 6.1; decisions 0003 (AI-native), 0013, 0024 and 0025 (milestone gating, `since`), 0032 (CLI conventions), 0035, 0039, 0049, 0053, 0057, 0062, 0064, 0065 (gates lifted ahead of the milestone gates: the build reports M1 and the registry rows say M1).
- Supersedes: nothing. Replaces the placeholder `ContextRequest`/`ContextResult` of `spec/compiler-architecture.md` §4.12.

## Context

`spec/ai-and-benchmarks.md` §2 gives a sketch of the output and five rules. The repair harness (M6-07) will call the command for every task, so the output has to be exact, deterministic, honest about what this build implements, small enough for a prompt, and testable. The sketch leaves open what "derived from what this build implements" means while the build reports milestone M1 and every registry row says `since: M1`, how a neighbourhood is chosen, what the examples are and how they are tested, the full truncation order, and what happens when the project does not load or the budget cannot be met. All items below are **proposals** unless labelled.

## Decision

1. **Format (proposal).** The output is the JSON of the sketch with exactly its keys in its order (`languageVersion`, `compilerVersion`, `contextFormat`, `supported {features, notSupported}`, `syntax {keywords, precedence, rules}`, `project {entry, scene, modules}`, `symbols`, `schemas`, `examples`, `diagnosticsGuide`) plus the optional trailing `truncated`. `contextFormat` is `1`; it is bumped when a key is removed, renamed or added, because `spec/context.schema.json` (JSON Schema 2020-12, checked in, validated by tests) forbids unknown keys. Text: two-space indentation, one trailing line feed, LF only, no floats, no maps; the order of every array is fixed below. Schema fields carry only `name`, `type`, `default` (canonical source text or `null`) and `flags` (`R W B C` in that order); a symbol's `doc` is `""` when there is none. `scene` is `null` when the project selects no entry scene.
2. **Where it lives (proposal).** `mtek_compiler::context::context(root, fs, &ContextOptions) -> Result<ContextOutput, ContextError>` (module `context/`: `capabilities`, `syntax_info`, `program`, `examples` with its `examples/*.mtek`, `fit`, `model`). It runs `analyze` (so it sees exactly what `check` sees, including types) and never touches the GPU. The CLI part is `crates/mtek-cli/src/context_cmd.rs` plus an enum variant and a match arm in `args.rs`/`commands.rs`.
3. **`supported.features` is derived (proposal).** One entry per row of the build, from the sources the compiler itself consults, never from a list: (a) every `Construct` of the resolver's table whose `since` the build has reached, named by an exhaustive `feature_name` match (`scenes`, `entities`, `state`, `bind`, `handlers`, …); (b) every registry row whose `since` is reached, sorted, as `kind:name`: `type:`, `method:` (type accessors), `schema:`, `scene-object:`, `event:`, `enum:`, `namespace:`, `function:` (intrinsics and namespace functions, `function:quat.identity`), `value:` (`value:frame.time`), `body-command:`, `body-property:`. Schema fields and enum members are rows too but are listed only when gated (fields are the `schemas` section). A row nested under a gated parent is covered by the parent's entry. The function is `derive_for(registry, milestone)`; `derive(registry)` uses the build's `IMPLEMENTED_MILESTONE`.
4. **`supported.notSupported` is derived (proposal).** In this order: (a) rows whose `since` the build has not reached, as `name (planned for Mn)`, by milestone then name (none today: gates were lifted ahead of the milestone gates by the decisions listed above, so the build reports M1 and every row says M1); (b) the **hard gates**: constructs the checker rejects with `E9010` from a check of its own, whatever the milestone says. They are now rows of `resolve::gate::HARD_GATES` (`HardGate { feature, subject, plural, since }`); the checker takes its `E9010` wording from the row (`NON_CONSTANT_INITIAL_VALUES`, "Initial values that are not constant expressions", planned for M3, which `types/scene.rs` used to spell inline), so the export and the build cannot disagree. Lifting a hard gate means deleting its row and the check that uses it. (c) the reserved words (`RESERVED_WORDS`, `E0013`), as plain words; (d) every catalogue code for which `Code::is_unsupported_feature()` holds, as an agent-facing phrase from a table keyed by code (`bitwise operators`, `transparency`, …). The set is derived; only the wording is a table, and a test fails for a code that has no phrase (the fallback, the title without " not supported", is never used). Limits, stated honestly: a rejection with an ordinary code (package imports `E2034`, Unicode identifiers `E0010`) is a syntax rule or a diagnostic, not a gate, and is not listed; build modes and CLI commands are not language features and are out of scope (`--mode preview` is another task's).
5. **Syntax (proposal).** `keywords` is the lexer's `KEYWORDS` table. `precedence` (tightest first, `level 6: * / % (left)`) is read from `BINARY_OPERATORS`, which this record makes the table the Pratt parser itself uses (`syntax/parser/expr.rs`; before, a `match`); the postfix and prefix levels 8 and 7 are structural and a test compares all eight lines with the table of `spec/language.md` §6.1. `rules` are eight sentences, each stored with a program that breaks it and the diagnostic code the compiler reports for it; a test runs every one, so a rule cannot outlive the behaviour it states. `diagnosticsGuide` is one sentence; a test checks that every field it names exists in `spec/diagnostic.schema.json`.
6. **Project and symbols (proposal).** `--entry` must be the project's `project.entry` (the project is the nearest directory above it with an `mtek.toml`, as for every command); anything else is a usage error. `project.modules` lists the project's own modules in load order (the embedded `std/materials.mtek` that a built-in material pulls in is never listed). A symbol is a declaration: scene, entity (nested ones too), prefab, material, struct, `fn`, `cpu_fn`, module and body `const`, `state`, `param`, or a scene object (`kind` is its keyword, `camera`). `name` is the chain of declaration names from the module item down joined by `.` (`Demo.Cube.speed`, the same chain as the IR symbols without the file), `file` the module path and `line` the 1-based line the declaration (not its doc comment) starts on. `type` is the type as written (the checker's inferred type for an unannotated `const`; `unknown` if it has none), a signature for a function (`(x: f32) -> f32`), `struct { a: f32; b: vec3 }`, the schema name for a scene object, `entity: Prefab` for an instance, a plain `scene`/`prefab`/`material`/`entity` otherwise. `doc` is the `///` run directly before the declaration (`spec/language.md` §1.5), the `///` and one space removed, lines joined by `\n`. A project that loads but has errors still has a context, from what parsed; a project that does not load (`E9001`, `E9004`, `E9005`, …) gets the diagnostics report instead (item 10).
7. **Neighbourhood (proposal).** *Seeds*: the declarations named by `--symbol` (by name, or `path::name`; every match; none is a usage error with up to three "did you mean" names within edit distance 2), or without it the entry scene, or, when no scene is selected, every top-level declaration of the entry module. The context holds (i) the seeds and everything nested in them, (ii) the declarations one reference away in **either direction**: a *reference* is a name that resolves (through imports too) to a project declaration, attributed to the innermost declaration containing it, and the neighbours are the declarations a seed-or-nested one refers to and those that refer to one, (iii) the schemas of the declarations themselves (`Scene`, `Entity`, the scene-object kind's schema) and of every descriptor literal inside (i), sorted by name, with only the fields this build implements, (iv) the examples of item 8. Symbols come in module load order, then source order. Nothing is followed a second time.
8. **Examples (proposal).** `context/examples/NN-*.mtek` are eleven complete entry modules (embedded with `include_str!`; `eol=lf` keeps the bytes the same on every host). Their tags are **computed**, not written: the features an example uses are found by the code that finds the features of a neighbourhood (declarations, a few syntax nodes, resolved library names, named as in `supported.features`), so a tag cannot name something the example does not use; `tests/context/golden/examples.features.json` pins them. An example is chosen by weighted Jaccard similarity of its features with the seeds' (a feature weighs 1000 / the number of examples that use it), ties to the shorter then the earlier; at most four, most relevant first. Tests: every library example checks with zero errors and zero warnings; every example in every emitted context (goldens, every truncation step, the real binary's output) is re-checked from the JSON; a project that is an example gets that example back; every feature an example uses is in `supported.features`.
9. **Truncation (proposal).** The text never exceeds `--max-bytes` (default 24000, bytes of the text with its trailing line feed). If it is longer, items are dropped lowest priority first: examples (least relevant first), neighbour symbols (last in file order first), schemas (last by name first), the requested symbols (last first); the version fields, `supported`, `syntax`, `project` and `diagnosticsGuide` are never dropped. A later phase starts only when the earlier ones are empty, and within a phase the fewest items are dropped that make it fit (found by bisection: an item is always longer than the name `truncated` keeps of it, so dropping more is monotone; the cost is a handful of renderings, and a unit test checks it against dropping one at a time). `truncated` has one key per section that lost something, `{ "count": N, "names": [first ≤ 16, lowest priority first] }`; the cap keeps the note short when a 3 000-entity scene loses nearly everything (a first design listing every name made the default budget unsatisfiable for large scenes). Absent when nothing was dropped. If the text is still too long with everything droppable gone, there is no such context: usage error naming the smallest budget that works (item 10); that number works.
10. **CLI behaviour (proposal).** `mtek context --entry FILE [--symbol NAME…] [--max-bytes N] [--format json]`; `--symbol` repeats or takes several values; `json` is the only format and the default (`human` is a usage error). Success: the document on stdout, exit 0, nothing on stderr. The project cannot be loaded: the one diagnostics report of `spec/diagnostics.md` §2.2 on stdout, exit 1 (`--format json` convention). Usage errors (wrong `--entry`, unknown symbol, budget too small, bad number, missing `--entry`): message on stderr, nothing on stdout, exit 2. The output does not depend on the working directory.
11. **Determinism (proposal).** No clock, no absolute path, no hash-map order, no host dependence: paths are project-relative with `/`, every array has a fixed order, the text is a pure function of the build, the project's files and the options (tested across working directories, in-memory listing orders and repeated runs, and byte-compared with goldens).
12. **Not in format 1 (proposal).** Intrinsic signatures, schema ranges and docs, schema rules (`mesh` requires …) and namespace member signatures are in `spec/stdlib-schema.json` but not in the context; adding them is a `contextFormat` 2.

## Tests

`crates/mtek-compiler/tests/context.rs` (32 tests): features equal the rows of `stdlib-schema.json` read as a second path to the registry, planned rows likewise; mutated registries (a new row appears in `features`, the same row planned appears in `notSupported` with its milestone, a gated schema covers its fields, gated enum and namespace members, a build that has reached the milestone lifts them); the hard gate against the real `E9010`; reserved words and unsupported codes against their catalogues, the phrase table complete; keywords, reserved words and precedence against `spec/language.md`; every syntax rule against the compiler; every example; neighbourhoods (default, one symbol, both reference directions, imports, several symbols, docs, lines, kinds, unknown symbols, entry mismatch, unloadable and erroneous projects, the prelude not leaking); truncation order over every budget step, the minimum budget, a 400-entity scene; determinism; schema validity and invalidity; goldens of the three example projects (default, symbol, truncation). Unit tests in `context/fit.rs` (bisection against one-at-a-time). `crates/mtek-cli/tests/context.rs` (13 tests): the real binary, cwd independence, symbols, budgets, every exit code, the golden byte for byte, every emitted example through the real `mtek check`. Goldens: `tests/context/golden/` (7 contexts and the example tags); regenerate with `MTEK_BLESS=1 cargo test -p mtek-compiler --test context`.

## Consequences

- Adding or gating a registry row, a construct or a hard gate changes `supported`, hence every golden, until blessed; the coverage tests fail first if a row is neither listed nor planned.
- A future milestone that lifts a gate by changing a `since` (or `CURRENT_MILESTONE`) changes the context with no edit here; one that lifts a hard gate deletes its row.
- The harness (M6-07) can rely on `contextFormat` 1 and `spec/context.schema.json`.
- `BINARY_OPERATORS` is now the parser's precedence table; changing precedence means changing it and `spec/language.md` §6.1 (a test compares them).
- A large scene's default context is a prefix of its declarations plus a count; callers that need a part ask for it with `--symbol`.
