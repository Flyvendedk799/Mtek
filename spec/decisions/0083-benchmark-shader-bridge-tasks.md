# 0083. Benchmark tasks `shader-bridge-02` to `shader-bridge-06`: what each tests, how every expected pixel is derived, what the fixtures can and cannot observe, and what was left out

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-08 (the shader/bridge part); blueprint §12.2 (the AI/token benchmark: 6 shader/bridge tasks, each solvable on both sides); `spec/ai-and-benchmarks.md` §6 (task format, set composition, prompt and baseline fairness); `spec/materials.md` §§1 to 4 and 7 (materials, parameters, `bind`, light bindings); `spec/scenes.md` §§7.5, 8.4, 10 (frame values, binding rules, frame order); decisions 0021 (task format, fixtures, `set_input`), 0039, 0041, 0046, 0051 (materials, shader lowering, runtime materials, `bind`), 0053 and 0067 (lights and bindings that read them), 0074 (`mtek test`), 0077 (the repair harness, `validate`).
- Supersedes: nothing. Fulfils the shader/bridge share of the sentence of `spec/ai-and-benchmarks.md` §6.2 that gave M6 the completion of the 30-task set (with `shader-bridge-01` of M0-10 this makes 6).

## Context

`shader-bridge-01` (one host colour input bound to one material colour) is the only shader/bridge task. The set needs five more that test different parts of the bridge between CPU values and GPU material parameters, and each must be solvable in both Mtek v0.1 (only what this build supports, `mtek context`) and in three.js WebGPU with TSL, with the same `mtek-tests/*.test.toml` fixtures defining success on both sides (decision 0021 item 8). The prompts must be fair, precise and equally implementable on both sides, without leaking either side's API. Every expected pixel must be derived from the task description, never from running a reference.

## Decision

1. **The five tasks.** All use the camera of `shader-bridge-01` (position (0, 0, 6) looking at the origin, `fov_y` 0.9, 128 x 128 target, clear colour #202020) and unlit custom materials, so that the expected colours do not depend on any lighting model.

   | Task | Mode | What it tests | Fixtures |
   |---|---|---|---|
   | `shader-bridge-02` | edit | One `f32` host input drives one shared value; two instances of one material read it through different expressions (`level` and `1 - level`). The material gets a parameter, the scene a state, `bind` takes an expression, not only a name. | `default` (Left and the background keep the starter's look: the starter passes it), `level` (the default 0.25 / 0.75 pair, then four `set_input` values) |
   | `shader-bridge-03` | **cold** | A custom fragment computed per pixel from the object-space position and the elapsed time (`sin`, `mix`, colour constants converted from sRGB, blend in linear light). The shader cannot read `frame.time` (`E4040`), so time must reach it as a bound parameter. The panel stands at x = 0.4, so a shader that reads world x instead of object x is wrong. | `sweep` (5 columns at 3 times), `shape` (colour constant along y, the panel's extent, the clear colour) |
   | `shader-bridge-04` | edit | A CPU counter changed by two key handlers (`Space` +1 up to 4, `Backspace` -1 down to 0) reaches the shader as `f32(charge) / 4` through `bind`: an `i32` to `f32` conversion, `if` in handlers, only key-down transitions count (a held key is one press). | `start` (black cube; the starter passes it), `charge` (both limits, see item 4), `hold` |
   | `shader-bridge-05` | edit | A binding that reads a light field: the dial's level follows `Lamp.light.intensity`, which is itself bound to a host-driven state (decision 0067, the `light` dependency kind; a chain host input, state, light, material parameter). In three.js the lamp is a `PointLight` whose `intensity` is read each frame. | `start`, `power` (five values), `surroundings` (the lamp draws nothing; the starter passes it) |
   | `shader-bridge-06` | edit | Ordering of bindings: the cube's `position.y` follows a host input and the material parameter follows the cube's own height in the same frame (a dependency chain, evaluated in topological order, `spec/scenes.md` §8.4), plus a two-colour blend in the starter's fragment. Every `set_input` is followed by exactly one `step`, so a colour that trails the height by a frame fails (in Mtek `bind` orders the chain, so the natural solution cannot lag; in three.js an `update` that reads the height before writing it does, item 5). | `start` (the cube at the origin in COOL; the starter passes it), `lift` (five heights; -1 is below the camera and makes the warmth negative, which the material limits to 0) |

   12 fixtures, 5 tasks, all `step`, `press`, `release`, `set_input` and `expect_pixel` (no `expect_state`, which the baseline interpreter rejects).

2. **Derivations.** Every expected value comes from `benchmarks/baselines/support/test/projection.ts`-style f64 geometry (front face extents, pixel centres at +0.5, object-space x of a pixel column) and the exact sRGB transfer function; the arithmetic is written into the comment at the head of each fixture. Examples: linear 0.25 is #898989 (136.96), 0.75 is #e1e1e1 (224.61), 0.3 is #959595 (148.88); `shader-bridge-03` evaluates `w = 0.5 + 0.5 sin(0.8 x + t)` and the blend of the linear forms of #1a237e and #ffb300 at the pixel centres of five columns for t = 0.0625, 1 and 2.75 (the frame step 0.0625 is exact in binary, so the accumulated time is exact in `f32` and `f64`); `shader-bridge-06` blends #1e3a8a and #f97316 at w = 0, 0.25, 0.5, 0.75 and 1 and places the cube's front face with the same projection for five heights. Pixels are chosen inside front faces, avoiding the strips of side, top and underside faces that the perspective shows (the first version of `shader-bridge-02` sampled a pixel on the inner side face of Left and was corrected by its own run; the numbers are in the comment).

3. **Fairness checks.** The prompts say what is drawn and computed, in terms of linear light and sRGB, object-space coordinates, host inputs, key presses and "a value that is updated"; they name no Mtek construct (`bind`, `param`, `state`, `[host.inputs]`, `frame.time`) and no three.js construct (`uniform`, TSL nodes, `onBeforeRender`). Entity and material names are given, so the required declarations exist on both sides. The baseline starters use only the support module of decision 0021 item 6 (`startTask`, `host.onInput`, `host.onKeyDown`, `boxMesh`, `lookAtCamera`, `srgb`): no new helper was added, so the fairness rule of `spec/ai-and-benchmarks.md` §6.3 is met by what already exists. Each task has a natural solution on both sides of about the same size (a parameter or a uniform, a state or a variable, a binding or an `update` assignment). Alternative correct programs are accepted by the fixtures on both sides (item 5).

4. **What the fixtures can and cannot observe.** The render target clips at 1.0 and no tone mapping exists, so a grey above 1 is indistinguishable from 1. Therefore (a) `shader-bridge-05` does not ask for a limit to 1 and states that `power` lies in 0 to 5 (a first draft with a `saturate` requirement was removed because no fixture could observe it), and (b) the limit 4 of `shader-bridge-04` is made visible by lowering the charge afterwards (six presses of `Space`, then `Backspace` must show charge 3, where a limit of 5 shows white); the lower limit is made visible by pressing `Space` after `Backspace` was pressed at 0. The panel of `shader-bridge-03` is shifted to x = 0.4 for the same reason (object versus world x). Behaviour that the prompts require and no fixture can distinguish is listed here, not hidden: that the material and shader are not replaced (decision 0021 item 8 has the same limitation for `shader-bridge-01`: the fixtures see pixels only), that `shader-bridge-05` is solved through the light and not through `power` (both give the same pixels and both are correct: the intensity is twice the power), and that `shader-bridge-06`'s warmth is read from the cube's height and not from `lift`.

5. **Mutation check of the fixtures (Mtek side).** 24 changed copies of the references were run through `validate`: 22 are rejected (a swapped or non-complementary pair, a wrong initial level, a state read without `bind` (the compiler refuses it, `E9010`), the time one frame late or early (4 to 7 bytes), no time binding, another frequency, a flipped sign, a blend in sRGB instead of linear light, world x for object x, a panel of another height, limits 5 and none, a `Backspace` that does nothing, a divisor of 3 or 20, `Space` on key-up, `power` as the intensity, another divisor of the height, a cube that does not follow `lift`, the lift on the x axis) and the 2 equivalent programs are accepted (`power / 5.0` instead of the light's intensity, `lift / 2.0` instead of the cube's height). The changes and the first failing pixel of each are `evidence/M6/benchmark-shader-bridge/mtek-mutants.json`. One mutant of the three.js side was run as well: the reference of `shader-bridge-06` with the two lines of `update` swapped (the colour computed from the previous frame's height) fails its fixture (`baseline-mutants.json`).

6. **Measured agreement.** On the hardware adapter both sides reproduce the independently derived values exactly: with every tolerance of the 12 fixtures set to 0 (temporary copies, not committed), the Mtek references pass 12 of 12 through `mtek test` and the three.js references pass 12 of 12 through Playwright. The committed tolerances stay 2 (flat colours) and 3 (the `shader-bridge-03` gradient, which changes by up to 4.5 bytes per pixel along x, so a quarter of a pixel of difference would matter) so that another adapter's rounding does not fail a correct program. This is a measurement of one machine (AMD Radeon RX 7900 XTX, `isFallbackAdapter` false), not a guarantee for others.

7. **Language gaps found and how they were handled.**
   - *No texture or sampler task.* The planned "texture/sampler parameter" task is not in the set. A fair one needs an image that both sides load: the Mtek side needs an asset file inside the project (which the harness lets a model neither create nor edit, `mtek.toml` and `src/**/*.mtek` only) and the baseline support module has no texture or asset helper (a new one would have to be added to the shared support module and counted in the baseline's documentation cost). The built-in textures are 1 x 1 constants, so a task built on them would test nothing about `sample`. This is a gap of the benchmark, not of the language (decisions 0054 and 0060 and the M4 browser tests cover textures); it is reported to the orchestrator.
   - *`dt = 0` cannot be used in a task fixture.* `mtek test` accepts `{ step = 1, dt = 0.0 }` (the example fixtures use it) but `benchmarks/tools/validate-tasks.mjs` requires `dt > 0`. Time 0 is therefore not observed; the tasks observe t = 0.0625 as the first value.
   - *`frame.time` is not readable from a fragment* (`E4040`): the intended bridge, and what `shader-bridge-03` needs a model to find.
   - *A state read in a material parameter value without `bind`* (`material: Shade { amount: level }`, which `spec/materials.md` §4 describes as a value evaluated once at construction) is `E9010` in this build: "Initial values that are not constant expressions are specified for v0.1 but not implemented by this compiler build yet (planned for M3)", with the note "this compiler build implements the language up to milestone M1" (listed in `notSupported` by `mtek context` as `non-constant-initial-values`). A model that tries it gets a diagnostic, not a silent frozen value, and the tasks need nothing but `bind`. The gate and its two milestone sentences look stale at M6; that is a finding for the owner of the milestone gating (decision 0025), not something this record changes.
   - Nothing else in the Mtek v0.1 subset blocked a task. No task was changed for language reasons after it was written, and no language, runtime or compiler code was touched.

8. **Shared files not touched (the orchestrator applies these once).** `benchmarks/baselines/support/test/starters.test.ts` lists the task ids it type-checks (`["scene-rendering-01", "interaction-01", "shader-bridge-01"]` for starters and four ids for references): the new ids `shader-bridge-02` to `-06` (and those of the other M6-08 workers) must be added, or the list must be derived from the directory listing. The same type check ran here through `npm run check:ts` (`tsc -b`, whose `benchmarks/tsconfig.json` includes `tasks/*/baseline/src` and `tasks/*/reference/baseline/src`) and `eslint`, both green for all ten new projects. `benchmarks/README.md` (status table, the seed-task table, the baseline results) is not updated here.

## Fixtures and tests

`benchmarks/tasks/shader-bridge-0N/mtek-tests/*.test.toml` (12 files), the starters and references of both sides, and the one-line Playwright spec per task (`defineFixtureSuite`). Every fixture has its derivation in a comment. Evidence: `evidence/M6/benchmark-shader-bridge/` (`validate/` the ten `tools/ai-eval validate` reports with all layers, `baseline-reference-results.json`, `baseline-starter-results.json`, `environment-benchmarks.json`, `mtek-mutants.json`, `baseline-mutants.json`).

## Consequences

- The set has 6 shader/bridge tasks (01 to 06); all six are `mtek_side_status = "verified"` and their baseline sides are verified on hardware.
- Five of the six are edit tasks and one (`shader-bridge-03`) is cold, so a shader written from nothing is part of the Mtek and baseline comparison.
- A starter fails in the way its task names: the host input does not exist, the key does nothing, the light is not read, the cube does not move; the starters of `shader-bridge-02`, `-04`, `-05` and `-06` each pass one fixture on purpose (retention).
- No model has been run on these tasks; the budgets (3 repairs, 4000 output tokens, 300 s) are those of the seed tasks and have not been calibrated.
