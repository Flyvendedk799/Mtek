# 0090. The VS Code extension: a thin client of `mtek lsp`, a TextMate grammar generated from the reference grammar, a language configuration checked against the formatter, a `.vsix` packaged in CI, and an integration suite that runs in a real VS Code

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M6 (blueprint §11), task M6-04; blueprint §10 (the editor tools call the compiler service and re-implement nothing), §13; `spec/tooling.md` §§7 and 8; `spec/grammar.ebnf` and `spec/grammar-notes.md` (the lexical lists, nested block comments); `spec/language.md` §§1.5, 2, 3.3; decisions 0007 (dependency table, exact versions, no install-time lifecycle scripts), 0070 (the canonical formatter: indentation), 0073 (the grammar model; `mtek grammar export --format ebnf`), 0076 (the language server: launch command, capabilities, the `mtek-prelude:` scheme and `workspace/textDocumentContent`, position encodings, what a client provides)
- Supersedes: nothing. Fulfils `spec/tooling.md` §8 and the "editor extension (M6-04) is a client of exactly this" paragraph of decision 0076 item 12.

## Context

`mtek lsp` (0076) already does everything an editor shows: diagnostics with quick fixes, hover, definition, completion and the standard library as virtual documents. M6-04 is the client around it plus what no server provides in VS Code: syntax highlighting (a TextMate grammar; the server has no semantic tokens), a language configuration and a way to install the result. The task is judged on the extension building and packaging in CI and on a smoke test that launches the server through the client test harness. Things that were not obvious and are decided here: where the lists a highlighter needs come from and how they cannot drift, whether the extension needs code of its own for the `mtek-prelude:` documents, what "trace setting" means for the current client library, how the file events reach the server, and what the smoke test runs in (a real VS Code, or the client code against a mock of the `vscode` module).

## Decision

1. **Package.** `packages/editor-vscode`, npm workspace `mtek-vscode` (a VS Code extension name cannot be scoped), extension id `mtek.mtek-vscode`, version `0.1.0` (proposal: an extension's version is its own and plain `major.minor.patch`, the form every marketplace accepts; the other workspaces' `0.1.0-dev` is not used: `vsce` accepted `0.1.0-dev` for packaging when tried, so this is a choice, not a limit), `private`, `license: UNLICENSED` (no licence is chosen, decision 0007), `engines.vscode ^1.91.0` (the floor `vscode-languageclient` 10.1.2 declares). The extension is bundled by esbuild into `dist/extension.cjs` (`.cjs` because the package is `"type": "module"` and VS Code loads `main` with `require`), so the `.vsix` carries five files and no `node_modules` (a test lists them and checks that the bundle requires nothing but `vscode` and Node built-ins).
2. **The client** (`src/extension.ts`, `src/server.ts`; about 320 lines, no language logic). `vscode-languageclient` 10.1.2 (LSP 3.18). Activation `onLanguage:mtek`; document selector `{ scheme: "file", language: "mtek" }` (0076 item 12); no `workspaceFolders` or configuration is sent or read by the server, so none is set up. The extension **spawns `mtek lsp` itself** and hands the running process to the client (`ServerOptions` as a function), instead of giving the client an `Executable`: the client does not expose how the process ended, and "the server ends with exit code 0 after `shutdown` and `exit`" (`spec/tooling.md` §7) is something the test can only see if the extension holds the process. The exit status is logged ("The language server ended (exit code 0, signal null)") and kept for the test; a server that does not end within 5 s after `exit` is killed. The executable is the setting `mtek.server.path` (default `mtek`). **Resolution** (`resolveServer`, unit-tested on both Windows and POSIX path rules with a fake file system): an absolute path as it is (on Windows also with `.exe` or `.com` added); a bare name through `PATH` (the same extensions on Windows; a `.cmd` or `.bat` wrapper is not started, because no shell is involved); anything else, a relative path with directories, is refused with a message, because relative to what is not something a setting can say. **A missing executable is a loud failure**: an error message naming what was looked for, how to fix it (install `mtek`, set `mtek.server.path`, restart VS Code if `PATH` changed), with *Open Settings* and *Show Log* buttons, the same text in the **Mtek Language Server** output channel, and nothing started; a server that starts and fails to initialise gets the same treatment. Changing `mtek.server.path` restarts the server; the client library's own error handler restarts a server that crashes, and gives up when it crashed five times in three minutes (its default), saying so in the channel. Commands: `mtek.restartServer` (*Mtek: Restart Language Server*) and `mtek.showServerLog`. Starts and stops are serialised.
3. **`mtek-prelude:` documents: no provider of our own** (proposal). The server advertises `workspace.textDocumentContent` with `schemes: ["mtek-prelude"]` (0076 item 6); `vscode-languageclient` 10.1.2 has a `TextDocumentContentFeature` that registers a `TextDocumentContentProvider` for each advertised scheme and answers with `workspace/textDocumentContent`. Writing a provider as well would register the scheme twice for no gain, so there is none. This is shown, not assumed: the integration test follows go to definition from `Box` to `mtek-prelude:/std/prelude.mtek`, opens it (the text contains `schema Box`, the language is `mtek`), opens `mtek-prelude:/std/materials.mtek` (it contains `material Unlit`), and shows the document is read-only to the editor (typing into it changes nothing, with a control that typing changes an ordinary document; `applyEdit` from the extension API is *not* refused for such a document, so it is not the test).
4. **File events: the server's dynamic registration, no static `fileEvents`** (proposal; this reads 0076 item 12's closing parenthesis, "file-event synchronisation for `**/*.mtek` and `**/mtek.toml` (so the dynamic registration is not needed)", as a description of what a client *may* provide and not as a requirement). The server registers `**/*.mtek`, `**/mtek.toml`, `**/*.glb`, `**/*.png`, `**/*.jpg` and `**/*.jpeg` watchers after `initialized` (0076 item 3) and the client supports `workspace/didChangeWatchedFiles` registration; a static `synchronize.fileEvents` as well would deliver every `.mtek` and `mtek.toml` event twice and would still not cover the assets. Shown by the test that changes an imported module **on disk** while it is not open and sees its diagnostics appear and clear. Limit: a string glob watches the workspace folders, so a `.mtek` project outside every opened folder is only synchronised through the editor (`didChange`/`didSave`).
5. **Settings** (proposal). `mtek.server.path` (`machine-overridable`, and listed in `capabilities.untrustedWorkspaces.restrictedConfigurations`: a workspace must not choose which executable the editor starts; the extension is `limited` in an untrusted workspace) and `mtek.trace.server`. **Ambiguity decided: "trace setting".** In `vscode-languageclient` 10 the trace follows the log level of the client's output channel (`Trace` level turns tracing on); the `<id>.trace.server` setting then only chooses `messages` or `verbose`, and a value of `off` is read as `messages`. A setting with `off` as a value would be a switch that does nothing, so `mtek.trace.server` has the values `messages` (default) and `verbose`, its description says that tracing is switched on with the channel's log level (*Set Log Level... > Trace*), and the *Show Language Server Log* command opens the channel. This was read from the library's source (`client.js`, `refreshTrace`); **it was not exercised by a test** (the log level of a channel cannot be set from an extension).
6. **Language configuration** (`language-configuration.json`; proposal). Line comment `//`, block comment `/* */` (block comments **nest** in Mtek, `spec/language.md` §1.5; an editor's block-comment toggle does not know that, and a JSON configuration has no place to say so, so it is said here); brackets `{}`, `[]`, `()` (`<` and `>` are comparison operators and are never paired); auto-closing `{}`, `[]`, `()`, `""` (not inside a string or a comment) and `/* */`; surrounding pairs; **a documentation comment continues on the next line** (`onEnterRules`, `///` but not `////`, the lexer's rule); the word pattern reads names, numbers with an exponent and `#hex` colours as one word. **Indentation** follows `mtek fmt` (0070): `increaseIndentPattern` (a line that opens a bracket and does not close it), `decreaseIndentPattern` (a line that starts with a closing bracket), `unIndentedLinePattern` (comment lines do not decide). `package.json` sets for `[mtek]` the defaults of what the formatter writes: 4 spaces, no indentation detection, a ruler at 100, LF, a final newline, no trailing whitespace. The rules are **tested against the formatter itself**: the examples, the benchmark tasks and the syntax and semantic `pass` fixtures are copied to a temporary directory, rewritten by `mtek fmt`, and the indentation of every line (more than 5 000 line pairs in 278 files) must be what the rules give from the line before it. One file is exempt, `tests/syntax/pass/comments_between_tokens.mtek`, a signature with a comment between every token, which the formatter wraps at the comments (two lines differ); that is a limit of regular-expression indentation rules, stated in the test.
7. **The TextMate grammar is generated** (`scripts/gen-grammar.ts`, run by `npm run gen:grammar -w mtek-vscode`; `src/grammar/{ebnf,builtins,generate}.ts`) and committed as `syntaxes/mtek.tmLanguage.json`; `npm run check:grammar` and a unit test regenerate it and compare. **One source for the language's lists: `spec/grammar.ebnf`** (the file `mtek grammar export --format ebnf` prints, kept equal to it by a compiler test of 0073; the generator reads the file, so generating needs no build): the `Keyword` and `Reserved` productions, the punctuation and operators, the bitwise operators "the lexer also recognises", and the contextual words with the rule each belongs to (`camera` SceneObject, `update` and `fixed_update` LifecycleFn, `fragment` StageFn, `from` Import). **The registry's names are not in that file** (types, schemas, `Key`, namespaces, the intrinsic functions, `quat.axis_angle`-style members, `frame.time`-style values, event names): they are one table in `src/grammar/builtins.ts`, the one thing kept by hand. **Drift tests** (`drift.test.ts`) fail, naming the difference, when: the keywords, the reserved words or the punctuation of `spec/grammar.ebnf` differ from the compiler's `KEYWORDS`, `RESERVED_WORDS` and `PUNCTUATION` (read from `crates/mtek-compiler/src/syntax/token.rs`); `spec/grammar.ebnf` differs from `mtek grammar export --format ebnf` (through the real binary); `builtins.ts` differs from the rows of `mtek context` (types, schemas, enums, namespaces, events, scene-object kinds, global functions, namespace functions, namespace values); the committed grammar differs from a regeneration. The generator itself refuses a keyword or an operator it has no scope for (a new keyword in the grammar fails the generation until it is classified), so a language change cannot silently be unhighlighted. (The compiler's token table is read as text, by a regular expression, because no other way to the lists exists without changing the compiler; the test fails if the shape of that file changes.)
8. **What the grammar scopes** (every scope ends in `.mtek`). Comments: `///` documentation (`comment.line.documentation`; four or more slashes are an ordinary comment), `//`, nested `/* */` (`comment.block`, the rule includes itself); strings (`string.quoted.double`, the escapes of §2.5 `constant.character.escape`, any other escape `invalid.illegal.escape`, an unterminated string ends at the end of its line); colours `#rrggbb[aa]` in either case (`constant.other.color`; `#` followed by any other length `invalid.illegal.color`); integers and floats with an exponent (`constant.numeric`); **numbers the lexer rejects** (leading zeros, hexadecimal, suffixes, `1e3`, `1.`) are `invalid.illegal.number`, because v0.1 has **no hexadecimal literal and no suffixes** (`spec/language.md` §2.5), and `0..n` is an integer, a range and a name; keywords by class (`keyword.control`, `keyword.control.import`, `keyword.other.declaration`, `storage.modifier` for `export` and `cpu`, `constant.language.boolean`, `variable.language.self`); **reserved words** `invalid.illegal.reserved-word` (they are rejected wherever a name stands, E0013); **bitwise operators** `invalid.illegal.operator.bitwise` (E1901); every other operator and punctuation token of the lexical grammar (`keyword.operator.*`, `punctuation.*`); any character that is no token of the language outside a string or comment `invalid.illegal.character`; the names declarations introduce (`fn`, `struct`, `material`, `scene`, `entity`, `prefab`, constants, locals, `state`, `param`); the event name after `on`, the lifecycle and stage functions, `camera Name`, `from` in an import; the standard library (types, schemas, `Key`, namespaces with their functions and values, intrinsic functions only when called, since a local may reuse the name of a function, `spec/language.md` §4.2). **There are no attributes or annotations in v0.1** (no `@`, no `#[...]`: `#` starts a colour only), so there is nothing to scope for them and `@` is illegal. **Heuristics, stated as such**: a name before `:` is a field, a name before `(` a call, a name after `.` a member, `SCREAMING_SNAKE_CASE` a constant and `PascalCase` a type, from the naming conventions of §3.3; `update(`, `fixed_update(` and `fragment(` are scoped as lifecycle and stage functions wherever they stand (a user function with such a name, or a call of one, is scoped the same); `material` before `:` is a field (decision 0023, "`material` is accepted as a field name"). A grammar is not a parser: no scope depends on types or scopes.
9. **Packaging.** `@vscode/vsce` 4.0.0 (exact). `npm run package -w mtek-vscode` = `npm run build` then `vsce package --no-dependencies --skip-license` (the dependencies are bundled; there is no licence file to include, decision 0007) and produces `packages/editor-vscode/mtek-vscode-0.1.0.vsix` (7 files, 145 KB: `package.json`, `README.md`, `language-configuration.json`, `syntaxes/mtek.tmLanguage.json`, `dist/extension.cjs`, the manifest and content types), `.vscodeignore` keeps everything else out, `*.vsix` is ignored by git. **No publishing**: no `vsce publish`, no token, no secret anywhere. `@vscode/vsce-sign`'s postinstall (it only verifies signatures when publishing) is denied in the root `allowScripts`, like esbuild's, to keep the rule of no install-time lifecycle scripts (`spec/testing.md` §1).
10. **The smoke test is the integration suite in a real VS Code, not the client against a mock** (proposal; the task named both and asked to prefer a real one if it runs in CI headlessly and on this machine). `@vscode/test-electron` 3.1.0 downloads VS Code **1.142.0** (pinned in `scripts/run-vscode-tests.ts`, overridable with `VSCODE_VERSION`; cached in `target/vscode-test/`: a cache under `packages/` was scanned by `tools/ai-eval`'s boundary check, which found the harness SDKs in VS Code's own files), opens a temporary project (`src/integration/fixture.ts`; written at run time, never committed as `.mtek` files because the main module is broken on purpose) as the workspace folder, sets `mtek.server.path` to `target/debug/mtek` in a throw-away user-data directory and runs ten tests in the extension host (`src/integration/suite.ts`): (1) the extension activates on a `.mtek` file and the client is running with the capabilities of 0076 (`positionEncoding` utf-16, hover, definition, code actions, completion triggered by `.`, `workspace.textDocumentContent.schemes = ["mtek-prelude"]`); (2) the two diagnostics of a program with an error after an emoji arrive with the exact UTF-16 ranges, codes (`MTEK-E0022`, `MTEK-E2003`), severity and source; (3) hover on an imported name; (4) go to definition across modules, with the exact range; (5) definition into `mtek-prelude:`, the document's text, its language, read-only (item 3); (6) completion (`Space` after `Key.`) and diagnostics on unsaved text, with no save; (7) the quick fix applied through the code-action provider fixes the program; (8) a change on disk to a module that is not open reaches the diagnostics (item 4); (9) *Restart Language Server* ends the first server with `{ code: 0, signal: null }`, starts a second and the open document's diagnostics return; (10) a missing executable is an error (message names the path and the setting, no client) and fixing the setting recovers. It exchanges `initialize`/`initialized`, opens a document with an error, receives the diagnostics and shuts the server down through `shutdown`/`exit` with status 0, as asked. `scripts/run-vscode-tests.ts` checks the suite's own record: exactly ten outcomes, none failed, VS Code's exit code 0; a VS Code that cannot be downloaded or started, a missing build or a missing binary prints `NOT-RUN: ...` and **exits 1**, so a skipped run can never be counted as a pass. **Why not the mock**: `LanguageClient` uses most of the `vscode` API (output channels, file watchers, diagnostics, workspace and window events, configuration, text document content providers); a mock of that is a second, unchecked implementation of VS Code that would pass on its own assumptions, and a real VS Code runs headlessly in CI under Xvfb (the documented practice) and on Windows, as shown below.
11. **CI** (`.github/workflows/ci.yml`, job `vscode-extension`, `ubuntu-latest` and `windows-latest`, `fail-fast: false`): checkout, Node from `.nvmrc`, the pinned Rust toolchain, `npm ci`, `npm run build` (which also builds `target/debug/mtek`), `npm run check:grammar -w mtek-vscode`, `npm run test:unit -w mtek-vscode`, `npm run package -w mtek-vscode`, the `.vsix` uploaded as the workflow artifact `mtek-vscode-vsix` (Linux job; `if-no-files-found: error`), then `xvfb-run -a npm run test:integration -w mtek-vscode` (Linux) or `npm run test:integration -w mtek-vscode` (Windows). The existing `node` job's `npm run test:unit`, `npm run lint` and `npm run check:ts` cover the workspace too. Nothing is published and no secret is used (`permissions: contents: read`).
12. **Decisions taken on ambiguous points**, each also where it is described above: (a) no content provider of our own for `mtek-prelude:` (item 3); (b) no static file-event synchronisation (item 4); (c) the trace setting follows the client library's log-level semantics, so its values are `messages` and `verbose` (item 5); (d) the extension spawns the server itself, to know its exit status (item 2); (e) the smoke test is a real VS Code, not a mock (item 10); (f) the extension's version is `0.1.0` and its npm name `mtek-vscode` (item 1); (g) the grammar's registry names are a hand-kept table guarded by a test against `mtek context`, because `spec/grammar.ebnf` does not contain them (item 7); (h) numbers with a hexadecimal form or a suffix are `invalid.illegal`, not highlighted as hexadecimal or suffixed numbers, because the language has none (item 8); (i) a relative path with directories in `mtek.server.path` is refused (item 2); (j) the VS Code cache is under `target/` (item 10).

## Tests

- Unit, `npm run test:unit -w mtek-vscode` (Vitest; **78 tests in 6 files**): `grammar/scopes.test.ts` (37: comments including nested, banner and `/**/`, keywords and the names they declare, contextual words, every literal form and the illegal ones, operators, the bitwise ones, punctuation, standard-library names, names by position), `grammar/corpus.test.ts` (4, below), `grammar/drift.test.ts` (9: lists against `token.rs` and `mtek grammar export`, `builtins.ts` against `mtek context`, committed grammar against regeneration, every keyword, reserved word and punctuation token has a scope), `language-configuration.test.ts` (8: the configuration and the indentation rules against the formatter), `server.test.ts` (13: the executable lookup), `package.test.ts` (7: what `vsce ls` packages, the manifest points at packaged files, exact pins, settings and commands, the bundle needs only `vscode` and Node).
- **The corpus**: every `.mtek` file of the repository except `benchmarks/holdout/` (**955 files, 18 768 lines, 210 559 tokens**: tests/semantics 479, tests/syntax 236, tests/assets 91, benchmarks/tasks 68, tests/codegen 27, tests/browser 26, crates 13, examples 5, evidence/M6 5, tests/modules 3, tools/ai-eval 2) through `vscode-textmate` 9.3.2 over `vscode-oniguruma` 2.0.1: no tokenizer exception, every line covered by tokens from column 0 to its end, no line abandoned for taking longer than 5 s (`stoppedEarly`), and no token of a *valid* source (examples, benchmark tasks, `tests/syntax/pass`, browser, codegen and module fixtures) scoped `invalid.illegal`; the same count over the fixtures that are invalid on purpose is above 20 (133 tokens in 26 files over the whole corpus), so the check can fail.
- Integration, `npm run test:integration -w mtek-vscode`: the ten tests of item 10.
- **Checks that the tests can fail** (run once, by hand, and reverted): removing `abs` from `builtins.ts` fails the registry test and the regeneration test; moving the expected diagnostic range by one column fails the diagnostics test (9 of 10 pass); changing the server's argument `lsp` to `lspx` fails all ten integration tests.

## Consequences

- The extension is thin: everything but highlighting is the server's, so a better checker, hover or completion shows in VS Code with no change here. The price is that nothing works without an `mtek` on `PATH` (or the setting), which the extension says.
- A language change is caught by tests, not by a user: a keyword or token added to the grammar fails the generator until it has a scope; a registry row added or renamed fails the `builtins.ts` test, whose message lists the difference to put into the table; the committed grammar is a diff in review.
- The highlighting is lexical plus heuristics (item 8): a user type in lower case, a user function named `update`, a constant in mixed case or a name before `:` that is not a field are scoped by their shape. Semantic tokens would be exact and are the server's to provide (0076 item 12 lists them as not provided).
- The integration suite downloads a VS Code (about 150 MB, cached) and needs a display; on a machine without either it prints NOT-RUN and fails, by design. VS Code is pinned, so a new VS Code release does not change a result until the pin is changed; a pin change is a one-line edit plus a run.
- Findings worth keeping: VS Code releases a document opened with `openTextDocument` that no editor shows, which the client reports to the server as a close, so a test that wants the document open must show it; the `type` command needs the editor focused (`workbench.action.focusActiveEditorGroup`) to be a control; `vscode-languageclient` 10's trace semantics (item 5).
- Not in this release: a marketplace publication, semantic tokens, snippets, a status bar item, a debug adapter, a setting for extra server arguments, and a `.mtek` project outside every opened workspace folder being watched on disk (item 4).
