# 0076. The language server `mtek lsp`: stdio framing that survives garbage, UTF-8 or UTF-16 positions, a debounced single-threaded state machine over unsaved buffers, diagnostics with validated quick fixes, hover, definition and completion read from the compiler, and the standard library as virtual documents

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-03; blueprint §10 (basic language server: diagnostics, hover, go to definition, completion), §13 (the editor tools call the compiler service and re-implement nothing); `spec/tooling.md` §7; `spec/compiler-architecture.md` §2 (dependencies), §4.1 (source manager, UTF-16 conversions, in-memory file system), §4.12 (service API); `spec/diagnostics.md` §6 (validated suggested edits); `spec/stdlib.md` §1 (one registry); `spec/language.md` §1.5 (documentation comments); decisions 0007 (dependency table), 0028 (the analysis result), 0071 (validated edits, "the language server of M6-03 can build on the documented edit model")
- Supersedes: nothing. Fulfils the "language server" row of `spec/tooling.md` §7 and the consumer side of decision 0071.

## Context

Everything an editor needs is already produced by the front end the command line uses: the diagnostics with their validated edits (0071), a name for every name (`Resolution`), a type for every expression (`Typeck`), the doc comments (the lexer's trivia) and the registry. M6-03 is the protocol layer over it. Three things were not obvious and are decided here: how a language server stays correct when its client sends garbage or the compiler has a defect (the editor owns the user's text, the server must never be the reason it is lost), how positions are counted (the compiler's offsets are UTF-8 bytes; the protocol's default is UTF-16 code units), and what "go to definition" means for a name that is defined in Rust data and not in a file (the whole standard library).

## Decision

1. **Transport.** `mtek lsp` (`mtek lsp --stdio` is the same: the flag is accepted for clients that always pass it) speaks JSON-RPC 2.0 with `Content-Length` framing on standard input and output, and nothing else: stdout carries the protocol only (a test reads it frame by frame and fails on anything else), diagnostics of the server itself go to stderr as one line starting `mtek lsp:`. The message types and the serialisation of outgoing messages are `lsp-server` 0.10.0's (`Message`, `Request`, `Notification`, `Response`, `RequestId`, `ErrorCode`, `Message::write`), the protocol types are `lsp-types` 0.97.0's (item 13). **The reading side is this repository's** (`crates/mtek-cli/src/lsp/transport.rs`, about 500 lines with its tests), because `lsp-server`'s reader (a) ends the session on a payload that is not a message, where JSON-RPC asks for an error reply (`-32700` parse error with `"id": null`, `-32600` invalid request, with the request's id when it has one); (b) allocates the announced `Content-Length` before reading, so `Content-Length: 99999999999999` is an out-of-memory abort; (c) parses a client's reply to a server request (`"result": null`) as a request. Ours bounds the body at 64 MiB (a 4 MiB source file is at most 24 MiB as JSON), bounds a header line at 8 KiB and a frame at 32 header lines, tells requests, notifications and replies apart by their members, and answers a bad payload with the error reply and goes on. **Damaged framing** (no length, an unreadable length, a length above the bound, a truncated body, a line that is not a header) cannot be resynchronised: the session ends with the reason on stderr and exit code 1. **The loop** reads on a thread (so the client's writes never wait for ours), handles every message that is waiting, then publishes what is due, then writes; the server itself is single-threaded on a thread with the compiler's 16 MiB stack (`guard::COMPILER_STACK_BYTES`) and answers requests in the order they arrive, so `$/cancelRequest` finds the request answered or running and is ignored (honest scope, item 12). **Exit codes** (the protocol's rule): 0 for `exit` after `shutdown`, or the input ending after `shutdown`; 1 for `exit` without `shutdown`, the input ending without it, damaged framing; 3 if the server thread itself dies (it should not: item 11). Before `initialize` a request is answered `-32002` and notifications other than `exit` are dropped; a second `initialize` is `-32600`; after `shutdown` every request is `-32600` and only `exit` is honoured. (proposal: the bounds and the reply to garbage)
2. **Position encoding.** `initialize` negotiates `positionEncoding`: **UTF-8 if the client lists `utf-8` in `general.positionEncodings` at all, else UTF-16** (the default every client supports, also when the list is absent or malformed); UTF-32 is never chosen. The rule is `spec/tooling.md` §7 ("UTF-8 if the client offers it"); the client's order is **not** read as a preference (the protocol does not say it is), because UTF-8 is the unit the compiler's spans are in, so every conversion is the line's start plus a byte count, and a client that offers it supports it. In UTF-16 a `character` is a count of code units, so an astral character (an emoji) is two; in UTF-8 it is a count of bytes. Conversions are the compiler's own `LineIndex` (`lsp_position`, `offset_of_lsp`, tested with multi-byte and astral text in `spec/compiler-architecture.md` §4.1) for UTF-16 and a byte count from `LineIndex::line_range` for UTF-8, wrapped in `PositionEncoding`, and are **total**: a character past the end of a line is the end of the line's content (before `\r\n`), a line past the last is the end of the text, a character inside a surrogate pair or inside a multi-byte character rounds down to the character's start, and an offset on a `\r\n` terminator is the end of the line's content (the `\r` is never a column). A leading byte-order mark is zero-width, as the compiler counts it (a client sends the document without one, as VS Code does). (proposal: the UTF-8 preference; the ambiguity is "UTF-8 if the client offers it" against "UTF-8 if offered and preferred")
3. **Documents and unsaved buffers.** Synchronisation is **full** (`change: 1`), with open/close and `save` notifications (no text). A client that sends ranges anyway is served: each change is applied in order with the negotiated encoding (a reversed range is an insertion, a range past the end clamps); a change to a document that is not open is ignored with a line on stderr. A document is identified by the exact URI string of `didOpen`. Its **home** is the project of the nearest directory above it that has an `mtek.toml` (found on disk, per document, so several projects at once need no configuration and `workspaceFolders` is not read), a **loose** document (a file with no project above it, a URI that is not a `file:` URI, a path the compiler cannot name) or a **virtual** document (item 6, never analysed). The compiler reads a project through `OverlayFs` (`crates/mtek-cli/src/lsp/overlay.rs`), the in-memory file system of `spec/compiler-architecture.md` §4.1 laid over the real one: a file with an open buffer is read from the buffer (`read`, `len`), a buffer of a file that does not exist on disk yet exists, appears in listings and can be imported, the buffer of a file deleted on disk is still served while it is open, and nothing is ever written. Text on disk changed by anything else is picked up on `didSave`, on `workspace/didChangeWatchedFiles` (the server registers `**/*.mtek`, `**/mtek.toml`, `**/*.glb`, `**/*.png`, `**/*.jpg` and `**/*.jpeg` dynamically after `initialized` if the client can; a client that cannot or does not send the events gets the new files at the next edit or save) and on every analysis of an edited project, which reads the disk again. Closing the last open document of a project drops its state and clears what was published for it.
4. **Diagnostics are debounced, 150 ms, on an injectable clock.** A change to a document starts a timer of `DEBOUNCE_MS = 150` (`spec/tooling.md` §7); a further change restarts it (trailing edge: diagnostics come when typing has paused that long), and nothing already due is delayed by a change. Opening, closing and saving a document and a change of files on disk are not debounced, but they are not synchronous either: they are due at once and published after the messages that are already waiting have been handled, so a client that opens twenty files at startup costs one analysis. The server asks a `Clock` for the milliseconds (the real clock, or `ManualClock` in tests, which moves only when told), so the debounce is tested without sleeping: after a change `millis_until_due()` is 150, at 149 nothing is published, at 150 exactly one publication, two changes 100 ms apart are one publication 150 ms after the second. Requests are never debounced. **What is published.** The diagnostics of the **whole project**, to the file each is in, whether open or not (a syntax error in a module that is imported but not open is shown, to that module's URI, which is the project directory's URI as the client spelled it plus the percent-encoded path; an open document keeps the exact URI the client used), with the version for an open document; a file whose list did not change since the last publication is not published again, a file whose list became empty is published empty, an open document with no diagnostics is published empty once. A diagnostic without a location (a problem of `mtek.toml`, a file the source manager rejected: `E9001`, `E9005`, `E0001`, `E0004`) goes to `mtek.toml` at 0:0 (the message names the file), a diagnostic inside the embedded prelude (a compiler defect, `E9999`) likewise. **A document the project does not reach** (not imported from the entry, or the project did not load) and a **loose** document get the lexical and syntax diagnostics of the compiler alone (`lex`, `parse_module`, no edits: the proofs of `spec/diagnostics.md` §6.3 re-check a whole project); names and types need the project. **The mapping** (`crates/mtek-cli/src/lsp/convert.rs`): `range` is the primary span in the negotiated encoding; `code` is the catalogue code (`MTEK-E2003`), `source` is `mtek`; the severity is the code's (error, warning, note as information); the `message` is the diagnostic's message, then the text of the primary label if it differs, then every note on its own line (`note: ...`, and the `help: ...` notes as they are); every related span with a text is `relatedInformation` (dropped for a client that does not say it takes it). **Cost.** The report that carries edits re-checks the project once per proposal (`MAX_EDIT_VALIDATIONS` = 32, decision 0071), so publishing uses the validated analysis and every request uses the analysis without (item 5); the two are cached per project and per generation of its buffers (bumped by every edit, save and file event), so a request after an edit costs one analysis and the debounce costs at most one more. Measured on the three examples with two injected errors (a debug build, Windows): 1 to 7 ms without validation, 3 to 25 ms with it. (proposal: the grouping, the placement of diagnostics without a location, the reach rule for syntax-only documents)
5. **Two additions to the compiler library**, both small and both tested in `mtek-compiler`: `analyze_without_edits(root, fs) -> Analysis` (`spec/compiler-architecture.md` §4.12): the same front end, the same diagnostics, order and tree as `analyze`, with no validated edit attached and no proposal left (`edits/tests.rs`: `analysis_without_edits_has_the_same_diagnostics_and_never_an_edit`), for callers that need what the front end made of text being edited and not the proofs; and `Lexed::doc_comment_before(text, start)`, the reading of the `///` block before a declaration (`spec/language.md` §1.5) that the context export had as a private method, now shared by the export and the server (`syntax/lexer_tests.rs`), so a doc comment means one thing in both.
6. **The standard library as virtual, read-only documents.** A name of the standard library is defined in the registry, in Rust data, so there is no file to go to; go to definition answers with a URI of the scheme **`mtek-prelude:`** (`PRELUDE_SCHEME`). Two documents exist: `mtek-prelude:/std/materials.mtek`, the embedded Mtek source of the built-in materials (`Unlit`, `Pbr`), byte for byte the text the compiler compiles, where the definition of a built-in material is the name of its `material` declaration; and `mtek-prelude:/std/prelude.mtek`, a **generated reference**, one declaration per registry item with the documentation as `///` comments (`type vec3;`, `schema Box { size: vec3 = vec3(1.0, 1.0, 1.0); }` with flags and ranges in trailing comments, `enum Key { Space, ... }` with the DOM code, `namespace frame { time: f32; }`, `fn smoothstep(edge0: T, edge1: T, x: T) -> T;` with domain notes, `on key_down(Key);`, `object camera Name;`, `Name.body.apply_impulse(..)`), deterministic for a registry (a test builds it twice), complete (a test checks every type, schema, field, enum member, intrinsic, event and scene-object kind has a place in it and that the recorded span of every item is the item's name). It is not source code to compile and not part of any project. **Serving them**: the server advertises `workspace.textDocumentContent.schemes = ["mtek-prelude"]` and answers the LSP 3.18 request `workspace/textDocumentContent` (`{ "uri": ... }` to `{ "text": ... }`; an unknown path is `RequestFailed`, a URI of another scheme `InvalidParams`), which is the whole interface a client needs: a `TextDocumentContentProvider` for the scheme that asks this request and opens the document read-only. A client that opens such a document and sends it in `didOpen` is accepted and ignored (no analysis, no diagnostics). Ranges in these documents use the negotiated encoding. (proposal: the generated document and its layout)
7. **Hover** (`hover.rs`, `semantic.rs`). The cursor's name is resolved to a *referent* from what the compiler recorded: a name expression or identifier through `Resolution::res` (to a declaration of a module, an imported name followed through `import_target` to the declaration in the module that exports it, or an item of the registry); a field name by where it stands (a member of a scene, entity, prefab or object body or of a descriptor literal is a field of a registry schema, a param of a user material or prefab, or a field of a struct; a name after a dot is what the type checker recorded for the access, `FieldKind`, or for the call it is the callee of, `CallKind`: entity and object fields, the `state` of an entity, a param of `Name.material`, a light field, a struct field, a field of a built-in record, a body property or command, a `glb_asset` accessor); the specifier of an import is the module. The text is Markdown (plain text without the code fences for a client whose `hover.contentFormat` omits `markdown`): a code block with the declaration as Mtek writes it and the checker's types (`fn double(x: f32) -> f32`, `state speed: f32`, `let angle: f32`, `const SPEED: f32 = 0.7` with the value as written, `struct Light { ... }`, `material Pulse { param tint: color = #6b5cff; }` with each param as written, `param tint: color = #6b5cff`), then the facts (an imported or other-module declaration says `declared in src/lib.mtek`), then the doc comment of the declaration or, for a registry item, the registry's documentation with its facts (fields with types and defaults, flags, range, domain, const-eligibility, handler-only, hosts of an event). A swizzle says its type (`.rgb` of `color`: `vec3`); a literal, an operator or a call that is not a name shows the expression's type (and the folded value of a constant expression). The `range` is the name.
8. **Go to definition** (`definition.rs`). The same referent: a declaration (including a local, a parameter, `state`, a constant, an entity, `self`), a declared member (a param of a material, a struct field: the declaration of the member, in its module), an imported name or the name in the import list (the declaration in the module that exports it), the import specifier (the start of the module), a registry item (item 6). The answer is one `Location`. A swizzle and a literal have no definition (`null`).
9. **Completion** (`completion.rs`). The text under the cursor is unfinished, so the server does not guess at it from characters: it makes it parse as well as it can and asks the compiler. If a name is being typed or the cursor is right before one, that text is analysed as it is; otherwise the placeholder identifier `__mtek_completion__` is inserted at the cursor and the buffer with it is analysed (a front-end run without the validation of edits, not cached, with the document's real buffer left alone). The context is read off the syntax tree around the name that starts at the cursor, with the innermost body as the fallback where the parser dropped the name; the candidates come from the resolver, the checker and the registry. After a dot: the members of what the base is (enum members, namespace members, the fields and `state` of an entity or object, the params of `Name.material`, the fields of `Name.light`, the properties and commands of `Name.body` for its body kind, the components of a vector, quaternion or colour, the fields of a struct or built-in record). At a field name of a descriptor or body: the fields of its schema, or the params of its material or prefab, or the fields of its struct, without the ones already written (read off the tokens inside the braces, because the parser's recovery may have swallowed what follows the name being typed). At a member of a scene, entity, prefab, material or object body: the fields of its schema and the member keywords. Where a value is written: the names in scope (parameters, locals declared before the cursor, `state`, constants, functions, entities, imports, with the visibility rules of `spec/language.md` §4.1: an inner body does not see the members of an outer one), the registry's intrinsics, namespaces, enums, descriptor schemas and scalar and vector constructors, the literals `true`, `false`, `self`, and at the start of a statement the statement keywords. In a type: the registry types and the structs in scope. After `on`: the events. After `entity Name:`: the prefabs. Nothing in a comment, a string, a number or a colour literal. Items whose registry milestone this build has not reached are left out (using them is `E9010`). Each item has a `kind`, a `detail` (the declaration or signature, one line), the registry's documentation and a `sortText` that puts the program's names before the library's and keywords last; its `textEdit` replaces the part of the name before the cursor. The trigger character is `.`. A file that no module of its project imports has no completion (it has no analysis).
10. **Code actions.** `textDocument/codeAction` answers, for every diagnostic of the document whose range touches the request's range, with one **quick fix per validated suggested edit** of decision 0071 (`kind: quickfix`, `isPreferred`, `diagnostics` the diagnostic, the title the suggestion's `description`): the `WorkspaceEdit` is exactly the edits of that one suggestion and nothing more (an edit in another file than the diagnostic's, an imported module, is in the same `WorkspaceEdit`), with the ranges converted from the byte offsets of the files as the compiler read them. A client that declares `workspace.workspaceEdit.documentChanges` gets `documentChanges` with the version of each open document; any other client gets `changes`. The server attaches no edit the compiler has not validated and drops none that it has; a request whose `only` leaves out `quickfix` gets none. A test applies the edit of an `E0022` quick fix to a text with emoji before the literal and shows the program is then clean, and one applies the `E2003` rename in another file.
11. **No input loses a buffer.** Every message is handled inside a panic guard: a defect in a handler or while publishing is answered with `InternalError` naming the method (a request), or a line on stderr (a notification), the cached analyses are dropped (they are recomputed from the buffers) and the loop goes on. The buffers are plain data mutated by single assignments before anything that can fail, and are never written to disk; a server that nevertheless dies (a stack overflow aborts, which no guard catches; exit code 3 if the thread only panicked outside a handler) loses only what the client holds anyway: a client restarts the server and sends `didOpen` for what is open. The tests make a handler and the publication panic on purpose and show that the same buffers answer afterwards; they feed every request kind positions that are not in the file, a document that does not exist, texts with NUL bytes, a misplaced byte-order mark, lone `\r`, an unterminated JSON-looking text and a text longer than the compiler's 4 MiB (`E0004`, no hover or completion, no failure); and, through the real binary, random byte streams with and without valid framing, payloads that are not JSON, and every kind of damaged frame.
12. **Capabilities and honest scope.** Advertised: `positionEncoding`; `textDocumentSync` (`openClose`, `change` full, `save` without text); `hoverProvider`; `definitionProvider`; `completionProvider` (trigger `.`, no resolve); `codeActionProvider` (`quickfix`, no resolve); `workspace.textDocumentContent` (item 6). Used when the client offers it: `client/registerCapability` for file watchers; `workspace.workspaceEdit.documentChanges`; `hover.contentFormat`; `publishDiagnostics.relatedInformation`. **Not provided** (out of scope of the "basic" server of blueprint §10): references, rename, document and workspace symbols, signature help, formatting (`mtek fmt` is its own task), semantic tokens, inlay hints, folding, pull diagnostics, progress, `completionItem/resolve`, and cancellation of a running request (single-threaded, items 1 and 11). A request for any of them is `MethodNotFound`. The editor extension (M6-04) is a client of exactly this: the launch command is `mtek lsp` over stdio (the extension's setting names the executable, default `mtek` on `PATH`), the document selector is `{ language: "mtek" }` plus `file` URIs, a content provider for `mtek-prelude`, and file-event synchronisation for `**/*.mtek` and `**/mtek.toml` (so the dynamic registration is not needed).
13. **Dependencies** (`decision 0007`). `lsp-server` =0.10.0 and `lsp-types` =0.97.0 (the latest on crates.io on 2026-10-18; MIT or Apache-2.0 and MIT), `serde` =1.0.229 for `mtek-cli` (the traits the protocol types are (de)serialised through; already in the lock file). New crates in `Cargo.lock`: crossbeam-channel 0.5.17 and crossbeam-utils 0.8.23 (`lsp-server`'s channels, unused by our transport but linked), fluent-uri 0.1.4 (`lsp-types`' `Uri`; the lock file already had 0.4.1 for `jsonschema`), bitflags 1.3.2 (beside 2.13.2), serde_repr 0.1.21. The server lives in `mtek-cli` (`crates/mtek-cli/src/lsp/`), as `spec/compiler-architecture.md` §2 says; the compiler library gained nothing that depends on them.
14. **Decisions taken on ambiguous points**, each also where it is described above: (a) UTF-8 is chosen whenever offered, the order of the client's list is not a preference (item 2); (b) diagnostics are published for every file of the project and not only the open ones, because the cause of an error is often in the file next to the one being edited (item 4); (c) an open file that the project does not reach gets syntax diagnostics only, and a file with no project is not told "no `mtek.toml`" (`E9004`): it is a loose document, which is what an editor's scratch file is (items 3 and 4); (d) a debounce of 150 ms is trailing and a change never delays what is already due (item 4); (e) the standard library's definition is a generated reference plus the real source of the materials, served through the 3.18 request and not a custom one (item 6); (f) the server reads no workspace folders and no configuration: projects are found per document and nothing is configurable (a setting would be a surface to document and test with no use today).

## Consequences

- A client needs a launch command, a document selector, a content provider for `mtek-prelude` and (optionally) file-event synchronisation: nothing else, no settings. The VS Code extension of M6-04 is a thin client.
- Every language feature the server has is a read of something the compiler already produces; a later checker improvement (a better message, a new validated edit, a new type fact) shows up in the editor without touching the server. The price is that the features see only what the front end records: a name the checker typed as an error has no hover, and a file no module imports has syntax diagnostics only.
- `analyze_without_edits` and `Lexed::doc_comment_before` are public compiler API; the first is documented in `spec/compiler-architecture.md` §4.12.
- Diagnostics for a project cost a validated analysis per pause in typing; on a project where that is too slow the constant is one place (`DEBOUNCE_MS`) and the validation can be skipped for the publication (the quick fixes would then be computed when asked for).
- The server holds the text of every open document and one or two analyses per project; it never holds a file open and never writes.
- Known limitations: no cancellation of a running request, no incremental analysis (every analysis is a whole front-end run), no resolve step for completion documentation (every item carries its short registry documentation), a project with thousands of modules would make every keystroke pause an analysis of all of them.
