# 0041. Shader lowering: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §4.4 (GPU code is only what stages reach), §5.2 (WGSL from a typed shader IR, Naga as validator), §6 (one layout, three consumers); `spec/compiler-architecture.md` §4.9, §7, §8; `spec/gpu-layout.md` §3–§5; `spec/materials.md` §3; `spec/language.md` §5.6, §6.3–§6.6; `spec/runtime-abi.md` §5.4; decisions 0026, 0029, 0035, 0036, 0037, 0038, 0039, 0040.

## Context

Task M2-05 compiles user materials to WGSL: the fragment stage and the pure functions it reaches go from the typed IR through the shader IR of decision 0029 to Naga-validated WGSL with span maps, and builds with user materials stop at the `E9010` of decision 0039 item 11 no more. The specification fixes the type mapping, the clamping, the `bool32` and padded-array rules, the mangling prefixes, the helper library and the `E6100` mapping, but not every choice an implementation has to make: how the IR names struct types so that a shader can name their WGSL structs, how user functions are qualified, in which order functions are emitted, how statements without a WGSL counterpart are lowered, what the helpers compute exactly, how literals are printed, and what the build does with a user material. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Struct types in the typed IR are spelled by their symbol** (`src/shapes.mtek::Wave`, `array<src/shapes.mtek::Wave, 2>`) wherever the IR writes a type: expressions, locals, results, params, struct fields, constants. The plain name did not say which declaration a type is — two modules may declare `Wave`, and a value of either reaches the other through a call or an imported constant without an import of the type — and the shader needs the declaring module for `S_<hash8>_<Name>`. This amends decisions 0035 item 6 and 0038 item 8; `Value::Struct` keeps the plain name, diagnostics keep the plain name, the layout records already used the symbol (decision 0036 item 11), and the manifest's material param `type` (`mtekTypeName`, "as written in source") is written with the module paths removed (`array<Wave, 2>`). The goldens `functions_statements_and_calls`, `materials_params_and_defaults` and the CPU emitter's signature comments changed by exactly this.
2. **Files.** `lowering/shader.rs` (`lower_material(program, material) -> MaterialShader`) with `lowering/shader/types.rs` (IR types to WGSL types) and `lowering/shader/helpers.rs` (the helper library). The shader IR gains `var`, assignment, `if` (an `else if` chain is one node, like the IR's), counted `for`, `break`, `continue`, blocks, a call statement of a function without result and `_ = value;` (WGSL's built-ins are `@must_use`, so a call with a result as a statement discards it); unary operators, index, `bitcast`, `bool32` encode (`select(0u, 1u, b)`) and decode (`(x != 0u)`) nodes and the built-in functions. `MaterialDescription` of the standard stage gains `structs` (declared after the param block's, skipping duplicates) and `functions` (printed before `mtek_fragment`).
3. **Names.** A user function is `u_fn_<hash8>_<name>` — module-qualified, the same `<hash8>` as `f_<hash8>_<name>` of decision 0040 item 2, so two modules' `fn shade` can reach one material — refining the `u_fn_<name>` illustration of `spec/compiler-architecture.md` §7.2. Parameters (the stage's `SurfaceInput` parameter too) are `u_p_<name>`, `let`/`var` locals and loop variables `u_l_<name>` (no shadowing; sibling blocks are separate WGSL blocks). Generated names: helpers `mtek_<helper>`, the array and counter of a `for x in arr` loop `mtek_each_<x>` and `mtek_at_<x>`.
4. **What is emitted, in which order.** Only the functions the fragment stage reaches, found with a worklist (each lowered once), ordered callees first by a depth-first post-order over the calls with an explicit stack (calls in order of first occurrence); before them the helpers the module uses, in a fixed order where every helper follows those it calls. Neither the lowering nor Naga's dependency search (which then finds every callee declared) needs a native stack proportional to a call chain; expressions and blocks recurse only as deep as the parser lets them nest.
5. **Types.** One Mtek type is one WGSL type everywhere (`spec/gpu-layout.md` §3): scalars, vectors, `color`/`quat` (`vec4<f32>`) and `mat4` directly; arrays and structs through the layout engine, which decides padded elements and the `@align`/`@size` of the struct declarations, so a struct local has exactly the declaration of the same struct in a parameter block. A top-level `bool` is `bool`; inside a struct, array or block it is stored as `u32`. `SurfaceInput` is `MtekSurfaceInput`. Field reads of user structs use the members `u_<field>`; `SurfaceInput` fields keep their names (decision 0029 item 4).
6. **Expressions.** Constants are their folded values (literals, constructors; a stored `bool` constant is `1u`/`0u`). Operators are WGSL's, except `quat * quat` (`mtek_quat_mul`) and `quat * vec3` (`mtek_quat_rotate`). Conversions between `f32` and the integers are WGSL constructors (which clamp), between `i32` and `u32` `bitcast`, a same-type conversion its operand. Vector constructors and `mat4.columns` are WGSL constructors, `color.linear(rgb, a)` is `vec4<f32>(rgb, a)`, `.rgb`/`.a` are `.xyz`/`.w`. The intrinsics of `spec/stdlib.md` §6 are WGSL's built-ins of the same name (`inverse_sqrt` is `inverseSqrt`; `saturate` is WGSL's own, so `spec/compiler-architecture.md` §7.3's `saturate` helper is not needed). A constant index is used as it is (`E3030`); every other index is clamped, `min(i, N - 1u)` for `u32` and `clamp(i, 0i, N - 1i)` for `i32`; a padded element is read through `.value`, a stored `bool` decoded. Naga 30 accepts run-time indices of array and matrix values (`let` locals, parameters), so no copy into a `var` is needed.
7. **Statements.** `let`/`var` are themselves (types inferred); a block constant emits nothing; `p op= v` is `p = p op v` (the place is a local or a component of one, evaluated once); `for i in a..b` is `for (var u_l_i = a; u_l_i < b; u_l_i++)` (bounds are constants in GPU code, `E4010`); `for x in arr` is `{ let mtek_each_x = arr; for (var mtek_at_x = 0u; mtek_at_x < Nu; mtek_at_x++) { let u_l_x = mtek_each_x[mtek_at_x]; … } }` (the array evaluated once, the counter always in range). *Decision 0045 extends assignment to struct fields and array elements: a compound assignment clamps each run-time index of its place once into `let mtek_index_<k>`.*
8. **Helpers** (`spec/compiler-architecture.md` §7.3), each in the CPU's operation order where WGSL lets it be (a GPU may still contract `a * b + c`): `mtek_quat_mul` and `mtek_quat_rotate` (decision 0026 item 6), `mtek_quat_axis_angle` (identity for a zero axis, else divided by the largest component magnitude, then by the length, `(n * sin(h), cos(h))` with `h = angle * 0.5`), `mtek_quat_euler` (`(axis_angle(+Y, y) * axis_angle(+X, x)) * axis_angle(+Z, z)` through the two helpers), `mtek_mat4_translation`, `mtek_mat4_scale`, `mtek_mat4_rotation` (decision 0037 item 7), `mtek_color_srgb` with `mtek_srgb_channel` (decision 0024 item 6; an `if`, so `pow` never sees a negative base). WGSL's integer `/`, `%`, `f32 %`, conversions and `round` already have the Mtek semantics: no helper.
9. **Literals.** The `i32` minimum is `i32(-2147483647 - 1)` as `spec/language.md` §6.6 prescribes (decision 0029 item 3 printed `i32(-2147483648)`). An `f32` is the shortest text that reads back as the binary32 value both directly and through a binary64 reading (how WGSL reads an abstract float); where the two could differ, the binary64 text of the value. Integers carry `i`/`u`.
10. **Span map.** Every node carries its IR node's span; generated nodes (clamps, decoding, the loop machinery, helper calls) carry the span of the IR node they serve, helper bodies the material declaration with the material's symbol, user functions their own symbol. An `if` maps each header line (`if c {`, `} else if c {`, `} else {`) to the `if` statement, a `for` its header. The IR has no span for assignment places, so an assignment target maps to its statement. *Since decision 0045 places carry spans, and a target maps to its own text.*
11. **Build.** `package` builds every material of the plan: a user material through `lower_material` and `emit_shader` (Naga first, so no artifact exists for rejected WGSL), the built-in `Unlit` through the temporary path until M2-09. The manifest's shader, material (params with their declarations' spans), layout and symbol entries and the writers in `app.js` follow from the artifact as for `Unlit`. Decision 0039 item 11's `E9010` and its test skips are removed; item 12's criterion is now asserted end to end. *Since M2-09 the built-in materials are compiled from the prelude and lowered by `lower_material` too (decision 0044).*
12. **Defects.** An IR node the lowering cannot represent is `E9999` ("The shader of material '…' could not be generated; this is a compiler bug."); Naga rejecting the output is `E6100` at the span the span map gives (decision 0029 item 6). Neither is producible by a checked program; a test-only broken emission proves the `E6100` mapping.

## Consequences

- No new dependency and no new diagnostic code.
- **M2-08** compares CPU and GPU through these shaders: the helpers above are the GPU half of the operation orders; the WGSL built-ins (`smoothstep`, `mix`, `normalize`, `cross`, …) are the implementation's and are covered by the tolerances.
- **M2-09** compiles the prelude's `Unlit` with `lower_material` (it takes any `MaterialItem`, the prelude's too) and deletes `lowering/builtin_unlit.rs`; `tests/shader_lowering.rs` already shows that the prelude's declaration lowered from source prints the `unlit.wgsl` golden up to its block name. It also checks the block limits (`E6001`) before lowering.
- **M2-10** (the M2 gate) can rely on every material of a program building; its programs can be goldens under `tests/codegen/wgsl-materials/`.
- **M2-13** (assignment to struct fields and array elements): the shader IR's assignment target is already an expression, so a place chain lowers through `field_place` and `index_place` (the stored reference of a field or clamped element, before `bool` decoding) with a `bool` value encoded on write and padded elements written through `.value`; an IR place form with spans would also let assignment targets map to their own text.
- `spec/compiler-architecture.md` §4.8, §4.9 and §7 point here.
