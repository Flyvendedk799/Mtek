# 0082. Asset diagnostics follow-ups: the image `source`, EXIF-oriented JPEGs and the final E70xx codes

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M4 (blueprint §11), follow-up task M4-13 of the M4-05 and M4-06 review questions; `spec/assets.md` §3 and §5, `spec/diagnostics.md` §5.7, `spec/manifest.schema.json`; decisions 0058 and 0060.
- Supersedes: decision 0058's "proposal" status of the codes listed in item 3 below (they are now final), and decision 0060 item 3's "gap" and item 4's EXIF constraint (both closed here).
- Numbering note: as 0080, 0064–0079 are left free for the parallel M5 work.

## Context

Decision 0060 reported two gaps: an `image` entry of the manifest carries no project path, so the overlay could not name the author's file of a failed image; and a JPEG with an EXIF orientation is rotated by the browser (`imageOrientation: "from-image"`) while the compiler did not look at EXIF, so such a texture would not show its stored pixels. Decision 0058 assigned several codes as proposals, among them the new `E7020`. The owner answered all three questions: add the `source`, reject EXIF-oriented JPEGs at compile time, and keep the codes.

## Decision

1. **`source` on image entries** (owner decision; details proposal). An image entry may carry `source`: the project path of a standalone image (`textures/wood.png`), or `<glb path>#images[N]` for an image embedded in a GLB (`models/chair.glb#images[1]`). It is optional in `spec/manifest.schema.json` (older manifests stay valid); this compiler always writes it. When identical bytes come from several files they share one entry, and `source` is the first of them in key order (files before embedded images, then by path and index). The runtime adds the note `source file: <source>` to every diagnostic of the entry and names it in the message (`Asset '<url>' (image '<source>') …`, `The browser could not decode the image '<url>' (from '<source>')`); the overlay prints messages and notes, so it shows the author's file.
2. **EXIF-oriented JPEGs are `E7017`** (owner decision; details proposal). The compiler reads the markers of a JPEG up to the first start-of-scan; in the first `Exif` APP1 segment it reads the `Orientation` tag (0x0112, SHORT) of IFD0, in either TIFF byte order. A value other than 1 is `E7017`: "it is a JPEG with the EXIF orientation N (rotated or mirrored); browsers apply the orientation when they decode the image, so the texture would not be the stored pixels. Re-save it without the orientation tag.", help "re-save the image without the EXIF orientation tag (apply the rotation to the pixels when exporting), or convert it to PNG". It applies to standalone textures and to images embedded in a GLB. Orientation 1 (the identity), no EXIF, and a malformed EXIF block (which browsers ignore too) are accepted.
3. **Final codes.** The uses of `E7001` (container), `E7010` (missing attribute, including a primitive without `POSITION`), `E7011` (sparse accessor, accessor without a buffer view), `E7018` (sampler modes no preset expresses), `E7020` (asset file not found, title "asset file not found") and `E7025` (out-of-bounds or misaligned accessor data, non-finite values) are final as decision 0058 lists them; `spec/diagnostics.md`, `spec/assets.md` and `diagnostics/codes.rs` already carry them and are unchanged apart from E7017's description.

## Consequences

- The manifest grows by one optional key per image entry; manifests without it still load.
- A project with a camera-rotated JPEG texture no longer builds until the image is re-saved.
