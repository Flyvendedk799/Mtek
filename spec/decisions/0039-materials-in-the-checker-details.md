# 0039. Materials in the checker: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §3.1 (the `Pulse` material), §4.4 (GPU code is only what stages reach), §7.2 (only the vertex attributes a material reads), §9.4 (diagnostics); `spec/materials.md` §1–§4, §6; `spec/language.md` §4.2, §8.4; `spec/gpu-layout.md` §5; `spec/diagnostics.md` §5.4–§5.5; decisions 0025, 0027, 0028, 0029, 0035, 0036, 0038.

## Context

Task M2-04 checks user materials: params with constant defaults, the one fragment stage, the `SurfaceInput` fields it reads, the restrictions on what stage code may capture, the constant-alpha warning, and instances of user materials in entity `material` fields; and it puts materials and their instances into the typed IR. The specification states the rules and codes but not every choice an implementation has to make: which pass reports which capture, how a misnamed or second stage is reported, what counts as reading a `SurfaceInput` field, how an instance value crosses modules, what non-constant initial values do in a build that folds every initial value, the IR shape, and what `build` does before shader lowering (M2-05) exists. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Landing.** The construct row `material` and the registry type `SurfaceInput` are marked `M1`, as decision 0035 item 1 prescribes for M2 work that lands before the M2 gate. `texture` and `sampler` stay `M4`: a param of either type is the resolver's `E9010` at the type, and its type is `Error`.
2. **Params** (`types/material.rs`). Materials take part in the dependency search of the constants (decision 0026 item 8, extended by decision 0035): a material after the constants and structs its param types and defaults name, a constant after the materials its descriptor literals name.
   - `E4030` at the type annotation of a param whose type is not a scalar, vector, `mat4`, `quat`, `color`, or a struct or array of those; for a struct or array the message names the part that is not ("(it contains string)"). `SurfaceInput` and other records are not param types. The param's type is then `Error`, so instances and stage code do not report it again.
   - `E4031` for a default that is not a constant expression (at the first non-constant form, whatever the default's type: a call of a user function is not typed while params are checked, which happens before function signatures) and for a default of another type (at the default, with expected and actual types). A default naming another param is not constant.
   - `E5100` for a constant `color` default with an alpha other than 1.0 (top-level `color` params only; a colour inside a struct or array param is not a "colour param").
   - `E4032` once, at the name of the 65th param.
3. **The stage function.** The first stage function of a material is its stage, whatever its name; a material without one is `E4020` at its name. A first stage not named `fragment` is `E4021` ("Unknown stage function 'fragmnt'", with a "did you mean" within edit distance 1–2); a further stage function is `E2002` with a related span at the first (its body is still checked, but it is not a GPU root). `vertex`/`compute` stay the parser's `E4901`. The signature is checked by parts, each its own `E4021`: not exactly one parameter (at the header), a parameter of another type than `SurfaceInput` (at the type), no result type (at the header; the body is then checked against `color`), another result type (at the type). The body is checked by the statement checker of decision 0038 (`start_body`/`end_body`, the generalised `function_body`); its messages name "the fragment stage of material 'Pulse'". Params are read-only values (`E3061` on assignment); `input.field` reads a field of the record (`E3023` for a field it does not have, with the fields as a note).
4. **`SurfaceInput` usage.** A field is read when the stage body writes `input.field` (also `(input).field`) with `input` its `SurfaceInput` parameter. Any other use of the parameter — passing it to a function, binding it to a local — reads every field. The fields are recorded in registry order (`local_position`, `world_position`, `world_normal`, `uv`), which is the varying order of `spec/materials.md` §3.3. Reads inside called functions are not tracked separately (the conservative rule covers them).
5. **Captures (`E4040`)**, each with the note of `spec/materials.md` §3 ("to use `frame.time` in a material, add a param and bind it: …"):
   - by the **resolver**, for names a stage can never read: `self` (instead of `E2003`); a namespace value whose registry domain is CPU (`frame.time`, `frame.delta`, `frame.index`; instead of the `E9010` of `frame`, because it is wrong in every build); a name that is not in scope but names scene `state`, a scene object or an entity (or entity `state`) of a scene of the module (instead of `E2003`). Their uses resolve to `Res::Error`.
   - by the **type checker**, in the stage body: a call of a `cpu fn` (of the module or imported; `E4002` does not apply to roots, and a `fn` the stage reaches that calls a `cpu fn` stays `E4002` there), and a read of a constant whose type has no GPU representation (a handle, a descriptor, a material instance). A string constant is not a capture (a local of type `string` is `E4011`).
6. **`W5101`** for a `return` in a stage whose value is a constant colour with an alpha other than 1.0 (at the value), or a call of a registry colour constructor whose `a` argument is a constant other than 1.0 (at the argument). A colour that reaches the `return` through a local is not followed.
7. **GPU roots.** The stage of every material is a `RootBody` of `Roots::gpu_bodies` (label "the fragment stage of material 'Pulse'", span its name, facts from its body), so `E4010`–`E4012` follow GPU reachability through the functions it calls, and those are `gpuReachable` in the IR. The test hook `AnalyzeOptions::gpu_root_functions` and `tests/semantics/gpu/` stay: they test functions without a material.
8. **Instances.** A descriptor literal of a user material — of the module or imported (`Imports::materials`) — has the type `Ty::MaterialInstance(MaterialKey { file, def })`, nominal like structs (decision 0035 item 5) and assignable to `material`. It is checked where it is typed, wherever it appears (constants, fields, function bodies): `E5001` at an unknown param (the params as a list, a "did you mean"), `E5002` at the second of two, `E5003` at the material's name per param without default that is not given (not when an unknown param was given, which is most likely the missing one misspelt), `E3102` at a value of another type ("Parameter 'phase' of material Pulse expects f32, but received vec3.", with the component counts of two vectors). A constant `color` value with another alpha is `E5100` when the literal is folded. A literal without errors folds to `ConstValue::Material { material, name, params }` with **every** param in declaration order, written or defaulted, so an instance stored in a constant carries its defaults across modules.
9. **Non-constant initial values.** A value that is not a constant expression in a field that need not be constant — an entity's `position: half(1.0)`, a param of a built-in or user material instance, a projection field — is valid v0.1 (evaluated once at construction, `spec/scenes.md` §11), but this build folds every initial value. It is `E9010` ("Initial values that are not constant expressions are specified for v0.1 but not implemented by this compiler build yet (planned for M3).", the field and the reason as a note) at the first non-constant form; a read of an entity or camera field stays `E5081`. This replaces the internal error (`E9999` from the IR) such programs produced since functions landed (M2-02).
10. **Typed IR.**
    - A material is an item `{ kind: "material", name, symbol, params: [{ name, type, default?, span }], layout?, fragment, span }`. `layout` is the parameter block's `LayoutRecord` (`spec/gpu-layout.md` §5): id `material:<path>::<Name>` and WGSL struct `MtekParams_<hash8>_<Name>` from `layout::naming` with the **declaring module's path**, user structs in it named by their symbol (decision 0036 item 11), laid out by `layout::compute`; absent for a material without params. `fragment` is `{ symbol: "<material>.fragment", surfaceInputs, result, locals, body, span }`: the `SurfaceInput` parameter is local 0, statements and expressions as for functions (decision 0038 item 8), a param is the expression `{ kind: "param", param: <index into params>, name }`, `input.uv` a `field` with the record's field index.
    - An entity's material instance names the user material by its symbol (`src/main.mtek::Pulse`) like a built-in one; every param, in declaration order, gains `update: "initial"` (the update class of `spec/materials.md` §4; `imperative`, `bound` and `resource` arrive with M3/M4).
    - A material instance used as a constant's value is a `Value::Struct` named after the material, with every param; a literal that is not constant (in a function body) is the expression `{ kind: "material", material: <symbol>, params }` with every param, the defaults as constants.
11. **Build.** The shaders of user materials need the shader lowering of M2-05 (and their manifest entries the resource plan of M2-09). Until then `build` reports `E9010` ("Builds with user materials (shaders generated from their fragment stage) are specified for v0.1 but not implemented by this compiler build yet (planned for M2).") at every user material the entry scene uses, and writes nothing; a program that declares user materials but uses none builds. `tests/build.rs` skips the pass fixtures that use one and asserts this diagnostic for them (`builds_with_user_materials_wait_for_shader_lowering`). *Superseded by decision 0041 item 11: user materials build since M2-05; the gate and the skips are gone.*
12. **The `Pulse` criterion of decision 0036 item 12.** `tests/modules/same_named_materials/` now checks without diagnostics. `same_named_materials_of_two_modules_build_to_distinct_names` asserts, from the real materials, the IR items `src/pulse_a.mtek::Pulse` and `src/pulse_b.mtek::Pulse`, their layout ids and `MtekParams_<hash8>_Pulse` structs, WGSL block declarations of both accepted together by Naga, and writers `w_<hash8>_Pulse` without a common name; the build gives exactly the two `E9010`s of item 11, one in each module, and the same test switches by itself, when the gate goes, to requiring the names in the `.wgsl` files, `app.js` and the manifest's layouts.
13. **Catalogue coverage.** `E4020`, `E4021`, `E4030`–`E4032`, `E4040`, `W5101` and `E5003` (no longer unreachable) have fixtures. `E4041` and `E6002` are listed for M4 (texture params), `E6001` for M2-09 (the resource plan's limits), and `E6003` and `E5902` as not producible by v0.1 programs (at most four inter-stage variables; no construct requests transparency).

## Consequences

- M2-05 lowers each IR material's `fragment` (with the `gpuReachable` functions) to WGSL through the standard stage of decision 0029, taking the varyings and vertex attributes from `surfaceInputs` and the block declaration from `layout`; it reads params from `mtek_params` by name. When it can build user materials it removes the gate of item 11, and the skipped build fixtures and the full assertion of item 12 switch on.
- M2-09 compiles the prelude's `Unlit` from source through the same path (its instances then carry a material item too), plans instances and update classes from the IR (`update` of every instance param), checks the block limits (`E6001`) and writes the manifest's `materials`, `materialInstances` and `layouts` from `layout`.
- M2-10 builds arenas per layout id; the writer names follow from the layout id (`w_<hash8>_<Name>`).
- The CPU emitter (M2-07, decision 0040) emits the expression `material` as a plain object of its params (nothing consumes one before M3) and treats `param`, which only stage bodies contain, as a defect.
- M3 replaces item 9's `E9010` with real initialisers and adds `bind` values (`bound` params) and handler writes (`imperative`).
