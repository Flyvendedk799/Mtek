# 0031. Runtime scene rendering: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §6 (one layout record, generated writers), §7.2 (pipeline cache), §7.4 (resources); `spec/runtime-abi.md` §4.2, §4.3, §5.2, §6.1, §8, §10; `spec/gpu-layout.md` §6, §8; `spec/materials.md` §3.3, §4, §6; `spec/scenes.md` §3, §11, §12; `spec/stdlib.md` §3, §4; decisions 0020, 0029, 0030.

## Context

Task M1-18 makes the runtime render an M1 program: the CPU world built from the manifest and `scenes.<Entry>.init(ctx)`, meshes, material parameter blocks, the frame and object blocks, pipelines, the draw list and the counters, all created before `mountMtek` resolves. The specification fixes the context's ABI, the matrices, the binding plan, the vertex interface, the cache key, the draw-list order and the arenas. It does not fix which context members an M1 runtime provides and what the others do, how setter validation interacts with the straight-line `init`, what a program module that does not match its manifest is, where run-time diagnostics of setters point, whether M1 shares parameter blocks, which frame-block members are written, or how the M1-14 browser fixture keeps working. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Files.** `src/scene/structure.ts` (resolving the manifest's cross references), `src/scene/program.ts` (checking `app.js` against the manifest), `src/scene/world.ts` (records, context, transforms), `src/scene/values.ts`; `src/render/meshes.ts`, `materials.ts`, `pipelines.ts`, `renderer.ts` and `startup.ts` (the mount-time sequence). `mountMtek` resolves the structure and checks the program before it acquires a device, so a broken program fails without GPU work.
2. **The M1 context.** `ctx` has exactly `e`, `cam`, `frame`, `setTransform`, `setVisible`, `setParam`, `setCamera` and `warn`. It is a read-only proxy: reading any other member (`s`, `spawn`, `body`, `random`, …), or assigning, defining or deleting any member, throws `RuntimeInternalError` whose message names the member. Setter arguments the ABI rules out (not an entity record, an unknown field or param, a value of the wrong CPU shape, `setCamera("target", …)` for a camera without a target, a projection field of the other projection kind, a code that is not a runtime warning) are internal errors too. The compiler gates every other member by milestone, so an internal error is a runtime bug or a hand-made program; it propagates out of `mountMtek` as itself (not an `MtekMountError`, no overlay: there is no runtime code for an internal error), after the usual cleanup.
3. **Records before `init`.** Entities start at the registry defaults (`position` 0, `rotation` identity, `scale` 1, `visible` true), `state` `{}`, `params` `{}`, `ref` `{ slot: index, gen: 0 }`, and `mat.p` with every param at its type's zero value. The camera starts at `position (0, 0, 5)`, `rotation` identity, `target` `null`, and `Perspective { fov_y: 0.9, near: 0.1, far: 1000 }` or `Orthographic { height: 10, near: 0.1, far: 1000 }` (f32 values). `ctx.frame` is replaced by a new frozen `{ time, delta, index }` (f32, f32, u32) in phase 1 of every frame; during `init` it is all zeros.
4. **Setter validation and `init`.** A write's own range is always checked: scale components finite and `> 0` (`E8090`), camera position/target/rotation finite, `fov_y` in `(0, π)`, `height > 0`, `near > 0`, `far` finite (`E8011`). Relations between camera fields (position ≠ target, `far > near`) are checked on every write **after** `init`, but not write by write during it, because the straight-line `init` of decision 0030 sets them one at a time from the defaults (`near = 2000` before `far = 5000` would otherwise be rejected); the compiler has checked them (`E5010`, `E5011`). After `init` the whole camera is checked once and a violation is reported as `E8011`. A rejected write leaves the previous value. A colour param with alpha ≠ 1 is `E8100`. `E8090` and `E8100` point at the entity's symbol span, `E8011` at the camera's (the ABI-1 setters carry no span ids). Diagnostics of `init` have phase `runtime:mount`, are not fatal and are delivered once the application exists; later ones have phase `runtime:update`. If the view matrix still cannot be built while rendering, `E8011` (phase `runtime:render`) is reported and the previous view kept.
5. **Program and structure checks.** A reference of the scene structure that does not resolve (entry scene, built-in layouts and the members the renderer writes, the active camera, entity indices and parent order, meshes, material instances, materials, their layouts, params and shaders, vertex attributes not in slot order) is `E8006` (`manifest-invalid`), one diagnostic per problem without cascades. A program module without the entry scene's `init`, without a writer entry for a manifest layout, or without a field writer for one of its members is `E8003` (`incompatible-program`: `app.js` and the manifest come from different builds). Asset meshes and texture/sampler params are `E8003` with a note that this build renders primitive meshes and value params only.
6. **Parameter blocks.** One `UniformArena` per material layout, sized for all its instances; every instance **owns** a slot (sharing identical immutable blocks is optional in `spec/gpu-layout.md` §8.2 and is left to M4 with instancing). `ownedParamBlocks` counts the slots, `sharedParamBlocks` is 0. Writes use `writeIfChanged`. Group-1 layouts are created once per block size and shared, as are the frame and object layouts; a material without value params binds one shared empty bind group. Every layout entry carries `minBindingSize` = the block size; group 0 is visible to vertex and fragment, group 1 to fragment, group 2 to vertex.
7. **Meshes.** Every primitive uploads all three attributes (position, normal, uv) whatever the materials read, so a later material never needs a re-upload; a pipeline binds only the attributes its shader lists. Buffers are sized up to a multiple of 4 bytes. Descriptors with equal values share one upload (canonical key of `mesh/cache.ts`); upload order numbers meshes for the draw list.
8. **Pipelines.** At mount, one pipeline per material of the manifest for the surface's colour format (the offscreen `rgba8unorm-srgb` target or the canvas's `<preferred>-srgb` view) is created with `createRenderPipelineAsync` inside a validation error scope; a rejection or scope error is `E8051` at the material's symbol span (shader compilation messages were already mapped through the span map when the module was created) with the pipeline key in a note. The cache key is serialised as a JSON array of its six parts.
9. **The frame.** The renderer writes only `view_proj`, `camera_position`, `light_count` (0) and `ambient` (ambient colour RGB × intensity) through the `builtin:frame` field writers; `reserved0` and `lights` are never written and stay zero. Object blocks (model, normal matrix) are written through the `builtin:object` writers for entities whose world matrix changed; the frame block is one static slot; object slots are allocated per entity with a mesh, in instance order, in a dynamic-offset arena. The clear value is the clear colour's RGB with alpha 1. The draw list is rebuilt when a visibility changes; pipeline keys compare by UTF-16 code unit, never by locale. A zero-sized target skips the frame entirely: no upload, no pass, `framesSkipped` counts it. `drawCalls` is the number of draws of the last rendered frame.
10. **Browser fixture.** The M1-14 mount fixture now runs the compiler's golden `app.js` of codegen fixture A (copied next to the minimal manifest with the bundle under its hashed name) and the golden `Unlit` shader; the page offers that program with the box hidden after `init` (the M1-14 clear-colour specs are unchanged) and as is (a new spec checks the drawn box's pixels).

## Consequences

- No new dependency and no new diagnostic code.
- M1-20/M1-21 (browser fixtures) mount compiled programs through `window.__mtekMount`; `app.debug.counters()` now reports `drawCalls`, `pipelinesCreated`, `uploads` and the param-block counters from real rendering, and `debug.scene()` the world's transforms.
- M3 adds the remaining context members (and removes them from the internal-error path), the per-frame bindings, handlers and `debug.setParam`, and must keep the "relations are checked after `init`" rule or replace it here.
- M4 may share immutable parameter blocks and instance compatible draws; it must then count `sharedParamBlocks` and `instancedDraws`.
