## Context

`spec/ai-and-benchmarks.md` §3 asks for a *grammar model* in the compiler (`syntax/grammar_model.rs`, a data description of the productions) from which `mtek grammar export --format ebnf` prints `spec/grammar.ebnf` (a test asserts equality) and `--format gbnf` prints a GBNF translation ([S9]) with `ExprNoDesc` expanded, nested comments by recursion, a `root` that accepts one module and a maximum output length enforced by the caller; for **exactly one backend/model/version combination**, chosen under three constraints (runs locally without an account; documents GBNF; a validator is available); adapter conformance in `tools/grammar-adapters/test/` (every positive syntax fixture accepted, every syntax-level negative rejected, escapes, comments, numbers and truncated inputs as the compiler does, known differences listed); and a capability check that fails with "grammar-constrained mode unavailable" and never runs unconstrained in its place. The harness that uses all of this is M6-07.

The specification does not say how a token-level grammar becomes a character-level one (GBNF has no tokens, no lookahead and no difference operator), which deviations of the parser from the reference grammar the adapter follows, where the capability check lives, how the backend is installed and pinned, or whether CI runs the suite. This record fixes those choices. Labels as in `spec/decisions/README.md`: **constraint** (external fact, with its source or the measurement), **proposal** (design choice), **hypothesis** (not shown).

### The grammar model and the exports

4. **The model** (`crates/mtek-compiler/src/syntax/grammar_model.rs`) is the reference grammar as data: every production as an expression tree (`Expr`: literals, code points, character classes, references, `EOF`, sequences, alternatives, groups, `?`/`*`/`+`, and `A - B`), its level (lexical, section 1, or syntactic), the derived production `ExprNoDesc` as a `Derivation` (Expr without `DescriptorLiteral` outside brackets), and the layout and comments of the file (which alternatives start a line, the comments after a line with their spacing, the comment lines under a production, the prose between productions, verbatim). `ebnf()` prints it; the rules of printing (name padded to 15 columns then ` ::= `, a continued `|` under the opening parenthesis of its group or two columns left of the right-hand side) make the layout data small. `mtek grammar export --format ebnf` prints exactly `ebnf()`; `crates/mtek-compiler/tests/grammar_model.rs` and `crates/mtek-cli/tests/grammar.rs` assert byte equality with `spec/grammar.ebnf`. The model's word lists are tested equal to the lexer's (`KEYWORDS`, `RESERVED_WORDS`), it has 73 productions, and every reference names a production. The `[S: …]` restrictions stay prose in the comments (they are the compiler's, decision 0042). The header of `spec/grammar.ebnf` now says that the file is printed from the model and that a change edits both.
5. **A correction of the reference grammar** (constraint, found by this task: the lexer test `block_comments_nest` accepts `/***/`). `BlockComment ::= '/*' ( BlockComment | [^*/] | '*' [^/] | '/' [^*] )* '*/'` rejected `/***/` and `/* a **/` (a lone `*` before the closing `*/` had no alternative) and let `'/' [^*]` swallow the `/` of a nested opener after a slash (`/* //* x */ */`). It now reads `BlockComment ::= '/*' ( '/'* BlockComment | '/'+ [^*/] | '*'+ [^*/] | [^*/] )* '*'* '*/'`, the language of the lexer's scan (a `/` before `*` opens a nested comment, a `*` before `/` closes, anything else is content). Productions (73), top-level alternatives (116) and rules (11) are unchanged, so `tools/grammar-coverage` pins nothing new; the cases are edge cases of the conformance suite (item 11) and `tests/syntax/pass/BlockComment.mtek` gained `/***/`, `/* stars before the end **/` and `/*/ a slash after the opener */`.
6. **`mtek grammar export --format ebnf|gbnf`** (`crates/mtek-cli/src/grammar.rs`; registered by one variant and one match arm): stdout, exit 0; no project needed; a model the translation cannot express is an internal error (exit 3). Any other format or a missing one is a usage error (exit 2).
7. **The GBNF translation** (`crates/mtek-compiler/src/syntax/grammar_gbnf.rs`, `mtek_compiler::syntax::gbnf()`, start rule `GBNF_ROOT` = `root`) is computed from the model, not written by hand:
   - **Separators.** Every token of a syntactic production is preceded by `ws` (whitespace and comments, possibly none) or `ws1` (at least one) where the two tokens written together would lex differently. Classes of the last character of a token: *word* (identifier, keyword, float, colour, `true`/`false`), *integer*, *punctuation* (the start of the file counts as punctuation); of the first: *word*, the `.` of a field access, *punctuation*. A separator is required after a word or an integer before a word (`fn main`, not `fnmain`; `#ffffffx` is E0025) and after an integer before `.` (`1 .x`, because `1.x` lexes as the malformed `1.`, E0022). Everything else needs none, which was checked against the lexer: `>` then `=` lexes as `>=`, which the parser splits in type context (decision 0023 item 2), so `array<f32, 2>= x` stays accepted. Because the token before a production comes from its context, productions are emitted in **variants** by that class (`-aw` after a word, `-ai` after an integer) and, where what follows cares, by the class of their last token (`-ei`, `-ewp`, …): the intersection of the grammar with the automaton that tracks the last token's class (Bar-Hillel), computed with exact first/last class sets, with the variants and the repetitions whose iterations depend on the token before them as helper rules (`postfix-expr-rep1-…`). It neither adds nor removes strings and adds no ambiguity: whitespace belongs to the token after it, and the end of the file takes trailing `ws` and a final line comment without a line break.
   - **Identifiers.** `IdentStart IdentContinue* - ( Keyword | Reserved )` becomes a trie over the 56 words (`ident`, `ident-x-<prefix>`): each node continues an identifier that starts with its prefix and ends only where the prefix is not a word.
   - **`ExprNoDesc`** is expanded as the duplicated rule set (`expr-no-desc`, `or-expr-no-desc`, …, `primary-no-desc`): the rules from which `DescriptorLiteral` is reachable outside a bracket pair of the same sequence are copied with that alternative dropped from `Primary`; inside `( )`, `[ ]` and call arguments the original rules are used.
   - **Nested block comments** are the recursive rule `block-comment`, **without a depth bound**: the lexer has none (it counts depth in a `usize`), and llama.cpp's engine keeps a stack per open comment; the suite runs 64 levels (item 12). Proposal: no artificial bound, because any bound would reject programs the compiler accepts.
   - **`root ::= "﻿"? module ws line-comment?`**: one module, an optional byte-order mark at the start only (E0002 elsewhere), trailing whitespace and comments.
   - **Where the compiler is stricter or wider than the reference grammar, the translation follows the compiler** (decision 0005): the keyword `material` is a field name before `:` in field initialisers and descriptor fields and after `.` (decision 0023 item 1); a negated character class never matches a lone carriage return (E0003; `"\r\n"` is an alternative where the class allows a line feed); `\u{…}` names a Unicode scalar value, at most `10FFFF` and not `D800`–`DFFF`, with one to six digits and leading zeros allowed (E0023; rule `unicode-scalar`); `_`, which the lexer makes a token of its own, does not name a descriptor literal (`_ { a: 1 }`) or a scene object (`camera _ { }`), because the parser reads those only after an identifier token (E1001; rule `ident-not-underscore`, the trie with `_` excluded too). The last refinement was found by the suite (an edge case whose stated verdict the compiler contradicted), not foreseen.
   - **Length.** The grammar does not bound the output; the caller sets the limit (`maxOutputTokens`, `spec/ai-and-benchmarks.md` §4.1) and a generation that reaches it is `truncated` (a failure state, §1), never complete. The header of the exported text says so.
   - Unit tests (`grammar_gbnf.rs`): every reference is defined once and every rule is used, names are GBNF names, the `NoDesc` set exists and lacks `descriptor-literal`, `block-comment` is recursive, every keyword and reserved word is excluded by the trie, the refinements are present, the output is deterministic. The exported grammar has 311 lines and 22 915 bytes, SHA-256 `6b267937…` (b11719 parses it; the capability check and the suite load it).

### The capability check

8. **Where it lives.** **Proposal:** in the adapter, not in the `mtek` binary: `tools/grammar-adapters` is a workspace crate `mtek-grammar-adapters` (library and binary `grammar-adapter`, dependencies `mtek-compiler`, `serde_json`, `sha2`, all already in the workspace, decision 0007), so the language tool carries no backend pins (decision 0003). The API the harness calls:
   - Rust: `mtek_grammar_adapters::check_capability(dir) -> Result<Capability, Unavailable>`; `Unavailable` displays as `grammar-constrained mode unavailable: <reason>` (`UNAVAILABLE` is the prefix); `generate(&capability, grammar, prompt, max_tokens) -> Generation { text, truncated, tokens, log }` runs one constrained generation (greedy, seed 0, CPU, `-c 4096`, the prompt as raw text).
   - Command line, for the TypeScript harness: `cargo run -q -p mtek-grammar-adapters --locked -- check --format json [--install-dir DIR]` prints one JSON object: `{"status":"available","mode":"constrained","backend","release","commit","generator","generatorVersion","validator","model":{id,revision,path,sha256},"grammar":{"root","sha256"}}` with exit 0, or `{"status":"unavailable","message":"grammar-constrained mode unavailable: …","reason":…}` with exit 1 (2 for bad arguments). `--format human` prints one line.
9. **What it checks, in order** (each failure names its reason; unit tests reach the install, generator-version and model failures, while the validator-enforcement and generation-probe failures are not exercised by a test, for want of a fake validator or generator): an `install.json` for the pinned release and commit in the directory (a stale one is "not the pinned"); the generator exists and its `--version` carries the pinned build and commit; the validator exists, loads the exported GBNF, **accepts a valid probe module and rejects an invalid one** (a grammar that loads but is not enforced is unavailable); the model file has the pinned size and SHA-256; and the generator loads the model and the grammar and samples four tokens under it. Only then is the answer `available`. There is no fallback path: nothing in the crate runs a generation without the grammar.
10. **Truncation.** `llama-completion` ends its output with ` [end of text]` when the model produced an end-of-generation token, which llama.cpp's grammar sampler allows only where the grammar accepts; without it the generation stopped at the limit and `Generation::truncated` is true.

### Conformance and the smoke

11. **The suite** (`tools/grammar-adapters/test/conformance.rs`, `harness = false` so that its report is always printed) writes the exported GBNF once and runs the pinned validator on every input (in parallel), comparing with the compiler's lexer and parser (`compiler_verdict`): the grammar must **reject** a text for which they report a lexical or syntax code (`E0002`, `E0003`, `E0005`, `E0006`, `E0010`, `E0013`, `E0020`–`E0025`, `E1001`–`E1004`, `E1010`, `E1011`, `E1901`, `E4901`) and **accept** a text with no error or only restriction codes the grammar does not express (`E0011`, `E1020`, `E1030`). Two codes stand for either: `E1050` (the parser skips what is nested too deep without reading it) and `E1040` (a member in a body whose production lacks it is ungrammatical, `param` in an entity is the restriction `param-only-in-prefab`); fail fixtures with only these are classified by name in the suite (13 ungrammatical, 1 grammatical, all `E1050` fixtures grammatical), and an unclassified one is a failure, as is a positive fixture with errors. Sections: the positive syntax fixtures; the fixtures of `tests/syntax/fail/`, `lex/` and `ast/`; every other `.mtek` file of `tests/`, `examples/`, `benchmarks/` and `packages/` (never `benchmarks/holdout/`); edge cases (each states its verdict, which must also be the compiler's, so that a case cannot test nothing): every escape and the scalar boundaries, every kind of comment (line, doc, `////`, block, `/**/`, `/***/`, `**/`, nested, `//*` inside, 64 levels, unterminated, unbalanced, lone carriage returns), CRLF, tabs, empty files, a byte-order mark first and later, E0005 characters, integer, float and colour edge cases (`00`, `01`, `1.`, `.5`, `1e3`, `1.5e`, `0x1F`, `1_000`, `1u`, `1.x`, `1 .x`, `1.0.x`, ranges, 3/7/9-digit colours), word boundaries (glued keywords, names that start with keywords, `_`, `__x`, keywords and reserved words as names, non-ASCII names, `material` in its four positions), the `>=` split, separated operators, chained comparisons, bitwise operators, descriptors in conditions; every prefix of every positive fixture cut at the start, the end and the middle of every token and comment; every positive fixture with one token deleted; every positive fixture with one word (name, keyword, word literal) replaced by `_`, `material`, the reserved word `type` or the keyword `self`, which reaches every position where the parser takes a token kind other than the grammar's `Ident`. Before the corpus it checks that the validator is sensitive: `fnf() {}` is rejected by the grammar and accepted when `ws1` is weakened to `ws`.
12. **Results on the pinned backend** (b11719 validator, 2026-10-18): see Verification; the acceptance criterion ("the conformance suite passes on the pinned backend") is met with **no disagreement outside the known differences**.
13. **Known differences** (between this grammar and the compiler; the suite allows only the first two and counts them):
    - *nesting-limit*: the compiler rejects nesting deeper than 256 levels (`E1050`, decision 0022); the grammar has no depth bound and accepts the 8 `E1050` fixtures.
    - *restrictions*: the `[S: …]` restrictions and the checker's rules are not expressed; `__x` (`E0011`), unused expressions (`E1020`), `break` outside a loop (`E1030`) and `param` in an entity (`E1040`, `param-only-in-prefab`) are accepted, as the reference grammar accepts them. Constrained output still goes through `mtek check`.
    - *validator input*: the validator reads its input file in text mode; on Windows `\r\n` reaches the engine as `\n` (the verdicts agree, since the lexer treats both alike) and a `0x1A` byte would end the input (no corpus file contains one; untested). The sampler of a real generation sees model tokens, not files.
    - *outside the domain*: invalid UTF-8 (`E0001`) and oversized files (`E0004`) are rejected before lexing; a grammar over Unicode code points does not see them. A NUL character inside a string or comment is accepted by the lexer and by the grammar's classes, but whether llama.cpp's engine matches code point 0 was not tested.
    - *length*: unbounded (item 7).
    Nested block comments are supported (grammar-notes note 5 needs no adapter difference).
14. **The smoke** (`tools/grammar-adapters/test/smoke.rs`, `harness = false`): the capability check, then one generation with the pinned model, a ChatML prompt (the model's own chat format written out, so that it answers with the module and ends the turn with its end-of-turn token), 400 tokens at most; it passes when the generation completed (not truncated) and the compiler lexes and parses the text. A first prompt as a plain comment block made the model repeat comments until the limit (truncated: a failure, recorded); the prompt was changed to the chat format, not the grammar.
15. **CI.** **Proposal:** CI does not download the backend. Without `install.json` the suite and the smoke print `NOT-RUN` with the reason and exit 0 (visible in the `cargo test` log); `MTEK_REQUIRE_GBNF_VALIDATOR=1` and `MTEK_REQUIRE_GBNF_BACKEND=1` turn NOT-RUN into a failure for gate runs. The capability check's negative paths, the pins, the verdict classification, the GBNF unit tests and the EBNF equality run everywhere. Reasons: the Linux path (the Ubuntu archive is pinned and its listing checked, but `fetch-backend.mjs` building the validator with GCC and the suite on Linux were not run by this task) is unverified, and the full suite takes about three minutes. A CI job (`fetch-backend.mjs --validator`, then the suite with `MTEK_REQUIRE_GBNF_VALIDATOR=1`) is the follow-up once it has run green on Linux.
