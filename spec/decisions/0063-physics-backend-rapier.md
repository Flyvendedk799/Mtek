# 0063. The physics backend: the adapter types, the Rapier adapter, its bundle and its emission

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: §8 (physics is a subsystem behind an adapter, not keywords pretending to be a solver), §13 (pinned, tested dependencies); `spec/physics.md` §1, §5 and §5.1; `spec/runtime-abi.md` §2 (`physics/<h16>.js`); decisions 0007 (dependency policy), 0030 (packaging), 0055 and 0060 (how runtime pieces, test hooks and extra files were added).
- Related: M5-03 (physics schemas and `subsystems.physics`) and M5-05 (stepping, commands, events) are separate tasks; this record changes neither the manifest schema nor `app.js`.

## Context

Task M5-04 is the backend-neutral interface and its Rapier implementation, built as a separate, lazily loaded bundle that the compiler writes into `dist/` only for programs that use physics. `spec/physics.md` §5 fixes the two interfaces and the mapping table; it leaves open the descriptor types, the version and licence of the dependency, how the bundle is produced and embedded, how a physics build can be produced before the checker knows about bodies, and several behaviours of the engine that the runtime integration must know. Claims are labelled: **proposal** (design choice), **constraint** (external fact or engine behaviour, each pinned by a test), **hypothesis** (not yet evidenced).

## Decision

1. **The dependency.** `@dimforge/rapier3d-compat` **0.21.0**, pinned exactly (`"0.21.0"` in `packages/physics-rapier/package.json`, no range operator; `package-lock.json` fixes the tarball integrity), licence **Apache-2.0**. **Constraint:** 0.21.0 is the `latest` dist-tag on npm (published 2026-09-25, checked 2026-10-18) and the version `spec/physics.md` was written against (source S8, verified 2026-10-03), so no newer stable release exists to prefer. **Constraint:** the `-compat` package embeds its WebAssembly as base64 (`RAPIER.init()` instantiates it; no fetch, no `import.meta.url`), which is why the bundle is one self-contained file and the adapter runs under plain Node. The dependency table of decision 0007 gets this row. `@types/three` (decision 0007, M0-09) pulls an unrelated 0.12.0 into the root `node_modules`; npm nests 0.21.0 under `packages/physics-rapier/node_modules`, and a test asserts that the bundle contains the nested copy (`src/bundle.test.ts`) and that `PhysicsBackend.name` equals the installed version (`src/backend.test.ts`), so neither the pin nor the name can drift.
2. **The interface types** (`packages/runtime-web/src/physics/types.ts`, **proposal** for the parts §5 does not spell out). `PhysicsBackend`, `PhysicsWorld` and `LoadPhysics` are exactly §5, member for member. The auxiliary types are `Vec3` and `Quat` (the CPU values of `math/types.ts`), `Pose = { position: Vec3; rotation: Quat }`, `BodyHandle` (an opaque branded number), `BodyDesc` (`{ kind: "static" } | { kind: "kinematic" } | { kind: "dynamic"; mass; linearDamping; angularDamping }`, the fields of the `Static`/`Kinematic`/`Dynamic` schemas) and `ColliderDesc` (`shape: { kind: "box"; size } | { kind: "sphere"; radius }` with full extents as in `BoxCollider`, plus `sensor`, `friction`, `restitution`). The file has no runtime code, so importing it pulls no backend into the runtime bundle. `packages/physics-rapier` imports it with a relative type-only import (`../../runtime-web/src/physics/types.js`), so the contract has one definition and the package has no runtime dependency on `@mtek/runtime-web`.
3. **The adapter** (`packages/physics-rapier/src/backend.ts`). Every row of §5.1 is implemented as written: `fixed()`, `dynamic()` with `setLinearDamping`/`setAngularDamping` and the collider `setMass(mass)` (also on a sensor collider), `kinematicPositionBased()` with `setNextKinematicTranslation/Rotation`, `cuboid(size/2)`, `ball(radius)`, `setSensor`/`setFriction`/`setRestitution`, `setActiveEvents(COLLISION_EVENTS)` **and** `setActiveCollisionTypes(ALL)` on every collider, one `EventQueue(true)` per world, teleport (`setTranslation`, `setRotation`, and unless `keepVelocity` `setLinvel(0)`, `setAngvel(0)`, all with `wakeUp`), `addForce` before the step and `resetForces` after it for exactly the bodies that were given a force, and a `Map<colliderHandle, userId>` that `drainCollisions` translates through. `applyImpulse` and `setLinearVelocity` act immediately on the velocity (and wake the body): "applied at the start of the next tick" (`spec/physics.md` §3) is the runtime's ordering, not the adapter's. The adapter changes none of Rapier's solver parameters.
4. **Defensive behaviour** (**proposal**). A WebAssembly panic cannot be recovered from, so inputs the engine could not survive are refused with a `RangeError` before they reach it: a non-positive or non-finite mass, size, radius or fixed step, a negative or non-finite damping, friction or restitution, and any non-finite vector, pose, impulse, force, velocity or gravity. The compiler already guarantees the ranges (`spec/stdlib.md` §3.7); the runtime reports a non-finite pose the *solver* produced as `E8103`. An unknown or already removed `BodyHandle` throws (`Error`), as does any call after `dispose()` except `counts()` (zeros) and `dispose()` itself (idempotent). The runtime drops commands to dead entities with `W8031` before they get here.
5. **Engine behaviour the runtime integration (M5-05) must know** (all **constraints**, each pinned by a test with a derivation in the test file):
   - **Events lag by one step.** Collision detection of step *i* runs on the poses step *i − 1* left, so the events drained after step *i* describe the poses *after step i − 1* (for a kinematic body: its target of step *i − 1*). A body that enters a sensor during step *i* is reported by step *i + 1*. The order and sorting of §6 are unaffected.
   - **Undrained events are discarded** at the next step (`EventQueue(true)`): the runtime must drain after every step, as §4 item 6 says; a missed drain loses events instead of growing the queue.
   - **Events of removed entities are dropped by the adapter**: the user id leaves the map with `removeBody`, and a pair with an unmapped collider is not delivered (§6, "events involving an entity that is pending removal are not delivered").
   - **Without `ActiveCollisionTypes.ALL` a kinematic body entering a fixed sensor raises no event.** `backend.test.ts` runs the same motion on raw Rapier with and without the flag (a control experiment) and through the adapter.
   - **Substeps.** Rapier 0.21 splits each step into `numSolverIterations` (4) substeps, so a free-falling body's position after *n* steps is `y₀ − g·dt²·(n²/2 + n/8)` rather than the textbook `n(n+1)/2`; velocities are exactly `g·n·dt`. The adapter leaves the default.
   - **The contact skin is 5 mm** (`normalizedAllowedLinearError`, 0.005 m in 0.21.0; the prediction distance is 20 mm): a resting body sits at most that far inside a surface, inside the 10 mm of §7. The observed rest of a unit box on a 1 m slab is 0.99993 against the derived 1.0.
   - **Friction and restitution coefficients of two colliders are averaged** (Rapier's default combine rule): friction 1 against 0 behaves like 0.5 against 0.5. The language has no combine rule, so this is the v0.1 behaviour.
   - **A kinematic body's velocity is derived from its pose change.** After a teleport of a kinematic body the previous derived value is still reported until the next step (`setLinvel` has no effect on a position-based body); after one step it is zero.
   - **A sleeping body is woken** by an impulse, a velocity or a teleport (every call passes `wakeUp = true`).
6. **The bundle** (**proposal**). `packages/physics-rapier/scripts/bundle.mjs` (shared by `scripts/build.mjs` and the bundle test) runs esbuild on `src/index.ts` with the options of the runtime bundle (ESM, ES2022, browser platform, unminified) and no source map, producing `packages/physics-rapier/dist/physics.js` (about 4.2 MB, almost all of it Rapier's embedded WebAssembly). It has no imports and no `require`; its **default export is `loadPhysics: LoadPhysics`**, which initialises Rapier once and resolves to the same `PhysicsBackend` on every call (a failed initialisation is retried by the next call). `npm run build` builds it with the other workspaces, before `cargo build -p mtek-cli`. `src/bundle.test.ts` builds the real bundle and imports it with a dynamic `import()` in a fresh Node process, creates a world, drops a box on a floor and disposes: the way M5-05 will load it, minus the browser.
7. **Emission** (**proposal**). `mtek-cli/build.rs` embeds `packages/physics-rapier/dist/physics.js` if it exists (cfg `mtek_physics_embedded`, independent of `mtek_runtime_embedded`); `Runtime.physics_bundle` carries it. `CompileOptions` gains `physics_bundle: Option<Arc<[u8]>>`. `package()` writes it as **`physics/<h16>.js`** (the first 16 hex digits of its SHA-256, like the runtime bundle; verbatim, so the name is the hash of the bytes) **only when the program uses physics**, i.e. when it sets `subsystems.physics = true` in the manifest; a physics program without the bundle is `E9030` ("the physics bundle is not available to the compiler, but the program uses physics"), a program without physics never needs it and never gets it, however the options are filled. The bundle is not part of the build identity (nor is the runtime bundle). The compiler's tests use `STUB_PHYSICS_BUNDLE` (`// mtek test physics stub\n`), which `CompileOptions::with_stub_runtime` carries, so goldens never contain it and the existing file-count assertions double as the proof that a non-physics build has no `physics/` entry.
8. **How a physics build is produced before M5-03** (**proposal**). No language construct sets `subsystems.physics` yet (M5-03 makes it true when any body exists). Until then the compiler's only trigger is the option `CompileOptions.force_physics_subsystem: bool` (library only, no command-line spelling, no source syntax); `package()` computes `uses_physics` from it, and M5-03 ORs the IR condition into that one line. The option never turns physics off. It exists for the packaging tests and for M5-05's runtime tests; it is documented in `spec/compiler-architecture.md` §4.12.
9. **Not in this record (honest scope).** The runtime does not load the bundle yet: the stepping from the scheduler, the components, the command categories, pose write-back, event sorting and delivery and the `physics-failed` mount error are M5-05. **Open point, resolved by decision 0066 item 1 (`subsystems.physicsModule`):** nothing in the manifest or `app.js` tells the runtime the content-hashed file name (`subsystems` is a bare boolean, `additionalProperties: false`). The proposal for M5-05 is an optional-when-false `subsystems.physicsModule` string (`"physics/<h16>.js"`, required iff physics is true) in `spec/manifest.schema.json` and `package/manifest.rs`; it is not made here because it changes the ABI surface that M5-03 and M5-05 own.

## Consequences

- `spec/physics.md` §5 points here for the descriptor types, the bundle and its emission; `spec/runtime-abi.md` §2 and `spec/tooling.md` §1 for the file and its embedding; `spec/compiler-architecture.md` §4.12 for the two new options; `spec/diagnostics.md` for the second meaning of `E9030`; `spec/testing.md` §1 for the new workspace's tests.
- `npm run test:unit` runs 61 more tests (`packages/physics-rapier`: adapter and bundle); `cargo test --workspace --locked` runs the packaging tests of `crates/mtek-compiler/tests/build.rs` and the embedding tests of `crates/mtek-cli/src/runtime.rs` and `dist.rs`.
- A CLI built without `npm run build` still builds every non-physics program; only a program that uses physics fails with `E9030`.
- A `dist/` of a physics program is about 4.2 MB larger; programs without bodies are byte-identical to before (the goldens did not change).

## Verification

- `packages/physics-rapier/src/backend.test.ts` (Node, Vitest): the version and pin; independent worlds; gravity and the fixed step (a step of 1/120, derived with the substep model); the static pose; box half-extents (a unit cube rests at floor top + 0.5 within the skin, a 1×2×3 box at + 1.0, a quarter-turned 2×3×1 box at + 1.0; the full size as half-extent fails them); the ball (radius, not diameter); impulse = Δv·mass for three masses, accumulation, mass independent of volume (cubes of 0.5, 1 and 2 m and a sphere with one mass) and on a sensor; waking by impulse and velocity; linear damping `v/(1 + c·dt)ⁿ`; angular damping through a rolling sphere (`v = 5/7·v₀`, `ω = −v/r`, and `e^(−2/7·c·t)` with damping); forces for exactly one step, accumulating, not leaking to other or later bodies; kinematic targets (pose after one step, derived velocity, pushing a dynamic ball); teleport (pose now, velocities zeroed, kept, angular velocity of a rolling ball, kinematic, waking); a sensor does not push; restitution (rebound ratio 0.64 ± 0.04, none at 0); friction (stopping distance `v²/(2μg)`, none at μ = 0, the averaging rule); events (user ids not handles, per-step draining, undrained events discarded, dynamic pairs, sensor enter/exit at the derived steps, kinematic-vs-fixed-sensor and kinematic-vs-wall events at the derived steps, the control experiment on raw Rapier, events of removed bodies dropped, recycled engine slots); counts after adds, removals, `dispose` and 20 create/dispose cycles; unknown handles and use after `dispose`; plain-object read-backs; rejected inputs. Mutating the adapter (full size as half-extent, no collision types, no force reset, density instead of mass) fails the tests that name those rows.
- `packages/physics-rapier/src/bundle.test.ts`: the bundle is written where the embedding expects it, contains the nested Rapier, has no imports or requires, and works when imported dynamically in a fresh Node process.
- `crates/mtek-compiler/tests/build.rs`: a build without physics has no `physics/` file even when the bundle is available (every fixture, three modes); a physics build has exactly one more file, `physics/<h16>.js`, equal to the bundle, a schema-valid manifest that differs from the plain build's in `subsystems.physics` alone, and the same build id; the file is written verbatim under the hash of its bytes; physics builds are reproducible; `E9030` without the bundle and no effect of the missing bundle on programs without physics. `crates/mtek-cli/src/runtime.rs`: the embedded bundle is the built file, and through the real runtime and physics bundles a physics build carries it and a plain build does not. `crates/mtek-cli/src/dist.rs`: the file is written into `physics/` by replace-on-success.
