# 0023. Parser conventions for the full grammar

- Status: Accepted
- Date: 2026-10-03
- Blueprint origin: none; `spec/grammar.ebnf`, `spec/grammar-notes.md`, `spec/compiler-architecture.md` §4.3, `spec/diagnostics.md` §5.1.

## Context

Implementing items, members and statements (M1-05) met one contradiction in the specification and several places where it names a diagnostic but not the rule that chooses it. The parser must be deterministic and its choices testable, so they are fixed here. Everything not listed follows `spec/grammar.ebnf` and `spec/compiler-architecture.md` §4.3 literally.

## Decision

1. **`material` is accepted as a field name.** `spec/grammar.ebnf` makes `material` a keyword, but the entity schema has a field `material` (`spec/scenes.md` §4.1, blueprint §3.1 `material: Pulse { … };`) and `Cube.material.phase = 0.5;` reads it (`spec/materials.md` §4). The keyword is therefore accepted where a *field name* is expected: before `:` in a field initialiser (scene, entity, prefab, scene object), before `:` in a descriptor field, and after `.`. At the start of an item (and nowhere else) `material Name { … }` is still a material declaration. No other keyword gets this treatment; a future schema field named like a keyword needs a decision of its own.
2. **Closing angle brackets in types.** In type context the lexer's `>>` and `>=` are split: the first character closes the type arguments and the rest is the next token (`let a: array<f32, 2>= x;` is a type, `=` and `x`). This clarifies note 2 of `spec/grammar-notes.md`.
3. **`E1003` versus `E1001` for a missing `;`.** After a complete statement, field or declaration whose next token is not `;`: it is `E1003` (empty primary span right after the last token, insertion recorded as a candidate edit, nothing consumed) when the next token is `}` or the end of the file, starts on a later line, or starts the next construct of that context (a statement keyword, a member keyword, `name :`, `name (`, `kind name {`, an item keyword). Otherwise it is `E1001` "expected `;`" and the rest of the construct is skipped. It is not reported when the previous token is a literal the lexer already reported (an unterminated string swallows its `;`).
4. **End of file.** An expectation that hits the end of the file is `E1004`, wherever it arises (it was `E1001` for a few expression positions in M1-04). A missing closing delimiter at the end of the file stays `E1002`, with the opener as related span.
5. **`E1040` is "valid here? no".** It is reported for a construct that is valid Mtek but not in the place it stands: an item (`fn`, `struct`, `material`, `prefab`, `scene`, `import`, `export …`) in a body or block; a member (`state`, `param`, `entity`, `on`, a field, a lifecycle function, a scene object, `const`) in a body that does not have it (`param` in a scene or an entity that is not a prefab, a field in a material, a scene object in an entity); `state`, `param`, `entity` and `on` at the top level or in a block; a statement in a body. The primary span is the first token of the construct. The construct is parsed (so its own mistakes are found) and replaced by an `Error` node. Nested `entity` in a prefab is not `E1040` (it is `E5040`, the checker's). `E1001` is for text that is nothing valid anywhere.
6. **A missing `}` before the next item.** An item keyword (`fn`, `cpu`, `struct`, `prefab`, `scene`, `import`, `export`, and `material` not followed by `:`) that is the first token of a line with no indentation ends the body or block it stands in, and the body reports `E1002` (opener as related span). So a forgotten `}` is one diagnostic and the next item is read as an item; an indented declaration in a body is `E1040` (item 5).
7. **`E1050` accounting.** Every block, every `else if` link of a chain, the body of every scene, prefab, material and entity, every level of type arguments and every level of expression nesting is one level of the single counter (an item is none); up to 257 levels can be active. A construct that would nest deeper is skipped without recursion and replaced by an `Error` node. The diagnostic is reported once per outermost expression and once per statement, member or item — a statement that starts below the limit is a fresh start, one at the limit continues the overflow already reported (a chain of 100 000 `else if` is one `E1050`). The advice names the construct that ran out of levels.
8. **Smaller rules.** `export import` is `E1001` (the import is read, without `export`). An import without names and a struct without fields are `E1001` (`Import` and `StructDecl` need one). A `vertex` or `compute` stage in a material is `E4901` and nothing else, no `E0013`. `W0007`: a doc comment is dangling unless the next token starts a declaration or member (any item but `import`, a struct field, a member of a body, a scene object field) and only doc comments (no ordinary or block comment) lie between; several in a row all document it. The parser reports `W0007`, using the trivia table.
9. **API.** `parse_module(text, tokens, trivia, sink)` reports to the `Diagnostics` sink (as `parse_expression` does and the lexer's `report_into` does, so the per-file cap and `W9003` stay in one place) and returns the module with the `E1003`/`E1011` candidate edits. The text is needed because tokens carry no names.

## Consequences

- `spec/grammar-notes.md` note 2 carries the `>>`/`>=` sentence; `spec/language.md` §2.2 lists `material` among the keywords and is now read with item 1.
- `tests/syntax/fail/` has a fixture per rule; `tests/syntax/pass/keyword_material_is_a_field_name.mtek` pins item 1.
- Nothing here changes a diagnostic code or its catalogue title.
