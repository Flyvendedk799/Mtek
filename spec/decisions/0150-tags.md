# 0150. Tags and tag queries

- Status: Accepted
- Date: 2026-10-21

## Context

A small game keeps asking "how many rocks are left", "which coin is nearest", "remove every bullet". Until now the only handle on a spawned entity was the `entity_ref` that `spawn` returned, so a program had to keep its own arrays of references. Arrays are fixed-length (`array<T, N>`), so that was clumsy and capped.

## Decision

1. **Declaring.** `tag` is a field of the `Entity` schema (`spec/stdlib.md` §3.2): construction-only, a `string` constant, no default. It is a field and not new syntax, so the parser, the formatter, the grammar and the editor needed nothing new, and the schema checks give the usual diagnostics: `E3102` for another type, `E3090` for a prefab tag that reads a param, `E5042` for an instance that sets it. An entity has **at most one** tag. Every instance of a prefab, placed or spawned, has the prefab's tag.
2. **Spelling.** A tag is 1 to 32 lowercase letters, digits and `_`, starting with a letter (`E5220`). Tags are names, like identifiers, and the manifest schema checks the same pattern.
3. **Queries** (`spec/scenes.md` §17, `spec/stdlib.md` §6). These are all CPU-only intrinsics:

   | Built-in | Result |
   |---|---|
   | `count_tagged(tag) -> i32` | the live entities with the tag |
   | `first_tagged(tag) -> entity_ref` | the first in instance order, or a dead reference |
   | `nearest_tagged(tag, point: vec3) -> entity_ref` | the nearest by world position; a tie goes to the first in instance order; a dead reference if none |
   | `has_tag(r, tag) -> bool` | `alive(r)` and its tag is `tag` |
   | `tagged(tag)` | only `for r in tagged(tag) { .. }` |
   | `destroy_tagged(tag)` | `destroy` for every live spawned entity with the tag; handlers and lifecycle functions only (`E5080`) |

   "Live" is what `alive` says: the named entities and the spawned entities that are not pending removal. Instance order is the stable order of `spec/scenes.md` §10.1, which keeps the results deterministic under a fixed seed.
4. **Tags are checked.** The tag argument is a string constant: a literal or a `const` (`E5221`). Some entity or prefab of the **program** must declare it (`E5222`, with a did-you-mean). Tags belong to the program, not to a module, so a prefab in `coin.mtek` can ask for the tag `"player"` of the entry scene. The check runs once over every module after type checking (`types::check_tags`). A misspelt tag is a build error rather than a query that is always empty.
5. **`tagged` is not a value** (`E5224`). It has a type of its own, `tagged entities`, which only the iterable of a `for` loop accepts. The loop variable is an `entity_ref`. At run time, `ctx.tagged(tag)` is a lazy iterable. It visits the named entities, then a snapshot of the spawned entities. It skips any entity destroyed before its turn, including one destroyed earlier in the same loop. An entity spawned during the loop does not exist before the next flush anyway. With no value, there is no list that could go stale, and there is no length to fix.
6. **`destroy_tagged` cannot meet a named entity** (`E5223`). A named entity cannot be destroyed (`E5030`, and `E8030` at run time). So a tag that a named entity has, either its own or its prefab's through a placed instance, cannot be passed to `destroy_tagged`. That rules out a call that would silently skip some of the entities with the tag.
7. **ABI.** `manifest.scene.entities[].tag` and `manifest.prefabs[].tag` are optional. They are omitted when there is no tag, so manifests of programs without tags are unchanged. The context members are `ctx.countTagged`, `ctx.firstTagged`, `ctx.nearestTagged`, `ctx.hasTag`, `ctx.tagged` and `ctx.destroyTagged` (`spec/runtime-abi.md` §4.2). `nearestTagged` brings the world matrices up to date before it measures, so it sees positions written earlier in the same handler.

## Alternatives considered

- **Several tags per entity** (`tags: ["enemy", "flying"]`). The registry has no array-of-string field type, and one group per entity covers the small games this is for. A later decision can add a `tags` field beside `tag` without changing what `tag` means.
- **A `tag "rock";` member.** That is new syntax in every tool for what a field already expresses.
- **Tags as identifiers** (`count_tagged(rock)`). That would need a namespace of their own, and it would clash with entity and state names.
- **Run-time tag strings.** These cannot be checked, and a typo would quietly give 0.
- **`tagged(tag) -> array`.** Arrays have a fixed length.
- **`destroy_tagged` skipping named entities.** This silently does part of what the call says.

## Verification

- `tests/semantics/pass/tags`. It covers a named entity, a nested one, a placed and a spawned instance of a prefab from another module, a `const` tag, every query, and a query from the imported module for a tag of the entry module.
- `tests/semantics/fail/gameplay/`: `e5220_invalid_tag`, `e5221_tag_not_a_constant`, `e5222_unknown_tag`, `e5223_destroy_tagged_of_named_entity`, `e5224_tagged_as_value` and `e5080_destroy_tagged_in_function`.
- `tests/syntax/pass/Tags.mtek`, which is the `spec/scenes.md` §17 example.
- `packages/runtime-web/src/scene/tags.test.ts`, which covers order, removal during a loop, ties, `has_tag` on dead and stale references, and `destroy_tagged`.
- The ABI fixtures `tests/abi/manifests/valid/full.json` (`tag` on an entity and a prefab) and `invalid/entity-tag-invalid.json`. The unknown-key fixtures `invalid/entity-extra-key.json` and `invalid/prefab-extra-key.json` now use `labels`, not `tags`, so they do not look like this feature.
