# 0109. Phase 1 of M7-05: the pilot against the real service — what it cost, what failed and why, and the scopes the full run can take

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M7 (blueprint §11), task M7-05; `spec/ai-and-benchmarks.md` §6.4; decisions 0001 (H4), 0077 (the harness), 0104 (release notes from evidence only), 0108 (the runner, the guard, the report and the rule).
- Supersedes: nothing.

## Context

The full M7-05 run is bounded by money (under 10 USD for the whole task, of which phase 1 spent 0.44 USD) and by what is learned before it. This record is what phase 1 measured with a small run against the real service, so that the scope of the full run is chosen from numbers. **It is a pilot, not the M7-05 result, and no conclusion on H4 follows from it**: 4 tasks, 2 trials per task and condition, one model, far below the protocol's 5 trials, 34 tasks and the holdout. Everything below is in `benchmarks/results/ai/pilot-2026-10-19/` (`report.md`, `projection.md`) and the two run directories `pilot-2026-10-19/` and `pilot-guide-2026-10-19/` (every call, edit and validation, with the final candidates), generated by `report-cli` from the stored `records.jsonl`.

## Decision

1. **What was run** (2026-10-19, Windows 11, AMD Radeon RX 7900 XTX with `isFallbackAdapter` false, Chromium 153, Node 24; model `claude-haiku-4-5-20251001`, temperature 1, prompt caching on, the tasks' own budgets: 3 repairs, 4 000 output tokens per reply, 300 s; trial-major order). Run `pilot-2026-10-19`: `scene-rendering-01` and `shader-bridge-03` (cold), `interaction-03` and `maintenance-01` (edit), Mtek with the compiler context and the baseline, 2 trials each = 16 attempts. Run `pilot-guide-2026-10-19`: `scene-rendering-01`, `shader-bridge-03` and `interaction-03` with `docs/language-guide.md` added to the Mtek context (decision 0108 item 4), 2 trials each = 6 attempts. No holdout task was run. Before them, 3 calls probed the adapter and 3 calls ran two single smoke trials (kept in the ledger, not in the pilot).
2. **The money.** The ledger (`<home>/gate-m7/ai-spend.json`, outside the repository) holds **0.4446 USD** over 59 calls at the end of phase 1: probe 3 calls 0.0075, smoke 3 calls 0.0194, `pilot-2026-10-19` 35 calls **0.2704**, `pilot-guide-2026-10-19` 18 calls **0.1473**. The cap given to the pilot runs was 0.60 and 0.80 against the ledger total; the phase's hard cap was 1.00. No call was refused, no attempt was unfinished by budget. The figures are provider-reported usage at list prices (decision 0108 item 6), not an invoice.
3. **Cost, tokens and time per attempt** (the mean over the pilot's attempts; the dearest attempt in brackets):

   | condition | attempts | completed | cost | input tokens (cache reads / writes) | output tokens | calls | wall time (model / validation) |
   |---|---|---|---|---|---|---|---|
   | Mtek, compiler context | 8 | 3 | 0.0263 USD (0.0417) | 26 781 (15 051 / 9 691) | 2 125 | 3.25 | 19.1 s (16.7 / 2.2) |
   | Mtek + `language-guide.md` | 6 | 5 | 0.0246 USD (0.0443) | 34 012 (24 965 / 9 038) | 2 150 | 3.0 | 21.2 s (16.9 / 4.1) |
   | baseline | 8 | 8 | 0.0075 USD (0.0145) | 4 777 (1 027 / 758) | 694 | 1.13 | 9.6 s (5.9 / 3.7) |

   Cold attempts cost more than edit attempts on the Mtek side (0.0315 against 0.0211 USD). A validation that opens the browser took 2.4 s on the Mtek side and 3.6 s on the baseline side (check-only validations 0.4 s and 1.0 s), so the GPU lock is held for seconds per attempt, and the whole pilot of 22 attempts took 357 s. Prompt caching changed the bill to 70 % of the uncached figure for the Mtek attempts, 55 % for the guide attempts and 91 % for the baseline's (same tokens, different price).
4. **Completion and tokens (provisional, 2 trials per cell).** Mtek with the compiler context completed 3 of 8 attempts (both `maintenance-01`, one of `interaction-03`; none of the 4 cold attempts); the baseline completed 8 of 8; Mtek with the guide completed 5 of 6 (both `scene-rendering-01`, both `interaction-03`, one of `shader-bridge-03`). Tokens per completed task: Mtek 77 083, baseline 5 471, Mtek + guide 43 394 (the report's table). With 4 tasks there is no interval, so the report's verdict is **inconclusive** for each comparison, as decision 0108 item 11 requires. This is a statement about 22 attempts, not about the language.
5. **Why the attempts failed — harness, model or Mtek/documentation.** No attempt ended `error`, `not-run`, `unavailable` or unfinished: none failed because of the harness. Defects of the harness found while building it and fixed with tests: baseline candidates made by parallel processes collided in the shared scratch directory (the name now carries the process and a nonce); a first reply that produced no candidate was counted as a missing first attempt instead of a failed one (the report now counts it as a failure on every layer); two TypeScript typing problems in the new runner. The five Mtek attempts that failed all ended by exhausting the 3 repairs:
   - `scene-rendering-01` (both): the model invented fields (`look_at` on the camera, `vertical_fov` on the projection, `base_color`, `fragment` on `Unlit`) and wrote materials as if they were functions (`E4020` "has no fragment stage", `E3001` "is a material, not a value"); the compiler's messages name the valid fields ("Valid fields: fov_y, near, far") and the model fixed one family of errors per round and introduced another. **Cause: documentation.** The context export of a cold-start task has `schemas: []`, `examples: []` and `symbols: []` (7.5 kB of feature list and syntax rules): there is no field name or example to learn from, so the model guesses and learns from the diagnostics. `mtek context` builds the neighbourhood of the entry scene and the schemas it uses (decision 0072); a stub uses none.
   - `interaction-03` (one of two): `E1001 Expected an expression, found if` three rounds in a row — the model wrote an `if` where an expression is required; the diagnostic does not say what to write instead, and the last reply was rejected by the exact-match rule. **Cause: the model's assumption about the language, with a diagnostic that does not correct it** (the other attempt hit the same error first and fixed it in 3 repairs).
   - `shader-bridge-03` (both): `E2033` (a material imported from a file that does not export it), `E1040` (statements in a scene), `E3001`, and in one attempt a program that compiled and ran with the wrong colours (2 of 2 fixtures failed after 3 repairs). **Cause: documentation and language unfamiliarity; the second failure is the task's own difficulty (a per-pixel blend in linear light).**
   The baseline had one first-attempt failure (`TS18046`, `materialA.color` is of type `unknown`), fixed in one repair. With the guide the Mtek first attempts still failed in 6 of 6 attempts (`vfov`, a conditional in the wrong place, a field of `SurfaceInput` that does not exist) but the repairs converged in 5 of 6. **What the pilot cannot tell**: how much of the baseline's 8 of 8 is the helper module and the skeleton that the baseline starters already contain (a baseline cold starter calls `startTask`, `lookAtCamera`; a Mtek cold stub is a comment), and how much is the model's familiarity with three.js.
6. **A finding about the benchmark, not a result.** The two sides do not get documentation of the same kind: the baseline gets one 10.2 kB reference with the API of everything a task of this set uses, the same for every task; the Mtek side gets the compiler's context, which is task-dependent and, for a cold task, contains no schema, example or symbol. Under the spec as written (§4.1: the ContextBuilder runs `mtek context`) that is the agent-facing contract that H4 is about, so the default Mtek condition stays the context alone; but a report that showed only that condition would attribute to "the language" what may be a property of the context export. Hence the second Mtek condition (decision 0108 item 4), which the orchestrator can include or not.
7. **The projection** (`projection.md`; arithmetic on the means of item 3 weighted by the share of cold and edit tasks, nothing was run for it). Per attempt: Mtek 0.0245 USD, Mtek + guide 0.0263, baseline 0.0078 over the main set's 11 cold and 23 edit tasks. `high` is central x 1.5 (the pilot is small), `ceiling` prices every attempt as the dearest one of the pilot. Against 8.00 USD:

   | scope | attempts | central | high | ceiling | time | what it drops |
   |---|---|---|---|---|---|---|
   | S0 full protocol: 34 + 8 holdout tasks, 5 trials, Mtek and baseline | 420 | 6.78 | 10.18 | 11.82 | 1.7 h | nothing |
   | S1 main set, 5 trials, Mtek and baseline | 340 | 5.48 | 8.22 | 9.57 | 1.4 h | the holdout |
   | S2 S1 + Mtek with the guide on 17 tasks, 3 trials | 391 | 6.81 | 10.22 | 11.83 | 1.7 h | the holdout; the guide on half the tasks, 3 trials |
   | S3 all 42 tasks, 3 trials, Mtek and baseline | 252 | 4.07 | 6.11 | 7.09 | 1.0 h | trials 5 to 3 (provisional) |
   | S4 main set, 3 trials, Mtek, Mtek + guide, baseline | 306 | 5.97 | 8.95 | 10.26 | 1.4 h | the holdout; trials 5 to 3 (provisional) |
   | S5 17 tasks, 5 trials, Mtek, Mtek + guide, baseline | 255 | 4.98 | 7.47 | 8.55 | 1.2 h | 17 main tasks and the holdout (a sample) |

   The spend guard turns an optimistic figure into fewer trials, never into an overspend: with the default trial-major order a run stopped at the cap has every task with the same number of trials or one fewer, and the records say which attempts did not happen. `--order task-major` makes the trials of one task and side adjacent so that their identical first prompt is served from the provider's five-minute cache (in the pilot an adjacent trial paid 0.0048 USD for the first call that had cost 0.0105 the time before); it applies to prompts of at least 4 096 tokens, which are the edit tasks of the Mtek side and about half of the baseline's, and is estimated to take 10 to 15 % off the figures above (not measured as a run). The ledger already holds 0.4446 USD and the cap is on the ledger total: a run with 8.00 USD to spend takes `--spend-cap 8.45`.
8. **Not done, deliberately.** No scope of item 7 was started. The holdout was not run, so nothing about the holdout's difficulty or the integrity log (`benchmarks/README.md`) changed. No second model, no constrained condition (the pinned backend is not installed on this machine; a constrained trial ends `unavailable`), no trial count above 2. The release notes keep their M7-05 placeholder (decision 0104): no number of the pilot is in them.

## Fixtures/Tests

The pilot's records validate against `spec/ai-eval-record.schema.json`; `tools/ai-eval/test/` runs the same code paths on fakes. The pilot itself is reproducible from its stored records: `node tools/ai-eval/src/report-cli.ts --run benchmarks/results/ai/pilot-2026-10-19 --run benchmarks/results/ai/pilot-guide-2026-10-19 --out report.md --projection projection.md` gives the stored files. The runs are not reproducible as model outputs (temperature 1).

## Consequences

- The orchestrator chooses a scope from item 7 (and whether the Mtek + guide condition runs, and with what trial count) and sets the cap; `benchmarks/results/ai/README.md` says how the final run's output is laid out next to the pilot.
- If the full run shows what the pilot suggests (Mtek with the compiler context fails cold-start tasks the baseline completes), the report's own rule says "worse" for that condition and the blueprint's risk response applies (strengthen the context export for a cold start; do not manufacture a comparison). That response is a language/tooling decision, not a harness one, and is not taken here.
