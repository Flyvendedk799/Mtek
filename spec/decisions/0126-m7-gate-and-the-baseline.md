# 0126. The M7 gate report is the baseline: a machine-readable file and generated tables, and the release decision it records

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M7 (blueprint §11), task M7-GATE ("check every criterion of M7, write `evidence/M7/report.md` with the decision, ask the owner before any tag or publication"); decisions 0001 (H4), 0095 to 0099 and 0119 to 0123 (runtime benchmark), 0108, 0109, 0124, 0125 (AI benchmark), 0104 (release notes from evidence only).
- Supersedes: nothing.

## Context

The owner said that the M7 gate report will later serve as the baseline when the project sets out to improve. A report that only records a decision cannot be compared against by a script, and a table copied by hand drifts. At the same time the measurements of M7 and M7.1 contradict two of the project's hypotheses (token efficiency, speed against hand-written WebGPU), which the gate report has to say plainly and still decide the release question honestly. All items are proposals.

## Decision

1. **Two artifacts.** `evidence/M7/report.md` (prose, the decision, the mapping of the exit criteria to evidence) and `evidence/M7/baseline.json` (kind `mtek-m7-baseline`, version 1). The JSON holds the pinned commits, the environment, the test counts of the clean-clone run, the three runtime runs (first, disturbed, quiet) per workload, the AI numbers (main set before and after M7.1 and the three.js baseline, holdout), the verdicts, the targets, the commands to measure again, what must stay constant, the known issues and rules for reading differences. It points at `evidence/M7/ai-baseline.json` (generated by `compare-cli`, decision 0125) by SHA-256 instead of copying it.
2. **Generated, not typed.** `scripts/gen-m7-baseline.mjs` writes the JSON and fills the number tables of the report between `<!-- baseline:NAME:begin -->` and `<!-- baseline:NAME:end -->` markers; `--check` (`npm run check:baseline`, in CI and in `npm test`) fails when either differs from what the stored results give. The prose is hand-written and holds only numbers that the tables or the linked reports contain.
3. **What a later comparison may and may not change** is stated in the file (`mustStayConstant`): tasks and holdout, the runtime workload definitions (the freeze hash), model, settings, budgets, trial counts and price table, the three.js baseline, the machine. A change starts a new baseline and is recorded in a decision.
4. **The noise floor is not measured.** No unchanged setup was repeated, because a repeat costs real API money; the report gives rough standard errors as a guide and says so. A later measurement should repeat the unchanged setup once before judging a small difference.
5. **The decision recorded.** The M7 exit criteria are met and every unsupported behaviour is excluded explicitly; H4 and the runtime threshold are not met. The recommendation is to release, if at all, as a tested pre-alpha toolchain with no claim about tokens or speed; the tag or publication is the owner's decision and has not been made.
6. **The holdout stays out of the repository except as the numbers-only summary** (decisions 0021, 0085, 0125); its aggregates appear in the baseline as counts, rates and token totals, never as content.

## Consequences

- A change that improves or worsens a benchmark can be reported as a diff of two `baseline.json` files.
- `npm run check:baseline` fails if a stored result is edited without regenerating the report; regenerate with `node scripts/gen-m7-baseline.mjs`.

## Verification

`node scripts/gen-m7-baseline.mjs --check`, the clean-clone suite recorded in `evidence/M7/gate/`.
