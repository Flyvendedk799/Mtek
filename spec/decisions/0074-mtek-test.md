# 0074. `mtek test`: declarative project fixtures in a real browser

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §12.1 "no new test syntax in the language"), task M6-09; `spec/tooling.md` §6; `spec/testing.md` §§5, 6.1, 6.3, 6.5; decisions 0012 (browser test environment, NOT-RUN), 0021 (the fixture steps `set_input`, the 128 x 128 target, pixel origin and tolerance), 0055 (build modes), 0056/0066 (manual clock, `app.debug`).
- Supersedes: nothing. Completes 0021 item 1 and 2 on the Mtek side (the baseline side already existed) and adds what 0021 did not need: `expect_counter`, the forms of `expect_state`, `seed`, the report.

## Context

`spec/tooling.md` §6 names `mtek test`, one example fixture and the sentence "builds the project in `test` mode, launches the browser harness of `spec/testing.md` §6 (Playwright must be installed; otherwise it reports NOT-RUN and exits 1 unless `--allow-not-run`) and reports per fixture". The task asks for seven step kinds, one of which (`expect_counter`) no specification text defines, leaves `expect_state` without a stated comparison, and says nothing about the report that the repair harness (M6-07) will read as its "original task tests" check. Every choice below is a **proposal** (a design choice; nothing external constrains it) unless it restates a rule of 0021 or of `spec/testing.md`.

## Decision

1. **Shape.** `mtek test [--allow-not-run] [--format human|json] [PATH]` is one module of the CLI (`crates/mtek-cli/src/test_cmd/`: `fixture.rs` reads fixtures, `runner.rs` finds and starts the browser runner, `report.rs` is the report, `mod.rs` the command). Registration outside it is one enum variant, one match arm and `mod test_cmd;`. The command (a) finds the project (as every command), (b) reads every `tests/*.test.toml` (that directory only, regular files whose names end in `.test.toml`, sorted by file name), (c) builds the project in `test` mode into a scratch directory in the system temporary directory (removed afterwards; the project's own `dist/` is never touched), (d) hands the valid fixtures to the browser runner and (e) merges the runner's results with the fixtures that were invalid. The browser part is a Node program, `tests/browser/support/mtek-test/main.ts`, that serves the test build on 127.0.0.1, opens each fixture in a **fresh page of a fresh browser context**, mounts with `__mtekMount({ seed, test: { manualClock: true, renderTarget: 128 x 128 } })` and drives `app.debug.step`, `pressKey`, `releaseKey`, `app.setInput`, `debug.scene()`, `debug.counters()` and `debug.readPixels()`. It launches Chromium with exactly the arguments of the `hardware` project (`tests/browser/support/launch-args.ts`, now shared with `playwright.config.ts`: `MTEK_BROWSER_ARGS`, `MTEK_BROWSER_CHANNEL`, `MTEK_HEADED` apply to both).
2. **The fixture file** (`spec/tooling.md` §6 and 0021, unchanged where they speak). Top level: `name` (non-empty string, required), `steps` (non-empty array, required), `seed` (optional integer 0 to 4 294 967 295, default **0**: the `random()` seed of the run, so a fixture is reproducible by default; the playground fixture uses 166). No other key. A fixture must contain at least one `expect_*` step (a file that asserts nothing is invalid, as in `benchmarks/tools/validate-tasks.mjs`). Every step is an inline table with exactly one action key (`step` has `dt` next to it). The vocabulary is closed: an unknown step, an unknown key, a value of the wrong kind or a number that is not finite is a problem of the file. All problems of a file are reported with their line (`line 4: step 2 (press): ...`) and the fixture counts as **failed** with the failure kind `invalid-fixture`; it is never sent to the browser, and the other fixtures still run.
   - `{ step = N, dt = SECONDS }`: `N` frames (1 to 1 000 000) of `SECONDS` (finite, not negative) on the manual clock, rendering included. `dt` is clamped to `runtime.max_frame_delta` like every frame delta (`spec/runtime-abi.md` §7); a fixture that wants one fixed tick per frame uses `dt = 0.016666668`, the default `runtime.fixed_step`, and a frame of `dt = 0` renders without time passing.
   - `{ press = "Space" }`, `{ release = "Space" }`: a `KeyboardEvent.code` that is the code of a `Key` member of the standard library (checked against the registry, so `"Hyper"` is a problem of the file, not a runtime error). Applied at the start of the next frame (0021).
   - `{ set_input = { name = value } }`: exactly one entry; a number, a boolean, a string (a colour is `"#rrggbb"`) or an array of 1 to 16 numbers; `app.setInput` validates it at once and a rejection fails the fixture with the code (`MTEK-E8040`, `E8041`, `E8100`); the value is applied at the next frame (0021). Following 0021, an entry means exactly one input per step.
   - `{ expect_pixel = { x, y, color = "#rrggbb", tolerance } }`: as 0021 (128 x 128 target, `(0, 0)` top left, `tolerance` integer 0 to 255 per channel, default 2, alpha not compared).
   - `{ expect_state = { key = value, ... } }`: **keys** are a scene state name (`speed`), or, quoted because of the dot, a named entity's pose or material parameter: `"Cube.position"`, `"Cube.rotation"`, `"Cube.material.tint"` (`debug.scene().entities[]`; spawned entities are not addressable). **Values**: a number; a boolean; a string; an array of numbers (a `vec2`/`vec3`/`vec4` component by component as `x y z w`, a `quat` as `[x, y, z, w]`, a colour as linear `[r, g, b, a]`); a string `"#rrggbb[aa]"` for a state of type `color` (compared as the linear components that a colour literal of that spelling has, within 1e-5); or `{ value = ..., tolerance = ... }` to give a tolerance. **Tolerance of a number or vector** (default `1e-5`): `|actual - expected| <= tolerance + |expected| * 2^-23`, the second term being the "plus 1 ULP for CPU rounding" of `spec/testing.md` §5, so `0.7` in a fixture equals the `f32` the program stores. For a rotation the negated quaternion is the same rotation and matches too. A string or boolean with a tolerance is a problem of the file. Several keys are all checked and all mismatches are reported.
   - `{ expect_counter = { name = value, ... } }`: a counter of `app.debug.counters()` (`spec/runtime-abi.md` §10.1) equals the number exactly, or `{ min = a, max = b }` (either may be absent, both inclusive, `min <= max`). An unknown counter fails the fixture and lists the ones that exist.
3. **Execution.** Steps run in order and the **first failure stops the fixture** (later steps depend on the earlier ones). A failure names the step (1-based index among the steps), its line in the file and the kind: `mount` (the program did not mount: the `MtekMountError` kind and its diagnostics), `step` (a call threw), `set_input`, `expect_state`, `expect_pixel`, `expect_counter`, `runtime-error`, `timeout`. **A program that reports an error-severity diagnostic or lets the page throw fails the fixture even when every expectation holds** (`runtime-error`, checked before the first step and after every step, so the failing step is the one that caused it; warnings are not failures). A fixture that does not finish within 120 s (`MTEK_TEST_TIMEOUT_MS` overrides it) fails with `timeout`.
4. **NOT-RUN, exit codes, `--allow-not-run`.** A fixture is `pass`, `fail` or `not-run`. **`not-run` is the status of a valid fixture that could not run on this machine, with the reason**: Node.js missing or older than 24 (the runner is TypeScript that Node strips itself; a JavaScript runner named by `MTEK_TEST_RUNNER` runs on any Node), the runner not found (it is found above the `mtek` executable, in the repository; `MTEK_TEST_RUNNER` names another), Playwright not installed, Chromium not launchable, or no WebGPU adapter (`navigator.gpu` missing or `requestAdapter()` resolving to `null`: `no WebGPU adapter: ...`, the reason of decision 0012). The exit code is **0** when every fixture passed, or, with `--allow-not-run`, when no fixture failed and the rest are NOT-RUN; **1** when a fixture failed, the project does not build (every valid fixture then fails with kind `build`), a fixture file is invalid, the project has **no fixtures** (a run that verified nothing is not a pass, even with `--allow-not-run`), or a fixture is NOT-RUN and `--allow-not-run` is absent; **2** for bad arguments; **3** when the tool itself fails (the runner crashed or wrote a malformed report, a scratch directory cannot be created, the build output cannot be written). `--allow-not-run` only changes the exit code: the report still says `not-run` for those fixtures and for the run (`status`), and it never hides a failure. An adapter with `isFallbackAdapter: true` is not NOT-RUN (the fixtures run: correctness only) and the report records it; `MTEK_BROWSER_ARGS` can add the software adapter's switches (`spec/testing.md` §6.1) and `--disable-gpu` simulates a machine without a GPU (0012).
5. **The report is the contract with the repair harness.** `--format json` prints exactly one document on stdout and nothing on stderr, described by `spec/test-report.schema.json` (version 1: keys are only ever added within a version): `schemaVersion`, `command`, `project`, `status` (`pass` only when at least one fixture ran and all passed; `fail`; `not-run`), `exitCode`, `allowNotRun`, `error` (a problem that belongs to no fixture), `summary` (`total`, `passed`, `failed`, `notRun`), `build` (`ok`, `mode`, `buildId`, `errors`, `warnings` and the `diagnostics` array of `spec/diagnostics.md` §2.2), `environment` (browser name, channel, version, launch arguments; `gpu.available`, `gpu.reason` and the adapter's `vendor`, `architecture`, `device`, `description`, `isFallbackAdapter`) and `fixtures[]` (`file`, `name`, `status`, `reason`, `failure` with `kind`, `step`, `line`, `message`, `details`, `seed`, `stepsRun`, `stepsTotal`, `durationMs`). No path of the machine appears in a fixture's result (reasons keep the first line of an error with file paths replaced by `<path>`); only the `error` of a crashed tool (exit 3) may name the files involved. The human format prints on stdout the adapter and one block per fixture (`PASS`, `FAIL` with the step, line and what differs, `NOT-RUN` with the reason) and a summary line, and on stderr the build's diagnostics and why the exit code is not 0. A crash of the whole tool (exit 3) still prints the document when it can (`exitCode` 3, `error` set); `mtek test` with arguments that do not parse prints no report (exit 2).
6. **Fixtures of the benchmark tasks** (`benchmarks/tasks/*/mtek-tests`, 0021 item 3) use only the vocabulary above: a Rust test parses every one of them with this parser, so a benchmark fixture cannot drift from the command that runs it. The harness copies them to `tests/` of a scratch copy as 0021 says; nothing else differs.
7. **Fixtures of the examples** (`examples/<name>/tests/*.test.toml`): `pulse-cube` (`rotation-and-pulse`, `space-reverses`, `host-tint`), `physics-playground` (`space-lifts-first`, `crates-and-sensor`, seed 166) and `material-configurator` (`chair-defaults`, `host-inputs`). Every expected number is derived from the program and from a model that is not the runtime, and the derivation is the comment at the top of each file: closed-form rotation (`speed * dt` per frame, a press applied at the next frame) and the `Pulse` colour (`tint * (0.65 + 0.35 sin t)` in linear light, sRGB-encoded) for the cube; the seeded positions, the fall times of the engine's substepped model (47 and 109 ticks), the lift `v^2 / 2g` and the projected meter for the playground (the model of 0069); the CPU ray tracer and PBR oracle of `configurator-scene.ts` for the chair, at pixels whose 1 px footprint sees one surface. `tests/browser/support/mtek-test/example-fixtures.test.ts` recomputes them in CI without a GPU, so a number that does not follow from its derivation fails there.

## Fixtures/Tests

- `crates/mtek-cli/src/test_cmd/*` unit tests: the example of `spec/tooling.md` §6 parses; every step kind and form; each rule of item 2 has a failing text that names its line; the benchmark fixtures parse; discovery; the exit-code table; the report; node and runner lookup.
- `crates/mtek-cli/tests/test_cmd.rs`: the real binary with a stand-in runner (`MTEK_TEST_RUNNER`): exit codes for pass, fail, NOT-RUN with and without `--allow-not-run`, a failure with `--allow-not-run`, no fixtures, no project, an invalid fixture, a project that does not build (the runner is not started), a missing Node or runner (NOT-RUN), a runner that crashes or writes garbage or forgets a fixture (exit 3); every JSON report validates against the schema and has no absolute path; the plan the runner receives (test-mode build with `__mtekMount`, the fixed target, tolerances and lines) and that the project directory is left as it was.
- `tests/browser/support/mtek-test/*.test.ts` (Vitest): comparison rules, step semantics against a fake application (including the runtime-error rule), the NOT-RUN paths of the runner with a fake Playwright, the entry point under Node's type stripping, the examples' derived numbers.
- `tests/browser/specs/m6/mtek-test.spec.ts` (hardware): the three examples pass through the real CLI, runner and Chromium; eight mutations of one expectation each fail at their step and line with the documented kind; an invalid file; NOT-RUN with `--disable-gpu`, without Playwright (the runner copied where no `node_modules` is above it) and without Node, each with the exit codes of item 4. The JSON of each run is written to the results directory.

## Consequences

- `spec/tooling.md` §1 and §6 carry the command line and the format summary and point here; `spec/testing.md` lists the new layers; the root `README.md` lists `MTEK_NODE`, `MTEK_TEST_RUNNER` and `MTEK_TEST_TIMEOUT_MS`.
- `tests/browser/playwright.config.ts` takes its browser configuration from `support/launch-args.ts`; nothing else about the existing suites changed.
- `mtek test` needs a checkout of the repository (the runner and Playwright live there): v0.1 has no installed distribution. A machine without them reports NOT-RUN with the reason; it never reports a pass.
- Known limits: entities that were spawned cannot be addressed by `expect_state`; the render target cannot be changed (0021); there is no step for pointer input, pause/resume or reload; a fixture cannot expect a *failing* `set_input`.

## Verification

Run on 2026-10-18 on the recorded development machine (Windows 11, AMD Radeon RX 7900 XTX, Chromium 153 new headless mode, Node 24):

- `mtek test` on the three examples, hardware adapter (`isFallbackAdapter: false`): `pulse-cube` 3/3, `physics-playground` 2/2, `material-configurator` 2/2 fixtures pass. The reports are `evidence/M6/mtek-test/mtek-test-<example>.json`, the environment record `environment-hardware.json` and the Playwright results `test-results-mtek-test.json` (sanitized with `npm run evidence:sanitize`).
- Eight mutations of one expectation each (a pixel colour, the sign after Space, a quaternion component, a host input name, the tick at which the sensor counts, the lift height, a draw-call count, a seat colour) fail exactly their fixture at the step and line of the mutated expectation with the expected failure kind and message.
- NOT-RUN: with `MTEK_BROWSER_ARGS=--disable-gpu` (`navigator.gpu.requestAdapter()` resolves to `null`) all three fixtures of `pulse-cube` are `not-run` with the reason `no WebGPU adapter: navigator.gpu.requestAdapter() resolved to null`, the exit code is 1, and 0 with `--allow-not-run` where the report still says `not-run` (`mtek-test-not-run-no-gpu.json`); without Playwright (`mtek-test-not-run-no-playwright.json`) and without Node the same.
- `MTEK_REQUIRE_GPU=1 npm run test:browser:hardware`: 232 passed, 0 failed, 0 not-run (the 217 of before plus the 15 of `specs/m6/mtek-test.spec.ts`).
- `cargo test --workspace --locked`: 1 271 passed, 0 failed (of which 15 in `crates/mtek-cli/tests/test_cmd.rs` and 24 unit tests of `crates/mtek-cli/src/test_cmd/`); with `packages/runtime-web/dist` moved away the five tests of `test_cmd.rs` that need no build run and clippy is clean. `npm run test:unit`: 2 709 passed (42 in `tests/browser/support/mtek-test/` and 7 for the derived numbers of the examples among them). `npm run check` is clean.
- Not verified: a Linux or macOS run of the runner, a headed run, a run on a software adapter (`isFallbackAdapter: true`) and a machine with Chromium missing (the launch failure is tested with a fake Playwright only).
