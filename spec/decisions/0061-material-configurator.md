# 0061. The material configurator: the example, its CPU model, the variants of the M4 gate, and the host-input codec defect found on the way

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M4 (blueprint §11) exit gate and guardrails; decision 0002 (the three release demonstrations); `spec/assets.md` §7; `spec/runtime-abi.md` §6.3; decisions 0052 (host inputs), 0056 (resilience helpers), 0057 (the PBR oracle), 0058 (the asset compiler and its generator), 0059 (instancing), 0060 (runtime assets).
- Supersedes: nothing. Corrects the packaging half of decision 0052 item 3 (codec selection), see item 8.

## Context

Task M4-10 is the first release demonstration and the evidence base of the M4 exit gate: "a multi-file material configurator loads a supported model, changes material inputs, survives resize, and produces repeatable test captures; an unsupported required asset feature fails explicitly; a repeated-object scene demonstrates the claimed instancing path through counters and equivalent output", under the guardrails "an unlit approximation is not a passing PBR implementation" and "do not declare broad glTF support from one hand-picked file". The specification fixes none of the example's contents. Every choice below is a **proposal**.

## Decision

1. **The example** (`examples/material-configurator/`) has three modules: `model.mtek` declares the GLB once (`asset.glb`) and exports constants read from its materials, `materials.mtek` holds the custom fragment material `Striped` (two colours from `uv.y`, shaded by `lighting.pbr`) and a function it calls, `main.mtek` imports both and declares the scene. `mtek.toml` exposes ten inputs: colour, metallic and roughness of the seat and of the rails (built-in `Pbr` bound to scene state), the two stripe colours and the roughness of the back, and the intensity of the sun. The four legs and the crest use the model's own constant `Oak` material, so the example itself contains the instancing case: one mesh, one parameter block, one instanced draw. A host page (`host/configurator.html`) mounts `../dist/app.js` and forwards its controls to `app.setInput`; the compiler emits no custom page, so the page lives beside `dist/` and is not part of the build.
2. **The model is generated, not downloaded.** `tests/assets/tools/make-glb.mjs` gained the chair (a seat, a back, a crest rail, four tapered legs, two rails as the two primitives of one mesh, a floor; a node hierarchy with a turn of the whole chair and a lean of the back) and two variants that break one row of the profile each (`tests/browser/fixtures/m4-variants/`: a normal texture, `E7016`; a required extension, `E7004`). The legs and the crest are **tapered prisms on purpose**: a box face keeps its direction under any scale, so a normal matrix taken from the model matrix instead of its inverse transpose does not show on boxes. The generator gained `--out DIR`, so a test can regenerate into a scratch directory and compare bytes with the committed files (`tests/browser/support/chair-glb.test.ts`); `npm run check:assets` still checks in place.
3. **The CPU model** (`tests/browser/support/configurator-scene.ts`) is a small ray tracer: the geometry is read from the GLB file by a parser of its own, placed by world matrices written down by hand from the node table (a test compares them with the file's nodes), the camera is a pinhole built from position, target and field of view (a test projects the hits back through the matrices of `spec/runtime-abi.md` §8.3), the surface normal of a hit is the geometric normal of the world-space triangle (so it depends on no normal matrix), and the colour is the oracle `shadePbr` of decision 0057. It shares no code with the compiler, the runtime or the GPU. A pixel is asserted only where the nine rays through its centre, corners and edge midpoints hit the same surface of the same entity (and, for the stripes, the same band); edge pixels are never asserted. The tolerance is the 3/255 of the PBR spec; the measured agreement is a maximum of 1/255 over 74 717 stable pixels of 76 800 at 320 x 240, and 162 896 stable pixels of 172 800 for the 80-copy scene. Sensitivity is tested, not assumed: with normals taken from the model matrix the model differs from the right one by more than 3/255 on 975 crest and 94 leg pixels (up to 32/255) of the 80-copy scene, and a deliberate mutation of the runtime (the instance record's normal matrix replaced by the model matrix) made the instancing spec fail with 1 076 pixels off by more than 3/255 (checked once by hand, not a committed test).
4. **Variants are built by the harness with the CLI.** Global setup builds the example and its host page (`.out/m4-configurator/site/{dist,host}`, laid out like the example) and the **repeated-object variant** (`.out/m4-configurator/repeated`): the example with `main.mtek` replaced by a generated scene of 80 copies of the chair's meshes (legs and crests with the model's `Oak`, seats with explicit `Pbr` values, rails with the model's `Steel`), each with its own `quat.euler` rotation and a non-uniform scale, and one seat with another roughness; one generator (`repeatedSource`) writes the Mtek source and the model's transforms, so they cannot drift apart. The expected counters follow from the table: four groups of compatible draws and one draw alone, `drawCalls` 5 for 80 entities, `instancedDraws` 4, three shared parameter blocks and one owned. The variants that must fail (the two GLBs above) are built inside the spec, because their build fails.
5. **What each spec proves** (`specs/m4/configurator.spec.ts`, `configurator-variants.spec.ts`, all on the hardware adapter with the manual clock and an offscreen `rgba8unorm-srgb` target): *loading*: the one packaged mesh file is `ready` before mount resolves, the entities sit at the hand-derived node transforms, the picture equals the CPU model, one hand-derived pixel (the ray through the camera target meets the seat top) is shaded by the oracle for an explicit normal and position, and the counters are the ones the scene's structure implies (7 draw calls for 10 drawn entities, 1 instanced draw, 1 shared and 5 owned parameter blocks, 3 pipelines); *inputs*: after each of seven input changes the whole picture equals the model for the accumulated inputs, a change of the seat's inputs changes only pixels the model assigns to the seat (or to no stable surface), every pixel of the changed entity changes, no shader, pipeline, bind group or texture is created, and rejected inputs (wrong type `E8041`, translucent colour `E8100`, unknown name `E8040`) change nothing; *resize*: seven sizes and aspects (including 96 x 72), each equal to the model at that size, the seat's pixel count follows the canvas height and not its width, a return to the first size reads back the same bytes, plus a pixel-ratio change (1, 2, 1) equal to the model at each backing size; *repeatability*: two mounts in separate browser contexts read back byte-identical frames at every step of a plan with 3, 30 and 1 frames, and a different plan reads back a different picture; *the host page*: its real controls (`fill` on the colour inputs, `input` events on the ranges) change the pixels to those of the model; *unsupported features*: `mtek check` and `mtek build` of the example with each variant GLB exit non-zero with the documented code only, a message that names the feature (`normalTexture` and the material, `KHR_draco_mesh_compression`), the span of the `asset.glb(..)` path literal, and `mtek build` writes nothing; *instancing*: the counters above, a pipeline and a buffer more than without instancing, instanced and individual pictures bit-identical (0 of 172 800 pixels differ) and both within 1/255 of the model.
6. **The guardrail is tested as consistency, not as support.** `tests/browser/support/assets-profile.test.ts` reads the table of `spec/assets.md` §3 and requires, for every diagnostic code it names (and `E7013` of §2.1), a failing fixture under `tests/assets/fail/` named for the code whose expectation lists it; the two rows without a code (node transforms, whose rule is in §2.1, and the "not inspected" row) are asserted by name. That the compiler really rejects each fixture with exactly those diagnostics stays the job of `cargo test` (`tests/fixtures.rs`). Nothing here widens the profile: one supported model, a list of what is supported, and a failing fixture for every way a file can be unsupported.
7. **Host page contract.** `window.mtekHostOptions` (the `options` of `mountMtek`) is read before mounting and the application is left in `window.mtekApp`; both exist so that tests drive the real page with the manual clock and read pixels back. Without them the page is an ordinary embedding. This is the only test seam in the example.
8. **A defect in the packager, found and fixed here.** `spec/runtime-abi.md` §6.3 says a colour host input whose state reaches a material `color` param through a binding uses the codec `color-hex-opaque`, which rejects a translucent value in `setInput` itself (`E8100`). The checker computed that set, but `package::builder::resolve_host_inputs` passed an empty set, so every colour host input of every built program (the `tint` of `pulse-cube` included) got `color-hex`: `setInput("seat_color", "#11223344")` returned `{ ok: true }`. The packager now derives the set from the IR (scene state read by a binding whose target is a `color` param of a material instance). Regression test: `crates/mtek-compiler/tests/build.rs`, `a_colour_state_bound_into_a_material_colour_gets_the_opaque_host_input_codec` (checked to fail without the fix); the browser spec "rejected inputs" covers the runtime side. An opaque input is unaffected; only translucent values change behaviour.

## Not covered (stated, not claimed)

- Only the hardware adapter of the recorded machine ran these specs for the gate; the software project is not hardware evidence. Cross-adapter equality of captures is not claimed: repeatability is within one adapter and driver.
- Frames are produced with the manual clock into offscreen targets that follow the canvas (decision 0056); the presentation of the canvas to the screen and the `requestAnimationFrame` loop of the host page are not asserted by pixels in this task.
- The chair has no texture; textured materials, the standalone textures and the corrupt-asset failures are covered by `assets.spec.ts` and `textures.spec.ts`. Only two profile violations are built end to end through the example; the other rows rest on the fixtures of `tests/assets/fail/` and `cargo test`.
- Mip-maps, normal maps, transparency, shadows and every other feature outside `spec/materials.md` §8 remain unsupported, as documented.
