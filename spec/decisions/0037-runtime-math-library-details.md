# 0037. Runtime math library `rt`: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §4.1 (numeric semantics), §12.1 (CPU/GPU ABI tests); `spec/runtime-abi.md` §3, §4.1; `spec/language.md` §5.4, §5.6, §6.2–§6.7, §10; `spec/stdlib.md` §6; `spec/testing.md` §5; decisions 0009, 0024, 0026, 0030.

## Context

Task M2-06 implements the runtime math library `rt` (`packages/runtime-web/src/math/`): the helpers generated CPU code calls for vector, quaternion, matrix and colour values, integer arithmetic, conversions and every pure intrinsic of `spec/stdlib.md` §6, plus the CPU conformance table `tests/semantics/numeric/cpu.json` that M2-08 reuses for the GPU comparison. The specification fixes the semantics in outline (WGSL-equal integers, `f32` rounding after every operation, `round` ties to even, `sign(0) = 0`, `normalize(0) = 0`, `abs(i32 MIN) = MIN`, the folding order of the quaternion and matrix products) but leaves open how helpers are named and exported, how values are kept immutable, several CPU results WGSL calls non-portable, the operation order of the functions decision 0026 does not list, and the format of the table. They are fixed here so that they are visible, testable and changeable by a later record; the CPU emitter (M2-07), the constant folder of the M2 intrinsics (M2-01) and the GPU conformance test (M2-08) depend on them.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Export.** `app.js` imports the runtime bundle as `import * as rt` (`spec/runtime-abi.md` §3), so every helper is a top-level export of the bundle's entry module: `src/index.ts` re-exports `src/math/rt.ts`. The helpers are not part of the hand-maintained host declarations `runtime.d.ts` (hosts never call them). A test asserts the entry module re-exports every `rt` name unchanged.
2. **Operation index and names.** `RT_OPERATIONS[callee][signature]` (`src/math/operations.ts`) names the helper of every Mtek operation: `callee` is an intrinsic (`round`), a namespace function (`quat.axis_angle`), a vector constructor (`vec3`), a conversion target (`i32`), a binary operator (`+ - * / %`) or `neg` (unary minus); `signature` is the concrete signature `"(vec3, f32) -> vec3"`. Helpers take the operands in source order (so `f32 * vec3` is `v3smul(s, v)` and keeps left-to-right evaluation). Names are a type prefix (`f32` none, `f` for the arithmetic operators `fadd`…`frem`/`fneg`; `vec2/3/4` `v2/v3/v4`; `i32` `i`; `u32` `u`; `quat` `q`; `color` `c`; `mat4` `m4`) plus the Mtek name in lower camel case (`v3inverseSqrt`, `qaxisAngle`); a vector form whose last operand is a scalar where the scalar form has the vector type ends in `s` (`v3mixs`, `v3divs`). Conversions are `f2i f2u i2f u2f i2u u2i`. Helpers that implement no callee are listed in `RT_STRUCTURAL_EXPORTS`: `quat`, `color` (component constructors), `swizzle2/3/4(v, "z", "x", …)`, `v2with/v3with/v4with(v, key, value)` (single-component assignment), `crgb` (`.rgb`), `m4col(m, i)` (`m[i]`), `clampIndex`, `srgbChannelToLinear`, `I32_MIN`, `I32_MAX`, `U32_MAX`. A test cross-checks the index against `spec/stdlib-schema.json`: every `both`-domain intrinsic and namespace function, instantiated over its type classes, has exactly one helper of the right arity, and every export is accounted for.
3. **Inline forms.** The emitter may inline the scalar operators instead of calling `fadd`/`iadd`/…: `Math.fround(a ∘ b)` for `f32`, `(a + b) | 0`, `(a - b) | 0`, `Math.imul(a, b)` for `i32`, the same followed by `>>> 0` for `u32`, and plain JavaScript comparisons. The conformance test evaluates every scalar row both ways.
4. **Immutability.** Values are never mutated after creation (`spec/runtime-abi.md` §4.1): every helper returns a new object or `Float32Array` and never writes its arguments (the conformance test checks arguments before and after every row). Values are not frozen: `Object.freeze` cannot freeze a `Float32Array` with elements and would cost time on hot paths; TypeScript callers see `readonly` types.
5. **`f32` results.** Every `f32` operation is computed in binary64 and rounded once with `Math.fround`. For `+ - * /`, `sqrt` this is the correctly rounded binary32 result; `%` is JavaScript's exact remainder (C `fmod`, the exact value of `x - y * trunc(x / y)`), which is always representable, so the rounding never changes it. `inverse_sqrt(x)` is `fround(1 / Math.sqrt(x))` (one rounding). Transcendental functions are the binary64 `Math` function rounded once; `exp2(x)` is `Math.pow(2, x)`. `radians`/`degrees` multiply once by the binary32 constant nearest `π/180` / `180/π`. `length(f32)` is `abs`, `distance(f32)` is `abs(a - b)`.
6. **CPU results where WGSL is non-portable** (the CPU result is the specified one, `spec/language.md` §6.4). `min(a, b)` is `b < a ? b : a`, except that a NaN operand yields the other operand (two NaNs yield NaN); `max` likewise; between `+0` and `-0` the first operand is returned. `clamp = min(max(x, lo), hi)`, so `saturate(NaN) = 0` and `clamp` with `lo > hi` gives `hi`. `step(edge, x)` is `0` for NaN. `sign(±0) = +0`, `sign(NaN) = NaN`. `round` keeps the sign of zero (`round(-0.25) = -0`). `fract(x) = x - floor(x)` rounded, so a tiny negative `x` gives `1` and `fract(±inf)` is NaN. `pow` has the IEEE 754 / C99 special cases of `libm` (`pow(1, y) = 1` and `pow(-1, ±inf) = 1` for every `y`, where JavaScript's `Math.pow` gives NaN). `normalize(v)` returns the zero vector (positive zeros) whenever the computed length is `0`, which includes vectors whose squared length underflows. `quat.axis_angle` of an axis whose largest magnitude is `0` (NaN components are ignored when finding it) is the identity. `f2i`/`f2u` truncate and saturate at `[-2147483648, 2147483520]` / `[0, 4294967040]` (WGSL §15.7.6; decision 0047 amends the earlier clamp to the integer maxima); NaN gives `0`; `±inf` saturate.
7. **Operation orders** not listed in decision 0026 (every operation rounded; M2-01 folds the M2 intrinsics in the same order so that run-time and folded values agree bit for bit wherever no transcendental function is involved): `dot(a, b) = ((a.x*b.x + a.y*b.y) + a.z*b.z) + a.w*b.w`; `length(v) = sqrt(dot(v, v))`; `distance(a, b) = length(a - b)`; `normalize(v) = v / length(v)` per component (division, not multiplication by a reciprocal); `cross(a, b) = (a.y*b.z - a.z*b.y, a.z*b.x - a.x*b.z, a.x*b.y - a.y*b.x)`; `reflect(i, n)`: `t = 2 * dot(n, i)`, then `i - t * n` per component; `mix(a, b, t) = a*(1 - t) + b*t`; `smoothstep`: `t = clamp((x - e0) / (e1 - e0), 0, 1)`, result `(t*t) * (3 - 2*t)`; `mat4.rotation(q)` with `xx = x*x, …, wz = w*z`: columns `(1 - 2*(yy + zz), 2*(xy + wz), 2*(xz - wy), 0)`, `(2*(xy - wz), 1 - 2*(xx + zz), 2*(yz + wx), 0)`, `(2*(xz + wy), 2*(yz - wx), 1 - 2*(xx + yy), 0)`, `(0, 0, 0, 1)`. `qmul`, `qrotate`, `qaxisAngle`, `qeuler`, `m4mul` and `m4mulv` follow decision 0026 item 6. The renderer's internal matrices (`src/math/mat4.ts`, binary64 intermediates) are not Mtek-visible and keep their own rounding; the `rt` constructors without arithmetic reuse them.
8. **`clampIndex(i, n, spanId, ctx)`** clamps to `[0, n - 1]` and calls `ctx.warn("W8030", spanId)` the first time a given span clamps for a given `ctx` (a `WeakMap` per context); whether the warning is shown (development builds only) is the context's concern.
9. **`color.srgb`** (decision 0024 item 6) uses the folding formula with binary32 constants and `Math.pow` in binary64 rounded once. The golden `tests/semantics/numeric/srgb-fold.json` holds the values the real constant folder produces for 1285 channel inputs (written and checked for staleness by `crates/mtek-compiler/tests/numeric_srgb_golden.rs` through `mtek_compiler::analyze`); `src/math/srgb.test.ts` asserts the run-time values are within **1 ulp** of them (bit-identical on the linear segment). The tolerance of `spec/testing.md` §5 for `pow` is the WGSL bound plus 1 ulp for CPU rounding, so 1 ulp is inside it. Measured: 1177 of 1285 bit-identical, the rest 1 ulp.
10. **The CPU table** `tests/semantics/numeric/cpu.json` (format tag `mtek-numeric-cpu/1`): an object with `$comment` (lines of documentation), `format` and `cases`. A case is `{ "id", "fn", "args", "expect", "portable", "note"? }`: `id` is unique (`<family>#<n>`); `fn` is a callee of item 2 or a comparison (`< <= > >= == !=`); `args` and `expect` are typed values `{"f32": x}`, `{"i32": n}`, `{"u32": n}`, `{"bool": b}`, `{"vec2"|"vec3"|"vec4"|"quat"|"color": [...]}`, `{"mat4": [16 column-major]}`, where every `f32` is a JSON number that is exactly a binary32 value, or one of the strings `"NaN"`, `"Infinity"`, `"-Infinity"`, `"-0"`. The argument types select the overload, so the row is the Mtek expression `fn(args…)` (or `a fn b`); M2-08 can print it as WGSL and M2-07's execution tests as Mtek source. `expect` is the specified CPU result bit for bit (a NaN expectation accepts any NaN). `portable: false` marks cases the GPU need not reproduce: every case with a non-finite input or result (enforced by both validators), `f32` division by zero, `normalize` of a (numerically) zero vector, a zero `axis_angle` axis, `clamp` with `lo > hi`, `smoothstep` with `e0 >= e1`, `min`/`max` with NaN, NaN conversions, and inputs outside the mathematical domain (`sqrt`, `log`, `log2`, `inverse_sqrt` of non-positive values, `asin`/`acos` beyond `[-1, 1]`, `pow` with a negative base or `0^y` for `y <= 0`, `atan2(0, 0)`, `tan` at the pole). Portable cases still have to be inside the input domain of their tolerance entry for M2-08 to compare them (`spec/testing.md` §5); the table does not repeat those domains. The file is canonical (one compact case per line); the independent Rust oracle `crates/mtek-compiler/tests/numeric_cpu_table.rs` (native binary32 arithmetic, `as` conversions, wrapping integers with the WGSL division rules, binary64 `libm` rounded once, and the compiler's own `quat_mul`, `quat_rotate`, `mat4_mul`, `mat4_mul_vec4`) recomputes every expectation and fails when the file differs; `MTEK_BLESS=1` rewrites it, so new rows are added with any `expect` and blessed. The same oracle compares the portable `quat.axis_angle`, `quat.euler` and `color.srgb` rows with the compiler's binary32-`libm` folding (within 1, 2 and 1 ulp).

## Consequences

- M2-07 emits calls through `RT_OPERATIONS` (or the inline forms of item 3) and runs the conformance rows against generated code; generated `app.js` gains its `import * as rt` line (decision 0030 item 3) and its execution test then builds with the real bundle.
- M2-01 folds the M2 intrinsics with the orders of item 7 and the NaN-free subset of item 6; a fold that differs from `rt` beyond the transcendental functions is a defect of one of them. The Rust oracle can switch to the compiler's folding functions once they exist.
- M2-08 reads `cpu.json` (portable cases) and adds `tests/semantics/numeric/tolerances.json`.
- `spec/stdlib.md` §6 names the conformance table `tests/semantics/intrinsics/`; the table lives at `tests/semantics/numeric/cpu.json` as `spec/testing.md` §5 says, and covers the intrinsics too.

## Verification

`packages/runtime-web/src/math/rt.test.ts` (hand-checked semantics, no `Math.round` in the library), `conformance.test.ts` (every `cpu.json` row bit for bit against `rt` and the inline forms; property tests that `+ - * /` equal `Math.fround` of the binary64 operation and are correctly rounded), `operations.test.ts` (index against `spec/stdlib-schema.json`, export surface, entry-module re-export), `srgb.test.ts` (item 9); `crates/mtek-compiler/tests/numeric_cpu_table.rs` and `numeric_srgb_golden.rs`.
