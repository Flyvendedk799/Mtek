# 0098. Runtime benchmark: raw results, the generated report and its verification, and how resource plateaus are judged

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: §12.3, M7; `spec/ai-and-benchmarks.md` section 7; `spec/runtime-abi.md` section 9.3 ("counters at zero live objects after 50 mount/dispose cycles"); `spec/testing.md` section 6.6; decisions 0012, 0095, 0097.
- Supersedes: nothing.

## Context

The acceptance criterion of task M7-04 is "report numbers reproducible from stored raw results; no workload removed after a failure". The report must also say whether the resource counts of the mount/reload/dispose workload **plateau**, and explain what is observed. A statement like "no leak" needs a rule for what counts as a plateau, and the spec's own words ("a bounded plateau", decision 0068 item 7) were about counters of the runtime's registry, not about a JavaScript heap.

## Decision

1. **Raw results** are published under `benchmarks/results/runtime/raw/<run-id>/`: `run.json` (what ran, the commit, whether the tree was dirty, the frozen tree hash and the recorded one, the protocol, the seed, the pass order, versions, the command line, whether a GPU lock was configured), `environment.json` (the environment record of the browser harness: OS, browser and its launch arguments, adapter with `isFallbackAdapter`, adapter features and limits, toolchain), `sizes.json`, one `<workload>--<implementation>.json` per implementation with every pass of every run (raw frame samples in milliseconds rounded to microseconds, raw counters, raw allocation profile summaries, raw startup runs, raw per-cycle records, the host load before and during each pass, the GPU-lock wait, page errors), `floor.json` (the harness floor) and `parity/<workload>--<implementation>.png` (the pictures). Paths and ports are removed before writing (`sanitizeReport` of the browser harness; the evidence sanitiser is also run over the files). Only a complete hardware run is published; smoke runs stay under `benchmarks/runtime/.out/`.
2. **The report is generated, never edited.** `tools/report.ts` reads one run directory and prints `benchmarks/results/runtime/report.md` and `summary.json`; every number in them is computed by `tools/analyze.ts` from the raw files (the percentile of each run, the median across runs, the counters per frame, the ratios against direct). The qualitative text in the report (method, implementations, limitations) is fixed text in the generator and contains no measured number; text that cites numbers (the failing-workload list, what the plateau tables show) is built from the data.
3. **Reproducibility is a test.** `tools/report.test.ts` regenerates the report and the summary from the published raw run and requires them byte-for-byte equal to the committed files; `node tools/report.ts --check` does the same from the command line. It also requires the run to be complete, on hardware (`isFallbackAdapter === false`), not a smoke run, produced under the recorded frozen hash, to have for every workload and implementation at least 600 measured frames after at least 120 warm-up frames in each timing run, and the published results to contain no absolute paths. Statistics are tested on synthetic raw runs against values worked out by hand: a Mtek p95 at +19 % is within the threshold and at +21 % exceeds it; a failed or missing implementation is listed, not dropped; GPU time unavailable is printed with its reason.
4. **Failing workloads in the report.** The summary table has a row per workload, whatever happened; a workload whose Mtek p95 is more than 20 % above the direct reference is marked **exceeds** and listed again with the counters of the same run (draw calls, `writeBuffer` calls, bytes uploaded, CPU split, JavaScript allocation); an implementation that errors (a page error, an uncaptured WebGPU validation error, a lost device, a timeout) or has no raw result is listed with its message and never removed.
5. **The plateau rule.** After every dispose of the cycles workload the page waits 50 ms; the runner then forces a garbage collection through the DevTools protocol and reads the JavaScript heap in use, the DOM node count and the event-listener count; the instrument gives the GPU buffer and texture bytes created and not destroyed, and the devices requested and not destroyed; for Mtek the runtime's live-object counters (`liveBuffers`, `liveTextures`, `liveSamplers`, `liveShaderModules`, `livePipelines`, `liveBindGroups`, `liveListeners`) are read just after `dispose()`. For each series over the cycles the report gives the values at cycles 1, 10, 25 and the last, the least-squares slope over the **last half** of the cycles, and the growth that last half would add again as a percentage of its mean value. A series is a **plateau** when that growth is at most 1 %, **growing** otherwise, and **zero** when it is zero in every cycle. The report does not call anything "leak-free": a plateau of a JavaScript heap is a statement about the observed cycles only.
6. **Two lengths.** The workload is 50 cycles (the number of spec/runtime-abi.md section 9.3); a supplementary run in the same page with the same code does 800, because a heap that is still rising after 50 cycles may be a warm-up (code caches, inline caches, lazily created tables), a staircase (V8 grows its heap by pages, so a flat series can show steps), or a leak, and the longer run separates them better than a cleverer rule. The long run is part of the protocol and of the frozen definitions (`longCycles`), and its table is in the report.
7. **What the page retains.** The page keeps nothing that grows with the number of cycles: each cycle's record is handed to the runner (a first version kept them in the page and added about 2 KB per cycle to every implementation's heap, which showed as growth in the direct reference too and was removed before any reported run), the instrument forgets destroyed devices (`pruneDestroyedDevices`), and a destroyed device's problems are kept as text.
8. **Not observable, so not claimed:** GPU memory (no API), the number of bodies asleep inside Mtek's physics world, and the destruction of pipelines and bind groups (WebGPU has no call); where the report shows these cells they say "not observable".

## Consequences

- A reader can recompute any number in the report from `raw/<run-id>/` with `analyze.ts`; a reviewer can see exactly which raw pass a figure came from.
- A plateau verdict depends on the 1 % rule; the report prints the slope and the growth, so a reader can apply a stricter one.
