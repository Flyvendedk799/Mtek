# 0027. Scene and schema checks: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §3.4 (one registry), §9.4 (diagnostics); `spec/scenes.md` §2–§4, §11, §12; `spec/stdlib.md` §1.1, §3; `spec/materials.md` §2; `spec/testing.md` §3.2; `spec/compiler-architecture.md` §4.7, §9; decisions 0024, 0025, 0026.

## Context

Task M1-11 implements `crates/mtek-compiler/src/types/scene.rs`: the schema checks of scene, camera and entity bodies and of descriptor literals, the camera and entity rules of the M1 subset, and the result the typed IR (M1-12) is built from. The specification fixes the rules and their codes but not every choice an implementation has to make: where rules that name particular fields live, which values must be constant, where each diagnostic points, a few edge cases of the active camera, what the result looks like, and how the catalogue-wide fixture coverage test of `spec/testing.md` §3.2 treats codes no fixture can produce. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Scene rules are registry data.** The checker names no schema and no field (a unit test asserts that no registry schema, field or scene-object keyword appears as a string literal in `types/check.rs`, `consteval.rs`, `scene.rs` or `mod.rs`). The registry model of decision 0024 gains:
   - `Registry.declaration_schemas` (`scene: "Scene"`, `entity: "Entity"`): the schemas of scene and entity bodies; the resolver and the type checker use it instead of their own constants.
   - `SchemaDef.rules: Vec<FieldRule>`: `Requires { field, requires, code }` (`Entity.material` requires `mesh`, `E5020`) and `ExcludedBy { field, excluded_by, code }` (`Camera.rotation` is excluded by `target`, `E5010`). The rule carries the code because the specification gives such rules their own codes (`E5120`, a collider without a body, will be one more `Requires`).
   - `FieldDef.range_code`: the code for a constant outside the field's range: `E5006` unless the specification names another (`E5011` for every `Perspective`/`Orthographic` field, `E5090` for `Entity.scale`).
   - `SceneObjectKind.active: Option<ActiveObject { field, missing, ambiguous }>`: every scene needs an object of the kind (`E5012`) and, with several, exactly one with `field: true` (`E5013`).
   `Registry::validate` checks that rules and active fields name real fields of the right type and that every code is a `5xxx` error. `stdlib-schema.json` is unchanged; exporting these facts (for the AI context export) is left to the task that extends the export.
2. **What is checked.** Every scene the module declares (not only the entry scene), with its cameras and its entities at every depth, and every descriptor literal the type checker typed — in field values and in constants alike. A descriptor is checked for its own fields (unknown, duplicate, missing, type, range, opacity, rules); whether it must be constant is its context's business. Fields, schemas and constructs gated in this build were reported by the resolver (`E9010`) and are skipped; a literal the type checker rejected (`E3041`) has type `Error` and is not reported again; a value rejected by any check causes nothing further (no range check, no active-camera count).
3. **Constant expressions.** A value must be constant where its field is construction-only (`C`), judged field by field inside a descriptor: a construction-only field whose value is a descriptor literal requires constants only in the descriptor's own construction-only fields. So scene fields, `Camera.active` and every value inside `Box`/`Sphere`/`Plane` (and, later, body and collider descriptors) must be constant (`E3090`, at the first non-constant form, with the reason `Typeck::non_constant` records), while the parameters of a material instance and the fields of a projection need not be. In M1 every non-constant value in a field that need not be constant comes from a construct gated in this build (a user function, `state`, `self`, `frame`), already `E9010`, so nothing more is reported; the scene robustness test asserts that a scene without errors has a value for every field.
4. **`E5081`** is reported for a field initialiser — of a scene, a camera, an entity or a descriptor inside them — whose first non-constant form reads a field of an entity **or a camera** (`Cube.position`, `Main.position`): cameras are initialised in the same declaration-order pass as entities (`spec/scenes.md` §11). It replaces `E3090` there. A constant that reads an entity field stays `E3090` (decision 0026 item 8).
5. **Where diagnostics point.** `E5001` at the field name; the message lists the fields the build implements ("Unknown field 'colour' on Unlit. Valid fields: color.", the example of `spec/testing.md` §3.1) and a `help:` names the single implemented field within edit distance 1–2 (decision 0025 item 9; no edit). `E5002` at the second name, related span at the first. `E5003` at the descriptor's schema name or the declaration's name. `E3102` at the value ("Field 'position' of entity 'Cube' expects vec3, but received vec2.", `expected`/`actual` set, a note with the component counts of two vectors; a material field is a "Parameter 'color' of material Unlit"). Range codes at the value; a cross-field range (`far > near`) at the written field of the two, naming the other's value and whether it is a default. `ExcludedBy` at the excluded field, related span at the other; `Requires` at the field that needs the other. `E5100` at the value.
6. **The active camera.** No camera: `E5012` at the scene's name. Several cameras and none declares `active: true`: `E5013` at the scene's name with a related span per camera. Several declare it: `E5013` at the second `active: true`, related spans at the others. The only camera declaring `active: false` is `E5013` too: the scene would render through no camera, which `spec/scenes.md` §3 rules out. A single camera is active whether or not it declares `active: true`.
7. **Opaque colours** (`E5100`) apply to `color` fields of schemas of the category `material` (in M1, `Unlit.color`), whatever the value's form (a literal, a constant, `color.linear(…)`); scene colours accept any alpha (`spec/scenes.md` §2).
8. **Declaration schemas are not descriptors.** `Entity { … }`, `Scene { … }`, `Camera { … }` are `E3001` at the schema name, with a help naming the declaration to write (`entity Name { … }`); their field values are still typed.
9. **`E5092`** counts every static entity of a scene, nested and prefab instances included, and points at the name of the first entity beyond 16 384 (`types::scene::MAX_STATIC_ENTITIES`).
10. **The result** (`Typeck::scenes()`, `Typeck::scene(def)`): a `CheckedScene` per scene with its `fields`, `objects` (cameras, declaration order, the active one marked `active`; `active_object("camera")`) and root `entities`, each `CheckedEntity` holding its `children` (`entities_in_order()` is the stable instance order of `spec/scenes.md` §10.1). Each `CheckedField` has the registry name and type, an `origin` (`Written { span, value }` or `Default`) and the folded `value`, with every descriptor completed: its schema's implemented fields in schema order, written values and registry defaults (`material: Unlit { color: #ffffff }` next to a `mesh`; `projection: Perspective { fov_y, near, far }`). A field neither written nor defaulted (`target`, `mesh`) is absent. With errors, a rejected value is `None` and gated constructs are absent; the typed IR runs only without errors.
11. **Fixture coverage** (`spec/testing.md` §3.2). `tests/fixtures.rs` collects the codes of every expected-diagnostics file and requires each other catalogue code to be listed, exactly once and only while no fixture produces it, as: not implemented yet (with milestone and work item; the allow-list later milestones shrink, empty at M7), unreachable in this build (implemented, but no program this build checks produces it: `E5003`, `E9002`, `E9999`, each with the test that covers it), or covered by another test (codes a fixture cannot express — files the source manager rejects, a missing `mtek.toml`, over 200 diagnostics, over 16 384 entities — and the runtime codes, covered by the runtime's tests). The named test file must contain the code. It replaces the per-area code lists of the earlier fixture tests.

## Consequences

- When a milestone adds a field rule, a range with its own code or a scene-object kind, it adds registry data, not checker code.
- When `state`, `bind` or functions arrive (M2, M3), item 3's "nothing more is reported" no longer covers every non-constant value: the work item that implements them decides which fields accept which values (`spec/scenes.md` §11) and the scene robustness test keeps the completeness invariant honest.
- M1-12 builds the typed IR from `CheckedScene` and never reads registry defaults itself.
- `spec/compiler-architecture.md` §4.7, `spec/stdlib.md` §1.1 and `spec/testing.md` §3.2 point here.
