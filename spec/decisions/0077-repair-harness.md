## Context

`spec/ai-and-benchmarks.md` §4 names the components of the harness (`ModelClient`, `ContextBuilder`, `Editor`, `Validator`, `RepairLoop`, `Recorder`), the integrity rules and the edit format, and leaves open what they have to be exact about: which compiler output each layer of the taxonomy is derived from, what counts as "the feature under test still exists" when a task declares `required_symbols` before the compiler existed, what the whole-file block ends with, what happens to a reply of which only some edits apply, what a truncated or refused generation does to a trial, which budget is which, what a record contains and how it is validated, how a constrained trial is kept apart from an unconstrained one while the grammar adapter (task M6-06, a parallel task) is not here, and how "no language package imports any adapter" is enforced rather than promised. Every item below is a **proposal** (a design choice) unless it restates a rule of the spec or of a decision named above.

## Decision

1. **The workspace (proposal).** `tools/ai-eval` is the npm workspace `@mtek/ai-eval` (in the root `workspaces` and `tsc -b` references; `lint` and `test:unit` run with the others). It is TypeScript that Node 24 runs without a build (`erasableSyntaxOnly`, imports with `.ts`), like `tests/browser/support/mtek-test`. Dependencies: `@mtek/benchmarks` (for its strict TOML subset parser, now exported as `@mtek/benchmarks/toml-subset`, so there is one parser of `task.toml`), the **optional** `@anthropic-ai/sdk` 0.135.0 (used by the `anthropic` adapter only), and `ajv` (tests only, to validate records and the fake compiler's output against the checked-in schemas). The entry point is `src/cli.ts` (`run`, `validate`); `README.md` has the usage.
2. **`ModelClient` (spec 4.1, with additions).** `generate({ system, messages, maxOutputTokens, temperature, stop?, seed?, grammar? }, { signal? }) → { text, usage, finish, error? }` with `finish` one of `stop | length | refusal | cancelled | error`. Differences from the sketch, each so that a record cannot be false: `temperature` may be `null` (no sampling parameter is sent and `null` is what is recorded, because some current models reject sampling parameters and a temperature that was recorded but not applied would be wrong); `usage` fields are `number | null` and `null` means the provider did not report the number (it is unknown, never zero, and a sum with an unknown term is unknown); a client states its `capabilities` (`grammar`, `seed`) and refuses, with an `error` result, a grammar or a seed it cannot forward (the loop also refuses such a run before it records anything); provider failures are returned as `finish: "error"` with a message (a thrown exception is mapped to the same), never as a pass. Everything that is sent is hashed (`requestHash`: system, messages, token cap, temperature, stop, seed, the grammar by its own hash) and the hash is recorded with the full prompt text.
3. **Adapters (proposal).** `replay` (required) reads a JSONL transcript, either plain entries `{ text, finish, usage?, promptHash? }` or the `model-call` records of a recorded run, serves them in order, checks `promptHash` when an entry has one, and answers an exhausted or mismatching transcript with an `error` result. It is the only adapter the unit tests and CI use. `anthropic` uses the official SDK with an injected `fetch`, has no default model (the model id is part of the condition), forwards no seed and no grammar, and reports `inputTokens` as the whole input (`input_tokens` plus cache writes plus cache reads) with `cachedInputTokens` the cache reads, so uncached input is the difference; its `stop_reason`s map to `stop` (`end_turn`, `stop_sequence`), `length` (`max_tokens`, `model_context_window_exceeded`), `refusal` (with the `stop_details` category) and `error` (anything else). `openai-compatible` speaks `POST {base-url}/chat/completions` (hosted and local servers; `length` is truncation, `content_filter` and a `refusal` member are refusals, anything else is an error; seed forwarded, no grammar). `llama-cpp` uses `llama-server`'s `/v1/chat/completions`, forwards `grammar` and `seed`, and defaults to `http://127.0.0.1:8080/v1`. The two HTTP adapters share only the wire format (`src/chat-completions.ts`), not each other. **No key is in the repository**: keys are read from the environment variable named by `--api-key-env` (defaults `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `LLAMA_API_KEY`) when a client is created and appear in no record and no error text. The adapters are loaded lazily by name by `src/adapters/registry.ts` (`import("./anthropic.ts")`), so a replay run never loads another adapter and a missing optional dependency cannot break it. Their unit tests inject a fake `fetch`; the `anthropic` test runs the real SDK on it. `llama-cpp` and `openai-compatible` were never run against a server, and `anthropic` never against the API: nothing here is a statement about any model.
4. **The Editor (spec 4.3; proposals where the spec is silent).** The block format is the spec's. Decided here: (a) the closing marker of a whole-file block is `>>>END`; (b) one `<<<FILE` line may be followed by several `<<<SEARCH` blocks, and only the first `===` line of a block divides it; (c) text outside the blocks (prose, code fences) is ignored; (d) the SEARCH text matches as a substring, **exactly once** (overlapping matches count, so `aa` in `aaa` is two), with no fuzzy matching; zero matches, several matches and an empty SEARCH are rejections, an empty replacement is a deletion; (e) the edits of a reply are applied in order, each against the file as the earlier ones left it, and **atomically**: one rejected edit means nothing is applied, and every rejection is reported at once; (f) a reply that changes nothing is rejected (`no-change`); (g) the only normalisation is `\r\n` to `\n` in the reply (project files are LF, `.gitattributes`); (h) only `mtek.toml` and the `.mtek` files under `src/` can be changed (a host input is declared in `mtek.toml`), never `tests/`, assets or a path that leaves the project; (i) whole-file blocks may replace or create files in a `cold` task, and in an `edit` task only create a file that does not exist ("whole-file blocks only for files the task allows"): rewriting an existing file wholesale is how features get deleted, so it is refused there; (j) the optional JSON transport `{ "edits": [ { "file", "search", "replace" } ] }` of §4.3 is parsed when a reply begins with `{`, and a constrained trial may name the reply format `module`, the whole new content of the entry file. Each rejection has a code (`no-edit-blocks`, `malformed-block`, `json-invalid`, `path-invalid`, `path-not-allowed`, `file-not-found`, `empty-search`, `search-not-found`, `search-ambiguous`, `whole-file-not-allowed`, `empty-whole-file`, `no-change`), says what to do, and for a search that matches nothing names the line where its first line does occur. An unclosed block (what a reply cut off by the token cap looks like) is `malformed-block`.
5. **The layers of the taxonomy (spec 1).** A candidate is validated by fresh processes of the real `mtek` (`src/validator.ts`); each layer is recorded on its own as `pass`, `fail` or `not-run`:
   - `parse`: `mtek check --format json` has no error diagnostic of phase `parse`. `check`: it has no error at all (a syntax error therefore fails both; the layers after it are `not-run`, kind `skipped`).
   - `build` is the spec's "shader/target validation": `mtek build --mode test --format json --out <outside the project>` (the compiler emits and Naga-validates the shaders). Its error codes `E9030`, `E9031` and `E9999` (runtime bundle missing, output not writable, internal error) are failures of the tool chain, not of the candidate.
   - `start` and `tests` come from **one** `mtek test --allow-not-run --format json` per candidate, with the task's `mtek-tests/*.test.toml` copied to `tests/` of the scratch project (decision 0021 item 3). `tests` passes only when the report's status is `pass` (at least one fixture, every fixture passed), fails when a fixture that started failed an expectation, and is `not-run` when fixtures could not run or the program did not start. `start` passes when at least one fixture got past mounting and none failed to mount; it fails on a fixture of kind `mount` or a runtime error reported before the first step (then `tests` is `not-run`, `skipped`); it is `not-run` when no fixture ran. `--allow-not-run` is passed so that the exit code means "failed or not"; the classification comes from the JSON, which is cross-checked against the exit code.
   - **NOT-RUN is not success (decisions 0012, 0074).** A fixture that could not run (no Node, no Playwright, no Chromium, no WebGPU adapter) leaves `start` and `tests` `not-run`, kind `environment`, with the reason (machine paths in it are replaced by `<path>`), and the verdict is `not-run`: the trial ends `not-run`, is counted as neither a success nor a failure of the model, and nothing is repaired (there is nothing to repair). A report whose `fallbackAdapter` is true (a software adapter) is recorded as such: correctness only, never hardware evidence.
   - **The verdict** is `pass` only when every layer and the required symbols pass; `fail` when anything fails; `not-run` when nothing failed but something did not run; `error` when the tool chain failed: the binary is missing or cannot start, a command times out, `mtek` exits with 2 or 3, output is not the documented shape, a report contradicts its exit code (`mtek check` exit 0 with errors, `mtek test` pass with a fixture that did not), a fixture of the task is `invalid-fixture`, or `mtek test` could not build what `mtek build` built. An `error` verdict says nothing about the candidate and ends the trial `error`.
   - **Fresh process, fresh browser context.** Every command is a new process, and `mtek test` opens each fixture in a fresh page of a fresh browser context (decision 0074), so nothing carries from one candidate to the next; each trial has its own scratch copy (`<scratch>/<trial-id>/project`), made from the starter and the fixtures, removed afterwards, with the final candidate (without the fixtures) preserved in the run directory.
6. **Required symbols (spec 4.2, decision 0021).** A task's `required_symbols` are the names **exactly as `mtek context` reports them**: the chain of declaration names (`Demo.Cube`, `Demo.Cube.Marker` for an entity nested in `Cube`, `Flat` for a top-level material). Each is checked with `mtek context --entry <entry> --symbol S --max-bytes 1000000 --format json`: exit 0 and the name listed means present; exit 2 with "no declaration is named" means missing; exit 1 (the project does not load) leaves the check `not-run`; anything else is a tool error. It runs for every candidate whether or not it checks, so a "repair" that deletes the feature under test fails here even when parse, check, build, start and tests pass (the unit test makes the tests vacuous to show exactly that). The check ensures the declaration exists; that it still does its job is what the task's fixtures are for. The seed task `interaction-01` said `Demo.Marker` for what the compiler names `Demo.Cube.Marker` (a prediction written before the compiler existed); `task.toml` now carries the real name. The holdout task was not opened for this record (decision 0021, spec 6.2); a holdout task that names a nested entity or any name the compiler spells differently has the same problem, found at the first run on it.
7. **The loop (spec 4.1; proposals for budgets).** One trial is one task under one condition. Round 0 is the first generation; round n is the n-th repair; there are at most `maxRepairs` repairs (default the task's `max_repairs`, spec 3). Per round: check the budgets, call the model with an `AbortSignal` that fires at the wall-clock budget, record the call, apply the edit, record the edit, validate, record the validation, then stop or send feedback. Budgets: the per-reply cap is the task's `max_output_tokens` (sent as `maxOutputTokens`); the wall-clock budget is its `max_wall_seconds`, checked before every call and aborting a call in flight (a command that is running is not interrupted, bounded by its own timeout instead); `--max-total-tokens` is an optional budget of input plus output tokens over the trial, and a provider that does not report usage cannot enforce it (the trial ends `error` instead of pretending). A call that a budget prevents is recorded as a `model-call` with generation `budget-exceeded` and no request. **A generation that is not `completed` ends the trial as a failure at once**: `length` (truncated), `refusal`, `cancelled` (or the wall-clock abort) and `error` give the reasons `generation-truncated`, `generation-refused`, `generation-cancelled` (`budget-wall-clock` when the budget is what aborted it) and `generation-error`; the reply is neither applied nor repaired nor retried, even when it is a complete, correct edit. A rejected edit is a repair round (spec 4.3) and produces no validation of its own. After the last repair a failing candidate ends the trial `max-repairs`. Success is only a candidate whose verdict is `pass`; the first validated candidate and the final one are both kept in `trial-end` (first-attempt parse, check, start and test success are metrics of their own, spec 6.4).
8. **What the model sees (proposal).** The first message is the task title and prompt, the required declarations, the output of `mtek context` for the task's project (for `edit` tasks seeded with the required symbols, `--max-bytes` default 24000) and the starter's files (`mtek.toml` and the sources). The task's tests are never shown. After a failed candidate the message holds the result of each layer, the **localized diagnostics** (per error diagnostic its envelope as canonical JSON, so `suggestedEdits` and `related` arrive unchanged, and the numbered source lines around its span read from the candidate as it is, at most 12 diagnostics), the missing declarations, the failing tests, and the current text of every file the model has changed (so the next SEARCH can match). After a rejected reply it holds the structured rejections and the current text of the files involved. Test failures are shown with the messages `mtek test` prints (`--test-feedback messages`, the default: what a developer sees) or by name and kind only (`status-only`); the choice is part of the condition. The wording lives in `src/prompts.ts` under `PROMPT_VERSION`, which is part of the condition: changing any wording bumps it. The size in characters of every prompt section is recorded with the call (`promptSections`), so token attribution (spec 6.4) can be done afterwards from the provider's counts; the harness does not estimate tokens.
9. **The Recorder and the schema (proposal).** `records.jsonl` in `<out>/<run-id>/` (default `benchmarks/results/<run-id>/`, never overwritten, `wx`), one record per line, six types: `run-start`, `trial-start` (the condition, its id, the compiler version, the context's hash, size and `truncated` note), `model-call` (the full request, `promptHash`, response, usage, finish reason, generation outcome, error, budget, `startedAt`, `durationMs`), `edit` (applied or rejected edits and the hash of the candidate's sources after the reply), `validation` (every layer, the required symbols, the diagnostics of the failing layer, the test report as the harness read it, the commands run and their exit codes and durations, the tool error), `trial-end` (outcome, reason, calls, repairs, first and final attempt, token totals, duration, where the final candidate was preserved). The schema is `spec/ai-eval-record.schema.json` (JSON Schema 2020-12, version 1, unknown keys forbidden, with conditional rules: `completed` only for finish `stop`, a `pass` verdict only with every layer `pass`, a `success` only with a final `pass`, an `unavailable` trial with no calls). **Deterministic**: canonical JSON (keys sorted, no whitespace), a `seq` instead of reliance on file order, no absolute path, scratch location or host name, and the only clock readings are `startedAt` and `durationMs`, taken from an injected clock, so equal runs under an equal clock write equal bytes (tested). A **condition** is the provider, model, temperature, token cap, stop sequences, seed, prompt version, feedback mode, context budget, repair, wall-clock and token budgets, trial kind and reply format; `conditionId` is the SHA-256 of its canonical JSON, so changing any part is a new condition (spec 4.2). A recorded run is a valid replay transcript.
10. **Trial kinds and the boundary with M6-06 (proposal).** Constrained and unconstrained trials are separate trial kinds in the records and separate conditions (the M6 exit gate requires it). `src/grammar.ts` defines `GrammarCapability.check(client)`, answering either `available` with `grammar` (the GBNF text), `backend` (a label for the one supported combination) and `replyFormat` (`edit-blocks` or `module`), or unavailable with a `reason`. This workspace does **not** depend on M6-06's code: `defaultGrammarCapability` honestly reports unavailable. A constrained trial asks first; if the answer is unavailable, or the client cannot forward a grammar, the trial ends `unavailable` with the message **"grammar-constrained mode unavailable"** followed by the reason, with no model call, and is **never run unconstrained instead**. When available, every request of the trial carries the grammar and the reply is read in the declared format. The orchestrator wires M6-06's real check in after both tasks are merged, by giving `RepairLoop` a `GrammarCapability` (a few lines in `src/cli.ts`). **Wired (2026-10-19):** `src/command-grammar.ts` runs M6-06's `grammar-adapter check --format json` and `mtek grammar export --format gbnf` as commands (so the workspace still imports no adapter code), and `src/cli.ts` uses it for `--trial-kind constrained` when the binary is named (`--grammar-adapter`, `MTEK_GRAMMAR_ADAPTER`) or built in the repository; otherwise the default stays unavailable. It is unavailable here whenever the pinned backend and model are not installed (`tools/grammar-adapters/.cache`), with the adapter's own reason; `test/command-grammar.test.ts` (10 tests) covers every unavailable path with scripted programs. No constrained trial has been run against a real model by this repository's tests. The `llama-cpp` adapter forwards `grammar`; whether a server honours it is the capability check's business, and an adapter that forwards it is not a claim that constrained decoding works.
11. **The dependency boundary is a check (decision 0003).** `src/check-boundary.ts` reads imports (static, type, re-export, dynamic, `require`, multi-line; comments ignored) and the manifests, and fails on: a file of `packages/*` or `crates/*` that imports `@mtek/ai-eval`, a path into `tools/ai-eval`, an adapter or an inference provider's library, or a `package.json` or `Cargo.toml` of theirs that depends on one (`language-package`); a module of the harness core that imports an optional adapter or a provider library (`core-adapter`); an adapter that imports another adapter or the registry, any provider library but the Anthropic SDK in `anthropic`, or a registry that imports an optional adapter statically (`adapter-isolation`); a provider library that is not an `optionalDependency` of the harness (`optional-dependency`). It runs in `npm run lint -w @mtek/ai-eval` (so in `npm run check`) and in the unit tests, which run it on the repository and on synthetic trees with one planted violation per rule (so a scanner that finds nothing fails).
12. **Evidence run (not a model result).** `evidence/M6/ai-eval/` holds the `validate` output for the starters and the references of the four seed tasks on a hardware adapter, and two runs of the loop through the replay client with hand-written transcripts on the real compiler and browser (`transcripts/`): `interaction-01` solved by one edit, and `maintenance-01` where the first reply "repairs" by deleting the right cube (the required symbol and the fixture fail), the second is rejected (its search matches nothing any more) and the third restores the cube with the real fix. Token counts in them are `null` (replay).
13. **Not decided here (limits).** Token attribution by section (item 8) is sizes in characters; the harness does not run models, so no completion rate, tokens per task or any other §6.4 aggregate is computed (an aggregator over `records.jsonl` and `report.md` belong to M7); there is no retry of a failed generation (a retry is a different condition); a `mtek` command that is running is not interrupted by the wall-clock budget, only by its own timeout (check 60 s, build 120 s, context 60 s, test 900 s); the start layer is derived from `mtek test`, not from a separate smoke run, so a program that mounts but has no fixture reaching `step` is not distinguished from one that starts (tasks always have fixtures: a task without them is refused); only `web` and the `test` build mode exist; candidates are untrusted programs that run only inside `mtek test`'s browser with its per-fixture timeout (120 s, failure kind `timeout`), and the harness adds no sandbox of its own (`spec/ai-and-benchmarks.md` §5: compiler correctness is not a sandbox), so it belongs on a machine where running generated programs in a browser is acceptable.
14. **The Mtek side of the seed tasks is verified (follows `benchmarks/README.md`).** With the harness the references and starters of the four tasks in `benchmarks/tasks/` were compiled and run (item 12). `mtek_side_status` is `verified` for those four, their `// UNVERIFIED` header comments are removed, and the README table says what was measured. The holdout task keeps `unverified-until-M6`.

## Consequences

- `spec/ai-and-benchmarks.md` §4 and `spec/testing.md` point here; `spec/ai-eval-record.schema.json` is the schema of the records; `tools/ai-eval/README.md` is the usage.
- Wiring M6-06 is one `GrammarCapability` implementation passed to `RepairLoop`; until then every constrained trial is `unavailable`, which is the honest state.
- Any task whose `required_symbols` are not names the compiler reports fails every candidate at the symbols check; `npm run check:tasks` still only checks that the words occur in the sources. A check that the starters of edit tasks declare their required symbols with `mtek context` would close that gap and is a candidate follow-up.
- The `@anthropic-ai/sdk` optional dependency adds one package (and its few dependencies) to `package-lock.json`; replay runs never load it.
- The four seed tasks' Mtek side is now verified, so a failing candidate on them is a statement about the candidate, not about the task.
