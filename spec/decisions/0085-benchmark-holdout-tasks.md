# 0085. The benchmark holdout set completed to eight tasks, its re-hash, and the verification of its Mtek side

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-08; blueprint §12.2 (30 tasks plus a holdout of 8, never used while designing syntax, docs or context); `spec/ai-and-benchmarks.md` §6.2 and §6.3; decisions 0021 (task format, the holdout rules, the tree hash, the identifier scan), 0074 (`mtek test`), 0077 (the repair harness, the verification layers, required symbols as the compiler reports them).
- Supersedes: nothing. Completes the holdout half of `spec/ai-and-benchmarks.md` §6.2 ("a holdout set of 8") and the sentence of `benchmarks/README.md` that listed the seven further holdout tasks as not started.

## Context

M0 delivered one holdout task and its hash. Task M6-07 verified the Mtek side of the four seed tasks in `benchmarks/tasks/` and deliberately did **not** open the holdout (it is "never used while designing syntax, docs or context"), so the Mtek side of the one holdout task stayed `unverified-until-M6`. Task M6-08 owns the whole benchmark set; its holdout part is written and verified by one worker who is the only one allowed to touch `benchmarks/holdout/` and `benchmarks/holdout.sha256`. This record says what the set now is, how it was made, what was verified and what was not. **It names no task, prompt or solution**: decisions are read by everyone who designs the language, and the identifier scan of decision 0021 item 7 fails the build if a file under `spec/` contains a holdout task id (so this record refers to the tasks by number and category only). Every item is a **proposal** unless it restates a rule of 0021 or 0077.

## Decision

1. **The set.** Eight tasks in `benchmarks/holdout/`: the existing one and seven new ones. Mix by category: **3 scene-rendering** (all cold), **2 interaction** (edit), **1 shader-bridge** (edit), **2 maintenance** (edit). The main set's 10 / 8 / 6 / 6 scaled to eight tasks is 2.7 / 2.1 / 1.6 / 1.6; every category has at least one task, and the two categories that round up are scene-rendering and maintenance (the work item's proposal, followed here; 3 / 2 / 2 / 1 is as close and was not chosen). The existing task was scene-rendering, so the seven new ones are 2 scene-rendering, 2 interaction, 1 shader-bridge and 2 maintenance.
2. **Skill areas** (coarse on purpose). Scene-rendering: composition of transforms through a parent chain; depth ordering, visibility and a flat floor. Interaction: discrete selection state driven by key presses; a timed state machine driven by frame time. Shader-bridge: scalar and colour material parameters that follow scene state written by host inputs. Maintenance: behavioural defects in a time-driven animation (frame-rate independence, parent-relative placement, rotation sense); a project with one compile-time diagnostic and one behavioural defect in a key-driven display.
3. **Distinctness from the 30 main tasks** was a design constraint, not a result: the seven tasks were designed from the format of the four seed tasks only, without reading the other main-set tasks (four other workers wrote them in parallel). Overlap in skills with the 30 was therefore **not checked**; the orchestrator should compare the lists of skill areas when the branches are merged.
4. **Where the expected values come from.** Every fixture of the new tasks is derived from the task statement, never from running a reference: an independent f64 ray caster of the described scene (spheres, boxes and a plane under a perspective or orthographic look-at camera, with the parent chain composed as `T · R · S`), a pinhole projection for the one task whose picture is a single face, and a small state model (key presses, frame time, limits) for the interaction and maintenance tasks. The derivation is the comment at the top of each fixture file. Probes keep at least 1 pixel from a box silhouette and 2 to 3 pixels from a sphere (so the different tessellation of the two sides does not matter) and at least 2.4 pixels from a shader boundary. Each fixture set contains retention checks (behaviour that must survive the edit) where the task is an edit.
5. **One definition of success for both sides** (decision 0021 item 8). The same `mtek-tests/*.test.toml` run through `mtek test` (Mtek) and through the baseline interpreter (three.js WebGPU/TSL). Only pixel expectations are used. The baseline support module offers key-down handlers and host inputs but no key-up or polling hook, so no holdout interaction task needs a key release or `is_key_down`. The support module and the validator were not changed.
6. **Maintenance and the baseline's type check.** `benchmarks/baselines/support/test/starters.test.ts` requires every holdout baseline starter to type-check. The two maintenance baseline starters are therefore type-correct and wrong in behaviour. In one of them the Mtek starter additionally has a compile error (`starter_diagnostics`, the single-writer rule): its baseline counterpart is the same mistake as a run-time defect (a handler's write is overwritten by the per-frame update). The two sides of that task thus do not fail in the same way until the repair is made; this asymmetry is deliberate and is a property of the languages, not of the fixtures.
7. **A correction in the existing task.** Its `required_symbols` named a nested entity by its bare name; the compiler reports a nested entity with its parent's path (`mtek context --symbol`, decision 0077 item 2), so the entry was wrong and the harness reported the symbol missing even for a correct solution. It now carries the compiler's path. Its reference lost the `UNVERIFIED` header with the status change below.
8. **Verification status.** `mtek_side_status = "verified"` was set for all eight tasks only after the harness (`tools/ai-eval validate`, decision 0077) reported, on the hardware adapter, for the Mtek reference of each: parse, check, build, start and tests **pass**, every required symbol found; and for the Mtek starter of each: the outcome its mode declares (a cold task's empty starter does not check; an edit starter fails its tests, except the retention fixtures, which pass; the one starter with a declared diagnostic fails `check` with exactly that code and no other). The baseline reference of each task passes its fixtures on the hardware adapter and the baseline starter fails as intended (retention fixtures pass). Counts are in `evidence/M6/benchmark-holdout/` (task ids, layer outcomes and counts only: no fixture names, no messages, no prompt or solution text).
9. **Mutation check of the fixtures.** Ten plausible wrong solutions of the baseline references (the kind of mistake a model makes: a missing limit, a missing wrap, a position in the wrong frame, a frame-rate dependent step, a parameter that is ignored) were run against the fixtures of the five tasks they belong to; the count of the ones that fail at least one fixture is in the evidence (counts only). This shows that the fixtures can tell a plausible wrong answer from the right one; it does not show that no wrong answer passes.
10. **The hash and the leak scan** work as in 0021 items 5 and 7: `node benchmarks/tools/hash-holdout.mjs` hashes every file below `benchmarks/holdout/`; `--write` recorded the new value in `benchmarks/holdout.sha256` in the commit that added the tasks; `npm run check` (`check:tasks`) recomputes it and scans `spec/`, `tools/`, `packages/`, `crates/`, `scripts/`, `docs/` and `benchmarks/tools/` for the eight ids. The scan found none; the evidence directory is outside the scanned directories and does name the ids.
11. **Exposure.** The author of these tasks is an agent that had the full specification and the compiler, and that ran the references; the holdout is therefore not blind to its author. The rule "never used while designing syntax, docs or context" holds from here on and is what the hash and the scan protect; the hash only makes a later edit detectable. The exposure already recorded in `benchmarks/README.md` (integrity log) is unchanged. Nothing in the language, the documentation or the context export was changed from anything seen in the holdout.

## What was not verified

- Only one machine and adapter (Windows 11, AMD Radeon RX 7900 XTX, Chromium 153, new headless): no Linux or macOS run, no software adapter, no second GPU.
- Nothing about models: no model has attempted any holdout task, so difficulty is a design intention, not a measurement.
- The fixtures are validated by three agreeing sources (the independent model, the three.js baseline and the Mtek runtime), not by a second Mtek implementation.
- Skill-area overlap with the 30 main tasks (item 3).
- That the baseline's TSL idioms are the idiomatic ones for r186; the references are correct, not necessarily what a model would write.

## Fixtures/Tests

## Verification

Run on 2026-10-18 on the machine of item "not verified" above: `tools/ai-eval validate` on the reference and the starter of every task; `MTEK_REQUIRE_GPU=1 npm run test:benchmarks -- holdout` (reference) and with `MTEK_BASELINE_SOURCE=starter`; the ten mutants with `MTEK_BASELINE_DIR`. Results: `evidence/M6/benchmark-holdout/`: Mtek side, 8 of 8 references pass every layer and 21 of 21 fixtures; 8 of 8 starters behave as declared (the 3 empty cold starters do not check, 1 starter fails `check` with its declared diagnostic code and no other, 4 build and fail their tests, where 3 retention fixtures pass and 11 other fixtures fail); baseline side, 21 of 21 reference fixtures pass, 17 of 21 starter fixtures fail and the 4 that pass are retention fixtures; 10 of 10 wrong solutions are caught. `npm run check` is clean (including the new hash) and `npm run test:unit` passes (3 805 tests, 1 skipped, across the workspaces; the benchmark package's 88 include the type check of every holdout baseline starter and reference). No Rust or runtime code was changed, so `cargo test` was not rerun.
