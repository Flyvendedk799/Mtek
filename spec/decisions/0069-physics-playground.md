# 0069. The physics playground: the example, its seed and geometry, the model the browser spec derives its numbers from, the ownership fixture and the check of every example

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M5 (blueprint §11), task M5-07; blueprint §3.3 (the `Playground` scene) and §8; decision 0002 (the three release demonstrations: the second is `examples/physics-playground/`); `spec/physics.md` §§2, 3, 6, 7; `spec/scenes.md` §§8.2, 8.3, 9, 10; `spec/stdlib.md` (`random`); decisions 0062 (prefabs), 0064 (spawn, destroy, `entity_ref`), 0065 (ownership checks), 0066 (the tick, command categories, event delivery, `ctx.body`).
- Supersedes: nothing.

## Context

Decision 0002 names the physics playground as the demonstration whose pressure is "rigid bodies, colliders, impulses, sensors, collision events, single pose ownership, spawn/destroy". Everything it needs exists since M5-05 (0066); what was missing is a program a reader can run that uses all of it together, and a browser test that proves the combination on the real engine and the real GPU with numbers that are derived, not read back. The task's own wording leaves open which features of the language the example may rely on, how a spec can know where a seeded crate lands, and what "dynamic transforms cannot be written by handlers" is a fixture of, given that `tests/semantics/fail/e5071_*` already covers every shape of the write. Every choice below is a **proposal** the owner may overrule.

## Decision

1. **The example** is one module, `examples/physics-playground/src/main.mtek`, and a `mtek.toml` with no host inputs. The scene `Playground` has a static `Floor` (14 x 1 x 8, top face at y = 0), a named instance `First` of the prefab `Crate` (a 2 kg dynamic unit cube) resting at x = -4.5, a static `Zone` (a 4 x 2 x 6 **sensor** box at (4, 1.5, 0)), a `ZoneMarker` (a thin plate that draws where the zone is, because the sensor has no mesh), a `Meter` (a bar whose `position` and `scale` are `bind` expressions of the state `entered`), a camera, a sun and a little ambient light. Space calls `First.body.apply_impulse(vec3(0.0, JUMP_IMPULSE, 0.0))` with `JUMP_IMPULSE = 10.0`; C spawns `Crate { origin: vec3(x, SPAWN_HEIGHT, z) }` with `x = (random() * 2.0 - 1.0) * SPAWN_RANGE_X` and `z` likewise (`SPAWN_RANGE_X = 9.0`, `SPAWN_RANGE_Z = 2.5`, `SPAWN_HEIGHT = 6.0`). The module constants are the only numbers the browser spec reads from the source; the rest of the geometry is transcribed in the model (item 5) and a unit test checks that every transcribed line occurs in the source.
2. **A crate removes itself.** `Crate.fixed_update` destroys `self` when `self.position.y < KILL_HEIGHT` (`-10.0`). The scene cannot do it: a sweep over stored `entity_ref`s would have to read each crate's height, and a read through an `entity_ref` is `E5074` (`spec/scenes.md` §8.3). Reading `self.position` of a dynamic body is allowed and returns the pose the solver wrote last tick; `destroy(self)` is queued and the body leaves the world at the next flush (0066 items 4 and 8), so the removal is visible one tick after the check that decided it.
3. **The floor is narrower than the spawn area** (14 units against 18), so a crate whose footprint is clear of the floor falls past it and is destroyed: destruction needs no extra key or timer. A crate that straddles the end of the floor tips off in a way the geometry does not settle, so the browser spec refuses a seed that produces one (item 6).
4. **The sensor floats half a unit above the floor** (y from 0.5 to 2.5). The adapter gives every collider `ActiveCollisionTypes.ALL` (`spec/physics.md` §5.1), so a sensor that touched the floor would report the floor as an overlap; at 0.5 only crates reach it, and a crate resting on the floor (centre y = 0.5, extent 0 to 1) overlaps it for good, so `inside` equals `entered` once everything has come to rest. The handlers skip `First` (`other != First`: an `entity_ref` may be compared with a named entity) so that `entered` counts crates only. `entered`, `inside` and `spawned` are scene `state`, which is how the spec (and a host page) read the count; the visible count is the `Meter`, a `bind`-driven bar, because the task does not ask for a text-rendering feature and `bind` is the supported way to show state.
5. **The model** (`tests/browser/support/m5-playground.ts`, unit-tested by `m5-playground.test.ts`) knows nothing of the runtime. It reads the five constants from the source and transcribes the geometry; it has its own xoshiro128** with splitmix32 seeding written from the reference algorithms, with every operation of the spawn expression rounded to binary32 (a test pins the six positions of seed 166 against the runtime's generator and every later position is then the model's); it classifies a crate (`zone`, `floor` or `off`) from its x; it derives times from the engine's substepped free fall of 0063 (`fallDistance(n) = g dt² (n²/2 + n/8)`, `fallTicks(d)` the first `n` that reaches `d`); the lift of an impulse (`v = J/m`, rise `v²/2g`, time `v/g`); and the meter's silhouette by projecting its eight corners through the camera (a pinhole with the camera's position, target and field of view, a test checks the projection by hand-derived cases).
6. **What the spec asserts, and why those tolerances** (`tests/browser/specs/m5/playground.spec.ts`, hardware adapter, manual clock, frames of exactly the manifest's `fixedStep` so that one frame is one tick, decision 0066 item 12). All expected values come from the model:
   - *Lift.* After 60 ticks `First` rests at y = 0.5 (10 mm, `spec/physics.md` §7). After Space, with J = 10 N·s and m = 2 kg, v = 5 m/s and the peak is 5² / (2 · 9.81) = 1.2742 m above the rest height, measured within 2.5 cm (the engine's substeps lower the peak by about `v·dt/2` = 10 mm); the apex tick is within two ticks of `v/g/dt` = 30.6; `First` comes back to rest at 0.5 and has not moved sideways.
   - *Crates.* The six seeded spawns appear at the model's x and z and at `6 − fallDistance(1)` (they are created at the flush of the tick after the press and stepped by it, 0066 item 4). Each crate that lands on the floor rests at y = 0.5 within 10 mm and moves less than 2 mm over its last ten ticks. It ends within 3 cm of where it was dropped: every crate slides by the same 1.5 cm in x and 1.0 cm in z at the impact (a landing at 10.8 m/s; the solver's contact order, not a position effect), so the tolerance is stated as the engine's slide, not as zero.
   - *Sensor.* `entered` is constant until a zone crate arrives and then rises by exactly one, at a tick in `[fallTicks(3), fallTicks(3) + 2]` = `[47, 49]` (the crate's bottom meets the zone's top when its centre is at y = 3; events lag the poses by one step, 0063); it never changes for a crate that rests outside the zone or misses the floor; `inside` equals `entered` at the end of every cycle; the totals are `entered = inside` = the number of zone crates.
   - *Destroy.* A crate that misses the floor is destroyed at a tick in `[fallTicks(16) + 1, fallTicks(16) + 3]` = `[110, 112]` (it passes y = -10 at tick 109, its `fixed_update` sees it at tick 110 and the flush is at the start of tick 111); at that tick `physicsBodies` and `liveEntities` drop by exactly one, `entitiesDestroyed` rises by one, no spawned entity of its generation is left; at the end `entitiesSpawned`, `entitiesDestroyed`, `liveEntities`, `physicsBodies`, `physicsColliders`, `pendingSpawns`, `pendingRemovals`, `physicsSteps` and `physicsFrozenBodies` equal the arithmetic of the six fates; no runtime diagnostic is reported anywhere.
   - *Meter.* The columns the bar's pixels cover agree with the projection of the derived box within 2 px with no entry and with two.
   - *Seed.* The same seed gives the same three positions in two mounts and another seed gives others, and they equal the model's.
   - *Preconditions.* The seed is chosen so that every crate has a certain fate (`MARGIN = 0.1` from every boundary) and no resting crate is within `1.3` (one crate plus 0.3) of `First` or of another; the spec throws if a change of the program or the seed breaks that, instead of becoming flaky. Seed 166 gives two crates in the zone (x = 5.96 and 2.55), two on the floor outside it (x = -0.23 and -3.08) and two past the floor (x = -7.96 and 7.87).
7. **The compile-time fixture and the check of every example.** `tests/semantics/fail/e5071_playground_pose_writes` is the playground-shaped program with the three mistakes its handlers avoid (lifting `First` by `First.position.y += 5.0`, putting a fallen crate back with `self.position = ..` in the prefab, resetting `First.rotation`): three `E5071`, each naming the entity or prefab and the commands that are allowed. It adds the combination (prefab `self` write, named prefab instance write, component compound assignment) in one program of the example's shape; every single shape was already covered by the `e5071_*` fixtures and none was removed. The new CLI test `writing_the_pose_of_a_dynamic_body_in_the_physics_playground_is_e5071` takes the real source of the example, asserts that two literal lines are there, edits them into writes and requires exactly two `E5071`, so the fixture cannot drift from the example. `every_example_checks_without_diagnostics` runs `mtek check` on every directory of `examples/` (there was no such test; the configurator and the playground are now covered and a later example is covered when it is added).
8. **Build.** Global setup builds the example with `mtek build --mode test` into `.out/m5-playground/` (`support/m5-playground.ts`), like the configurator; a build that fails fails the run. The example's own page is the ordinary one: `mtek dev examples/physics-playground` serves it, and the 4.4 MB physics module is requested only because the manifest names it.
9. **No defect was found.** The example compiled and ran on the first attempt; nothing in the compiler or the runtime was changed by this task. One behaviour is recorded rather than fixed because it is the engine's and not a defect: a flat crate landing at 10.8 m/s slides 1.5 cm in x and 1.0 cm in z before it rests, identically for every crate (item 6).

## Not covered (stated, not claimed)

- Only the hardware adapter of the recorded machine ran the spec; the software project runs it too and is informational.
- Frames are produced with the manual clock into an offscreen target; the on-screen loop of `mtek dev` and real keyboard input are not asserted by pixels in this task (the harness injects the keys).
- The sensor's exit event is exercised only through `inside` staying equal to `entered` for resting crates; a crate leaving the zone is covered by the engine-level tests of M5-06, not here.
- A crate that straddles the end of the floor, a crate that lands on another, and long runs of many spawns are not part of the derivation; the seed is chosen so that none occurs.
- Hot reload of the example is not asserted (0066 item 13 and the reload tests cover it).

## Fixtures and tests

- `examples/physics-playground/` (the example and its README); `tests/semantics/fail/e5071_playground_pose_writes/` (blessed with `MTEK_BLESS=1 cargo test -p mtek-compiler --test fixtures`).
- `crates/mtek-cli/tests/cli.rs`: `every_example_checks_without_diagnostics`, `writing_the_pose_of_a_dynamic_body_in_the_physics_playground_is_e5071`.
- `tests/browser/support/m5-playground.test.ts` (10 unit tests of the model), `tests/browser/specs/m5/playground.spec.ts` (3 hardware specs). Mutation checks run by hand and reverted: halving the impulse fails the lift spec (rise 0.96 m too low), `sensor: false` fails the sensor spec at the first zone crate, replacing `destroy(self)` fails the destroy spec at the first crate that misses the floor.

## Consequences

- `README.md`, `spec/testing.md` and `spec/physics.md` §7 point here; `spec/decisions/0002-initial-use-case.md` is unchanged (the directory it names now exists).
- The coverage matrix that M7 requires (decision 0002) can read this example for: dynamic and static bodies, sensors, collision events, body commands, `spawn`/`destroy`, `random`, prefab instances, `bind` beside physics; the configurator exercises none of them.
