# 0032. The `mtek` command line tool: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §10 (tooling), §13 (one library API, never panic); `spec/tooling.md` §1–§3; `spec/compiler-architecture.md` §3, §4.1, §4.12; `spec/diagnostics.md` §2.2, §4; `spec/runtime-abi.md` §2; decisions 0007, 0028, 0030.

## Context

Task M1-19 implements `mtek check`, `mtek build`, `mtek inspect --ir` and `--version` in `crates/mtek-cli`, the real file system behind the compiler's `Fs` trait, and the embedding of the runtime bundle. The specification fixes the commands, their options, the exit codes, the rule that `--format json` prints exactly one document on stdout, colour only on a terminal without `NO_COLOR`, replace-on-success, and `catch_unwind` → `E9999`. It does not fix what the commands print besides diagnostics, which stream decides about colour when diagnostics go to stderr, how an I/O failure is reported in a JSON report, where `--out` is relative to, how `PATH` is searched on disk, or how the bundle reaches the binary. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Arguments** (`clap` derive, decision 0007). `--version` prints exactly the line of `spec/tooling.md` §1 and conflicts with every other argument. `--help` (of the tool or a command) prints to **stdout** and exits `0`; no command at all is a usage error. Everything the specification names for a later milestone is a usage error (exit `2`) that names it and its milestone instead of clap's "unrecognized subcommand": `mtek dev` (M1, a later task), `new` (M3), `fmt`, `test`, `context`, `grammar`, `lsp` (M6), `build --mode preview` (M6) and `inspect --bindings`/`--shaders` (M2). These commands are hidden from `--help`. So the library's `E9010` for `BuildMode::Preview` (decision 0030 item 1) is not reachable from the command line until M6. `--target` accepts only `web`. An `--out` without a final directory name (`.`, `..`, a root, empty) is a usage error. *Amended by decision 0044 item 12: `inspect --bindings` and `--shaders` are implemented since M2-09.*
2. **Finding the project.** `PATH` (default: the working directory) is made absolute against the working directory with `.` and `..` resolved lexically; a file starts the search at its directory, a path that does not exist at its nearest existing ancestors (as `ProjectRoot::discover` does). The tool walks up the real directory tree looking for a file named exactly `mtek.toml`, then roots its file system at that directory and calls the library with `ProjectRoot::at_base()`, so every path the compiler sees and reports is project-relative. The `E9004` texts are the library's (`ProjectRoot::not_found`, `ProjectRoot::unreadable`, shared with `discover`); the place is "the current directory" without `PATH`, otherwise `PATH` as the user typed it.
3. **`RealFs`** compares every segment of a path with the directory listing of its parent (`OsStr` equality), so a different case is `NotFound` on every operating system, and reads a file only after that check. Directory entries whose names are not UTF-8 are left out of listings (no `ProjectPath` can name them). Error messages carry the project-relative path and the operating system's message, never an absolute path.
4. **Streams.** `--format json`: stdout holds exactly one document and stderr nothing — the report (`spec/diagnostics.md` §2.2) for `check` and `build`, the IR for a successful `inspect --ir`. `inspect --ir` with errors prints the report instead of the IR (exit `1`); the warnings of a successful inspection have no place in the IR document and go to stderr in human form in both formats. `--format human`: diagnostics on stderr; on success one line on stdout (`checked 'demo': 0 errors, 1 warning`; `built 'demo' (release): 9 files in dist, build 7c4846274cc3a51e; 0 errors, 0 warnings` — the first 16 hex digits of the build id, the output directory as given by `--out` or as `build.out_dir` relative to the project) or the inspection; on failure the line `<command> failed: N errors, M warnings` on stderr. Usage errors print to stderr only, in both formats.
5. **Colour** is decided for the stream the diagnostics are written to: stderr must be a terminal, and `NO_COLOR` must be absent — set to anything, including the empty string, disables colour (`spec/diagnostics.md` §4 says "stdout is a TTY", written when diagnostics and output shared a stream; the intent is "the reader is a terminal"). `clap`'s own colour feature is not used.
6. **Exit codes.** `0` no error; `1` the report has an error; `2` usage error, including an output directory that would replace the project (item 8); `3` the report contains `E9999` or `E9031`. `E9999` wins over `1` when both kinds are present.
7. **Panic safety.** The whole command — discovery, compilation, rendering and writing `dist/` — runs on a thread named `mtek-compiler` with a 16 MiB stack inside `catch_unwind`; only argument parsing and the final writes to stdout/stderr run on the main thread. A panic hook replaces the default one (which would print to stderr) and records `panicked at <file>:<line>:<column>:\n<message>`; the result is a report with the single diagnostic `E9999` "The compiler stopped because of an internal error; this is a compiler bug.", that text as a note, the help "please report it with the program that caused it and this message", `project: null`, exit `3`. Failing to start the thread is reported the same way.
8. **`mtek build` output.** `--out DIR` is relative to the working directory (like any path argument); without it the output goes to `build.out_dir` relative to the project root. Before writing, the tool refuses (exit `2`) an output directory that is the project directory, contains it, or contains one of the build's source files, comparing the lexical paths and, if the directory exists, the canonical ones — replace-on-success would otherwise delete the project. The file set is written with `dist::write_dist` (decision 0030 item 10).
9. **`E9031` "build output not written"** (new, `spec/diagnostics.md` §5.9): a write that fails is reported as a diagnostic so that `--format json` still prints one report: phase `emit`, no source location, message `Could not write the build output to '<out as shown in item 4>' (<operating system message>).`, the note that the previous output is left in place and a help line; it follows the build's other diagnostics without a location and counts as an error; exit `3` (an I/O failure in `spec/tooling.md` §1). A new code rather than `E9999`, because it is not a compiler defect.
10. **Embedding.** `build.rs` always prints `cargo::rustc-check-cfg=cfg(mtek_runtime_embedded)` and `cargo::rerun-if-changed` for `packages/runtime-web/dist/runtime.js` and `runtime.d.ts`. When **both** exist it copies them into `OUT_DIR` (`src/runtime.rs` includes the copies with `include_bytes!`, which avoids writing a host path into generated Rust) and sets the cfg; with one or none, nothing is embedded and `mtek build` reports `E9030` from the library. It never runs npm. Two consequences of Cargo's change detection: while the files are missing the build script reruns on every Cargo invocation (a missing `rerun-if-changed` path is always stale), so `mtek-cli` is rebuilt each time — about a second; and files restored with old modification times (for example moved back) are not noticed until they are touched or rebuilt (`npm run build` writes `runtime.js` afresh).

## Consequences

- One new dependency, `clap` =4.6.7 (allow-listed in `spec/compiler-architecture.md` §2), and two dev-dependencies already in the workspace, recorded in decision 0007. One new diagnostic code, `E9031`, covered by `crates/mtek-cli/tests/cli.rs` (listed in `COVERED_BY_OTHER_TESTS` of `crates/mtek-compiler/tests/fixtures.rs`).
- The CI `node` job runs `cargo test -p mtek-cli --locked` after `npm run build`, so the embedded path is tested there and the path without the bundle in the `rust` job.
- M1-21 (browser fixtures): build each fixture with `mtek build --mode test --out <dir> <fixture>` from a CLI built **after** `npm run build`; exit `0` and the `dist/` tree of `spec/runtime-abi.md` §2 mean success, `--format json` gives a machine-readable report.
- M1-20 (`mtek dev`): replace the hidden `Dev` stub in `crates/mtek-cli/src/args.rs`; reuse the build path in `commands.rs` (`build_project`, `dist::write_dist`), the `Outcome`/`Printer` model and `guard::run_guarded` per rebuild.
- `spec/tooling.md` §1 and `spec/diagnostics.md` §5.9 point here.

## Verification

`crates/mtek-cli/tests/cli.rs` (the binary in temporary directories: `--version`, `--help`, usage errors with nothing on stdout, `check` success and errors in both formats with schema-valid reports and no absolute paths, warnings, project discovery from subdirectories, files and missing paths, `E9004`, deep nesting as `E1050`, `inspect --ir` equal to the IR goldens in both formats and with errors, `E9030` without the bundle, a failed build leaving the previous `dist/` byte-identical in both configurations, and with the bundle: the output tree equal to the codegen golden apart from the runtime, reproducibility, `--mode test --out`, `E9031` with exit `3`, the `--out` guard), `src/args.rs` (parsing), `src/commands.rs` (colour rule, exit codes, `E9999` from a real panic in both formats, `E9031` placement), `src/guard.rs` (panic capture, stack size), `src/real_fs.rs` (case-exactness, errors), `src/runtime.rs` (the embedded bytes are the built files), `src/dist.rs` (replace-on-success with injected failures).
