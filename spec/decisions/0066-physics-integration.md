# 0066. Physics integration: the module named by the manifest, the fixed tick, command categories, pose write-back, deterministic collision delivery, `ctx.body` and what happens when physics fails

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M5 (blueprint §11), task M5-05; blueprint §8 (physics is a subsystem behind an adapter, one pose authority); `spec/physics.md` §§1, 3, 4, 5, 6 and 8; `spec/scenes.md` §§9, 10, 10.2, 11; `spec/runtime-abi.md` §§2, 4.2, 4.3, 5.2, 6.1, 9.3, 10.1, 11.3; `spec/diagnostics.md` (`E8101`–`E8104`, `W8031`); decisions 0049 and 0050 (lifecycle, scheduler), 0056 (device recovery), 0063 (the backend and its bundle: item 9 left the file name of the bundle open, resolved here), 0064 (flush points, the entity table, the physics hook `addListener` and `commandTarget`), 0065 (the manifest data and the shape of `ctx.body`, item 12, extended here).
- Supersedes: nothing. Resolves the open point of 0063 item 9 (how the runtime learns the hashed file name) and fulfils the "honest scope" of 0065 item 14 and 0064 items 16 and 17 for physics.

## Context

The specification fixes the contract of the adapter (`PhysicsBackend`, `PhysicsWorld`), the order of one fixed tick (flush, commands by category, `fixed_update`, step, write-back, events), the sort key of collision events, the commands, the readable velocities and the codes `E8101`–`E8103`. Decisions 0063 and 0064 built both ends of the bridge (the Rapier adapter and its bundle; the entity table with its flush points and the `addListener`/`commandTarget` hook). What nothing fixes is how the runtime finds the bundle, what exactly the five command categories mean for commands issued in different phases, what "pose write-back" does to a record that other parts of the runtime read, how a pair of events is ordered when two readings of the sentence are possible, what a handler may do to the entities it is delivered to, what a body command with a non-finite argument does, what a frozen body is, how pause, the fixed-step accumulator and the manual test clock interact with the tick, and what a hot reload does to a running simulation. Every choice below is a **proposal** the owner may overrule; facts about the engine are **constraints** of decision 0063.

## Decision

1. **The manifest names the module** (resolves 0063 item 9). `subsystems` gains the optional string `physicsModule`: `"physics/<h16>.js"`, the relative path of the content-addressed bundle, **present exactly when `physics` is true** (`spec/manifest.schema.json`: a pattern, and `if`/`then`/`else` that require it for a physics program and forbid it otherwise; `additionalProperties` stay closed). `package()` writes it from the bundle it also writes (`Subsystems::physics_module`, the file inserted is the one named), so the two cannot differ. The runtime resolves it against `program.baseUrl`; `buildId` is unchanged (the bundle is not part of the build identity, 0063 item 7). `MtekManifest.subsystems` has `physicsModule?: string`. A program without bodies has the manifest it had, byte for byte.
2. **Loading** (`physics/load.ts`). The module is imported with a dynamic `import()` of the absolute URL, through a new member of `HostEnvironment`, `importModule(url)` (the default is a real `import()` of a computed specifier, which the bundler keeps; the fake host serves modules from a map and records every URL asked for, so a test can state that a program without bodies imported **nothing**). It happens **only when `manifest.subsystems.physics` is true**, concurrently with the device request, the shaders and the assets, so the 4 MB bundle does not add to the mount time; the result never rejects, so a mount that fails first leaves nothing dangling. **Every** failure is `E8102` ("physics module failed to load", with the URL and the browser's own message as notes): the import rejects (a missing file, a network error, a syntax error), the module has no default export that is a function, the engine does not initialise, the default export does not resolve to something with `name` and `createWorld`, the manifest names no module, or `createWorld` or the creation of a body throws after the scene was initialised. `E8102` maps to the new `MtekMountError.kind` **`"physics-failed"`** (`spec/runtime-abi.md` §6.1, `runtime.d.ts`); the mount releases the device, the registry and the world like every other failure and shows the overlay. A reload (`replaceProgram`) of a candidate that has bodies uses the module already loaded when the candidate names the same file and imports the new one otherwise; a candidate whose module does not load is **refused** with `E8102` (phase `runtime:reload`) before anything is swapped.
3. **One `PhysicsSystem` per mounted scene** (`physics/system.ts`). It creates the backend world with `scene.fields.gravity` and `runtimeConfig.fixedStep`, creates **the bodies of the named entities after initialisation** (`spec/scenes.md` §11 step 5: after `init`, the bindings and the propagation of transforms, in entity order, at the entity's pose), registers an `EntityLifecycleListener` on the entity table (0064 item 16) and so creates **the body of a spawned entity at the flush that creates it** (after the prefab's `init` and first binding pass, so the pose is final) and **removes it at the flush that removes the entity**, never from inside a handler or a collision callback. The body data of a spawned entity is the `body`/`collider` of its prefab in `manifest.prefabs` (`ResolvedPrefab.body`/`.collider`). The user id the backend reports collisions with is the entity's **slot** (0064 item 8), which is also what makes the order of events stable. `E8104` covers a pose that is not finite at creation (item 11).
4. **The tick** is the application's `phase2_tick`: (a) `dynamic.flush()` (spawned bodies are created, destroyed ones removed), (b) `applyCommands()`, (c) the `fixed_update` handlers, (d) `step()`, (e) the write-back, (f) the collision events and their handlers. **Spawn timing.** A spawn issued in phase 1, in `update` or in an earlier tick is created at the next flush point: the start of the next tick, or the end of the frame after `update`. So an entity spawned by a key handler gets its body at the flush of the very tick that follows and is stepped by it; an entity spawned in `update` gets its body at the end of that frame and is first stepped by the next frame's first tick; an entity spawned in `fixed_update` or a collision handler of tick *n* is created at the start of tick *n + 1*. A command through the reference of an entity that is not created yet is dropped with `W8031` (`DynamicEntities.commandTarget`); there is no queue for pending entities.
5. **Command categories** (`physics/commands.ts`). A command is queued when the handler calls it, in one of five lanes, and the whole queue is taken **once at the start of the next tick**: teleports, linear velocities, kinematic targets, impulses, forces; **issue order within a lane** (across entities). Consequences, all of them intended: a teleport issued after an impulse still happens first; `teleport(.., keep_velocity = false)` followed by `set_linear_velocity` in one tick ends with the velocity that was set, an impulse issued before a `set_linear_velocity` is still added on top of it (impulses come after velocities), forces come last and last for exactly the step that follows (the adapter resets them, 0063 item 3). A command issued **during** a tick (`fixed_update`, a collision handler) lands in the next batch because the batch was taken before `fixed_update` ran; a command issued in phase 1 or in `update` waits for the next tick however many frames come first. **Each command is applied once**, so `apply_force` called from `update` at 144 Hz with a 60 Hz step queues two or three forces for the same tick and they add up (a program that wants one force per tick issues it in `fixed_update`; the manual says so). A command whose entity was destroyed after it was issued is dropped **silently** when the batch is applied (it was valid when issued; the destroy is the program's own act); the check compares the generation of the reference with the body's, so a slot that was freed and **reused** by a later spawn never receives the old entity's commands.
6. **Pose write-back** writes the pose of every **dynamic and kinematic** body into its entity record through `ctx.setTransform` (the same path a script's write takes, so the transform is marked dirty, propagated in phase 6 and drawn) with binary32-rounded, frozen vectors; **static bodies are never read** (their pose is fixed at creation, `spec/physics.md` §2). A sleeping body returns the same pose and `setTransform` ignores an equal value, so a resting scene dirties nothing. Scale, visibility and everything else are not touched. The poses are world poses and bodies are root entities, so world = local. `bind` on `position` and `rotation` of a body entity is `E5072`, so phase 5 can never overwrite a pose the solver wrote.
7. **Velocities** are cached after every step for every dynamic and kinematic body and handed out frozen: `ctx.body(t).linearVelocity` and `.angularVelocity` are **the values of the last completed tick**, zero before the first tick. A command applied at the start of this tick (an impulse, a velocity, a teleport) is therefore not visible to this tick's `fixed_update`; it shows after the step that integrated it. A frozen body (item 10) reads zero. A read through an `entity_ref` of an entity that is pending, pending removal or dead gives zero **without** a diagnostic (a read cannot be "dropped"); a read of a velocity the target's kind does not have (a static body, an entity without a body) gives zero and `E8101`.
8. **Collision events** are sorted **enter before exit, and within each kind by `(min slot, max slot)`**; the entity with the lower slot gets its delivery first (`physics/events.ts`). `spec/physics.md` §6 says "sort pairs by (min, max), enter events before exit events"; read literally as "primary key the pair, tie-break the kind" the second half would be vacuous, because the solver reports a pair as started or stopped in one step, never both, so this record reads it as **kind first, then the pair** and records the reading here. **Delivery** (`PhysicsSystem.deliverCollisions`): the pairs are drained into a snapshot after the write-back, sorted, and walked; **before every single delivery both entities must be alive** (a named entity, or a spawned one that exists and is not pending removal), checked again between the two deliveries of a pair. So an entity that a handler destroyed, and an entity whose partner was destroyed, receive nothing more in this tick (`spec/scenes.md` §9: "no further collision events involving it are delivered"), and a pair whose entities are both pending removal is not delivered at all. A handler can only **queue** `destroy`; the body leaves the world at the flush after the handlers, so no collection the delivery walks is ever edited while it is walked. Events of bodies removed before the step are dropped by the adapter (0063 item 5). A named entity's handlers are those of the scene's table with its index as `owner`, a spawned entity's those of its prefab, each in declaration order, each called with the **other entity's reference** as `other`; an entity that declares none is skipped. An exception thrown by a handler propagates like any handler's (a frame error, `E8050`). Commands issued by a handler apply in the next tick (item 5).
9. **`ctx.body(target, spanId)`** (`spec/runtime-abi.md` §4.2). The ABI row of 0065 item 12 gains a trailing **span id**: the compiler passes the manifest span of the command or property (`ctx.body(a_who, 20).applyForce(..)`, `ctx.body(self, 19).linearVelocity`), as `ctx.spawn` and `ctx.destroy` do, so `W8031`, `E8101` and `E8104` point at the Mtek source (§4.2: "generated code passes span ids so the runtime can map any run-time diagnostic to the Mtek source"). The runtime had no `ctx.body` before this record, so the extra argument breaks no program. `target` is an entity record or an `entity_ref`; anything else is a `RuntimeInternalError` (a compiler defect). The handle is a small object per call with the five commands and the two properties. **What a command does, in order:** a target that is pending removal, not created yet or dead is dropped with `W8031` (`commandTarget`, the one place that decides it); a target without a body or whose kind does not support the command is dropped with `E8101` (the message names the entity, its kind and the kinds the command applies to; the table is `spec/physics.md` §3); the arguments are checked (item 11); then the command is queued. The compiler has checked named targets (`E5123`), so for a record the runtime check is a second line of defence that reports instead of failing. A diagnostic is reported once per `(code, span)` by the sink, so each site speaks once.
10. **`E8103`: a pose that is not finite.** After the step, a dynamic or kinematic body whose position or rotation is not finite is **frozen**: it is **removed from the world** (a non-finite body would poison the contacts of everything it touches, and the adapter has no "become static"), its entity record keeps the **last finite pose**, its velocities read zero, its commands are dropped silently, it takes part in no event, and `E8103` is reported **once per body**, at the declaration of the entity (or the prefab), with the pose in the message; the counter `physicsFrozenBodies` counts it. The loop, the other bodies and the program go on; the entity itself stays alive and a `destroy` of it works as always. Only the pose is checked, as the spec says; velocities of a body whose pose is finite are not.
11. **`E8104`: a value that is not finite is given to a body** (new; in the range `spec/diagnostics.md` reserved as "E8104–E8199 further physics runtime codes", a **proposal**). A command argument that is not finite, or a rotation whose length is below 1e-10 (the solver cannot normalise it), drops the command; a body whose initial pose is not finite is not created (the entity stays where `init` put it and takes no part in the simulation; its commands are then dropped silently). Why a code and not the adapter's `RangeError`: the adapter refuses such input before it reaches the engine (0063 item 4), but an arithmetic slip in a program (`1.0 / 0.0` is `inf` in Mtek, `spec/language.md`) must not stop the application: a thrown error inside a handler is a frame error and ends the loop. Why not `E8101` or `E8103`: they are about the body kind and about the solver's output.
12. **Time: pause, resume, the accumulator and the manual clock.** Ticks come only from the scheduler's fixed-step loop (`spec/scenes.md` §10.2, decision 0050), so physics inherits its rules: `pause()` (explicit, or a hidden document) stops frames and cancels the frame request, the accumulator keeps its remainder (less than one step), `resume()` forgets the last timestamp, so **the first frame after a resume has delta 0 and the paused interval is never stepped**; a frame delta is clamped to `max_frame_delta` and at most `max_catch_up_steps` ticks run per frame, the surplus is dropped and counted in `discardedSteps` (so a stall of a second advances the simulation by four steps, not sixty). The system adds no time of its own: there is exactly one `step()` per tick and the step is the manifest's `fixedStep`. **With the manual clock** (`debug.step(n, dt)`) each frame adds `dt` (clamped) to the accumulator, so a test that wants **one tick per frame must pass the manifest's `fixedStep` exactly (`0.016666668`)**: `1/60` in binary64 is slightly *smaller* than the binary32 step and the first frame would not tick (the third would be the second tick); tests derive step counts from the accumulator or use the exact value (every spec of this record does). The counters `physicsSteps` and `discardedSteps` make it observable.
13. **Lifetime.** `dispose()` frees the physics world (every body and collider, the event queue: the adapter's `dispose`, 0063), drops the command queue and the listener, and leaves `physicsBodies`/`physicsColliders` at 0 (`spec/runtime-abi.md` §9.3, `spec/physics.md` §7); a mount that fails after the world exists disposes it. **Device recovery** does not touch physics: the world, the bodies and the queue are CPU state like the entity records, so the simulation is exactly where it was (the application is paused during recovery). **Hot reload** (`replaceProgram`, 0064 items 18 and 19): at the swap, before the migration, a new `PhysicsSystem` is made for the candidate's world (so it hears of the spawned entities the migration re-creates); after the migration carried the poses, the bodies of the named entities are made from **the carried poses**; the old system is disposed. **Velocities and queued commands do not survive a reload**: the new world starts at rest (a documented limitation; the pose is what an author sees). A candidate that adds or removes a body restarts the scene anyway (`W8070`, `findStructuralChange`); the physics of the old scene goes with it, and a restarted scene that has no bodies has no physics system.
14. **Counters** (`spec/runtime-abi.md` §10.1): `physicsBodies`, `physicsColliders` (the backend's `counts()`, 0 without physics and after dispose), `physicsSteps` (cumulative), `physicsFrozenBodies` (cumulative).
15. **Generated code and goldens.** `ctx.body(target, spanId)` (item 9) changes the golden `app.js` and the manifest's span table of `tests/codegen/physics` (the spans of the commands are appended, no existing span id moves) and adds `subsystems.physicsModule` to its manifest; no other golden changed (`MTEK_BLESS=1 cargo test -p mtek-compiler --test build`). The shared manifest examples (`tests/abi/manifests`) follow: `valid/full.json` has a module, every invalid example that has `physics: true` got one so it still fails for its own reason, and `physics-module-missing`, `physics-module-without-physics` and `physics-module-bad-path` are new.
16. **Not in this record (honest scope, known limitations).** The rest of the required tests of `spec/physics.md` §7 that need the real engine and are not listed under Tests below (the high-speed/tunnelling limitation, sensor counts on the engine, waves of 1 000 crates) are not part of this task (**done by decision 0068**, M5-06); the ordering, removal-in-callback, pause and diagnostics tests run against the fake backend, the engine is exercised by resting contact, free fall, impulse response, the landing event and twenty mount/dispose cycles. Forces issued faster than the step accumulate (item 5). A reload loses velocities (item 13). No render interpolation (`spec/scenes.md` §10 item 6). A frozen body leaves the world and does not come back (item 10). The span of `E8103`/`E8104` at creation is the entity's declaration, not a statement.

Rust: `crates/mtek-compiler/tests/build.rs` (the manifest names the file exactly when the bundle is written, in every fixture and mode), `tests/fixtures.rs` (`E8101`–`E8104` leave `NOT_YET_IMPLEMENTED` and are covered by the unit tests that name them).

## Consequences

- `spec/physics.md` §§3 to 8 and `spec/runtime-abi.md` §§2, 4.2, 4.3, 5.2, 6.1, 10.1 and 11.3 point here; `spec/diagnostics.md` has `E8104` and the new wording of `E8101`–`E8103`; decision 0063 item 9 and decision 0065 items 12 and 14 point here.
- The runtime bundle grows by the integration (about 30 KB, release and development builds alike) and still contains no engine; a program without bodies is byte-identical to before and makes the same requests.
- A program with bodies has a manifest with one more key; an older runtime (ABI 1, but older) rejects it with `E8006`, as it would any manifest key it does not know, which is the intended behaviour of `additionalProperties: false`.
- The next physics tasks add tests, not integration: the engine-level checks of `spec/physics.md` §7 that are not listed above.
