# 0054. Textures and samplers: params, built-ins, `sample` and the test texture

- Status: Accepted
- Date: 2026-10-17
- Blueprint origin: §6.1 (params are never folded into shaders), §6.3 (update classes), §7.4 (resource lifetime), §9.4 (diagnostics); `spec/materials.md` §2, §4, §5; `spec/gpu-layout.md` §6, §8.3; `spec/stdlib.md` §2, §6; `spec/runtime-abi.md` §5.2, §8, §10.2; `spec/diagnostics.md` (`E4030`, `E4041`, `E6002`); decisions 0016, 0025, 0035, 0039, 0041, 0044, 0046, 0049.

## Context

Task M4-04 adds the resource types of `spec/materials.md` §5: `texture` and `sampler` as material params, the built-ins `texture.white()`, `texture.black()` and the four `sampler.*` presets, and the GPU intrinsic `sample`. The registry, the checker's types, the manifest schema (`materials[].resources`, the `resource` instance param class) and the runtime's manifest types already described them; nothing compiled or rendered them. The specification fixes the binding plan (group 1, bindings `1…` in param declaration order, at most 8), the colour-space rule and the `E4041` rule, but not how the gate is lifted, where `E6002` is reported, what `sample` lowers to, what the runtime creates and when, or how a test can sample a texture that is not 1×1 before assets exist (M4-05 and M4-06). They are fixed here so that they are visible, testable and changeable by a later record.

Everything here is a **proposal** (design choice) unless it repeats the specification.

## Decision

1. **Gate.** As M3 did for `state` and `bind` (decisions 0049 and 0051), the rows are marked implemented by the current build (`since` `M1`; `CURRENT_MILESTONE` is unchanged): the types `texture` and `sampler`, the namespaces `texture` and `sampler` with their six functions, and the intrinsic `sample`. `asset`, `glb_asset`, `lighting` and `Pbr` stay `M4` (tasks M4-03 and M4-05). `spec/stdlib-schema.json` was regenerated, and the `gate_builtin_type` fixture, which used `sampler` as its example of a gated type, now uses `glb_asset` and `asset`.

2. **Values.** The six built-ins are const-eligible: the checker's `ConstValue` gains `Texture` and `Sampler` (the registry's `BuiltinTexture` and `BuiltinSampler`), `namespace_function` evaluates them, and `from_registry` no longer drops them, so a default, an instance value and a `const` of these types are constants. The IR spells them `{ "texture": "texture.white" }` and `{ "sampler": "sampler.linear_repeat" }`, the names the manifest uses. The built-ins stay CPU-domain functions: calling `texture.white()` inside a stage is `E4012`, and a stage that reads a `const` of type `texture` is `E4040` (the capture rule of decision 0039 item 5, since the type exists only on the CPU).

3. **Params** (checker, `types/material.rs`).
   - A resource is a param of its own. `array<texture, 2>` and a struct with a `texture` field are `E4030` ("it contains texture"); the help of `E4030` names the two types.
   - **`E4041`** is reported at every use of a `texture` or `sampler` param in a stage except as the first or second argument of a `sample` call (a parenthesised operand counts as direct): `let copy = map;`, an argument of a user function, an operand of `==`, a returned value. The expression then has type `Error`, so the use causes no second diagnostic. A user `fn` that declares a `texture` parameter is also `E4011` as for every type that does not exist on the GPU; that is reported with the `E4041` of its call, not instead of it.
   - **Construction-only.** `self.material.map = …` is `E5073` (the record 0016 rule, "texture param assignment rejected", now a fixture); `map: bind(…)` in an instance is `E5004`, and the `bind` is not checked further. A texture or sampler is therefore always `initial`-valued data of the instance literal or the material default.
   - **`E6002`** is reported by the checker at the name of the ninth param of type `texture` or `sampler` (both kinds count, `MAX_MATERIAL_RESOURCES` = 8), with the material's name as a related span. It is a limit of the declaration, so `check` reports it and a `tests/semantics` fixture covers it; `E6001`, which depends on the computed block size, stays a limit of the resource plan (decision 0044 item 8). The code keeps the default phase of its range (`emit`) in the JSON report although `check` produces it.

4. **IR and plan.** A param of type `texture` or `sampler` has the update class `resource` (`ir::UpdateClass::Resource`, `ParamClass::Resource`, the manifest's `resource` class). The parameter block holds the value params only: resource params are skipped when the block is laid out, so a material with resources and no value param has no block (`layout` is `null` and group 1 binding 0 is absent), and instance params of the block keep their member positions by name. The plan gives every material `resources`: `{ name, kind, binding, span }` with bindings `1…` in param declaration order (a texture and a sampler each take one). An instance is `shareable` when every param is `initial` or `resource`: resources are immutable, so they do not make a block unshareable. Generated `app.js` writes no resource param (`ctx.setParam` is for the block).

5. **WGSL** (decision 0041 extended). Each resource is a module-scope variable in the order of the bindings, after the block and before the object block: `@group(1) @binding(1) var mtek_texture_<param>: texture_2d<f32>;` and `@group(1) @binding(2) var mtek_sampler_<param>: sampler;` (generated names, so no user name can collide). A read of a resource param in a stage is that global; the shader IR gains `ShaderType::Texture2d` and `Sampler` and `GlobalKind::Texture` and `Sampler`.
   - **`sample(t, s, uv)` is `textureSampleLevel(t, s, uv, 0.0)`.** `textureSample` needs uniform control flow because it takes derivatives, and Naga rejects it inside an `if` or a loop that depends on non-uniform values; that would make a valid Mtek program `E6100`. Derivatives only select a mip level, v0.1 has one level (`spec/materials.md` §5, §10), so level 0 is the same texel in every control flow. A later record that adds mip-maps changes this lowering together with the restriction on derivatives.
   - The `sample` operands are the resource globals directly; `E4041` guarantees that no other form reaches the lowering, and a resource value anywhere else is a defect (`E9999`).

6. **Manifest and views.** `materials[].resources` is `[{ name, kind, binding }]`; each instance lists its resource params as `{ name, class: "resource", value: { kind: "builtin", name } }` (`kind: "asset"` arrives with M4-05, and the runtime rejects it with `E8003` until M4-06). `mtek inspect --bindings` shows an instance's resource param with `binding` and `resource` (the built-in's name) instead of `field`, `offset` and `size`; the human table prints `binding 2 = sampler.nearest_clamp` in the field column. `--shaders` is unchanged (the WGSL shows the bindings).

7. **Runtime** (`render/resources.ts`, `render/materials.ts`, `render/pipelines.ts`).
   - **Built-in textures** are 1×1, opaque, `rgba8unorm-srgb`, one mip level, usage `TEXTURE_BINDING | COPY_DST`, filled by one `writeTexture` through the registry (which counts it as an upload): `texture.white()` is `(255, 255, 255, 255)`, `texture.black()` `(0, 0, 0, 255)`. Colour textures are created with an `-srgb` format, so `sample` returns linear values (`spec/materials.md` §5); a `linear` texture is `rgba8unorm`, returned as stored.
   - **Samplers** are filtering samplers: `linear_*` have linear magnification and minification, `nearest_*` nearest, `*_repeat` repeat and `*_clamp` clamp-to-edge in both directions; the mip filter follows the filter and is never observable.
   - Each object is created **once per scene, on first use**, through the resource registry (`texturesAllocated`, `liveTextures`, `liveSamplers`), shared by every instance that names it, and released by `MaterialStore.dispose()` with the scene. A scene without textures creates none.
   - **Bind groups.** The group-1 layout is `[uniform block at 0, if any] + [texture: float, 2d | sampler: filtering at each resource binding]`, fragment visibility, and depends only on the block size and the kinds at the bindings, so materials of the same shape share it and the pipeline layouts built from it; a pipeline cache hit still depends on the shader hash alone. An instance's group-1 bind group holds the block slot (static offset, as before) and the texture views and samplers of its resource params; it is created on first draw and cached by its arena. An instance with resources and no block gets its own cached bind group from the store; an instance with neither keeps the shared empty group. Bind groups are not shared between instances (instancing is M4-08).
   - **Validation.** `resolveStructure` checks that `resources` match the material's params (binding `k+1` for the `k`-th resource, kind equal to the param's type, `E8006` otherwise), that every instance names a built-in of the right kind for each resource, and rejects an asset-valued resource with `E8003`.

8. **Test control.** `options.test.textures` (`spec/runtime-abi.md` §10.2) replaces the pixels, size and colour space of `texture.white()` and `texture.black()` for the mount: `{ width, height, data, colorSpace? }` with `data` a `Uint8Array` of `width × height × 4` bytes, top row first, `colorSpace` `"srgb"` (default, `rgba8unorm-srgb`) or `"linear"` (`rgba8unorm`). It goes through the same creation path as the 1×1 built-ins, so it exercises the real texture and sampler path with a generated image; the alternative, a program whose texture comes from an asset, needs the asset compiler and loader of M4-05 and M4-06. It is validated when `mountMtek` is called (a wrong size or an unknown name is a `RangeError`, a wrong colour space a `TypeError`), is for tests only like the rest of `test`, and is passed on to the scenes a hot reload starts. `runtime.d.ts` declares `MtekTestTexture`.

9. **Not in this record:** asset textures and `asset.texture` (M4-05, M4-06), texture params of `Pbr` (M4-03), mip-maps, texture arrays and cube maps, anisotropic filtering, replacing a texture at run time (v0.2).

## Consequences

- `spec/materials.md` §5, `spec/gpu-layout.md` §6 and §8.3, `spec/runtime-abi.md` §10.2 and `spec/diagnostics.md` point here. Decision 0039 items 1 and 13 and decision 0044's consequences about `E6002` are amended by pointers.
- The remaining M4 work builds on these pieces: M4-03's `Pbr` uses `sample`, M4-05 adds `ResourceValue::Asset` values and `asset.texture`, M4-06 loads and uploads them through `BuiltinResources`' creation path (the same formats, `COPY_DST` and `writeTexture`), M4-08 may share bind groups of identical instances. (Decision 0060 did the M4-06 part: the runtime now renders asset-valued texture params, so the `E8003` of items 6 and 7 for them is gone.)
- No new dependency and no new diagnostic code. `E4041` and `E6002` leave the not-yet-implemented list of `tests/fixtures.rs`.

## Verification

- Compiler: `tests/semantics/pass/materials/{textures,resource_limit}` (built-in defaults, instance overrides, parenthesised operands, eight resources among value params); `tests/semantics/fail/materials/e4041_{texture_in_local,texture_passed_to_function,sampler_outside_sample}`, `e6002_too_many_resources`, `e4030_texture_inside_struct_or_array`, `e3102_sampler_for_texture_param`, `e5073_assign_texture_param`, `e5004_bind_texture_param`; `src/plan/tests.rs` (bindings in declaration order beside the block, a material with resources only); `tests/shader_lowering.rs` and the golden `tests/codegen/wgsl-materials/textures` (bindings, `textureSampleLevel` inside `if` and `for`, resources not in the block); `tests/ir_goldens.rs` and `tests/inspect_views.rs` (goldens for `materials/textures`, the view's bindings agree with the manifest's); `tests/build.rs` (manifest resources, resource instance params, `app.js` writes none); `tests/stdlib_registry.rs` and `types/value.rs` (the gate and the evaluators).
- Two codes became reachable with the gate and moved from the unreachable list of `tests/fixtures.rs` to fixtures: `E4013` (`tests/semantics/fail/e4013_gpu_only_builtin_in_cpu_code`, a `cpu fn` calls `sample`; the M2 gate's `specs/m2/rejections.spec.ts` asserts it in place of the `E9010` stand-in, as the M2 report planned) and `E4012` (`materials/e4012_builtin_texture_called_in_stage`, a stage calls `texture.white()`).
- Runtime: `render/materials.test.ts` (built-ins created once and shared, presets, group-1 entries and layout sharing, test textures and their validation, disposal), `render/renderer.test.ts` (a textured material draws with the layout it was made with; `test.textures`), `scene/structure.test.ts` (resolution and `E8006`/`E8003`), `host/mount.test.ts` (option validation).
- Browser (`tests/browser/specs/m4/textures.spec.ts`, hardware adapter): a generated 2×2 sRGB texture is sampled with nearest filtering at the exact texel centres and compared with expected linear values derived by hand (`support/texture-reference.ts`: the sRGB transfer function written from its definition, a table of hand-evaluated values, a CPU sampler for nearest and linear filtering with clamp and repeat); the same panels across texel edges and outside `[0, 1]`; a `linear` texture sampled as stored; the 1×1 white and black built-ins; no resource, bind group or pipeline is created after mount.
