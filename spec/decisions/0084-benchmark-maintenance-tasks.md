# 0084. The benchmark maintenance tasks 02 to 06: off-by-one in a loop, four diagnostics at once, wrong units and direction, a rename with retention, an extension with retention; their derivations, fairness checks, evidence and the limits found

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: §12.2 (the AI/token benchmark: 6 maintenance/repair tasks of the 30), §9.2 (a repair must not delete the feature under test), §9.4 (diagnostics for repair: validated edits only); `spec/ai-and-benchmarks.md` §6 (task format, set composition, baseline fairness); decisions 0021 (task format, `starter_diagnostics`, one definition of success for both sides), 0071 (validated suggested edits: `E0022`, `E1003`, `E1011`, `E2003`, `E7024`), 0074 (`mtek test`), 0077 (the repair harness, required symbols as compiler names, the edit format and which files may change), 0052 (host inputs).
- Supersedes: nothing. Part of task M6-08 (the full benchmark task set); the other parts add the scene/rendering, interaction and shader/bridge tasks and the further holdout tasks in their own records.

## Context

`maintenance-01` (a wrong vector dimension and an unknown field) was the only maintenance task. The set composition of §6.2 asks for six. The category is where the starter is a working or a broken program and the job is a change to it, so what it measures is different from the cold and the add-one-thing tasks: finding the defect from a symptom or a diagnostic, changing the least that is needed, and not breaking what works (the fixtures that pass on the starter are the retention checks, as in `interaction-01`). The five new tasks vary the skill: a behaviour bug found by a failing fixture (an off-by-one), a program with several diagnostics at once (three of them with a validated suggested edit, so that the repair harness is exercised on the path of decision 0071), a bug of units and handedness, a rename that touches the interface to the host page, and an extension that must keep an existing feature. Every task has a Mtek side and a three.js (TypeScript) side judged by the same `.test.toml` fixtures (decision 0021 item 8).

## Decision

1. **The tasks** (every one is an `edit` task with the budgets `max_repairs = 3`, `max_output_tokens = 4000`, `max_wall_seconds = 300`; every Mtek starter and reference is formatted by `mtek fmt` except the starter of `maintenance-03`, which does not parse):

   | Task | What is tested | Mtek starter | Baseline starter | Fixtures |
   |---|---|---|---|---|
   | `maintenance-02` | an off-by-one in a `for` loop found from a failing fixture | compiles; the loop is `for i in 1..COLUMNS` and the left-most of five markers is never placed | compiles; `for (let i = 1; i < COLUMNS; …)` | 3 |
   | `maintenance-03` | four defects of four kinds at once (a malformed number, a missing separator, a misspelled name, a type error) | `E0022` (`2.`), `E1003` (a missing `;`), `E2003` (`elapsd`), `E3014` (`f32 * i32`) | `TS1351` (`2.0f`), `TS1005` (a missing `)`), `TS2552` (`elapsd`), `TS2363` (`number * string`), plus the cascade `TS2304`, `TS2554` | 2 |
   | `maintenance-04` | wrong units (degrees where radians are meant) and wrong direction (a minus sign) in one handler | compiles; `axis_angle(…, -heading)` with `heading` in degrees | compiles; `turret.rotation.y = -heading` | 3 |
   | `maintenance-05` | a rename of the page-facing input (`glow` to `brightness`) and of the variable behind it, with retention of everything else | compiles; fails the fixture that sets the input `brightness` | compiles; the same fixture fails (`unknown-input`) | 3 |
   | `maintenance-06` | an extension (a new entity bound to existing state, a new key handler) without breaking the existing counter and its cap | compiles; fails the two fixtures that need the alarm and R | compiles; the same two fail | 4 |

2. **What each task describes, and where its numbers come from.** Every expected pixel is derived from the prompt, by hand and by an independent CPU projection (f64, a look-at camera with `fov_y` 0.9 at `(0, 0, 8)`: a point at depth `d` is `64 / (d · tan 0.45)` pixels per unit from the centre; `benchmarks/baselines/support/test/projection.ts` for the centres, a throwaway script that projects the eight corners of every box and takes their convex hull for the margins), never from running a reference. Every sampled point is at least 3 pixels inside the shape it names or outside every silhouette it must not be in (most are 4 to 9); the fixtures state the numbers they come from in comments, as the seed fixtures do.
   - **`02`**: Space places a row of five markers (edge 0.8, `#facc15`) at x = -3, -1.5, 0, 1.5, 3 and y = 2.0 − 2.5 · rows, over a static `Rail` (8 × 0.4 × 1 at y = -3, `#475569`). Markers are centred on pixels x = 12, 38, 64, 90, 116 and y = 29 (first row) or 73 (second row), 12 pixels wide; the gaps (26, 51, 77, 102) are background. Fixtures: nothing but the rail before a press (a retention check: it passes on the starter), one row after one press, two rows after two.
   - **`03`**: `Bob` (a unit cube, `#ec4899`) at x = 2 sin t, y = 0.5 per press, with t the accumulated frame time. Frame 1: pixel 64.6; frame 30 (t = 0.5): x = 0.959, pixel 80.9; frame 60: 1.683, pixel 93.7; frame 240 (t = 4): -1.514, pixel 37.3 (the other side of the centre, where the sine is negative). After one press (frame 32) the box is centred on pixel y 55.2, after two (frame 34) on 46.3, x 82.0 and 83.0. The expected values include one frame of delay for the key (applied at the start of the next frame) and nothing else.
   - **`04`**: a purple cube of edge 2 (`Turret`) with an orange child cube of edge 0.8 (`Barrel`) at local (0, 0, 2.2), between the turret and the camera. A positive angle `a` about +Y puts the barrel at (2.2 sin a, 0, 2.2 cos a): 30 degrees (one press) is (1.1, 0, 1.905), pixel 87.9; 90 degrees is (2.2, 0, 0), pixel 100.4; 120 degrees is (1.905, 0, -1.1), pixel 91.7; 180 degrees puts it directly behind the turret, hidden by it (depth test). A turn to the left would put the barrel at pixel 40 after one press, which the fixture shows as background (36, 64).
   - **`05`**: a grey `Housing` (5 × 5 × 1, `#4b5563`, pixels 20 to 108) and a yellow `Bulb` plate (mesh 2 × 2 × 0.2 at z = 1, scaled by `0.5 + brightness` in x and y, `#fde047`), whose silhouette in pixels is 54.4 to 73.6 at brightness 0, 49.6 to 78.4 at 0.25, 44.8 to 83.2 at 0.5 (the start), 35.2 to 92.8 at 1. Space sets 1.0, D sets 0.0, the host input sets any value. Retention fixtures: the start, the keys (both pass on the starter); the new fixture: `set_input = { brightness = … }`, which fails on the starter with `MTEK-E8040` (Mtek) and `unknown-input` (baseline).
   - **`06`**: five pips (edge 0.7, `#22c55e`) at x = -3 … 3, y = -2, centred on pixels (12, 99), (38, 99), (64, 99), (90, 99), (116, 99), each visible while the count is at least its number; the new `Alarm` (edge 1, `#ef4444`, (0, 2, 0), pixel (64, 29), 20 to 38 in y) is visible exactly while the count is 5; R resets the count. Fixtures: nothing lit at the start and one press per pip with the alarm off (both pass on the starter), five and more presses (the alarm, and the cap), R after five presses and after one.

3. **Why these tasks are the same task on both sides** (fairness, `spec/ai-and-benchmarks.md` §6.3). The prompt is one text and names no API of either side (words like "box", "flat colour", "the page sets an input", "a variable named …" are the task's, not a language's). The fixtures are pixel-only because the baseline interpreter rejects `expect_state` (decision 0021 item 8); everything a prompt requires that no pixel shows is said so below (items 6 and 7). The helpers (`boxMesh`, `unlit`, `lookAtCamera`, `startTask`) are the baseline's counterparts of the standard library. Where the two languages differ, the task keeps the meaning and not the syntax:
   - `03` has four defects on each side but not the same four. `E1003` (a missing `;`) has the baseline counterpart of a missing `)` (JavaScript's automatic semicolon insertion makes a missing `;` legal). `E0022` (`2.`) has the counterpart `2.0f` (a malformed number; `2.` is legal JavaScript). `E2003` and the type error are the same slip in both. The baseline starter does not build at all (`esbuild` stops at the syntax error, so its fixtures fail at the build), and `tsc` reports six diagnostics for the four defects, where `mtek check` reports four: a model's repair loop on each side sees what that side's tool says. Mtek attaches a validated suggested edit to three of its four (the fourth, a type error, is never given one, `spec/diagnostics.md` §6.2); TypeScript's "did you mean" is text. That is a property of the tool chains and is not corrected for.
   - `02` and `06`: Mtek has no loop in a scene body, so `06` declares five entities where the baseline builds five meshes in a loop; the prefab loop of `02` is in a handler on both sides (`spawn` and `scene.add`).
   - `04`: both sides have the conversion (`radians`, `MathUtils.degToRad`) and the same handedness (a positive rotation about +Y turns +Z toward +X), which is why a sign slip is a fair defect in both.
   - `05`: the rename touches two files in Mtek (`mtek.toml` declares the host input, the source declares the state) and one in the baseline; the Editor may change `mtek.toml` (decision 0077 item 4 (h)).

4. **Required symbols are compiler names that the starter already declares.** `02`: `Demo.Rail`, `Marker`; `03`: `Demo.Bob`, `Demo.elapsed`, `Demo.presses`; `04`: `Demo.Turret`, `Demo.Turret.Barrel`, `Demo.heading`; `05`: `Demo.Bulb`, `Demo.Housing`; `06`: `Demo.count`, `Demo.Pip1` … `Demo.Pip5`. Every name was checked with `mtek context --symbol` on the starter and the reference (the validate layer `requiredSymbols` is `pass` for each).

5. **`maintenance-05` as first designed required `Demo.brightness`, and the harness cannot take that.** The ContextBuilder runs `mtek context --symbol S` for every required symbol on the **starter** before the first model call; a name the starter does not declare yet (every rename and every "add a named thing" task has one) exits with 2 and ends the trial with a tool error (`error`, "no declaration is named 'Demo.brightness'"), which was seen on the first replay run of this task. The task was changed, not the harness: `required_symbols` lists only what the starter has. The consequence is item 6.

6. **Limits of what the checks can show** (found by mutants, `evidence/M6/benchmark-maintenance/mtek-mutants.json`: a plausible wrong fix is validated against the same fixtures and required symbols; eight of ten fail, two pass).
   - `05b` passes: renaming only the key of the host input (`brightness = "Demo.glow"`) while the variable keeps its name satisfies every fixture and every required symbol. The prompt asks for the variable to be renamed too, and the reference does it, but nothing the fixtures or the required symbols can see distinguishes it. **The consistency of an internal rename is not machine-checked on either side**; what is checked is the page-facing name and that nothing else changed. A partial rename of the other kind (a use of the old name left behind) is caught by the compiler (`05c`: `E2003`) and a source renamed with a stale `mtek.toml` by `E9021` (`05a`), so the common failures of the task are caught; the silent one is not. Closing the gap needs the ContextBuilder to tolerate an absent required symbol (item 5); then `Demo.brightness` can be required.
   - `06c` passes: raising the cap of the count from 5 to 6 changes nothing a pixel shows (the pips are five and the alarm stays on at 6). The prompt states the cap, the starter has it, the reference keeps it, the fixture "more presses change nothing" checks the visible outcome; the value itself is Mtek-only state (`expect_state` could check it on the Mtek side and the baseline interpreter rejects the step).
   - The first version of `04`'s third fixture passed the mutant `04b` (the sign fixed, the unit not) because 90 and 120 degrees read as radians (116.6 and 35.5 degrees) happen to put the barrel where the checks look. The fixture got a third stage (six presses: 180 degrees, the barrel hidden behind the turret) and now fails `04b`; the first fixture (one press) failed it all along, so the validation verdict never changed, and the reference passed before and after.

7. **Other observations about the compiler and the harness** (not changed here).
   - `0.5 * presses` with `presses: i32` is two errors for one slip (`E3041`, the literal `0.5` is resolved as `i32` from the other operand, and `E3001`, an argument of `vec3`), because of the literal resolution of `spec/language.md` §6.6; a named `f32` constant in its place (`RISE * presses`) is the clean `E3014` ("not defined for f32 and i32", with the hint to convert). `maintenance-03` uses the constant so that the starter has one diagnostic per defect. The double report is accurate to the specification and is recorded as a candidate message improvement.
   - With four errors in one file the validated edits were attached to the three that have one (`E2003`, `E0022`, `E1003`), none was withheld by the conservatism of decision 0071 item 4, and an applied set leaves exactly the `E3014`: this is what the replay run `replay-maintenance-03` does.
   - `mtek check --format json` on the starter of `03` lists the diagnostics in the order `E2003`, `E0022`, `E3014`, `E1003` (not in source order); `starter_diagnostics` is a set and is written in code order.

8. **Shared files that need a change (not made here, for the orchestrator).** The baseline starter of `maintenance-03` has errors on purpose, like that of `maintenance-01`: `benchmarks/eslint.config.js` must ignore `tasks/maintenance-03/baseline/**` and `benchmarks/tsconfig.json` must exclude `tasks/maintenance-03/baseline/src`, or `npm run lint` and `npm run check:ts` fail on it; `benchmarks/baselines/support/test/starters.test.ts` should list the starters of `02`, `04`, `05`, `06` as type-checking, the references of `02` to `06` as type-checking, and the starter of `03` with its six diagnostics (the list in `evidence/M6/benchmark-maintenance/baseline-tsc-diagnostics.json`); `tools/ai-eval/test/integration.test.ts` lists only the four seed tasks. With the first two changes applied locally, `npm run check` passes (it was run that way and the changes reverted).

## Fixtures and tests

- 15 fixtures in `benchmarks/tasks/maintenance-0{2..6}/mtek-tests/` (3, 2, 3, 3, 4), the same files for `mtek test` and for the Playwright suite of each task (`baseline-tests/fixtures.spec.ts`, one line as in the seed tasks).
- A fixture never asserts the starter's defect only: every task has at least one fixture that **passes on the starter** (the retention checks: `02` 1, `04` 1, `05` 2, `06` 2; `03` has none, the starter does not build).
- No new unit test (no tool changed). The validator (`npm run check:tasks`) accepts the six maintenance tasks, the holdout hash is unchanged.

## Consequences

- The set has 6 of the 6 maintenance tasks. `mtek_side_status` is `verified` for all five: the Mtek reference passes parse, check, build, start, tests and the required symbols on a hardware adapter, and the starter fails as declared (below). The baseline reference passes its fixtures and the baseline starter fails as intended on the same adapter.
- The maintenance tasks exercise the harness's repair path with the compiler's own feedback: `replay-maintenance-03` (the three validated edits applied by one reply, the type error fixed by the next), `replay-maintenance-04` (units fixed, then direction) and `replay-maintenance-05` (the source renamed, the stale host-input target reported as `E9021`, then fixed) each end in `success` after one repair. These are hand-written transcripts through the replay client (the model is `replay-hand-written`, token counts are unknown): they show the loop and the real feedback, **not a model result**.
- Nothing here measures a model. No claim about tokens or completion rate follows from these tasks.
