# 0028. Typed IR and the public `check`/`inspect` API: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §5.1 (the typed IR as the contract between language and code generation), §13 (one library API for CLI, tests and LSP); `spec/compiler-architecture.md` §3, §4.8, §4.12, §5; `spec/scenes.md` §10.1, §11; `spec/runtime-abi.md` §5, §5.2; `spec/tooling.md` §1; decisions 0025 (item 12), 0026, 0027.

## Context

Task M1-12 implements `crates/mtek-compiler/src/ir/`: the typed high-level IR built from a checked program, `lower_to_ir`, and the library entry points `check` and `inspect(…, Inspect::Ir)` of `spec/compiler-architecture.md` §4.12 (the `mtek inspect --ir` command itself is wired by the CLI task). The specification lists what the IR contains for the whole language and that it serialises with a stable field order; it does not fix the node shapes, how values and spans are written, the symbol of a built-in material, how much of a declaration a node's span covers, or how the existing `check` (decision 0025 item 12, which returns the front end's internals) relates to the "diagnostics only" `check` of §4.12. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Public API.** `check(&ProjectRoot, &dyn Fs) -> CheckResult { project_name, sources, report }` is diagnostics only, as §4.12 says: the report plus what a caller needs to print it (the project name of the JSON report, the source map for human rendering). The front end's full result moves to `analyze(&ProjectRoot, &dyn Fs) -> Analysis { project, module, resolution, types, report }`, an addition to §4.12 for the IR, tests and later the LSP; it supersedes the shape of decision 0025 item 12. `inspect(&ProjectRoot, &dyn Fs, Inspect) -> InspectResult { project_name, sources, report, ir }`; `InspectResult::render(InspectFormat::{Json, Human})` gives the text, `None` when the program has errors. `Inspect` has the single variant `Ir` until `--bindings`/`--shaders` (M2). The three share one front-end function, and `inspect` reports to the same sink, so its diagnostics are exactly `check`'s (plus `E9999` below).
2. **`lower_to_ir(&Analysis) -> Result<ir::Program, LowerError>`** runs only when the analysis has no error (`LowerError::HasErrors`, §3). It reshapes the `CheckedScene`s of decision 0027 and the folded constants of decision 0026 and never evaluates or reads registry defaults. A checked program it cannot represent (a field, schema or scene-object kind it does not know, a missing value) is `LowerError::Internal(text)`, which `inspect` reports as `E9999` with the text as a note — never a panic. The lists of fields, schemas and kinds it lowers are compared with the registry by unit tests (`every_implemented_body_field_is_lowered`, `every_implemented_descriptor_schema_is_lowered`), so a milestone that implements a new field fails until the IR represents it.
3. **Symbols** are `normalised/path.mtek::Qualified.Name`, the qualified name being the chain of declaration names from the module item down: `src/main.mtek::Demo`, `src/main.mtek::Demo.Main` (camera), `src/main.mtek::Demo.Ground.Fountain` (nested entity), `src/main.mtek::Demo.Ground.SIZE` (a constant of an entity body). Built-in materials are named after the prelude source that declares them: `std/materials.mtek::Unlit`, exactly like a user material `src/main.mtek::Pulse`. The IR carries no `DefId`s (they are per-build numbers); symbols are the identity, as for hot reload.
4. **Node shapes (M1).** `Program { entryScene, modules }`; `Module { path, file, span, items }`; `Item` is `const` or `scene` (tagged `kind`; functions, structs, materials and prefabs become further kinds when their milestones implement them). `Scene { name, symbol, span, fields: SceneFields { clearColor }, constants, cameras, entities }`: `constants` are those of the scene body and of its entities' bodies in source order (their uses are already folded, they are listed so the IR is a complete account); `entities` is flat in stable instance order (`spec/scenes.md` §10.1) with `index` (its position) and `parent` (an index or `null`). `Camera { name, symbol, span, active, position, target?, rotation, projection }`, `projection = { desc: { kind: "perspective", fovY, near, far } | { kind: "orthographic", height, near, far }, origin, span }`. `Entity { index, name, symbol, parent, span, position, rotation, scale, visible, mesh?, material? }`, `mesh = { desc: { kind: "box", size } | { kind: "sphere", radius, segments, rings } | { kind: "plane", size }, origin, span }` (the keys of the manifest's `meshes` entries), `material = { material: <symbol>, params: [{ name, type, source, span }], origin, span }` with every parameter in declaration order, written or defaulted. A field is `{ source: { "const": <value> }, origin: "written" | "default", span }`; `source` gains variants for initialisers that read state (M3) and bindings. Scene state, handlers, lifecycle functions, bindings with dependency edges, host inputs, lights and bodies join `Scene`/`Entity` with the milestones that implement them; new keys are added where they belong, keys are never reordered.
5. **Spans.** Every node has one, serialised as `{ "file": <id>, "start": <byte>, "end": <byte> }` (half-open, into the file as stored; the id is the module's `file`). A declaration's span is the whole declaration (`entity Crate { … }`; `CheckedScene`/`CheckedObject`/`CheckedEntity` gain `span` for this). A written field's span is the `name: value;` member. A registry default has no source, so its span is the declaration that holds the field (the entity for a default `scale`, the camera for a default `projection`). A material parameter's span is its material instance's: a descriptor may come from a constant, so per-parameter spans do not exist at every use. Line and column are not in the IR (the manifest's `spans` table computes them from the source map, decision 0019).
6. **Values** are tagged by their type: `{ "f32": 0.9 }`, `{ "u32": 24 }`, `{ "vec3": [0.0, 0.5, 0.0] }`, `{ "quat": [x, y, z, w] }`, `{ "color": [r, g, b, a] }` (linear, straight alpha, the folded colour of decision 0026, never the literal's bytes), `{ "mat4": [[…] × 4] }` (columns), `{ "struct": { name, fields: [{ name, value }] } }`, `{ "array": […] }`. Inside the typed descriptor nodes (`MeshDesc`, `ProjectionDesc`) the field types are fixed and values are plain numbers. An `f32` is written as the shortest decimal that reads back as the same binary32 value (`serde_json`'s `f32` formatting, the Ryu algorithm): lossless for any binary32 parser and identical on every host. Code generation reads the in-memory `f32`, not the JSON; how the manifest and the JavaScript print floats remains `spec/compiler-architecture.md` §6's rule.
7. **The two formats.** JSON: `serde_json` pretty printing (two-space indentation, keys in declaration order, camelCase) with arrays of numbers and objects whose members are all numbers (spans) on one line, and a final line break; the change is whitespace only (a unit test parses both forms). Human: an indented tree, one line per node with its symbol and `@line:column-line:column` (columns in Unicode scalar values), one line per field with its value in Mtek-like notation (`vec3(0.0, 0.5, 0.0)`, `u32(24)`) and `written`/`default`.
8. **Determinism.** No hash collections in `ir` or `inspect` (the guard test of `tests/determinism.rs` covers both); the IR depends only on the project's files. Every semantic pass fixture inspected twice and with shuffled `MemFs` listings gives byte-identical text in both formats.
9. **Goldens** are `tests/codegen/ir/<fixture>.ir.json` and `<fixture>.ir.txt` for the two M1 pass scenes of decision 0027 (`scene_a_target_camera_box`, `scene_b_orthographic_nested`), read from `tests/semantics/pass/`, blessed with `MTEK_BLESS=1 cargo test -p mtek-compiler --test ir_goldens` and reviewed like code. The directory holds nothing else (a test fails on a stray file). `ir/` is not a codegen fixture directory (`spec/testing.md` §3).

## Consequences

- No new dependency (`serde`, `serde_json` are in decision 0007's table) and no new diagnostic code (`E9999` exists).
- Callers that looked inside `check`'s result use `analyze`; the CLI task (M1-19) prints `check`'s and `inspect`'s results and maps `has_errors()` to exit code 1.
- Code generation (M1-16/M1-17) maps the IR to the manifest: `Scene.fields.clearColor` to `fields.clearColor` (the manifest's `ambientColor`, `ambientIntensity` and `gravity` belong to registry fields that M4/M5 implement, so until then the manifest builder takes their registry defaults), `Camera.projection.desc.kind` to `projection`, `target.is_some()` to `hasTarget`, entities one to one (`index`, `name`, `symbol`, `parent`), a `MeshDesc` per entry of `meshes`, a material instance per entity with a material.
- `spec/compiler-architecture.md` §4.8 and §4.12 point here.
