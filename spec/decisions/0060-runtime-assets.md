# 0060. Runtime assets: the loader and its states, integrity, image decoding and texture uploads, mesh buffers, device limits, recovery, reload and visible failures

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: §7.3 (assets are explicit dependencies; a missing or invalid asset never produces an unexplained black canvas), §7.4 (resource lifetime, device loss), §9.4 (diagnostics); `spec/assets.md` §5 and §6, `spec/runtime-abi.md` §5.5, §6.1, §9.4, §9.5, §10; decisions 0054 (textures and samplers), 0055 (culling), 0056 (resilience), 0057 (Pbr), 0058 (the asset compiler, whose manifest this consumes), 0059 (instancing).
- Amended by: decision 0082 (the image `source` gap and the EXIF question are closed).
- Supersedes: the `E8003` that decisions 0031 and 0054 gave to an asset mesh and an asset-valued texture param (the runtime now renders both).

## Context

Task M4-06 is the runtime side of assets. `spec/assets.md` §5 fixes the observable states, the verification (`E7030`), the decoding (`E7031`), the upload formats and usages and the `asset-failed` rejection. Decision 0058 §6 fixes the manifest the runtime consumes (`assets` entries with `url`, `sha256`, `bytes`, `kind`, `colorSpace`, per-primitive offsets, counts, index format and bounding sphere). They leave open how the loader is built, what the diagnostics say, what is retained for device recovery, how culling and instancing treat a mesh whose bounding sphere is not around its origin, how a hot reload treats assets, and how a test can observe the states. Everything below is a **proposal** unless it repeats the specification; external facts are labelled **constraint**.

## Decision

1. **The loader** (`packages/runtime-web/src/assets/loader.ts`). `loadAssets` takes the manifest, the base URL, the environment's `fetchBytes` / `sha256` / `decodeImage` and the device's `maxTextureDimension2D`, and resolves (it never rejects) with the verified files, the decoded images and one diagnostic per failed file in manifest order. Every file is fetched **concurrently**; each has the observable state `pending → ready | failed`: all files are `pending` first (synchronously), then each becomes `ready` or `failed` as it finishes (an image is `ready` only after it decoded). `options.test.onAssetState` receives every change; `debug.assets()` lists the files of the running program (`{ url, kind, state, bytes }`, all `ready` after a successful mount). These two test hooks are new (`runtime-abi.md` §10.2, `runtime.d.ts`).
2. **Integrity.** The URL is `url` resolved against `baseUrl` (the name is opaque and never parsed). Order: HTTP status (`ok`), body, **byte length** against `bytes`, then **SHA-256** against `sha256` when `crypto.subtle` exists. Every mismatch is `E7030` and the bytes are dropped: stale or tampered data is never used. Without `crypto.subtle` (an insecure context) only the length is verified, silently, as `spec/assets.md` §5 says (a loud warning on every plain-HTTP development page would be noise; the build identity already covers production). The digest comparison is on lowercase hex; the diagnostic carries `expected` and `actual` (the digests, or the lengths as `"N bytes"`).
3. **Diagnostics name the file and the declaration.** Every asset diagnostic has `source` = the manifest span of the entry, i.e. the **path literal** of the first `asset.*` call that named the file (`src/main.mtek:4:25`; the `spans` table points at the string with its quotes, decision 0058 item 3), the note `asset file: <url>`, and a message that begins with the packaged url and says what it is: `mesh data of 'models/chair.glb'` for mesh data (the GLB path comes from the primitives' `source.file`) and `image` for images. **Gap, reported to the owner:** an `image` entry carries no project path (a standalone texture's `textures/wood.png`, or the GLB an embedded image belongs to), so the overlay names the packaged url and the declaring location but not the author's file name for an image. The minimal compatible fix would be an optional `source` string on image entries; it is **not** made here, because it changes the compiler contract (a question was filed on the board). The overlay (`host/overlay.ts`, unchanged) prints code, title, message, location and notes, so it shows all of this.
4. **Images.** `decodeImage` is `createImageBitmap(new Blob([bytes]), { colorSpaceConversion: "none", premultiplyAlpha: "none" })`: no MIME type is passed (the browser sniffs PNG or JPEG), nothing is converted. **Constraint:** `imageOrientation` keeps its default `"from-image"`, so a JPEG with an EXIF orientation is rotated; the compiler does not inspect EXIF and the supported fixtures have none; `"none"` is not in the current DOM typings (a question about rejecting or pinning this was filed on the board). A decode failure is `E7031` (message `The browser could not decode the image '<url>': <browser message>`). A decoded size above `maxTextureDimension2D` is **`E8002`** (kind `device-failed`) at the declaration: the compiler checked the configured limit (at most 8 192, the WebGPU default of the only target profile), the device is re-checked at mount, and the bitmap is closed. A conforming device cannot trigger it; the unit tests do, with a smaller limit and an 8 193 pixel image.
5. **Textures** (`render/resources.ts`, `AssetTextures`). One texture per image file, created on first use through the registry (counted in `texturesAllocated` / `liveTextures`, inside the out-of-memory scope), `rgba8unorm-srgb` for `colorSpace: "srgb"` and `rgba8unorm` for `"linear"`, one mip level, usage `TEXTURE_BINDING | COPY_DST | RENDER_ATTACHMENT` (**constraint:** `copyExternalImageToTexture` requires the last two), filled by `ResourceRegistry.copyExternalImage` = `queue.copyExternalImageToTexture({ source, flipY: false }, { texture, colorSpace: "srgb", premultipliedAlpha: false }, size)`, counted as one upload of `width × height × 4` bytes. The destination colour space `"srgb"` is the only one WebGPU offers besides display-p3 and, with the bitmap decoded unconverted, writes the stored texel bytes as they are: an `-srgb` format reads them as sRGB-encoded (so `sample` returns linear values), a plain format as data. Instances whose texture param is `{ kind: "asset" }` bind the file's texture view in group 1 exactly as built-in textures are bound (decision 0054 item 7); the sampler param stays a built-in preset. Two instances that name the same file share one texture. `ResolvedInstanceResource` is now `ResolvedBuiltinResource | ResolvedAssetResource` (the latter carries the manifest's image entry).
6. **Mesh buffers** (`render/meshes.ts`). A mesh of kind `asset` is uploaded from the verified bytes of its file: for each region of the primitive (`mesh/asset.ts`, `meshRegions`: position, normal and uv if present, then the indices) one buffer through `uploadBuffer` and so through the registry (out-of-memory scope, `E8063`; usages `VERTEX | COPY_DST` and `INDEX | COPY_DST`), the bytes being the file's bytes at the manifest's offsets (no conversion: the compiler already de-interleaved, widened and narrowed, decision 0058 item 6). An odd number of `uint16` indices is padded to the 4 bytes `writeBuffer` needs. `GpuMesh.vertexBuffers` is now partial (only the attributes the primitive has; `vertexBufferOf` throws an internal error for an absent one, which a checked structure cannot reach). A region larger than the device's `maxBufferSize` is reported as `E8063` **before** anything is created (`ResourceRegistry.reportAllocationFailure`) and `startScene` throws; `mountMtek` turns an exception raised while an allocation failure was reported into `allocation-failed` with that diagnostic. Meshes are keyed `asset:<url>#<primitive>` (`meshKey`), so equal primitives share one upload and compatible instancing groups them like any mesh (decision 0059 needs no change). Index values are not scanned at run time (`E7014` is the compiler's); WebGPU's robust buffer access bounds an out-of-range index.
7. **Culling.** A mesh's bounding sphere is the manifest's (`center` and `radius`, in the mesh's local space) and, unlike the primitive shapes', its centre is not the origin. `GpuMesh.boundingCenter` carries it (the origin for a shape) and the renderer's per-entity sphere is `world · (center, 1)` with the radius times the largest world scale (`worldBoundingSphere` gained an optional centre; with none it is the translation as before). The unit tests place an entity whose origin is outside the view and whose sphere is inside (drawn) and the reverse (culled), and compare with the shape-style sphere.
8. **Manifest consistency** (`scene/structure.ts`, `E8006`, `manifest-invalid`, before any device work). An asset mesh must name a `mesh-data` entry and a primitive of it; every region of the primitive (offset a multiple of 4, positive counts, inside the file's `bytes`) must fit; the bounding sphere must be finite; an asset-valued texture param must name an `image` entry; and an asset mesh must have every attribute the shader of its entity's material reads (the compiler's `E7010` is re-checked, not trusted). Nothing of this is fetched first.
9. **Mount** (`host/mount.ts`). Assets load **concurrently with the startup shaders**, after the device exists (the limit check needs it); the failures of both are reported together, shaders first, and the mount error's kind is that of the first (`shader-failed` before `asset-failed`). Any asset failure rejects with `asset-failed` (`E7030`, `E7031`) or `device-failed` (`E8002`); `onDiagnostic` and the overlay get every one; the decoded bitmaps are closed in every path (after `startScene` returned, on failure, on an exception); a failed mount leaves no live resource, listener or device (the same cleanup as every mount failure). `mountMtek` resolves only when every file is `ready`.
10. **Device recovery** (decision 0056). The `LoadedAssets` (the verified bytes) are kept by the application. A rebuild decodes the images **again from the retained bytes** (no request, no re-verification; bitmaps are not retained because an `ImageBitmap` may be backed by GPU memory that a lost device takes with it), runs `startScene` in recover mode with them (meshes and textures are created exactly as at mount) and closes the bitmaps. **A defect found by this task and fixed:** `World.rebindParams` replayed every param of a material through the block writers, including texture and sampler params, which have no field in the block, so the recovery of **any** textured material (built-in textures included, decision 0054) failed all three attempts with `E8062`; resource params are now skipped there (the material store binds them from the manifest).
11. **Hot reload** (`replaceProgram`, development builds). The candidate's assets are loaded with the running program's files as `previous`: a file with the same url, hash and length is **not fetched again**; the images are decoded again for the candidate scene, and the new scene creates its own buffers and textures. A candidate whose asset fails is refused (`E7030`/`E7031`/`E8002`, phase `runtime:reload`) and the running scene is untouched; on a swap the application's files are replaced.
12. **Test support.** `HostEnvironment` gained `fetchBytes`, `sha256` (absent without `crypto.subtle`) and `decodeImage` (the real ones are `fetch`, `crypto.subtle.digest` and `createImageBitmap`; `environment.test.ts` pins their options); the fake host serves bytes, hashes with Node's crypto, decodes a trivial image format (`fakeImage`) and records every bitmap so tests assert they are closed; the fake queue implements `copyExternalImageToTexture` with the destination rules of WebGPU. The browser fixtures are generated by `tests/assets/tools/make-glb.mjs` (checked by `--check` in `npm run check`).
13. **Not in this record:** mip-map generation (`spec/assets.md` §3 records it), KTX2/Basis, lazy or streamed assets and assets after mount, retry and progress events, remote URLs (`E7901`), a Cache API layer, EXIF orientation control, texture parameters beyond the base colour (v0.2), scanning of index data.

## Consequences

- `spec/assets.md` §5 and §7, `spec/runtime-abi.md` §5.5, §6.1, §9.4, §10.2, `spec/diagnostics.md` §5.7 (`E7030`, `E7031`) and §5.8 (`E8002`), `spec/testing.md` §1 and `spec/decisions/0054` point here. The compiler's `tests/fixtures.rs` lists `E7030` and `E7031` as covered by `loader.test.ts` instead of "not yet implemented".
- The material-configurator example (M4-10) can use `asset.glb`, `asset.texture` and `material_texture` with the runtime as it is; only the image's author-facing file name in a failure message is missing (item 3).
- A texture is created per image file, never per instance; a scene with many instances of one textured material still has one texture and, by decision 0059, one instanced draw.
