# 0095. Runtime benchmark: how each metric is measured, what "frame time", "GPU time" and "allocations" mean, and the hardware-only refusal

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: §12.3 (runtime benchmark), M7 (blueprint §11), task M7-04; `spec/ai-and-benchmarks.md` section 7; `spec/runtime-abi.md` sections 8.1, 10.1; decisions 0012 (browser test environment), 0055 (counters, GPU time).
- Supersedes: nothing. Followed by 0096 (workloads), 0097 (freezing), 0098 (results and report), 0099 (findings).

## Context

`spec/ai-and-benchmarks.md` section 7 names the metrics (CPU update time, render-preparation time, GPU time only with `timestamp-query`, frame-time distribution p50/p95/p99 over at least 600 frames after 120 warm-up frames, upload bytes, draw calls, pipelines created, allocations, bundle size, startup latency) but not how each is measured, and three of them are ambiguous in a browser: **frame time** (the presented cadence of a page is capped by the display and hides every workload that is faster than a refresh), **allocations** (GPU objects, JavaScript objects, or memory?) and **GPU time** (a timer that has no feature behind it must not be replaced by another clock). Every choice below is a **proposal**; the facts about Chromium and WebGPU are **constraints**.

## Decision

1. **Frame time is the CPU time of one frame**: `performance.now()` around `app.frame(dt)`, which is the update (input, fixed ticks and physics, update functions, bindings, transform propagation, animation maths) plus render preparation (culling, draw-list building, uploads, command encoding) up to the return of `queue.submit`. It is the same quantity as the runtime's own `frameTimeMs` counter, which the development overlay reports. The p50 / p95 / p99 are **nearest-rank** percentiles (the sample of rank `ceil(p/100 * n)`, `harness/stats.ts`) over the measured frames of a run, and a workload's figure is the **median across its timing runs** (3 runs, each in a fresh page) of the per-run percentiles, with the range of the p95 reported. The investigation threshold of 20 % is applied to this p95 (decision 0096 says to which metric for the two workloads that are not frame workloads).
2. **Why not the display cadence.** **Constraint**: a page drawing into a canvas is presented at the display's refresh rate; every workload here costs a few milliseconds of CPU at most, so a `requestAnimationFrame` interval would be the refresh interval for every implementation. The benchmark therefore drives frames from a manual loop into an offscreen `rgba8unorm-srgb` target of 640 x 360 with a `depth24plus` target (Mtek: `test.manualClock` with `test.renderTarget`, a mode the runtime supports for tests; the other two render into targets of the same format), one frame per loop iteration, with a fixed delta of 0.016666668 s (exactly one fixed physics tick per frame).
3. **The loop keeps one frame in flight.** After each frame the page waits for `queue.onSubmittedWorkDone()`. That keeps the CPU time free of back-pressure from a queue that is full. The wait is timed as **frame latency to GPU completion** and reported, but it is **not** used for the threshold: **constraint** (measured, in the report's harness floor): an empty frame already costs a queue round trip of a few milliseconds in headless Chromium, which would swamp the 0.05 to 2 ms differences between implementations and make every ratio look closer to 1 than the work is.
4. **CPU update time and render-preparation time** are the two parts of item 1. Mtek's are its own counters `cpuUpdateMs` and `renderPrepMs` (read after the frame, outside the timed window); the direct and three.js implementations time the same two parts around their own code. three.js updates matrices inside `renderer.render`, so its split differs by convention; the sum is what is compared.
5. **GPU time exists only with `timestamp-query`.** A separate pass on its own page load requests the feature on the device (the instrument adds it to `requestDevice`; the adapter of the recorded environment offers it) and the instrument puts `timestampWrites` on every render pass the application begins, resolves them in the encoder's `finish`, and the page reads the sum of end minus begin after the frame's work is done. All three implementations are timed by the same code, so Mtek's release runtime flavour (which has no timer of its own; the development flavour's timer samples one frame in flight at a time, decision 0055) is measured the same way as the others. Without the feature the figure is printed as **unavailable** with the reason; it is never derived from a CPU clock. One command encoder per frame is timed (all three implementations record a frame in one encoder); a frame with more is counted in the raw result (`encodersSkipped`) and not timed. **Constraint**: `--enable-webgpu-developer-features` (already in the hardware launch arguments, decision 0012) disables Chromium's timestamp quantisation; the values are small (microseconds) and are printed as measured.
6. **Counters come from an instrument, not from the runtime.** `harness/instrument.ts` wraps the WebGPU prototypes before any application code runs and counts draw calls (`draw`, `drawIndexed`, the indirect forms, with instances), `writeBuffer` / `writeTexture` / `copyExternalImageToTexture` calls and bytes (**upload bytes** = the sum of the three, plus buffers created with `mappedAtCreation`, counted separately), and creations of buffers, textures, samplers, shader modules, bind groups, bind-group and pipeline layouts, render and compute pipelines (**pipelines created** counts both kinds and the asynchronous creators), plus destroys. The same code counts all three implementations; Mtek's own counters (`drawCalls`, `pipelinesCreated`) are compared with the instrument's in the report as a check that the instrument sees what the runtime reports (they must agree; a disagreement is printed as DIFFER). Counting costs CPU time, so it runs in its own pass: the timing pass installs only the device capture (one call per device).
7. **Allocations are two numbers.** (a) **GPU objects created per steady frame** (buffers, textures, samplers, shader modules, bind groups, pipelines): zero for a renderer that retains its resources, and the report states the largest count seen in any counted frame; and (b) **JavaScript heap bytes allocated per frame**, from the Chrome DevTools Protocol sampling heap profiler (`HeapProfiler.startSampling`, 4 KiB interval, collected objects included) over 300 measured frames of a pass of its own, divided by the frames; the allocation sites with the most bytes are stored with the result. It is a statistical estimate (the report says so) and includes what the harness's own frame loop allocates, which the harness floor measures (an application that draws nothing). **Constraint**: WebGPU exposes no GPU memory use to a page; memory is therefore reported only as bytes the application created and did not `destroy()` (instrument), and as the JavaScript heap after a forced collection (DevTools `Runtime.getHeapUsage`).
8. **Startup latency** is the time from the start of the page's navigation (`performance.now()` origin) to the completion of the first frame on the GPU, over 15 fresh page loads in fresh browser contexts (no HTTP cache; the files come from a local server). The page also records the part between the call that creates the application and the first frame. For Mtek it includes the dynamic import of the program module and the runtime bundle (as `mtek build` ships them) and the fetching and validation of the manifest, shaders and assets.
9. **Bundle size** is the JavaScript the page runs, raw and gzip (level 9): Mtek as `mtek build` ships it (unminified in v0.1), direct and three.js bundled by esbuild without minification; the minified figures apply esbuild's minifier to all three. Mtek's program data (manifest, shader files, packaged assets) is separate; its physics module is a lazily loaded file counted in its JavaScript total.
10. **One pass per page load.** Timing, counting, GPU time, allocation, picture (parity), startup and the mount/reload/dispose cycles each run in a fresh page in a fresh context, so no pass perturbs another; the passes of a run are executed in a pseudo-random order (a recorded seed) so that drift of the machine over the run does not line up with an implementation.
11. **Hardware only, and the refusal.** The runner probes the adapter with the environment probe of the browser test harness (`tests/browser/support/env-probe.ts`, `buildEnvironmentRecord`, validated against `tests/browser/environment.schema.json`) and **refuses to measure** unless `navigator.gpu` exists, an adapter exists and `isFallbackAdapter === false` (`tools/adapter.ts`): it writes `run.json` with status `not-run` and the reason, prints `NOT-RUN`, and exits with code 3, never 0. The environment record is stored next to every result (`environment.json`). A `--smoke` run (a handful of frames, to prove the machinery) is allowed on any adapter that passes the same check, is never published and is marked as smoke in its `run.json`; the report generator prints it as "not a result".
12. **Shared machine.** The runner holds the machine's GPU lock (`MTEK_GPU_LOCK_DIR`, a directory created atomically with `mkdir`, released in a `finally` and on exit signals) around every pass, waits up to 45 s before a pass for the machine's CPU busy share to fall to 30 % or less, and records the busy share before and during every pass and whether it was still above the limit (`noisy`). The report shows the distribution. Nothing is trimmed.

## Consequences

- The numbers describe CPU cost of the application and runtime on this machine, not presented frame rates; the report says so in its limitations.
- A workload that becomes GPU-bound on other hardware would need its GPU-time row read first; the harness already produces it.
- The instrument has its own unit tests against a fake WebGPU (`harness/instrument.test.ts`), including the element-versus-byte semantics of `writeBuffer`'s `dataOffset` and `size`.

## Verification

- `npm run test:unit -w @mtek/runtime-benchmarks`: `harness/stats.test.ts` (nearest-rank percentiles, the p95 of 600 samples is the 570th), `harness/instrument.test.ts`, `tools/adapter.test.ts` (a fallback adapter, a missing adapter and a browser without WebGPU are NOT-RUN), `tools/plan.test.ts` (the protocol has at least 120 warm-up and 600 measured frames in every frame pass).
- `node tools/run.ts --smoke` ran every pass on the recorded hardware before the numbers were taken.
