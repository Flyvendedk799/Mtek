# 0067. Bindings that read light fields and hot reload of light colour and intensity: the `light` dependency kind, the update classes of light fields and the migration rule

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M4 (blueprint §11), follow-up task M4-14 of the M4-02 question; `spec/scenes.md` §8.4; `spec/materials.md` §7; `spec/runtime-abi.md` §§5.2 and 11.3; `spec/diagnostics.md` (`E5005`, `E5075`); decisions 0019 (manifest versioning), 0051 (`bind`), 0053 (lights), 0059 (update classes of material params), 0065 (item 9: body properties), 0081 (the last manifest key added without a version change).
- Supersedes: items 6 and 11 and the two matching known limitations of decision 0053 (a binding could not read a light field; a hot reload reset every light value). Nothing else of 0053 changes.
- Numbering note: 0066 is the physics runtime (M5-05), written in parallel.

## Context

A binding may read the fields of named entities, their state, material params, scene state and `frame`; the manifest records those reads as dependencies and the compiler orders the bindings by them. Decision 0053 left two things out because the manifest had no vocabulary for them: a binding could not read the colour or intensity of a light (`E5005`, the precedent of camera fields), and a hot reload gave every light the values its new `init` set, so a colour or intensity that a handler had written was lost (transforms and `imperative` material params were already carried). The owner asked for both as a follow-up (task M4-14): a `light` dependency kind, and a per-field update class for light colour and intensity. Every choice below that the specification does not already make is a **proposal** the owner may overrule.

## Decision

1. **Dependency kind** (constraint of the task, shape a proposal). The manifest's binding dependencies gain `{ "kind": "light", "entity": i, "field": "color" | "intensity" }`, `entity` being the static entity index, the same shape as the binding target of the same name (`spec/runtime-abi.md` §5.2, `spec/manifest.schema.json` `lightDep`, `MtekBindingDependency` of the runtime's types, `BindingDep::Light` in the compiler's manifest model, `ir::BindingDep::Light`, `types::BindDep::LightField`).
2. **What counts as a dependency** (proposal). A read of `Name.light.f` in a `bind` expression is a dependency when the registry marks `f` bindable, i.e. when `f` can change after construction: `color` and `intensity`. A read of `range` is allowed and is **no dependency**: it is fixed at construction, so nothing orders a binding against it, and the runtime record always holds it. The check asks the registry (`FieldFlags::BINDABLE` of the light's schema), so a later light field that is writable and bindable is a dependency without a change here. Only named entities have lights (a light in a prefab is `E5110`), so the reads are always `Name.light.f`.
3. **Order and cycles** (constraint, decision 0051 item 4, unchanged code). A binding that reads a light field depends on the binding that writes it, if any: `BindDep::reads` gained the pair (`LightField` dependency, `LightField` target). The order is topological with ties by declaration order, so a binding declared before the light binding it reads is still evaluated after it; a cycle, through lights only or through a light and a transform, a parameter and so on, is `E5075` with the existing message, one report per cycle and every binding of the cycle as a related span, the targets spelled `Sun.light.intensity`. A binding that reads its own target is a cycle of one. A light field that no binding writes (a literal, or written by a handler) makes no ordering: handlers run in phase 3, bindings in phase 5, so a binding reads the value a handler wrote in the same frame.
4. **What stays `E5005`** (constraint). Calls of `cpu fn`s and CPU intrinsics, reading a camera field (decision 0051 item 2) and reading a body property (decision 0065 item 9) are still `E5005`: no dependency kind covers them. The note of the diagnostic names what a binding may read, now including "the colour and intensity of their lights". The fixture that expected `E5005` for a light field (`e5005_bind_reads_light_field`) is now the pass fixture `bind_reads_light_field`; `e5005_bind_reads_camera_field` and `e5005_bind_reads_body_velocity` keep the failing cases.
5. **Update classes of light fields** (proposal, the classes of material params of decision 0059 with the same meaning). Each of `color` and `intensity` is `bound` when its value is a `bind`, `imperative` when some lifecycle function or handler writes it (the writes the single-writer analysis already records, `WriteTarget::LightField`), and `initial` otherwise (a constant that only `init` sets). Bound and written are exclusive (`E5070`). The IR has them as `Light::color_update` and `Light::intensity_update` (`UpdateClass`, never `Resource`), set when the light is lowered and raised to `imperative` by the same pass that marks material params; the manifest carries them as `scene.lights[].classes: { "color": c, "intensity": c }` with `c` one of `"initial"`, `"imperative"`, `"bound"` (`spec/manifest.schema.json` `lightClasses`; required for both kinds of light). `range` has no class: it is never written after construction.
6. **Hot reload** (proposal; `spec/runtime-abi.md` §11.3). When `replaceProgram` swaps without a restart, `migrateWorld` handles the light of every entity that exists in both programs by identity (the entity symbol), field by field:
   - **kept**: the field is `imperative` in the previous **and** the next program, both lights exist and have the **same kind**: the value the running record holds is written into the new record through `ctx.setLight` (a colour is copied), after the new `init` ran;
   - **applied**: the next program's field is `initial`, or was not `imperative` before: the new record keeps what the new `init` set, so an edited literal is live;
   - **evaluated again**: the next program's field is `bound`: the bindings run after the swap, in phase 5 of the first frame, on the migrated state (an edited formula is live, and a binding that reads a kept light field sees the kept value);
   - a light that was **added**, **removed** or whose **kind changed** is not migrated: the new `init` made it (as before this decision). None of these restarts the scene (`findStructuralChange` does not look at lights), and no other state is touched: scene and entity state, transforms and material params migrate by their own rules.
   The rule needs both classes because the previous value of a field that was `initial` or `bound` is the old literal or the last evaluation, which the author just edited away, and a field that is `imperative` now but was not before has no run-time value worth keeping.
7. **Known limit, as for material params** (recorded, not fixed). An `imperative` field keeps the running value even if the source literal changed in the same edit; the literal of an `imperative` field is only its starting value. A field a handler writes only on some event, and that has not been written yet, keeps its old starting value: the runtime cannot tell it from a written one.
8. **Runtime evaluation is unchanged.** Every binding is still evaluated once after `init` and every frame in phase 5 in the manifest's `order`; the runtime does not read `deps`, so the new kind adds no runtime check beyond the schema (`E8006` for a malformed one) and the structure checks stay (a prefab cannot bind a light).
9. **Versions** (proposal). `manifestSchema` and `runtimeAbi` stay `1`, as in decision 0019 ("the project is pre-release and no manifest has shipped") and the changes since (0064, 0065, 0081 added required keys the same way). The new dependency kind and the required `classes` are additions to the schema of v0.1: a runtime that does not know them rejects the manifest with `E8006` at validation (never silently), and compiler and runtime are built from the same tree. Every manifest example and golden that carries a light was updated; none needed a version.
10. **Inspection.** `mtek inspect --ir` prints a light dependency as `entity#1.light.intensity` in the `reads` list of the binding (golden `tests/codegen/ir/bind_reads_light_field`); the manifest shows the dependencies and the classes.

## Fixtures and tests

- Pass: `bind_reads_light_field` (a binding declared first that reads what two other light bindings write, a light bound to a transform that is bound to a light, a read of `range`), and the codegen fixtures `light_bindings` and `light_bindings_edited` (`tests/codegen`, golden manifests, `app.js`; the second is the first with an edited literal colour, an edited formula and an edited literal intensity).
- Fail: `e5075_light_binding_cycle`, `e5075_light_and_transform_cycle`, `e5075_binding_reads_own_light_field`; the `E5005` cases that remain are `e5005_bind_reads_camera_field` and `e5005_bind_reads_body_velocity`.
- Compiler: `tests/build.rs` (`bindings_that_read_light_fields_are_ordered_by_them_and_lights_carry_update_classes`: ids, orders, dependencies and classes derived by hand), `tests/ir_goldens.rs` (`bind_reads_light_field`), `tests/manifest_model.rs` and the shared examples `tests/abi/manifests` (the dependency in `valid/full.json`; invalid: `binding-light-dep-bad-field`, `light-missing-classes`, `light-unknown-class`), the unit test of the manifest key order.
- Runtime (`packages/runtime-web/src/host/light-bindings.test.ts`): the compiler's `light_bindings` program mounts and its bindings are evaluated in dependency order after `init` and every frame (a binding that reads a bound light field, a binding that reads a field a handler wrote in the same frame, and bindings that feed lights; the packed frame block is read back); a reload to `light_bindings_edited` applies the edited colour literal and formula, keeps the value a handler wrote and the unrelated scene state, does not restart, and a second reload back applies the old literal again; `migrateWorld` on hand-made manifests for every combination of classes, a changed kind, an added and a removed light, and the colour copy. `abi.test.ts`, `structure.test.ts`, `world.test.ts` and `renderer.test.ts` carry the new manifest key.
