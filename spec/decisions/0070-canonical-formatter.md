# 0070. The canonical formatter: `mtek fmt`, comment attachment, blank lines, width, literals, the self-check and the corpus properties

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §10, §11), task M6-01; `spec/tooling.md` §5 (the rules and properties; blueprint D14 §5), `spec/compiler-architecture.md` §4.3 (the trivia side table; blueprint D09 §4.3), `spec/language.md` §§1.2, 1.5, 2.5, `spec/grammar.ebnf`, `spec/grammar-notes.md`; decisions 0032 (CLI details), 0042 (grammar freeze: no grammar change here).
- Supersedes: nothing. Every detail below that `spec/tooling.md` §5 leaves open is a **proposal** of this record, marked as such.

## Context

`spec/tooling.md` §5 fixes the style (4 spaces, 100 columns, LF, descriptor literals on one line when they fit, one blank line between items, comments preserved) and three properties (idempotence, the same tree, the same comments). It does not say where a comment goes when it sits between two tokens of an expression, what a blank line between members means, how a long call or condition wraps, how literals are spelled, what happens to a file that does not parse, or how the command behaves (exit codes, `--check` output, which files). The lexer already keeps comments in a side table keyed by the following token (`Trivia`, M1-04) and the AST has spans and keeps parentheses (`ExprKind::Paren`), so an AST-based printer needs no new syntax-stage data.

## Decision

1. **Shape.** `mtek_compiler::format` (`crates/mtek-compiler/src/format/`) is a library function on text: `format_text(file, text) -> Result<String, Vec<Diagnostic>>` and `comment_texts(file, text)`; it performs no I/O (`tests/no_direct_io.rs`). The printer builds a `Doc` (text, groups, indentation, `Line`/`SoftLine`/`HardLine`, `IfBreak`) from the tree and renders it in 100 columns (Wadler/Prettier algorithm with the rest-of-the-line lookahead: a group is flat when it and everything up to the next possible break fit). The layout depends on the tree and the comments only, never on the source's line breaks, which is what makes it idempotent. `mtek fmt` (`crates/mtek-cli/src/fmt.rs`) finds files, reads and writes them, and reports.
2. **Files that do not parse are refused** (proposal). Lexical or syntax errors (any error diagnostic of the lexer or parser) are returned as the diagnostics and **nothing is formatted or rewritten**; warnings (`W0007`) do not stop the formatting and are not reported (the formatter is not the checker). Semantic errors are not looked for: a program with type errors formats (`tests/semantics/fail` fixtures that parse are in the corpus). In the CLI a refused file is reported like `mtek check` reports it and the run's exit code is 1; the other files are still processed.
3. **The self-check** (proposal). `format_text` re-parses its own result and returns it only if the tree (`dump_module`, which carries no spans) and the multiset of comment texts equal the original's; otherwise it returns `E9999` ("this is a compiler bug", the note says which property failed) and the CLI leaves the file untouched (exit 3). The two properties that decide whether a rewrite is safe are therefore guaranteed on every run, not only in tests; idempotence is a property of the algorithm, tested on the corpus.
4. **Literals are printed as written** (as `spec/tooling.md` §5 says for numbers; this record extends it to strings). Integer and float literals are copied from the source (`1.0` stays `1.0`, `1` stays `1`, `2.50e-3` and `1.0E3` keep their spelling): the spelling decides the type, and the lexical rules already make it canonical. String literals keep their escapes (`\u{41}` is not turned into `A`, which would also lose the author's intent). Colors are lowercased (`#AABBCC` → `#aabbcc`), the one rewrite of a literal. The parenthesization is the author's (`Paren` nodes are kept; `-(5)` ≠ `-5`).
5. **Layout rules, concretely.**
   - A body (`{ … }` of an item, a block) has one member per line, indented 4 spaces, `{` on the header's line, `}` alone; an empty body is `{}`; `} else {` and `} else if … {`.
   - Binary operators, `=` and the assignment operators have a space on both sides, `,` `;` `:` a space after (descriptor fields: `;` between fields), `..` in a `for` header none, prefix `-` and `!` none, no space inside `()`, `[]`.
   - A call, a parameter list, an array literal, an import list and a handler's arguments are printed on one line if the whole line fits in 100 columns, else **one element per line with a trailing comma** (all of these accept one, `spec/grammar-notes.md` item 3); a trailing comma in the source is dropped when the list fits. An import list is `import { A, B } from "…";` or broken with `{`, one name per line, `} from "…";`.
   - A descriptor literal is `Name { a: 1; b: 2 }` (no trailing `;`) when the line that contains it fits in 100 columns (the rest of the line after it counts, a trailing `;` or `,` included), else `Name {`, one field per line each ending in `;`, `}`. An empty descriptor is `Name {}`. Nested descriptors decide for themselves, outermost first. `bind(…)` is a call-like group.
   - A chain of binary operators of one precedence level (`a + b - c`, `a && b && c`) is one group: if it does not fit, **every operator starts a line**, indented one level (proposal: operator first, as Rust does). Operands of a different level are groups of their own.
   - The width is counted in characters (Unicode scalar values), not bytes or display columns. A line of exactly 100 columns fits. Comments and string literals are never wrapped, so a line can exceed 100 when it holds one.
   - Wrapping never changes the tree (white space is not significant anywhere in the grammar) and `{` stays on the line of the header: a condition that must wrap leaves `{` at the end of its last line.
6. **Blank lines** (proposal where §5 is silent). *Items* of a module are separated by exactly one blank line (§5), with one exception: **consecutive `import`s keep the source's choice** of none or one blank line, so import blocks stay grouped; the blank line is also put between the last import and the first other item. *In a body* (members, statements) the source's blank lines are kept, at most one in a row; none at the start or the end of a body and none between a doc comment and what follows it. Consecutive single-line `const`s are items and so get a blank line between them (the literal rule; the examples' import line and `model.mtek` change accordingly). Blank lines inside lists, expressions and descriptor literals are not kept.
7. **Comments** (proposal; §5 only says "doc comments stay attached to the following declaration; other comments stay at their relative position"). Comments are attached by position against the spans of the tree, in one pass in source order, so none can be printed twice or out of order. The unit of attachment is the comment's place between two tokens, and the printer never moves a comment across a *documentable* token (below). A comment *starts its line* if only white space precedes it on its line.
   - *In a body*: a comment before a member is printed on its own line before it (blank line before it kept, ≤ 1; the whole comment-and-member group counts as the item for the blank-line rule of item 6); a comment on the line where a member ends, after it (`let x = 1; // c`); a comment after the last member, before `}`, on its own line; a comment on the line of the `{` after the `{` (`fn f() { // c`), up to the first `//` comment, which ends the line (what follows goes on lines of its own in the body). A comment between a header and its `{` stays **before** the `{` (`fn f() /* c */ {`; after a `//` comment the `{` starts the next line): after the brace it would be taken for the first member's, and a doc comment would document it.
   - *In a list* (arguments, parameters, array elements, descriptor fields, import names): after an item's separator, on its line → printed after the separator (`a, // c`); on its own line before an item → before it, on its own line; after the last item → after the (broken) trailing separator; a `//` comment forces the list to break. A comment between an operator and its right operand is printed before the operand; between the left operand and the operator, after the left operand (`a /* c */\n + b`).
   - *Everywhere else* a comment is printed before the next node that starts after it (`let x /* c */ : T` → `let x: /* c */ T`), and one that is left when a member ends (a comment right before its `;`) is printed before the `;`. A `//` comment always ends its line (the next token starts a new one, indented as a continuation); a block comment is followed by a space. No comment is ever moved to a different member, and the order of the comments in a place is kept.
   - *Block comments* nest as in the lexer and are printed **verbatim**: the interior lines of a comment that spans lines keep their characters and their indentation (they are never re-indented, so the text is preserved bit for bit and the printing is stable); `\r\n` inside a comment becomes `\n`. A `//` or `///` comment loses its trailing spaces and tabs and nothing else (no space is inserted after `//`). Comment texts are never wrapped. These are the only text in the output that can have trailing white space (inside a multi-line block comment) or be wider than 100 columns.
   - *Doc comments* (`///`): consecutive doc comments are one group with no blank line between them or before the declaration; a blank line before the group is kept. A doc comment that documents nothing (`W0007`) stays that way: the printer keeps the comments between two tokens as a run (the parser's rule of `W0007` looks at the run before a documentable token), never moves a comment to before a documentable token it was not before, and a doc comment before a body's `{` stays before it. The corpus test compares the diagnostics (`W0007` count included) of the original and the formatted text.
8. **Other text.** A leading byte-order mark is dropped; `\r\n` is written `\n`; one final newline, none for an empty file (a file of only blank lines becomes empty); no trailing white space.
9. **The command** (`spec/tooling.md` §1, proposal for the unspecified). `mtek fmt [--check] [PATHS…]`: each path is a file (formatted whatever its name) or a directory (every `.mtek` file below it, sorted; directories named `node_modules`, `target`, `dist` and names starting with `.` are skipped, symbolic links are not followed); no path means the current directory; no `mtek.toml` is needed. A path that does not exist is an I/O failure. Without `--check` a file whose text changes is rewritten (written to a neighbour `*.fmt-tmp` and renamed over the file, so a crash leaves the old or the new file); with `--check` nothing is written. Output: `formatted <path>` per rewritten file or `would reformat <path>` per file that is not canonical, on **stdout**, then a summary on stdout (exit 0: `checked N files: all formatted`, `N files already formatted`, `formatted K of N files`) or on stderr (failure: `fmt --check failed: K of N files would be reformatted (run mtek fmt to format them)`); diagnostics of refused files on stderr as `mtek check` prints them (paths relative to the working directory). Exit codes: **0** all canonical / formatted; **1** `--check` found a file that is not canonical, or a file does not parse; **2** usage error; **3** an I/O failure or `E9999`. There is no `--format json` (the output is a list of files).
10. **Format the repository's sources.** `examples/` and the CLI template `crates/mtek-cli/templates/main.mtek` are formatted by `mtek fmt` and CI runs `mtek fmt --check examples benchmarks crates/mtek-cli/templates` in the Rust job (all of `benchmarks/`, which was already canonical; **the holdout tree hash is unchanged**, nothing under `benchmarks/holdout/` was read or rewritten). The test fixtures of `tests/` are **not** rewritten: their layout is part of the fixtures (diagnostic spans, `// covers:` lines, goldens with line numbers); they are in the property corpus instead. `crates/mtek-compiler/src/stdlib/std/materials.mtek` (embedded in the compiler, its spans reach shader maps) is left as it is; it passes the properties and is not checked by CI. Browser tests that edit an example's text by string replacement (`tint: bind(tint);`, `on key_down(Key.Space) {`) still match; spans and goldens that embed example text did not need `MTEK_BLESS`.
11. **Not done.** The naming lint `W0030` (`spec/language.md` §3.3) is not part of `spec/tooling.md` §5 and is not implemented. Range formatting, a stdin mode and configuration are not provided ("no options"). Comments inside a multi-line block comment are not re-indented (item 7).

## Fixtures and tests

- `crates/mtek-compiler/src/format/tests.rs`: one test per rule above (layout, operators, literals, descriptors at the 100/101-column boundary, wrapping, blank lines, every place a comment can be, doc comments, refusal, idempotence of every expectation).
- `crates/mtek-compiler/src/format/doc.rs` tests: the layout algorithm.
- `crates/mtek-compiler/tests/format_corpus.rs`, over every `.mtek` file of the repository (856 files: `tests/syntax`, `tests/semantics` pass and fail fixtures, `tests/codegen`, `tests/assets`, `tests/browser`, `tests/modules`, `examples`, `benchmarks`, the template, the standard materials): the 728 files that parse satisfy **idempotence, equal tree, the literals as written, equal comment multiset, equal parser diagnostics, canonical text**, and the 128 that do not parse (the syntax/lex and syntax/fail fixtures and the semantic fixtures with syntax errors) are all refused with errors and never `E9999`. Two mutation tests then insert comments of six kinds (inline block, `//`, own-line, nested block, multi-line block, doc) before tokens of the corpus: one comment at a time (20 223 programs, every kind at a rotating token of every file) and 2 to 5 at once (2 904 programs); `MTEK_FMT_EXHAUSTIVE=1` runs every kind at every token and 60 rounds of several comments (see Verification). The benchmark holdout is part of the plain corpus test (its failures print only the path) and is excluded from the mutation tests, whose failures print the program.
- `crates/mtek-cli/tests/cli.rs`: `mtek fmt` end to end (rewrite, `--check`, refusal, exit codes, directories, idempotent second run, nothing written on error), `args.rs` tests for the arguments.

## Consequences

- Authors and agents get one layout; diffs of formatted files are minimal and independent of how the author wrapped lines.
- A source change in `examples/` that is not formatted fails CI (Rust job).
- The formatter is part of the compiler crate (it uses the lexer, parser and `dump_module`), which keeps one tree definition; an LSP formatting request (M6-xx) can call `format_text` on a buffer.
- Because the output is verified on every run, a printer defect cannot corrupt a file; it shows up as `E9999` and a bug to fix.
- Known rough edges, all in rare comment placements (item 7): a comment between a function's name and `(`, or inside a type, moves to the next node; a `//` comment in the middle of an expression forces its enclosing groups to break and puts the rest of the expression on the next line.
