# 0029. Shader IR, standard stage and shader artifact: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §5.2 (WGSL from a typed shader IR, Naga as validator), §7.2 (only the vertex attributes a material reads); `spec/compiler-architecture.md` §4.9, §4.11, §7, §8; `spec/materials.md` §3.2, §3.3; `spec/gpu-layout.md` §5, §6; `spec/runtime-abi.md` §5, §5.4; decisions 0010, 0013, 0028.

## Context

Task M1-16 builds the shader IR, the WGSL printer and span map, the generated standard vertex stage and fragment wrapper, and the temporary compiler-built `Unlit` of decision 0013. The specification fixes the interface (entry names, attribute and varying locations, the binding plan, mangling prefixes, the span-map file) but not the files the code lives in, the generated identifiers inside the wrapper, how `SurfaceInput` reaches the fragment body, how fine the span map is, what `emit_wgsl::validate` needs to map an error, or the shape of the result M1-17 and M1-18 consume. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Files.** The shader IR types are `lowering/shader_ir.rs`, the standard stage is `lowering/standard_stage.rs`, and the temporary `Unlit` is `lowering/builtin_unlit.rs` (first line `// TEMPORARY (decision 0013): removed in M2-09`). `lowering/shader.rs` of §4.9 (typed IR of user code → shader IR) arrives with M2. `emit_wgsl/` gains `printer.rs`, `span_map.rs` and `artifact.rs`. `<hash8>` and the material block names of `spec/gpu-layout.md` §5 are `layout::naming`. `lowering/` joins the determinism guard.
2. **IR shape.** Expressions are typed (`ShaderType` is the WGSL type of `spec/gpu-layout.md` §3: a stored `bool` is `u32`, a padded element is its `MtekPad16_*` struct) and every node has an Mtek `Span`. Struct declarations of blocks are built from layout records with exactly the attributes of the block emitter; a test proves the printer reproduces every `tests/codegen/wgsl-blocks/` golden. A `Name` is `Generated(suffix)` (printed `mtek_<suffix>`) or `User { kind, name }` (printed `u_<fn|l|p>_<name>`); struct and member names come from the layout naming rules. M1 implements `let`, `return`, literals, locals, globals, field access, swizzles, constructors, `*`, `normalize` and calls; M2 adds variants to the same enums.
3. **Printing.** 4-space indentation, one struct member, global or statement per line, `\n` line ends, a final line break. Structs (a blank line between two), then the globals as one block, then functions (a blank line before each); an entry point's `@vertex`/`@fragment` is on its own line. A binary sub-expression is parenthesised as an operand or as the base of a field access or swizzle, and so is a negative literal operand. `f32` literals use the shortest text that reads back as the same binary32 value (`1.0`, `0.1`, `1e-7`); `i32::MIN` is printed `i32(-2147483648)`.
4. **The standard stage.** Declarations in this order: `MtekLight`, `MtekFrame`, the param block (if any), `MtekObject`, `MtekVertexOutput`, `MtekSurfaceInput` (if any field is read); the globals `mtek_frame`, `mtek_params` (if any), `mtek_object`; the functions `mtek_fragment`, `mtek_vs`, `mtek_fs`.
   - `mtek_vs(@location(0) mtek_position[, @location(1) mtek_normal][, @location(2) mtek_uv]) -> MtekVertexOutput` computes `let mtek_world = mtek_object.model * vec4<f32>(mtek_position, 1.0);`, when `world_normal` is read `let mtek_world_normal = normalize((mtek_object.normal_matrix * vec4<f32>(mtek_normal, 0.0)).xyz);`, and returns `MtekVertexOutput(mtek_frame.view_proj * mtek_world, <read fields>)` where `local_position = mtek_position` and `world_position = mtek_world.xyz`.
   - `MtekVertexOutput` is `@builtin(position) clip_position` plus one member per read field, named like the field, at its fixed location (0–3).
   - `MtekSurfaceInput` holds only the read fields, named like the Mtek fields (`world_normal`), so the M2 lowering of `surface.uv` is a plain field access. The fragment body is `fn mtek_fragment(<surface param>: MtekSurfaceInput) -> vec4<f32>`, without the parameter when no field is read (WGSL has no empty structs).
   - `mtek_fs` takes `mtek_in: MtekVertexOutput` (no parameter when nothing is read), builds `let mtek_surface = MtekSurfaceInput(mtek_in.<field>, …)` with `normalize(mtek_in.world_normal)`, then `let mtek_color = mtek_fragment(…);` and returns `vec4<f32>(mtek_color.xyz, 1.0)` at `@location(0)` (`.xyz` is `.rgb`): alpha is always 1.0.
   - Generated code carries the material declaration's span. The span-map symbol is the material symbol, and `<material>.fragment` inside `mtek_fragment`.
5. **Span map.** Every struct header, struct member, global, stage attribute, function header, parameter, statement and expression adds an entry. Entries are sorted by line, start column and widest first; lookup takes the narrowest covering entry and the first on a tie (the runtime's `findSpanMapEntry`). Columns count Unicode scalar values (generated WGSL is ASCII). In memory an entry holds a `Span`; `SpanMap::document(sha256, span_id)` writes the file of `spec/runtime-abi.md` §5.4 with span ids the packager assigns.
6. **`emit_wgsl::validate(module_text, span_map) -> Result<(), Vec<Diagnostic>>`.** It takes the span map as well as the text (§8 lists only the text, but the mapping it requires needs the map; the task statement asked for this signature). One `E6100` at the span found for Naga's primary position, or the material declaration; notes `Naga: <message and causes>` and the WGSL line, column and symbol; help "please report it with the program that caused it".
7. **`ShaderArtifact`** (`emit_wgsl::emit_shader`, which validates first, so no artifact exists for rejected WGSL): `material`, `wgsl`, `sha256` (64 hex digits of the WGSL bytes), `span_map`, `vertex_entry` (`mtek_vs`), `fragment_entry` (`mtek_fs`), `vertex_attributes` (slot order; serialised `position | normal | uv`), `surface_inputs` (varying order; serialised `local_position | …`) and `layout: Option<LayoutRecord>`. The task statement wrote `layout: LayoutRecord`; it is optional because a material without value params has no block (`spec/gpu-layout.md` §6). Helpers give `shaders/<h16>.wgsl`, `shaders/<h16>.mtek-map.json` and the span-map document.
8. **The temporary `Unlit`.** `unlit_shader(prelude: &SourceFile)`: the caller adds the embedded prelude (`prelude_text()`) to its source map as `std/materials.mtek` and passes that file; the declaration span is the `export material Unlit { … }` item found by parsing it, so spans resolve to lines and columns like any source file. The param block is the registry's `Unlit` schema laid out as `material:std/materials.mtek::Unlit` / `MtekParams_2b212d15_Unlit`; the body is `return mtek_params.u_color;`; it reads no `SurfaceInput` field, so its only vertex attribute is `position`. A defect of this path (wrong file, prelude without `Unlit`, a parameter type that is not a GPU value) is `E9999`.
9. **Catalogue.** `E6100` is implemented; no checked program can produce it, so the coverage test lists it as unreachable in this build, covered by `src/emit_wgsl/validate.rs`.

## Consequences

- No new dependency (`sha2`, `naga`, `serde`, `serde_json` are in decision 0007's table) and no new diagnostic code.
- M1-17 (packaging) adds `std/materials.mtek` to the build's source map (so the manifest's `sources` and `spans` include it), calls `unlit_shader` once if any entity uses `Unlit`, writes `wgsl_path()` and `map_path()` (span ids from its `spans` table) and fills the manifest's shader entry and `layouts` from the artifact.
- M1-18 (rendering) builds the pipeline from `vertex_entry`/`fragment_entry` and one vertex buffer per `vertex_attributes` entry (`location`, `format`, `array_stride`), and binds groups 0/1/2 per `spec/gpu-layout.md` §6.
- M2-09 deletes `lowering/builtin_unlit.rs`; `Unlit` then reaches the standard stage through `lowering/shader.rs` like any material, and the golden `tests/codegen/wgsl/unlit.wgsl` must stay equal or change in a reviewed diff.
- `spec/compiler-architecture.md` §4.9 and §8 point here.
