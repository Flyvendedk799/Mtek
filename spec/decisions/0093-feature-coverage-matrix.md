# 0093. The feature coverage matrix: what a v0.1 feature is, where the list lives, how use is derived and what is asserted

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M7 (blueprint §11), task M7-02; decisions 0002 (the three release demonstrations, "a coverage matrix derived from the compiled programs' IR, not from prose"), 0004 (rule 1: each area has a negative fixture for its nearest unsupported neighbour; rule 2: the table is the claim), 0027 item 11 (the fixture coverage of diagnostic codes), 0042, 0072 (`supported.features`); `spec/testing.md` §3.2
- Supersedes: nothing. The allow-lists of decision 0027 item 11 move to a data file (item 8).

## Context

M7-02 asks for a tool that proves two sentences: every advertised language feature has a passing positive fixture and appropriate negative tests, and the three demonstrations are distinct. The tool must not rest on prose: it has to read what the compiler made of the programs. Four questions had no answer in the records: which three programs are the demonstrations, what a "feature" is and where its list lives, what can be derived from the typed IR and what cannot, and what "appropriate negative tests" can mean when a feature has no diagnostic of its own.

## Decision

1. **The demonstrations.** Decision 0002's table names three: `examples/material-configurator`, `examples/physics-playground` and `examples/modular-scene` ("the third", added by M7-01, decision 0092). `examples/pulse-cube` "drives M0–M3 and does not count as a release demonstration". The matrix reads it as an *example*: it is a compiled, tested program, so it may name a feature as covered (column PUL of the document), but it takes no part in the distinctness assertion, and no feature is said to be covered by "a demonstration" because of it.
2. **Distinctness is asserted twice.** (a) Each demonstration exercises at least one fact (a feature of the registry or a form, item 3) that neither of the other two exercises; (b) each demonstration exercises the facts decision 0002 names as its *primary pressure* (host inputs, a static GLB and custom fragment logic for the configurator; bodies, colliders, a sensor, an impulse, a collision event and `destroy` for the playground; calls, static instances and `spawn` across files for the modular scene) and neither of the other two does. The pressure lists are data in `tools/coverage-matrix/src/matrix.ts`; they are read from the table of decision 0002, and a change to a demonstration that drops one fails the tool. `module/cross-file-material` is not a pressure: the configurator also keeps its materials in a module of their own.
3. **What a feature is: three vocabularies, one list.**
   - *Registry features* are exactly `supported.features` of `mtek context` (decision 0072): the 30 constructs of the resolver's table (`imports`, `materials`, `bind`, `arithmetic`, ...) and every row of the standard-library registry the build has reached (`spec/stdlib-schema.json`: types, schemas, scene objects, events, enums, namespaces, functions, values, methods, body commands and properties). That is the authoritative list: the compiler derives it from its own tables ("nothing is listed by hand"), and a new registry row appears in the matrix with no edit to the tool. The tool reads it from the compiler, not from a copy.
   - *Forms* are what the language reference describes and the registry has no row for: statements and their compound-assignment operators, locals, operators, expression forms, assignable places, lifecycle functions and handlers by owner, bindings by target and dependency, entity facets and written fields, material update classes, the forms of prefabs and modules (cross-file calls, static instances, `spawn`, materials), and the project-level facts of `spec/runtime-abi.md` §3 and §6.3 (host inputs and each of the ten codecs, the physics subsystem, packaged assets, lights, generated shaders). They are `tools/coverage-matrix/src/forms.ts`, each with the section of the reference that describes it. The table cannot drift from the compiler unnoticed: a unit test compares the variants of the IR enums (`crates/mtek-compiler/src/ir/model.rs`: statements, expressions, places, behaviours, bindings, descriptors, update classes) with the table, so a new IR node fails the tool until it is a form or a registry id.
   - *Not tracked one by one:* the fields of a schema (`BoxCollider.friction`) and the members of an enum (`Key.Space`). The compiler lists them as registry rows but not as features (`supported.features` skips them), and the matrix follows it. They are guarded by the codes of the descriptor area (item 6) and by the schema's own tests; a per-field matrix is future work. Runtime behaviours of the v0.1 table that are not language features (frustum culling, compatible instancing, hot reload, the language server) have no row either: their evidence is the browser specs and the unit tests named in `spec/testing.md`, and this matrix does not claim them.
4. **How use is derived, and what the IR cannot show.** Each program is compiled by the real `mtek`; a fact is read from three outputs. The typed IR (`mtek inspect --ir --format json`) gives the statements, expression forms, places, behaviours, bindings, entities, descriptors, schemas, events, body commands, enum members and cross-file references the compiler wrote. The program manifest (`mtek build`) gives host inputs with their codecs, the physics subsystem, packaged assets, lights and generated shaders. And the IR *folds*: a call whose arguments are constant leaves its value and no call. `quat.identity()`, `mat4.identity()`, `CHAIR.node_position("Seat")`, `CHAIR.material_base_color("Fabric")` and the other accessors that produce a constant are therefore invisible in it. For these nine features (marked † in the document; the list is computed, not typed) the matrix uses what the compiler itself recorded for the source: the resolver's table from names to standard-library items and the type checker's table of calls (`mtek_compiler::context::used_features`, the function behind the example selection of `mtek context`, extended with the glb accessors and body commands). That is the compiler's parse output, not a pattern over text; no regular expression touches a source file anywhere in the tool. The function is reached through a small helper, `tools/coverage-uses` (Rust, a member of the workspace like `tools/grammar-coverage`), because the command line has no view of it. `self` in the body of a *named* entity is its own index and indistinguishable from the entity's name in the IR; it is derived from prefab bodies (entity 0), where it is the only way to name the entity, and the resolver's records confirm it everywhere.
5. **Positive fixtures.** A positive fixture is a project under `tests/semantics/pass`, `tests/codegen`, `tests/assets/pass`, `tests/assets/inspect`, `tests/modules` or `tests/browser/fixtures` (`projects.ts`) that `mtek inspect --ir` accepts without errors; one that does not is listed in section 9 of the document and names nothing. For each feature the document names the *most focused* fixture (the one that uses the fewest features altogether) and how many others use it. The compiler's own suites run these projects with the assertions that make them evidence (`every_semantic_pass_fixture_checks_without_errors`, the codegen goldens and execution tests, the browser specs); the matrix adds that they exist and exercise the feature.
6. **Negative tests.** Four assertions, from the weakest claim a tool can make honestly to the strongest.
   - *Areas.* A feature has no diagnostic of its own that a tool could derive, so `tools/coverage-matrix/src/guards.ts` groups the features into 21 areas and names, per area, the catalogue codes that guard it (for modules: `E2002`, `E2030`..`E2036`). The grouping is reviewed data. The tool asserts that every feature belongs to an area, that every code an area names exists, and that every one of those codes has a fixture or a named negative test. Section 7 of the document lists them with the first fixture or test file. For the registry features that have a name a message quotes, the column Neg counts the fixtures whose expected messages quote it (informational).
   - *Nearest unsupported neighbours* (decision 0004 rule 1). Every entry of `supported.notSupported` is rejected by a fixture: a reserved word by an `E0013` fixture whose expected message names it, a hard gate by an `E9010` fixture, a feature of the `x9xx` codes by that code's fixture or reservation.
   - *Every diagnostic code* has a fixture. A fixture is the expected-diagnostics file that a compiler suite compares exactly (`tests/syntax/{lex,fail}`, the diagnostic lines of `tests/syntax/ast`, `tests/semantics/{pass,fail,gpu}`, `tests/assets/fail`); a warning cannot fail a program, so a warning's fixture is a passing program that lists it.
   - The tool exits 1 when a code has none of: a fixture, a named negative test, a mark in the catalogue.
7. **The strict list is empty, and what is behind that.** After the audit (decision 0094) 153 of the 201 codes have a compiler fixture. 42 have a named test because a fixture cannot express them: files the source manager rejects, sizes that are generated in the test, the project file that is missing, and the runtime codes `E70xx`/`E80xx`/`W80xx`/`E81xx`, whose tests are the runtime's unit tests. Two (`E6100`, `E9999`) are produced only by a compiler defect. Four are reserved or not implemented and are marked so in the catalogue itself (`spec/diagnostics.md` §5: `**Reserved:**`, `**Not implemented:**`): `E5901` and `E5902` (no v0.1 construct could produce them; the context export lists the features as not supported), `E6003` (the limit of 16 inter-stage variables cannot be reached when v0.1 allows 4 and no custom vertex stage) and `W0030` (the naming lint of `spec/language.md` §3.3, specified but not built, decision 0070 item 11). The reading of "the list of codes without a fail fixture is empty" is therefore: no code is without a fixture, a test that provokes it, or a registry mark with a reason; all three kinds are shown in the document. Nothing was removed from the registry and no assertion was weakened.
8. **One list of exceptions.** `tests/semantics/code-coverage-exceptions.json` replaces the three constants of `crates/mtek-compiler/tests/fixtures.rs`: `notYetImplemented` (must be empty at M7; the Rust test and the tool both fail if it is not), `reserved` (each code must be marked in the catalogue and vice versa), `unreachable` and `coveredElsewhere` (each names a test file that must exist and contain the code). The Rust test and the tool read the same file, so the two cannot disagree; a code that gains a fixture must leave its list in both.
9. **The document.** `docs/coverage-matrix.md` is generated by `npm run generate -w @mtek/coverage-matrix`, is deterministic (no dates, no paths, LF), and is compared byte for byte by a unit test of the tool and by `npm run check:coverage` (which the node job of CI runs after the build). A stale document fails both.
10. **Needs.** The tool needs `mtek` with the runtime embedded (`npm run build`) and cargo for the helper. Without a compiler the unit tests that need it are skipped locally and fail in CI (`CI` set), never silently pass there; `npm run check:coverage` always fails without one.

## Consequences

- A feature added to the registry, a construct added to the resolver, a variant added to the IR, a code added to the catalogue or a fixture removed changes what the tool says, and fails it until a demonstration, a fixture or a reviewed entry accounts for it.
- The areas of item 6 are judgement, not derivation. A reviewer of the M7 gate should read section 7 of the document and ask of each area whether its codes are the ways to misuse its features; the tool only proves that they are all tested.
- The matrix proves presence, not strength. A fixture that exercises `step` proves the feature compiles and runs where the compiler's other tests say it should; the numeric agreement and the pixels are the evidence of M2 and M4, not of this document.
