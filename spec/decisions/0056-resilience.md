# 0056. Resilience: resize and pixel ratio, device loss recovery, allocation failure and their test hooks

- Status: Accepted
- Date: 2026-10-17
- Blueprint origin: §7.4 (resource lifetime, device loss), §7.5; `spec/runtime-abi.md` §8.2, §9.4, §9.5, §10; decisions 0012 (browser test environment), 0020 (interim device loss behaviour), 0031 (runtime scene rendering), 0046 (materials that fail after mount).
- Supersedes: decision 0020 ("device loss is terminal until M4-09"). Fills the details `spec/runtime-abi.md` §9.4 leaves open; the normative budget (3 attempts, 250 ms / 1 s / 4 s, `W8060` / `W8061` / `E8062`, no infinite retry) is unchanged.

## Context

Task M4-09 makes the runtime survive the real browser: a canvas that changes size or pixel ratio or has no pixels, a hidden tab, a lost GPU device and a failed allocation. M1 already had the `ResizeObserver`, the depth texture recreation, the zero-size skip and the visibility pause, and treated device loss as terminal (decision 0020). What was missing is the pixel-ratio change, the recovery itself, and a way to drive each of these on hardware and read the result back from pixels. Everything below is a **proposal** (a design choice); the external facts are labelled **constraint**.

## Decision

1. **Resize, pixel ratio, zero size (unchanged parts, then additions).**
   - The backing size stays `round(clientWidth × dpr) × round(clientHeight × dpr)`, clamped to `maxTextureDimension2D`, recomputed on every `ResizeObserver` callback; the new depth texture exists before the old one is released; a size of zero skips the frame (`framesSkipped`) without error while the simulation continues.
   - **Pixel ratio (new).** With `devicePixelRatio: "auto"` the app watches `matchMedia("(resolution: <dpr>dppx)")`. That query names the current ratio, so when the ratio changes (window moved to another display, page zoom) it stops matching and fires `change`; the handler removes its listener, recomputes the backing size exactly like a resize, and registers a query for the new ratio. The listener is created through the registry (it counts in `liveListeners` and is removed by `dispose`). A numeric `devicePixelRatio` is not watched; a browser without `matchMedia` notices a changed ratio at the next resize. **Constraint:** Chromium evaluates media queries, and fires their `change` events, at the next lifecycle update; a ratio change that changes nothing else may be seen late. The hardware spec therefore changes the window width together with the emulated ratio, as moving a window to another display does.
   - A resize callback that arrives while the device is being recovered is ignored; the rebuilt surface reads the canvas size when it is configured, and one more size check runs when the recovery ends.

2. **`test.canvasRenderTarget` (new test option).** An offscreen `rgba8unorm-srgb` target that always has the canvas's backing size (and is recreated, before the old one is released, together with the depth texture on every size change). It makes resize, pixel ratio and zero size observable through `debug.readPixels()` without screenshots. It excludes `test.renderTarget` (`TypeError`). While the canvas has no pixels `readPixels` rejects (`the canvas has no pixels`).

3. **Device loss.**
   - **Detection.** Each device has an epoch. `device.lost` of the current device with a reason other than `"destroyed"` starts a recovery; a stale device's event is ignored; a `destroyed` event is ignored unless `debug.loseDevice()` (below) asked for it. A loss of the *new* device while an attempt runs makes that attempt fail. `state = "recovering"`, the scheduler and the input state are paused, a hot-reload candidate that was waiting for the next frame is discarded (its resources belong to the lost device) and `W8060` is reported as a warning (phase `runtime:device`; the note names the budget). The overlay shows errors only, so a successful recovery never shows it.
   - **Schedule.** Attempt 1 runs 250 ms after the loss, attempt 2 1000 ms after attempt 1 failed, attempt 3 4000 ms after attempt 2 failed (`environment.setTimeout`, so tests fake time). There are never more than 3 attempts per loss and nothing is scheduled after the third; `dispose()` cancels the timer.
   - **An attempt** (`MountedApp.rebuild`) requests a new adapter and device with the manifest's required capabilities (`acquireDevice`), then, on that device: (a) `registry.recycle(device)` forgets and destroys every GPU object of the lost device and keeps listeners and cumulative counters; (b) `surface.recover(device)` configures the canvas again and allocates the depth texture (and offscreen target) at the canvas's current size; (c) the startup shaders are created from the WGSL files remembered at mount (shader URLs are named by content hash; the rebuild needs no network); (d) `startScene` runs in **recover mode**: material arenas, meshes, binding plan, pipelines, frame and object arenas and the renderer are created exactly as at mount, but `init` does not run again. The **retained CPU state** is the `World` (entity records, transforms, visibility, state objects, material mirrors, camera, scene state), the `Bindings`, the behaviours, the scheduler's clock (`activeTime`, frame index, fixed-step accumulator), the queued host inputs and the input state. `World.rebindParams` points the world at the new parameter store, replays every mirrored param value through the generated writers (producing the bytes the lost device held) and marks every world matrix changed so the next frame fills the new object arena; (e) the attempt waits for `queue.onSubmittedWorkDone()` so out-of-memory results (`E8063`) and a loss of the new device are seen. Only then does the app commit (`device`, `modules`, `scene`), destroy the lost device and resume. On any failure the new device is destroyed and nothing of the app has changed.
   - **Success.** The state before the loss is restored: running, or paused if the host paused it; paused by visibility if the page is hidden and `pauseWhenHidden` holds. `W8061` is reported (attempt number). The first frame after a resume has delta 0, so the time spent recovering is never simulated. The canvas size is checked once more.
   - **Failure.** After the third failed attempt `state = "failed"`, the frame loop stops for good, and `E8062` (phase `runtime:device`) is reported and shown in the overlay; its notes list every attempt with its delay and the reason (the browser's message for a rejected `requestDevice`). `dispose()` still works.
   - **Materials.** A shader module or pipeline that fails on the new device does not fail the recovery: it is reported as `E8051` (phase `runtime:device`) and the material is no longer drawn (`Renderer.failMaterial`, decision 0046), like a material that fails after a hot reload. This is the first real caller decision 0046 anticipated. A material that had failed before the loss is tried again.
   - **While recovering** `pause()`, `resume()` and `replaceProgram()` do nothing / are refused (`E8050`, "while the application is recovering"); a `replaceProgram` that was already preparing a candidate when the device was lost discards it with `E8050`. `setInput` keeps queueing. Counters `deviceLosses`, `deviceRecoveries` and `recoveryAttempts` are cumulative.
   - **Repeated losses.** Each loss has its own budget of 3 attempts, and each is reported (`W8060` and `W8061` carry the ordinal from the second one on, so the host-facing duplicate filter of §12 does not swallow them). A device that is lost again after every successful recovery therefore keeps recovering, visibly, at no more than one cycle per 250 ms; a cap on that is not part of the specified contract and is not added here.

4. **Allocation failure.** The contract of §9.5 is unchanged and now covered end to end: creation inside an `out-of-memory` scope, `E8063` through the registry callback, and after mount `fail()` (state `failed`, overlay, frame loop stopped) rather than rendering stale data; during a recovery attempt the failure belongs to the attempt (it fails and the next attempt may succeed) and is not an `E8063` of the application.

5. **Test hooks (only with `options.test`; production mounts have no `debug`).**
   - `debug.loseDevice()` marks the current epoch and calls `device.destroy()`. The `destroyed` loss that follows is then handled as a real loss (it is the only way to lose a device deterministically on hardware); it throws unless the app is running or paused.
   - `debug.failAllocation()` calls `registry.reportAllocationFailure`, exactly what the out-of-memory scope's result does; it makes the failure path observable on hardware, where a real out-of-memory cannot be produced safely.
   - `test.recovery.delaysMs` (exactly 3 non-negative numbers, default `[250, 1000, 4000]`) shortens the waits for real-timer specs; it cannot change the number of attempts. `test.recovery.failDeviceRequests` makes the next `n` device requests of recovery attempts fail as a rejected `requestDevice` would.
   - `test.canvasRenderTarget` (item 2). `HostEnvironment` gains `setTimeout`, `clearTimeout` and an optional `matchMedia` as injectable seams (`defaultEnvironment()` reads the globals).

6. **Specification touch-ups.** `spec/runtime-abi.md` §9 points here; §10.1 lists the three new counters; §10.2 lists `canvasRenderTarget`, `recovery`, `loseDevice` and `failAllocation`. The `W8060` note "recovery arrives with M4-09" is replaced by the schedule note of item 3; `W8061` and `E8062` leave the not-yet-implemented list of the compiler's diagnostic coverage test.

## Consequences

- Later features that own GPU resources must create them inside `startScene` (or hand them to it) so that the recover mode rebuilds them from retained CPU data: textures (M4-04) must keep their decoded CPU image, lights and culling state live in the world or the frame arena. A resource created elsewhere is not recreated after a loss.
- `ResourceRegistry.recycle`, `Surface.recover`, `World.rebindParams`, `SceneStartupOptions.recover` and the app's recovery methods are the only shared-code changes; the renderer, material store and mesh store are unchanged.
- `liveListeners` is one higher with `devicePixelRatio: "auto"` in a browser that has `matchMedia` (the resolution query); `liveBindGroups` is 0 right after a recovery until the first frame encodes (bind groups are created lazily).
- A hot-reload candidate waiting for the next frame is lost with the device; the dev server's next build replaces it.

## Verification

- `packages/runtime-web/src/host/recovery.test.ts` (fake GPU, fake timers): the constants; W8060 and the 250 ms timer; destroyed losses and stale events ignored; success on attempt 1 and later; the new device used, the lost one destroyed; live counts equal and totals doubled; no network fetch; scene, GPU buffers, draws and pixels identical to a run that never lost its device; the param mirrors refilled; **at most 3 attempts with delays exactly `[250, 1000, 4000]`, then `failed`, `E8062`, the overlay and no timer left**; a device lost or an allocation failing during an attempt; dispose during the wait and during an attempt; resize during recovery; pause and visibility restored; pause/resume/replaceProgram while recovering; repeated losses; a pipeline that fails on the new device (`E8051`, `runtime:device`); the debug hooks and the option validation.
- `src/host/app.test.ts`: the pixel-ratio watcher (renewed query, fixed ratio and missing `matchMedia` not watched, dispose) and `test.canvasRenderTarget` (resize, ratio, zero size); `src/gpu/registry.test.ts`: `recycle`.
- `tests/browser/specs/m4/resilience-resize.spec.ts` (hardware): the box's silhouette read from the offscreen target matches the independent CPU projection at six canvas sizes (aspect 1, 2, 0.5, 1.67), its pixel size follows the height only (a stale aspect would stretch it), a real emulated pixel-ratio change (2, 1.5, 1) resizes the backing store and the picture, a zero-sized canvas skips frames without a diagnostic and the identical picture returns, and a hidden page pauses.
- `tests/browser/specs/m4/resilience-device.spec.ts` (hardware): `device.destroy()` of the real device on `examples/pulse-cube` recovers after at least 250 ms with `W8060`, `W8061`, unchanged scene state and identical live counts, and the pixels and scene after 30 + 30 frames equal a control run of 60 frames; a second loss recovers again; two failed device requests recover on attempt 3; three failed requests reach `failed` with `E8062`, the overlay and exactly 3 attempts, and nothing happens in the 400 ms after; `failAllocation` reports `E8063`, shows the overlay and stops the scene.
