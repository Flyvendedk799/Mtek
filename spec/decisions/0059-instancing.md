# 0059. Compatible instancing: shared parameter blocks, the instanced vertex entry and pipeline variant, the instance buffer, grouping, counters and `test.disableInstancing`

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: §6.3 (identical immutable instances may share storage), §7.2 ("measure instancing"), M4 (blueprint §11), task M4-08; `spec/runtime-abi.md` §§8.4, 10.1, 10.2; `spec/gpu-layout.md` §8.2; `spec/materials.md` §§3.3, 4; decisions 0029 (standard stage), 0031 (runtime scene rendering), 0041 (shader lowering), 0046 (runtime materials), 0055 (culling and counters), 0056 (resilience).
- Supersedes: nothing. Amends decision 0031 item "every instance owns its slot" (sharing is now done) and the `instancedDraws` note of decision 0055.

## Context

`spec/runtime-abi.md` §8.4 defines **compatible instancing**: entities with the same mesh, the same pipeline key and the same parameter block (material instances whose params are all class `initial` and byte-identical, sharing one slot per `spec/gpu-layout.md` §8.2) are drawn with one instanced draw; their model and normal matrices come from an instance vertex buffer; everything else is drawn individually; `instancedDraws` and `drawCalls` make it observable. The specification does not say how the shared blocks come about (until now every instance owned a slot and `sharedParamBlocks` was 0, so no two entities ever had "the same parameter block" and nothing could be instanced), which vertex locations the instance data uses, how the instanced vertex stage relates to the standard stage, how the pipeline key tells the variants apart, when the buffer exists, how groups are formed after culling, what exactly the counters count, or how a test switches the feature off. Every choice below is a **proposal**; the external facts are labelled **constraint**.

## Decision

1. **Shared parameter blocks (the precondition).** Every material instance starts with a slot of its own. After `init` has run (and after the world refilled the store on device recovery) `MaterialStore.shareIdentical()` lets instances share. Eligible are instances whose manifest entry has `shareable: true` (every param class `initial` or `resource`, `spec/gpu-layout.md` §8.2): candidates are bucketed by `(material id, FNV-1a hash of the block words, resource signature)`; a bucket hit is confirmed **word by word** (a hash collision never shares different blocks); the lowest-indexed instance keeps its slot and bind group, the others release their slots (`UniformArena.release` zero-fills and frees them) and use the first one's. Instances of a material without value params (no block) share when they are `shareable` and have equal resources; they have no slot to count. Mutable (`imperative`, `bound`) instances never share. The shared block is **named by the lowest instance index that uses it** (`MaterialStore.blockOf`); two instances have "the same parameter block" exactly when `blockOf` agrees.
2. **Copy on write.** Nothing in a program writes a `shareable` instance after `init`, but the test hook `debug.setParam` can. `MaterialStore.writeParam` on an instance whose block is shared first checks (without writing) whether the bytes would change; if not, nothing happens (a no-op write does not unshare); if so, the instance gets a **new slot** that starts as a copy of the shared bytes and the write goes there; the other users keep the old slot untouched, and the blocks are named again (the lowest remaining user names the old block). Blocks are never merged again after startup: a write that makes two blocks equal does not regroup them (`MaterialStore.blockVersion` increases on every change of `blockOf`, and the renderer rebuilds its draw list when it does). `sharedParamBlocks` counts the blocks used by two or more instances, `ownedParamBlocks` those used by exactly one (blocks only exist for materials with value params).
3. **Compatibility.** Two draws are compatible when they have the same **pipeline key**, the same **parameter block** (`blockOf`) and the same **mesh** (the uploaded mesh: equal descriptors share one upload). The draw list is still sorted by `(pipeline key, parameter block, mesh)`, ties by instance order; the second sort field is now the block's name instead of the material instance index, which is the same number whenever nothing is shared, so the order of a scene without sharing is unchanged. Compatible draws are therefore adjacent, and culling removes draws without reordering the rest, so they stay adjacent. **Grouping happens after culling and after the filters for hidden entities and failed materials** (`render/instancing.ts`, `batchDraws`): a run of two or more compatible draws is **one instanced draw**, a run of one is an ordinary individual draw. An entity that is culled, hidden or on a failed material is simply not in the list; an entity whose parameters differ has another block; a draw whose material has no instanced pipeline is always individual. Instance order inside a group is draw-list order (ties by entity index), so a group draws its entities in the same order the individual draws would, which keeps depth ties and blending-free overdraw identical between the two paths. Run-time re-parenting is not part of v0.1 (`spec/scenes.md` §14), so an entity's parent never changes; a parent that moves moves the world matrices of its children, which are what the records hold.
4. **The instanced vertex entry point.** The standard stage (`lowering/standard_stage.rs`) generates a third entry point, **`mtek_vs_instanced`**, from the same builder as `mtek_vs`; the two differ only in where `model` and `normal_matrix` come from. `mtek_vs_instanced` has the same parameters as `mtek_vs` (the fixed attributes, locations 0 to 2, only those the material reads) **followed by eight `vec4<f32>` parameters: the four columns of the model matrix at `@location(3)` to `@location(6)` and the four columns of the normal matrix at `@location(7)` to `@location(10)`**, and builds `mat4x4<f32>(c0, c1, c2, c3)` from them. It returns the same `MtekVertexOutput`, so the one `mtek_fs` serves both; it does not read `mtek_object`. The locations are the first free ones after the fixed attributes and are the same for every material whichever attributes it reads (the instance data never moves). The locations are documented in the module header of `standard_stage.rs` and as constants (`INSTANCE_MODEL_LOCATION`, `INSTANCE_NORMAL_LOCATION`, `INSTANCE_STRIDE`); the runtime has the same constants in `render/pipelines.ts` and a test pins both to the printed WGSL. The manifest's shader entry gains **`instancedVertexEntry`** (`spec/manifest.schema.json`, **optional**: a manifest of an older compiler has none and the runtime then draws that material individually); `mtek inspect --shaders` lists it. Adding the entry point changes the WGSL, so every shader hash and the codegen goldens changed (blessed in this task). **Constraint:** 11 of the 16 vertex attribute locations WebGPU guarantees (`maxVertexAttributes`) and, with position, normal, uv and the instance buffer, 4 of the 8 vertex buffers (`maxVertexBuffers`) are used.
5. **The instance vertex buffer and the pipeline variant.** The instance buffer layout is one buffer, `arrayStride` 128, `stepMode: "instance"`, eight `float32x4` attributes at offsets 0, 16, ..., 112 for locations 3 to 10: **record = model matrix (16 `f32`, column-major) then normal matrix (16 `f32`)**, the values the object block holds. Its slot is the next one after the mesh's attribute buffers (`attributes.length`). The **instanced pipeline** of a material is the plain pipeline with `vertex.entryPoint = instancedVertexEntry` and that extra buffer; layout (including group 2, which the instanced entry point does not read), fragment stage and state are unchanged. **Pipeline key:** `(shader hash, vertex attribute set, color format, depth format, cull mode, topology)` with `instance_matrices` appended to the vertex attribute set of the instanced variant (the instance data are vertex attributes), so the two variants of a shader have different keys and the plain key is unchanged. Both variants are created **at startup**, inside `startScene`: the instanced one only for materials that have, at that point, at least two entities with the same mesh, pipeline key and parameter block (`instancingCandidates`; visibility, culling and failure only shrink groups and blocks are never merged later, so this is an upper bound for the life of the scene). Parameter edits and frames create no pipeline. `pipelinesCreated` is one higher per instanced material; a scene with nothing to instance creates nothing extra. A failure to create the instanced variant is `E8051` like any pipeline failure (the same module and layout make it practically impossible when the plain one succeeded).
6. **The instance buffer's life.** The buffer is created in the `Renderer` constructor, i.e. inside `startScene`, through the registry (so `liveBuffers` and `buffersAllocated` count it, hot reload disposes it with the renderer, and **device recovery rebuilds it** exactly as it rebuilds the other buffers, decision 0056), with the capacity of the candidates (the number of entities in groups of two or more) times 128 bytes: a frame can never need more, so it never grows. The renderer keeps per entity the model and normal matrix it last wrote to the object block (refreshed in the same place, so a culled or hidden entity's record is current when it returns). Each frame, after culling and grouping, the records of the instanced draws are copied in draw order into a staging array and compared **word by word** with a CPU copy of what the buffer holds; only the range from the first to the last word that differs is uploaded with one `writeBuffer` (counted in `uploads` and `uploadBytes`). A static scene uploads nothing, and moving one instance along one axis uploads its object block (128 bytes) plus **4 bytes** of the instance buffer. Records past the ones the frame uses may hold stale data; they are never read.
7. **Encoding.** One render pass; group 0 once, group 1 when the parameter block changes (`blockOf`, so shared instances bind one group), the mesh's buffers when pipeline or mesh changes, and for an instanced draw the instance buffer in its slot and `drawIndexed(indexCount, instanceCount, 0, 0, firstInstance)` with `firstInstance` the group's first record (a direct draw with a first instance needs no optional feature). The pipeline layout has group 2, which WebGPU requires to be bound for every draw of the pass, so before the first instanced draw of a pass with no individual draw yet group 2 is bound at dynamic offset 0 (the entry point does not read it). Individual draws are as before (group 2 at the entity's slot).
8. **Counters.** `drawCalls` is the number of draw calls of the last frame (an instanced draw is one); `instancedDraws` is the number of those that draw two or more entities; `instancedDrawsTotal` and `drawCallsTotal` are the sums over rendered frames (decision 0055 item 5). The identity of decision 0055 becomes: `culledObjects` plus the entities drawn equals the drawable entities, where an instanced draw draws several; `drawCalls` is at most the entities drawn, and equal to it when nothing is instanced. A frame that draws nothing reports 0 for all frame counters.
9. **`test.disableInstancing`** (a test option, `spec/runtime-abi.md` §10.2, `MtekTestOptions` in `types.ts` and `runtime.d.ts`): every entity gets its own draw call as if instancing did not exist. It is passed into `startScene` (mount, hot reload and device recovery alike), which then creates **no instanced pipeline and no instance buffer**, so the plain path is exactly the pre-M4-08 path. Parameter blocks are **still shared** (sharing is a storage decision, not a draw decision), so `sharedParamBlocks` and `ownedParamBlocks` are the same in both modes. `instancedDraws` stays 0.

## Consequences

- Entities that differ only in transform and share mesh, material and parameter values (the common case of many identical props) cost one draw call and 128 bytes of instance data each, and an unchanged entity costs no upload.
- `sharedParamBlocks` is no longer 0 for scenes with identical `shareable` instances; unit tests that counted per-instance blocks for such scenes were changed to use `shareable: false` (they test per-instance behaviour) or to state the shared count (the `lights` golden program: its three Unlit instances share one block).
- A program's `initial` params can still be changed at run time by the test hook; the copy on write keeps that correct at the price of a regroup (the draw list is rebuilt when a block name changes).
- Not done, deliberately: merging blocks that become equal after startup, indirect or multi-draw, grouping across meshes, a growing instance buffer, instancing entities with a texture-only or block-less material beyond what the same rules give (they are grouped like any other when `shareable`).
- `drawCalls` no longer equals the drawn entities; anything that assumed it (the overlay's three counters, tests) reads the new meaning.

## Verification

- Compiler (`cargo test --workspace --locked`): `lowering/standard_stage.rs` tests (`mtek_vs_instanced` takes the fixed attributes then eight `vec4` at locations 3 to 10 for every combination of surface inputs, has the same result struct, builds the matrices from its columns and never mentions `mtek_object`; the plain entry still reads the object block; the constants), `emit_wgsl/artifact.rs` and `tests/unlit_shader.rs` (three entry points, names, stages), and the codegen, WGSL and inspect goldens (blessed; the diff is one extra entry point per shader and the manifest field).
- Unit (`npm run test:unit`): `src/render/instancing.test.ts` (hand-derived runs for `batchDraws` including different pipeline, block and mesh; the candidate scan; the instance buffer layout; then the renderer on the validating fake GPU: one instanced draw of five boxes with the records equal to their world matrices and normal matrices, `disableInstancing` gives five draws and no extra pipeline or buffer, a mixed scene of 5 entities (3 + 1 + 1), mutable params never grouped, culling (three culled, a single survivor drawn alone, back to two), a hidden entity, a parameter that differs (copy on write, the lowest user naming the block), a moving parent, no upload for a static scene and 132 bytes for one moved instance, nothing created while drawing, the buffer released with the app, no buffer when nothing can be instanced), `src/render/materials.test.ts` (sharing, naming, bind groups, copy on write), `src/render/pipelines.test.ts` (instanced descriptor and key), `src/host/recovery.test.ts` (device loss with instancing active: the instance buffer and pipelines are rebuilt, draws, records, counters and pixels equal a run without the loss).
- Browser (`MTEK_REQUIRE_GPU=1 npm run test:browser:hardware`): `tests/browser/specs/m4/instancing.spec.ts` on the hardware adapter. **Measured: 500 identical boxes, `drawCalls` 500 → 1 (`instancedDraws` 1), the readback image identical to the `test.disableInstancing` image (maximum channel difference 0 of 255, 0 of 32768 pixels differ, 11004 pixels drawn in 2936 colours)**; the same under a moving camera with culling (about 320 of 500 culled, still one instanced draw of the survivors) and equal to the unculled, uninstanced frame; the mixed fixture (17 entities: `drawCalls` 5, `instancedDraws` 4, `sharedParamBlocks` 3); a parameter that differs (`drawCalls` 6, one owned block); moving one instance (pixels outside its rectangle bit-identical, 2 uploads and 132 bytes against 1 upload and 128 bytes without instancing); device loss with instancing (same pixels and counters). The mixed fixture's ellipsoids (non-uniform scale) make a wrong normal matrix visible: swapping the normal matrix for the model matrix in the record made the mixed specs fail with a difference of 47 in a channel (checked once by hand).
