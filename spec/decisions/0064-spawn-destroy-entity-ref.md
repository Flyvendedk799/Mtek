# 0064. `entity_ref`, `spawn` and `destroy`: the entity table, the flush points, the `prefabs` manifest table and what reload does to spawned entities

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M5 (blueprint §11), task M5-02; `spec/scenes.md` §§4.5, 5, 8.3, 9, 10.1, 10.3; `spec/runtime-abi.md` §§3, 4.1, 4.2, 5, 7, 10, 11; `spec/diagnostics.md` (`E5030`, `E5074`, `E5080`, `E8030`, `W8031`, `W8032`, `E8033`); decisions 0025 (milestone gating), 0035 (items that land before their milestone's gate), 0049 (state, handlers), 0050 (lifecycle), 0051 (`bind`), 0056 (device recovery), 0059 (instancing and shared parameter blocks), 0062 (prefabs, the contract this record fulfils), 0065 (physics schemas).
- Supersedes: nothing. Lifts the last M5 gates of the checker: `spawn`, `destroy`, `alive`, the prefab literal and a named entity or `self` used as an `entity_ref` value. After this record no construct is gated (the fixture `gate_nested_reported_once` was removed with the last gate; a gate that returns brings its own).

## Context

The specification fixes the surface (`spawn(Prefab { .. }) -> entity_ref`, `destroy(r)`, `alive(r)`, handler-only, generation-checked, flushed at the lifecycle flush points, pending-removal semantics, `E8030`/`W8031`/`W8032`/`E8033`) and the contract of decision 0062 (the record of a spawned instance has `self.params` set to the object `init` receives). It leaves open how the runtime stores the entities and their GPU state, where exactly the flush points are, how the limit counts, what a manifest has to say about prefabs the program can spawn, how hot reload and device recovery treat spawned entities, and how a physics subsystem follows their lives. Every choice below is a **proposal** the owner may overrule.

## Decision

### Checker

1. **Gating.** The registry rows `entity_ref`, `spawn`, `destroy`, `alive` and the prefab-literal construct are `M1` (decision 0035; `CURRENT_MILESTONE` does not move). The helper `entity_ref_value_is_gated` and the fixtures `gate_entity_as_value`, `gate_prefab_literal` are gone.
2. **`spawn`.** `spawn(Prefab { name: value; .. })` returns `entity_ref`; its one argument must be a prefab literal (`E3001` otherwise, and `E3001` for a prefab literal anywhere else). The checks of a static instance apply to the params (`E5041` missing, `E5042` unknown or a non-param member, `E5002` twice, `E3102` type) **except** `E3090`: the values are run-time expressions (`spawn(Bullet { origin: self.position; speed: random() })`). A `bind` inside the literal is `E5004`. `spawn` is handler-only: in a state or field initialiser (scene, entity or prefab) and in a `fn` or a `cpu fn` it is `E5080` even when a handler calls that function (as `destroy` is, and decision 0065's body commands). The handlers and lifecycle functions of scenes, entities and prefabs (`update`, `fixed_update`, `on ..`) may spawn and destroy.
3. **`destroy`.** The argument must be an `entity_ref` (`E3001`). A named entity (`destroy(Cube)`) or `self` of a named entity is `E5030`; `self` of a prefab is a valid target, and so is any `entity_ref` value (run time decides: `E8030` for a named entity).
4. **`entity_ref` values.** A named entity or `self` in a place that expects an `entity_ref` (argument, `==`/`!=` operand, `let`, state initialiser, field of a struct) converts implicitly; `other == Floor` is a comparison of references. `==`/`!=` are the only operators (`<`, `>` are `E3014`). Field access through a reference (`r.position`, `r.hits = 1`) is `E5074`; body commands through a reference are decision 0065's.
5. **IR.** `ExprKind::PrefabLiteral { prefab, params }` and `ExprKind::EntityRef { entity }` (`self` in a prefab is entity 0). Generated JavaScript: `ctx.spawn(<prefab symbol>, <params object>, <span id>)`, `ctx.destroy(ref, spanId)`, `ctx.alive(ref)`, `<record>.ref` for a named entity and `self`, `rt.refEq(a, b)` for the comparison (`refEq` is the eleventh structural helper).

### Manifest

6. **`prefabs`** (`spec/runtime-abi.md` §5.6, `spec/manifest.schema.json`): an optional array, sorted by symbol, with one entry for every prefab the program can spawn: the prefabs named by a prefab literal, transitively through the handlers and lifecycle functions of those prefabs. A prefab that only has static instances, or none, is not in it (its code is in `app.js` all the same, decision 0062). An entry: `symbol` (the key of the `prefabs` table), `name`, `params` (`name`, `type`), `mesh` (id or `null`), `material` (`{ id, params, shareable }`: the layout id, the initial values by the classes of decision 0059 and whether instances may join an identical block) or `null`, `body` and `collider` (decision 0065 shapes, `null` or together), `state` (`name`, `type`, `symbol`, as for entities), `update`, `fixedUpdate` flags, `bindings` and `span`. **Bindings of a prefab** use the shapes of §5.2 with the instance as **entity 0** and the instance's material as **material instance 0**: targets and dependencies name `0`, never an index of the scene. This is the table the runtime needs to create an entity without the scene's structure, and the table M5-05 reads for the body data of spawned bodies. Asset references (mesh files, textures) of prefab instances are in the manifest's asset list, so loading and integrity cover them before the first frame.
7. **Spans for spawn sites.** `ctx.spawn` and `ctx.destroy` take the span id of the call as their last argument (the other CPU intrinsics with run-time diagnostics already do), so `E8030`, `W8032` and `E8033` point at the Mtek source.

### Runtime

8. **The entity table** (`scene/slots.ts`, no GPU knowledge). Slots `0..S-1` are the named entities: generation 0, alive for the life of the scene, never destroyed. The slots above are spawned entities and go **free -> reserved (spawn) -> alive (flush) -> removing (destroy) -> free (flush)**; freeing increases the generation. A **reference** is a frozen `{ slot, gen }`. `spawn` reserves a slot at once and returns the reference ("valid immediately"; `alive` is `false` until the flush). Free slots are reused **last in, first out**, so a program that spawns and destroys at a steady rate stays in a bounded table (`entitySlots`). `DEAD_REF` (`{ slot: -1, gen: 0 }`) is what `spawn` returns on `E8033`; it is never alive and never equal to a live reference.
9. **Cancellation.** A `spawn` destroyed before its flush (spawn then destroy in one handler, §10.3) is **cancelled**: nothing is created, `init` does not run, no resource is touched, the slot is freed (generation + 1) at the flush, and `entitiesSpawned`/`entitiesDestroyed` count neither.
10. **Flush points.** The scheduler calls `flush` at the start of `phase2_tick` (before each fixed tick, so a tick sees what the previous handlers spawned and no longer sees what they destroyed) and in `phase4_flush`, after `update`. A flush does **removals first** (in the order of the calls), then **creations in spawn order**; a slot freed by a flush can be reserved by the next frame's `spawn`, never by a spawn of the same flush. A created entity first runs in the next phase that starts after its flush. `destroy` flags the entity **at once**: `alive` is `false`, its handlers, bindings and `update` are skipped for the rest of the frame, commands against it are dropped with `W8031`, and the physics hook (item 16) sees it only at the flush.
11. **`destroy` outcomes.** A live entity: queued. A pending spawn: cancelled (item 9). A named entity (`E8030`, nothing happens). Pending removal, stale or dead references (`W8032`, nothing happens). All of them are runtime diagnostics with the span of the call.
12. **The limit.** `runtimeConfig.maxEntities` (default 16 384) counts the **named entities, the alive ones, the pending spawns and the pending removals** (a slot that is still in the table). A pending removal therefore still counts until its flush: a program that destroys and respawns in the same frame can hit the limit one frame early, which is the conservative reading of "maximum number of live entities". `spawn` over the limit returns `DEAD_REF`, reports `E8033` (with the prefab's name) and creates nothing.
13. **Creating an entity** (`scene/dynamic.ts`): a record (position, rotation, scale and visibility from the prefab's `init`, `state`, `params` set to **the same frozen params object `init` receives**, the 0062 contract; `ref`), a material instance through the material store (a shared block if the prefab's material is shareable and an identical block exists, otherwise an owned arena slot), the renderer's instance and object block, then `init(ctx, self, params)`, then the prefab's bindings evaluated once in `order`. The material of a spawnable prefab always gets the **instanced** pipeline variant (the number of instances is not known when the pipeline is built). Dynamic instance indices start at the scene's instance count and are reused LIFO; instance buffers grow on demand and do not shrink.
14. **Removing an entity** releases everything it created: its material instance (the block goes when the last member leaves), its renderer instance and object block, its place in the culling, instancing and draw lists, and its attachments. **Counters return to a bounded steady state** (`buffersAllocated` does not grow with the number of spawns once the arenas and the instance buffer have their capacity; `liveBindGroups` and `liveBuffers` are the same after 8 and after 208 spawn/destroy cycles, and back to the empty values after everything is destroyed except for the capacity the arenas and the instance buffer keep). The measured values of the hardware spec are in the task report and in the description of `tests/browser/specs/m5/spawn.spec.ts`.
15. **Draw order.** Draw ties are broken by `order`: the static index for named entities, `staticCount + spawn sequence number` for spawned ones, so the output does not depend on slot reuse.
16. **The physics hook.** `DynamicEntities.addListener({ created(entity), removed(entity) })` and `DynamicEntity.attachments: Map<string, unknown>` (dropped with the entity). `created` is called at the flush, after `init` and the first binding evaluation (the pose is final); `removed` at the flush that removes it, never from inside a handler or a collision callback. `DynamicEntities.commandTarget(ref, spanId, command)` is the one place that decides whether a body command is delivered or dropped with `W8031`. Nothing else of physics is in this task: M5-05 registers the listener, builds the body from the manifest's `body`/`collider` of the prefab and uses `commandTarget`.
17. **Introspection.** `app.debug.scene().spawned` lists the spawned entities in spawn order (`prefab`, `slot`, `gen`, `alive`, pose, state). Counters: `liveEntities` (named + alive spawned, excluding pending removal), `pendingSpawns`, `pendingRemovals`, `entitySlots` (the table's capacity), and the cumulative `entitiesSpawned`, `entitiesDestroyed` (cancelled spawns are in neither).

### Hot reload and device recovery

18. **Recovery.** After a device loss `DynamicEntities.rebuild(render, materials)` re-creates the renderer instances and object blocks of the live spawned entities under **the same instance indices** and re-binds their material instances; slots, generations, state and queues are untouched, so references held in state stay valid.
19. **Reload** (`app.replaceProgram`, non-restart). The spawned entities that exist are **created again in the same slot and generation** by the new program's `init`, with the params they were spawned with (the frozen object the old record carried), and the state, pose and imperative material params of the old record move over by identity like a named entity's (`carryEntity`; a state variable that is new or changed type is reset). References held in scene state stay valid for the re-created entities and dead for everything else. The swap is at the start of a frame, after the previous frame's `phase4_flush`, so both queues are empty then; an entity pending removal would be dropped and a pending spawn lost. The **restart with `W8070`** applies when a spawned prefab's **param signature** (`name: type` list) changed, or when the program's `prefabs` table gained or lost a prefab (as before, decision 0062 item 11). A prefab that is still in the program but no longer in the manifest's `prefabs` (the program no longer spawns it) drops its live entities silently; the references stay dead. A changed `init` of an unchanged signature is the normal case: the new code runs again for every live instance, which is what a developer expects from an edit.

### Known limitations

- Children of spawned entities do not exist (prefabs have one entity, v0.1).
- Reload re-runs `init` for spawned entities with the old params, then carries the old pose over the new `init`'s result (as for a named entity), so a position the old `init` computed from `random()` survives the reload; a changed `init` formula shows only for entities spawned afterwards.
- `mtek inspect --bindings` does not list prefab bindings (the manifest does).
- Physics for spawned bodies (creation, the removal order against collision events) is M5-05; item 16 is the whole interface.
