# 0045. Assignable places: struct fields and array elements

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §4.1 (numeric semantics: clamped indexing in both domains); `spec/language.md` §5.6, §6.9, §7.2; `spec/runtime-abi.md` §4.1; `spec/compiler-architecture.md` §4.7–§4.9; decisions 0009, 0037, 0038, 0040, 0041.
- Supersedes: decision 0038 item 4 for struct fields and array elements (the strict reading of §7.2).

## Context

Decision 0038 item 4 read the list of assignable places of §7.2 strictly: a `var` local or a single component of a vector place, and `E3061` for a struct field or an array element ("struct fields are not assignable places in v0.1"), noting that widening the list later breaks no program and leaving the question open on the board. The owner answered it on 2026-10-04 (the answer to M2-02's question): v0.1 allows assignment to **struct fields and array elements of assignable places** — simple forms like `p.offset = …` and `arr[i] = …`, nested forms like `arr[i].x = …` and `s.items[j] = …`, and compound assignments on all of them — and a run-time write index is **clamped exactly like a read** (§5.6), on the CPU and on the GPU.

Task M2-13 implements that. The specification does not say how a place is represented, which places stay errors, how the JavaScript keeps value semantics when arrays and structs are JavaScript arrays and objects, or how WGSL writes stored `bool`s and padded elements. Those choices are fixed here so that they are visible, testable and changeable by a later record.

## Decision

Item 1 is the owner's decision (an external constraint); everything else is a **proposal** (a design choice).

1. **Assignable places** (§7.2 as amended). A place is a root followed by a chain of steps, outermost last: struct fields (`.offset`), array elements with a constant or run-time `i32`/`u32` index (`[i]`), and at most one final single component of a vector (`.y`). In M2 the only root is a `var` local; scene state, `self.state_name` and writable entity fields are further roots in M3, with the same steps. Plain assignment and `+= -= *= /=` apply to every place; `p op= v` means `p = p op v` with `p` evaluated once. A run-time index of a place is clamped to `[0, N - 1]` in both domains, exactly like a read, and on the CPU reports `W8030` once per call site and context (decision 0037).

2. **What stays an error** (the checker, `types/body.rs`; the chain is walked with a loop, and only the first problem met from the outside in is reported):
   - `E3061` at the whole target for a root that is not assignable — a `let` local, a parameter, a loop variable, a constant (also an imported one), a material param — with a related span at its declaration; a target that is only a part of the root says so ("Cannot assign to a part of the local 'copy': it is declared with `let`."). Scene state stays `E3061` until M3 makes it a root.
   - `E3061` for a step that is not a place: a `mat4` column (`m[3] = …`; a column is not an array element, and a matrix is built with `mat4.columns(…)`), a component of a `quat` or `color` (§6.9 makes quaternion components read-only; colours are not vectors), any field that is not a struct field (the `SurfaceInput` record, entity fields until M3), and any other expression (a call, a literal, a parenthesised non-place). The note lists what is assignable.
   - `E3060` for a multi-component swizzle anywhere in the chain (`out[i].xz = …`), whatever its base.
   - `E3001` when the value does not have the place's type (a compound assignment types as `p op v`, decision 0038 item 4).
   - `E3030` for a constant index out of range: the target is folded like every expression of a body (decision 0038 item 3), so `xs[3] += 1.0` on an `array<f32, 3>` is an error and only run-time indices are clamped.
   - A `var` written only through a part of it counts as assigned (no `W2010`).

3. **The IR place form** (amends decision 0038 item 8's `assign` target). `target` is `{ root, steps, type, span }`: `root` is `{ kind: "local", local, name, type, span }`; `steps` lists `{ kind: "field", field, index, type, span }`, `{ kind: "index", index: <expression>, type, span }` and `{ kind: "component", component, type, span }` in application order; each step's `type` is the type of the place up to it and its `span` the text from the root to its end (`a[i]` for the step `[i]` of `a[i].x`); a constant index is a folded `const` expression. The human form prints `rig#2.probes[i#0].offset.x += 1.0`. Places carry their own spans, so in the JavaScript source map and the WGSL span map a target and each of its steps map to their own text (decision 0041 item 10's "an assignment target maps to its statement" no longer holds).

4. **Value semantics in JavaScript** (`emit_js/cpu.rs`; amends decision 0040 item 7). Arrays are JavaScript arrays and structs plain objects (`spec/runtime-abi.md` §4.1); vectors, quaternions, colours and matrices are never changed after they are built.
   - **Owned variables.** A `var` that some assignment of its function writes through a field or an element owns its storage and is written **in place**: `l_xs[rt.clampIndex(a_i, 4, 20, ctx)] = a_v;`, `l_q.weight = a_w;`. A final vector component rebuilds that vector and stores it into its container (`l_vs[t_0] = rt.v3with(l_vs[t_0], "z", …)`), as decision 0040 does for a whole vector variable.
   - **Nothing else may refer to owned storage.** A value stored into an owned variable (its initialiser, a whole assignment, a field or element write) is copied with `rt.copy` unless it is *fresh* — a constant (emitted as a literal, so each evaluation builds a new one), a copy, or an array or struct literal whose array and struct parts are fresh. An array or struct read out of an owned variable (the variable, or a field or element of it, used anywhere but as the base of a further field, element or component read) is copied before it goes anywhere else: into a `let` or another variable, an argument, a literal, the array of a `for x in xs` loop (which therefore runs over the array as it was when the loop started, like the WGSL `let mtek_each_x`). A returned value is not copied: the function's variables end with it.
   - Every other value is never changed in place and is shared freely; a variable that is only ever assigned as a whole (`a = b`) is not owned and costs no copy.
   - Hence `var a = b; a[0] = …;` leaves `b` unchanged, a constant folded into a literal is never changed across calls, and an argument is never changed. `rt.copy` copies arrays and plain objects at every depth and shares scalars, strings and `mat4` values (`Float32Array`, never written in place); it is a structural helper (`RT_STRUCTURAL_EXPORTS`, `STRUCTURAL_HELPERS`).
   - Copy on write (a new array for every element write, path copying for nested places) was rejected: it makes a write O(N), so filling an array in a loop would be O(N²) for `N` up to 65 536.
   - **Order and clamping.** The place is evaluated before the value, its indices from the root outwards. A run-time index is `rt.clampIndex(i, N, spanId, ctx)`, `spanId` being the manifest span of the indexing step (`base[index]` in the target), interned in emission order after every other span like the spans of reads (decision 0040 item 5). Where the place is read as well as written (a compound assignment or a final component), each run-time index is computed once into a temporary `const t_<n>` first, and the assignment becomes a block: `{ const t_0 = rt.clampIndex(a_i, 2, 23, ctx); l_rig.probes[t_0].offset = rt.v3with(…); }`.

5. **WGSL** (`lowering/shader.rs`; amends decision 0041 item 7). A place lowers through `field_place` and `index_place` — the stored reference of a field or element, before any `bool` decoding — so a run-time write index is clamped exactly like a read (`min(i, N - 1u)`, `clamp(i, 0i, N - 1i)`), a padded element is written through `.value`, and a final component is a single-letter swizzle of the reference. A value written to a `bool` stored as `u32` (a field or element) is encoded, `select(0u, 1u, b)`. A compound assignment clamps each run-time index once into `let mtek_index_<k>` (numbered per statement) inside a block before it reads and writes the place, so the place is evaluated once in WGSL too; its `p op v` maps to the text `p op= v`.

6. **M3 composes the same way.** Scene state, `self.state_name` and writable entity fields become `PlaceRoot` kinds with the same steps. In JavaScript a part of a root that lives behind the `ctx` setters of `spec/runtime-abi.md` §4.2 is written by reading the root's value, copying it (`rt.copy`), writing the chain into the copy as above and setting it back, so a runtime-owned value is never changed behind the runtime's back; the checker's chain walk, the IR steps and the WGSL lowering need no change.

## Consequences

- No new diagnostic code and no new dependency; one new `rt` helper, `copy`.
- `spec/language.md` §7.2 lists the new places; decision 0038 item 4 points here.
- The IR goldens changed by the new place form (`functions_statements_and_calls`, `materials_params_and_defaults`) and gained `functions_assignable_places`; the `cpu_functions` source map changed because targets map to their own text; the WGSL goldens did not change.
- Parallel work (M2-08, M2-09) that re-blesses goldens after this lands sees only these differences.
