# 0075. Untrusted preview mode: the loop budget, `E8080`, the `preview` manifest object, the network guard, the policy page, the compile time limit and the hosting guidance

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-10; blueprint §9.5 (untrusted previews: compiler correctness is not a sandbox); `spec/ai-and-benchmarks.md` §5; `spec/tooling.md` §§1, 2; `spec/compiler-architecture.md` §§6, 9; `spec/runtime-abi.md` §§3, 4.2, 5, 6.1, 6.5; `spec/diagnostics.md` (`E8080`, `E9032`); decisions 0033, 0040 (the CPU emitter), 0050 (scheduler), 0055 (release and development runtime flavours, the overlay), 0056 (resilience), 0063 and 0066 (the physics module is imported at run time and needs WebAssembly).
- Supersedes: nothing. Fulfils the M6 half of `spec/ai-and-benchmarks.md` §5 ("`mtek build --mode preview`", "host guidance"); the spec's sketch `if (--ctx.budget < 0) rt.budgetExceeded(spanId)` is refined in item 2 (the counter is read once per function) and `E8080`'s trigger is made precise.

## Context

The specification promises a `preview` build mode for programs that nobody has reviewed (typically written by a model): loop budgets, a runtime that only requests files below `baseUrl`, an external `bootstrap.js`, a restrictive Content-Security-Policy, compile limits and a timeout, and a document that tells hosts what is theirs to do. It leaves open what exactly counts against the budget, where the budget lives, what happens to the frame, the application and the page when it is exceeded, how the runtime learns it is running a preview, what a refused request looks like, how the budget is configured and by whom, what the timeout covers, and what the guarantees are. Every choice below is a **proposal** the owner may overrule; the facts about the language and the browser are constraints.

Facts the design rests on. **Constraints:** Mtek has no `while` or `loop` (`E0013`, reserved), no recursion (`E4001`, both domains), no closures, no exceptions a program could catch and no `try`; the only unbounded CPU work is therefore the iterations of `for a..b` (the bounds are run-time expressions on the CPU, `i32`/`u32`, up to 2^32) and `for x in array` (at most 65 536 elements), nested to the parser's depth. Code that the test harness evaluates over the debugging protocol is not subject to a page's Content-Security-Policy; a script the page loads is (measured in item 9). A `<meta>` policy cannot carry `frame-ancestors`, `sandbox` or `report-uri`.

## Decision

1. **What the mode is.** `--mode preview` is `release` (no overlay code, `print` compiled out, release runtime flavour, 0055 item 7) plus five things: (a) a budget check in every CPU loop (item 2); (b) the manifest's `preview` object (item 4); (c) `bootstrap.js` and the policy page (item 6); (d) the compile time limit of the command line tool (item 8); (e) a different build id (item 5). Nothing else differs: a preview of a program without loops differs from its release build in `index.html`, `bootstrap.js`, `program.manifest.json` (the `preview` key and the build id) only (tested). `BuildMode::Preview` was already in the library enum; its `E9010` is gone.
2. **The check, its cost, its place.** The generated code of a preview build starts **every iteration of every loop**, before the body, with `if (--budget.n < 0) { rt.budgetExceeded(<span id>); }`, and every function that contains a loop starts with `const budget = ctx.budget;`. Counting at the head means every path back to the head pays for the iteration it starts: `continue` and `break` are counted in the iteration they happen in, an empty range pays nothing (tested: `sum_to(10)` pays 8, `sum_to(0)` pays 0). The **span id** is the loop statement's entry in the manifest `spans` table (the whole `for` statement; for nested loops the loop whose check finds the counter below zero, which is the innermost one that is running). `ctx.budget` is `{ n }`, a plain object, **not a bare number**: `ctx` is a guarded proxy that is read-only by design (`world.ts`, so that a defect cannot write the context), and `--ctx.budget` would be a write; the spec's sketch is therefore refined, not followed. **Cost, measured (Node 24, 10 million iterations of `s += i`):** no check 4.5 ms; check on a plain object read once per function 11.6 ms (**+0.7 ns per iteration**, 2.6x on a loop with no body at all); the same check through the guarded proxy on every iteration 294 ms (**65x**; this is why the counter is read once per function). **In the browser** (`loop_cost`: 200 000 iterations of `sin` and f32 arithmetic per frame, 60 frames, hardware): median `cpuUpdateMs` **4.90 ms release, 5.00 ms preview, ratio 1.02**. The cost scales with the iterations and is invisible next to a real loop body. Release, dev and test output is **byte-identical** to before (the goldens did not change; a build without the budget interns no extra span and emits no extra text; unit test `a_preview_build_checks_the_budget_at_the_head_of_every_loop` strips the checks from the instrumented text and gets the plain text back).
3. **What is counted, and when it is refilled.** One counter per mounted world. `World.resetBudget()` sets it to `manifest.preview.loopBudget` at the **start of every frame** (phase 1, before the input handlers) and at the start of `initialise` (before `init`, the bindings evaluated after it and every state initialiser). So one budget covers every handler, every fixed tick (up to `maxCatchUpSteps` of them), every `update`, every binding and every spawned entity's `init` of one frame together; a program that fits in each frame runs for ever (tested: 50 frames at exactly the budget). **Default 10 000 000 iterations per frame** (`DEFAULT_LOOP_BUDGET`): measured about 0.65 s of main-thread time for the simplest nested loop with a state write per iteration on the test machine (`runaway_update`: longest stall 652 ms, overlay 0.8 s after navigation), and 12 345 iterations stall 15 ms. A frame that reaches the budget has been slow for 0.1 to 1 s; one that needs it is not a preview-sized program. Without a `preview` object the counter is never refilled and stays at 0, so an instrumented `app.js` mounted against a manifest that does not say so fails at its first loop instead of running unbounded (fail closed; tested).
4. **How the runtime knows: the manifest.** The optional top-level `preview` object (`{ "loopBudget": 1 … 4294967295 }`, `spec/manifest.schema.json`, `Manifest.preview`, `MtekManifest.preview`) is present exactly in the manifest of a preview build, between `runtimeConfig` and `entryScene`; the shared examples have it in `valid/full.json` and two invalid ones (`preview-budget-zero`, `preview-without-budget`). It is in the manifest and not in a mount option or the bootstrap, so the preview-ness **travels with the artifact**: a host page of its own that imports `app.js` gets the budget and the network guard too. Absent in every other mode (byte-identical manifests).
5. **The budget is the host's, not the project's, and part of the build id.** `CompileOptions.loop_budget: Option<u32>` (`None` = the default; `0` is read as 1) and `mtek build --mode preview --loop-budget N` (N a positive `u32`; the flag with another mode is a usage error). It is **not** in `mtek.toml`: a project is the untrusted input, and a budget the author can raise is no budget. `BuildIdentity` gains `previewLoopBudget`, written into the canonical JSON only for previews (key order stays lexicographic), so two previews with different budgets, and a preview and a release build, have different ids, and every other id is what it was (tested).
6. **`E8080`: what happens when the budget is exceeded.** `rt.budgetExceeded(spanId)` throws `ExecutionBudgetExceeded` (a class of the runtime bundle, not exported through `rt`: `RT_STRUCTURAL_EXPORTS` gains only the helper). It unwinds the handler, the tick and the frame (Mtek cannot catch it). In a **frame** (the animation-frame loop's error path, and `debug.step` of the manual clock, which reports and returns instead of rethrowing this one error): the application reports `E8080` ("execution budget exceeded", phase = the scheduler phase that was running: `runtime:input`, `runtime:tick`, `runtime:update`, `runtime:bindings`), **at the loop's span** (file, line, column from the manifest), with notes (what the budget counts; "build with a larger `--loop-budget`"), **stops the scene** (`state = "failed"`, the scheduler stops, no further frame is requested, so the page is free) and shows the **failure overlay** (`data-mtek-overlay`, which the release flavour has). The scene is stopped, not continued, because the frame was abandoned half way: state, transforms and queued spawns were left where the loop stood, a state no program produced. During **`init`** the mount rejects with `MtekMountError` of the new kind **`budget-exceeded`** (`E8080`, phase `runtime:mount`, the loop's span), releases everything and shows the overlay. State written before the check that threw stays written (a loop `total += 1` in an abandoned frame leaves exactly B - 1, tested), the runtime never rolls back.
7. **The network guard.** With a `preview` object, the mount wraps the host environment (`restrictToBase`) right after the manifest is parsed: `fetch`, `fetchBytes` and `importModule` (the physics module) reject with `NetworkRefusedError` ("refused <url>: a preview may only request files below its own directory") **before** the request is made, for any URL that is not below `baseUrl`: same scheme, host and port; a path that starts with `baseUrl`'s path after the URL parser resolved `.` and `..`; no credentials; no percent-encoded dot, slash or backslash below it (a server may decode them after the check); `data:`, `blob:` and `javascript:` are other schemes and refused. The manifest's own URL must be below `baseUrl` too (else `E8006`, "outside baseUrl"; the one request that precedes the manifest is the program module's own `manifestUrl`). The refusal is a rejection, so each loader reports it with its own code and the message (`E8051` for a shader, `E7030` for an asset, `E8102` for the physics module): **no new diagnostic code**. **Honest scope:** every URL the runtime builds is `baseUrl` plus a name the manifest schema constrains to a relative pattern (`shaders/<h16>.wgsl`, `assets/<h16>.<ext>`, `physics/<h16>.js`), so no program the compiler makes can reach a refusal; the guard is the single place every request passes through, so that a future call site or a manifest not made by the compiler cannot go outside, and the unit tests pin it down (`isWithinBase`, `restrictToBase`, the mount of a preview whose manifest came from outside). The browser's own refusal (item 9) is the second, independent layer.
8. **Compile limits and the timeout.** The compiler's limits were already diagnosed in every mode and are verified again through the command line in preview mode with hostile sources (the test builds each in preview and release and requires exit code 1, the code and under 9 s): a file over 4 MiB (`E0004`), over 1 024 modules (`E9002`), nesting past 256 (`E1050`: 100 000 nested parentheses, a chain of 100 000 operators, 100 000 prefix operators, 5 000 nested blocks), over 16 384 static entities (`E5092`); the deepest legal nesting (250) builds. Constant folding cannot be made to loop (no user function runs at compile time: constants are literals, constants and intrinsics; loops are run-time), so there is no expansion to limit beyond these. What a size limit cannot bound is time: **a preview build runs against a 10 s clock** (`PREVIEW_COMPILE_TIMEOUT`, `mtek-cli/src/limits.rs`): `build` runs on a thread of its own with the compiler's 16 MiB stack, the command waits with `recv_timeout`, and on expiry reports the new error **`E9032`** ("compilation timed out", exit code 1, nothing written) and ends; the thread is left behind and dies with the process (Rust cannot stop a thread). A panic in that thread is `E9999` as before. The limit is a constant of the tool (`spec/ai-and-benchmarks.md` §5 names 10 s), not an option; other modes run unbounded in time. Not tested through the real binary (no input takes ten seconds): `limits::run_within` is tested with a sleeping job and a 50 ms clock.
9. **The policy page and the bootstrap.** The page of a preview build has no script of its own: `<meta charset>`, then `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; img-src 'self' blob:; style-src 'self' 'unsafe-inline'">` (exactly the string of `spec/ai-and-benchmarks.md` §5, before anything that loads), the canvas and `<script type="module" src="./bootstrap.js">`; `bootstrap.js` is the release page's two lines (`import program, { mountMtek } from "./app.js"; mountMtek(...).catch(() => {});`). `'wasm-unsafe-eval'` is what the physics module's WebAssembly needs and allows no JavaScript `eval`; `'unsafe-inline'` for styles is for the inline `<style>` of the page and the overlay's styles. **Measured in the browser on hardware** (`specs/preview/csp.spec.ts`): the physics fixture runs under the policy exactly like the same program built in test mode (the 19 sampled heights are bit-identical, free fall matches the engine's model, rest at 0.5 within 10 mm, one landing, one request for the physics module with status 200, no violation, no console error, every request below the page's directory); the real clock, unmodified page runs too; from a script of the page a `fetch` to another origin (`connect-src`), `eval` and `new Function` (`script-src`), an inline script (`script-src-elem`), an image from another origin (`img-src`) are blocked and reported as `securitypolicyviolation` of that directive, and a second origin run by the spec receives **no request**; with the `'wasm-unsafe-eval'` token removed from the page the mount fails with `physics-failed` (`E8102`), so the token is needed and the policy is effective. A blob worker is not run. Code evaluated through the debugging protocol (Playwright's `page.evaluate`) is **not** subject to the policy, so the `eval` probe runs from a script the page loads.
10. **Guidance, honestly.** `docs/preview-hosting.md` says what the mode does (the budget, the guard, the page, the limits) and what it does not: it is **not a sandbox** (an unbounded allocation, a slow shader, a GPU hang, a page that is merely large are outside it; the program runs in the page's origin with the page's powers unless the host isolates it), the budget bounds iterations, not time (a budget of 10 million iterations of a heavy body is long), there is no wall-clock watchdog in the runtime, and the policy is a `<meta>`, which cannot carry `frame-ancestors`, `sandbox` or reporting: those are the host's response headers. The host's part: a separate origin, a sandboxed iframe without `allow-same-origin`, no credentials, a heartbeat watchdog that kills the frame, resource limits, the policy as a header as well.

## Consequences

- `spec/ai-and-benchmarks.md` §5, `spec/compiler-architecture.md` §§4.12, 6, 9, `spec/runtime-abi.md` §§4.2, 5, 6.1, 6.5, `spec/tooling.md` §§1, 2, `spec/diagnostics.md` (`E8080`, `E9032`) and `spec/manifest.schema.json` point here. New codes: `E9032`; `E8080` is now produced. New: the manifest key `preview`, the mount error kind `budget-exceeded`, `ctx.budget`, `rt.budgetExceeded`, `--loop-budget`, `bootstrap.js` in the dist of a preview, the `programs-preview` output of the `codegen_programs` example.
- The runtime bundle grows by the guard and the budget (a few hundred bytes); release and development builds of programs are unchanged.
- A host that wants a different budget builds with `--loop-budget`; a host that wants a wall-clock bound needs its own watchdog (the guidance says how).
- **Not done, honest scope:** no mutation check of the new runtime rules was run by hand (the reset per frame, the head position of the check); the unit tests state them. No test makes the real binary hit the 10 s timeout. The budget bounds loop iterations: a single very slow iteration (a large `array` copy per iteration) is bounded by the array limits, not by the budget. Nothing bounds GPU work; a heavy shader is the browser's and the host's to bound.
