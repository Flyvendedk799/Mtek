# 0125. Retry runs supply attempts for cells that were not judged; the final M7.1 main-set comparison; the exploratory holdout from summary files; the machine-readable baseline

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M7 (blueprint §11), task M7-05 and its re-run M7.1; `spec/ai-and-benchmarks.md` §§1, 4 and 6.4.
- Supersedes: nothing. Completes decision 0124 (which left the 57 lost attempts and the 80 lost holdout attempts as "not judged, no retry run") and applies decision 0108 items 10 (an attempt the harness could not judge is reported apart and stays out of the completion rate) and 11 (a baseline that was not re-run is borrowed from the earlier run).

## Context

Decision 0124 recorded that an API outage cost the M7.1 re-run of the Mtek conditions 57 of its 340 main-set attempts (28 context only, 29 with the guide; all trial index 4) and all 80 attempts of its holdout re-run (63 not reached, 17 refused by the spend cap), and that the owner had stopped spending, so none was re-run. The owner then paid for the re-run of exactly the lost cells with the harness as 0124 fixed it:

- `m7-1-retry-ctx` and `m7-1-retry-guide` (`benchmarks/results/ai/`): 28 and 29 attempts, trial index 4, the lost context-only and guide cells of the main set;
- `m7-1-retry-holdout` (outside the repository): the 80 holdout attempts (8 tasks, 5 trials, Mtek context only and Mtek with the guide).

The same model (Claude Haiku 4.5), temperature 1, prompt caching on and documentation as in the first M7.1 run (the retry attempts carry the same condition ids and the same context hashes as the attempts they replace; the tool checks this). There is no field in a record that says "this attempt replaces that one", and the report counted every attempt of every run it was given, so giving it a retry run next to the first run would have counted the lost cells twice.

## Decision

**Retry runs (tools)**

1. **A retry run supplies attempts for cells whose attempt in the other runs was not judged.** A cell is a task, a condition (side, trial kind, the Mtek variant: context only, or context plus a document) and a trial index. "Not judged" is the report's own reading of an attempt: outcome `error`, `unavailable`, `unfinished` or `not-run`, or the legacy rule of decision 0124 item 5 (a failure whose every call is a connection error or timeout with no response). `report-cli --retry-run DIR` (repeatable) and `compare-cli --after-retry RUN[,RUN]` name retry runs; `extractTrials(records, holdoutIds, retryRecords)` is the one place that does it.
2. **In every aggregate and in the verdict the retry attempt replaces the not-judged one.** `extractTrials` returns `trials` (what counts: the retry attempt in the place of the lost one), `superseded` (the lost attempts, each with `supersededBy`: the id of the retry run) and `listing` (every attempt of every run). The retry attempts carry `retryOf`: the id of the run whose attempt they replace. The report lists the lost attempts under "Attempts that could not be judged" apart from the attempts that count, and both in "All attempts" (the lost one as `superseded by retry run X`, the retry as `retry of the attempt in run Y`, the attempt cell naming its run, because both have the same attempt id); a run table marks retry runs. Without a retry run no text changes. If the retry attempt is itself not judged, it still replaces the lost one (the cell stays not judged, with the later attempt); nothing is imputed.
3. **A retry that does not fit is an error, not a silent drop.** The tool refuses (the CLI ends with exit 3 and writes nothing) a retry attempt for a cell whose attempt WAS judged (success or failure); for a cell no other run occupies; for a cell occupied by more than one attempt; a second retry attempt for one cell; a retry run with the id of a run it retries; an attempt with another model or provider, another condition id, or, when both records carry one, another context hash than the attempt it replaces. A failure is not "retried until it passes": a retry run can only fill a hole, never overwrite a result.
4. **The holdout summary** (`report-cli --holdout-summary`) now writes `runId`, `variant` (`""` or `+guide`), `trial` and, for a lost attempt `supersededBy`, for a retry attempt `retryOf`, from the `listing`; the summary of M7-05 (`holdout-summary.jsonl`) is not rewritten and is read by the attempt id for the keys it lacks. It still holds ids, outcomes, layer outcomes, token counts and cost, and no text.
5. **The holdout section of the comparison is computed from summary files only** (`compare-cli --holdout-before FILE[,FILE] --holdout-after FILE[,FILE]`, `holdout-compare.ts`): per condition the attempts, completed, failed, not judged, completion rate, tokens per completed task (input plus output of all attempts / completed tasks) and cost, over the rows that no retry replaced, and the rule of decision 0108 for each Mtek condition against the EARLIER holdout baseline (the holdout baseline was not re-run). The holdout has 8 tasks, at least the 5 the interval needs, so a verdict is allowed. **Every holdout figure is exploratory**: 8 tasks x 5 trials, one model, one run of each condition; the section says so. No holdout run directory is read, so a test regenerates the section from the repository.
6. **`compare-cli --baseline-json FILE`** writes `evidence/M7/ai-baseline.json` (`baseline-json.ts`): the model id, provider, temperature, prompt caching, test feedback, the prompt versions, the price table of `tools/ai-eval/src/spend.ts` for that model (list prices, not an invoice), the harness (package, version, record schema, decisions), the run ids seen, the path, run ids, row count and SHA-256 of every `records.jsonl` used and of every holdout summary used (the text read with CRLF as LF, so the hash is the same on every checkout), the conditions before and after with attempts, completed, failed, not judged, completion rate, tokens per completed task and cost, overall, per mode and per category, the baseline row, the holdout numbers, the verdicts with their reasons and token-ratio intervals, and the targets: the main-set baseline row (91.8 % completion, 9,388 tokens per completed task), the holdout baseline (97.5 %, 7,737) and the research target of spec 6.4 (a token ratio of at most 0.70 at matched success, with the verdict better; a target, not a result). The file is generated, never edited; a test regenerates it byte for byte.

**The final M7.1 documents**

7. `benchmarks/results/ai/report-m7-1.md` and `compare-m7-1.md` are regenerated with the retry runs; `holdout-summary-m7-1.jsonl` holds the 160 rows (the 80 lost attempts of `m7-1-rerun-holdout`, each `supersededBy` `m7-1-retry-holdout`, and the 80 attempts of the retry run); `evidence/M7/ai-benchmark-m7-1.md` states the final numbers. After the retry runs the main set has 170 attempts per Mtek condition, all judged (116 / 170 completed for the context alone and 145 / 170 with the guide), so by the rule of decision 0108 no verdict is provisional: every task has 5 trials per side, 0 % of the attempts are not judged (the limit is 10 %) and no token count is unknown. Both Mtek conditions are still **worse** than the three.js baseline (completion 68.2 % and 85.3 % against 91.8 %; tokens per completed task 33,648 and 29,872 against 9,388).
8. What the figures do not show is written on the evidence page, not left to a reader: the failures that K-01 to K-03 address were diagnosed on the main set, so its gains are optimistic; the holdout was not used for design but its tasks may be easier; 40 attempts per condition can show only large effects; one model, one run per condition, temperature 1; no repetition; the cost figures are list prices.

## Consequences

- A hole in a run can be filled for money, without a re-run of what was judged, and the records of both attempts stay. The price is that "the 340 attempts of M7.1" are no longer one run: they are three runs with a stated rule, and the lost attempts, the retry attempts and the hashes of the files are in the documents.
- The retry attempts ran after the first run, with the harness as decision 0124 changed it (retries and a better classification of a dead network); the model calls of the lost cells are the same requests as the first run would have made, but not the same replies. This is a second draw for those cells, not a recovery of the lost draw. The matched cells are now all the cells, so the comparison with the M7-05 runs is on all 170 cells of each condition.
- The ledger (outside the repository) is not corrected: the 120 failed calls of the outage were charged 3.96 USD at their worst case, the ledger total after all runs is 23.96 USD, and the real spend, about 20 USD if the 3.96 USD were never billed, has not been reconciled with an invoice.
- The 30 % token target of spec 6.4 is not met by any condition, on the main set or on the holdout. This decision does not change the target or the rule.
