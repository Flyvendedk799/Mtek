# 0096. Runtime benchmark workloads: the seven definitions, the three implementations of each, what "same visible result" means, and to which metric the 20 % threshold applies

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: §12.3, M7; `spec/ai-and-benchmarks.md` section 7; `spec/scenes.md` sections 4, 5, 9, 10; `spec/assets.md`; `spec/physics.md`; decisions 0059 (instancing), 0060 (runtime assets), 0063 / 0066 (physics adapter and integration), 0095.
- Supersedes: nothing.

## Context

Section 7 lists seven workloads and demands for each an Mtek program, a hand-written direct-WebGPU reference "with the same visible result and workload size", and a three.js baseline. It does not say how the reference is designed (a reference that mimics Mtek's renderer would prove nothing; one that is specialised by hand would compare Mtek with a ceiling), what the baseline's idiom is, how "the same visible result" is checked, or what the 20 % threshold applies to for the two workloads that are not frame workloads. Proposals follow.

## Decision

1. **The workloads** (`benchmarks/runtime/<workload>/workload.json` holds the numbers; `common/layout.ts` holds the formulas; both are frozen, decision 0097):
   - `constant-scene`: 400 unlit boxes on a 20 x 20 grid in 8 colours, nothing changes.
   - `changing-transforms`: 1,000 boxes (one mesh, one colour); every frame every box's position (bobbing along y) and rotation (about +Y) change.
   - `changing-material-params`: 500 boxes that never move; every frame every box's colour parameter changes (three phase-shifted sines).
   - `repeated-meshes`: 2,000 boxes of one mesh and one material on a 20 x 10 x 10 lattice, each with its own yaw and scale (the instancing path); nothing changes after startup.
   - `asset-heavy-startup`: 12 textured spheres drawn from 4 generated GLB meshes of 21,600 triangles each and 8 generated 512 x 512 PNG textures; the measured thing is startup (decision 0095 item 8); the frame passes also run on the finished scene.
   - `physics-bodies`: 300 dynamic unit boxes (10 x 10 x 3) on a static floor, Rapier 0.21.0 at the fixed step 1/60 s; a small periodic horizontal force on every box, applied every tick, so that no body ever sleeps and the solver works throughout the measured frames (a drop-and-settle scene would be asleep for most of 1,320 frames, which would measure the sleeping, not the simulation).
   - `mount-reload-dispose`: a scene of 100 boxes in 4 colours is mounted, drawn for 5 frames, reloaded with an edited program (the palette shifted by one entry), drawn for 5 frames and disposed; 50 times in one page (and 800 times in a supplementary run, decision 0098).
2. **All materials are `Unlit` (a flat colour) except the textured one** (a user material that samples one texture and returns its texel, in the asset workload), so the three implementations can show pixel-identical pictures without reimplementing Mtek's lighting; the cost of lighting is not part of this benchmark and is not claimed.
3. **The Mtek program is generated** from the same definition (`tools/gen-mtek.ts`; each program carries a "generated, do not edit" header; a test fails when the committed file differs from what the generator prints and another runs the real compiler over every program). Repeated things are prefab instances (`entity B017: Block { ... }`): `bind(...)` expressions of `frame.time` where the workload changes something every frame. Mtek has no loop that creates entities, so the programs are long (the 2,000-instance one is 160 KB of source); that is a fact of v0.1, not a defect of the benchmark.
4. **The direct-WebGPU reference** is hand-written TypeScript (`<workload>/direct/main.ts` on a small shared kit, `harness/kit/direct.ts`: device, targets, matrices, box mesh, one instanced unlit pipeline). Its design rule is: *what a competent engineer would write for that workload*, not a re-implementation of Mtek's renderer: one instance buffer and one instanced draw call where the scene is boxes (per-instance colours in a second vertex buffer, so a workload that changes colours rewrites only the colours); the asset workload draws its 12 meshes individually with a textured pipeline; physics uses Rapier directly (no collision events, because nothing consumes them; Mtek's adapter enables them on every collider, which is part of Mtek's cost). The reference is written once and not tuned afterwards; it is a point of comparison, not a ceiling, and a gap to it measures the design difference as much as implementation overhead (for `changing-material-params` the reference draws 500 boxes with one call, Mtek with 500, because their colours differ; the report prints draw calls so the reader sees which).
5. **The three.js baseline** (`three/webgpu`, r186.1, `WebGPURenderer` on the WebGPU backend) uses the three.js idiom of each workload: `Mesh` objects sharing a geometry and materials (matrices computed once and automatic updates switched off for scenes that never move, as the three.js manual recommends), `InstancedMesh` only for the instancing workload, `GLTFLoader` for the GLB, `Texture` objects configured like Mtek's `sampler.linear_repeat()` (bilinear, repeat, no mip-maps: Mtek v0.1 generates none) for the images. `renderer.dispose()` is awaited and, in r186, destroys the device.
6. **Same visible result is measured, not asserted.** After a workload's parity frames (60; 10 for physics, where chaotic divergence begins soon after contact; 5 for the asset and cycles workloads) each implementation's picture is stored as a PNG with the raw results and compared with the direct reference's pixel by pixel (`tools/parity.ts`): a pixel differs when a colour channel differs by more than 8 of 255, and two pictures show the same scene when at most 0.5 % of the pixels differ and the picture is not blank. For physics the positions of the first bodies are also compared. The report prints the table for every workload and implementation.
7. **Which metric the 20 % threshold is applied to** (`tools/analyze.ts`, `primaryMetric`): for the five frame workloads, the p95 frame time of decision 0095 item 1 against the direct reference's; for `asset-heavy-startup`, the p95 of the startup latency (navigation to first frame complete) over its 15 loads, because startup is what the workload is about; for `mount-reload-dispose`, the p95 over the cycles of mount + reload + dispose time. The spec's "controlled core-rendering workload" is `constant-scene` (nothing changes, no uploads, no physics); the other workloads are held to the same number so that no workload escapes, and every one that exceeds it is listed with the counters of the same run. The threshold is an investigation trigger, not a speed guarantee, and no release copy may quote the figures as one.
8. **Reload is not like for like.** Mtek's reload (`app.replaceProgram`, development runtime flavour, the only one that has it) validates a candidate program; the other two rebuild their scene objects on the same device. The workload compares what a developer waits for when a program changes, and the report says so. The Mtek build of this workload is the development flavour; the others are release flavour.
9. **Failure rule.** A workload or an implementation that cannot be implemented, errors, or exceeds the threshold stays in the table, with the failure; none is removed or redefined after a failure (decision 0097).

## Consequences

- Each workload exists three times; a change to one implementation is a change to the frozen definitions and needs a rationale.
- The Mtek programs are large because the language has no way to create many entities from a loop at scene scope (spawning is a handler-time operation, `spec/scenes.md` section 9); a program of 1,000 prefab instances was acceptable to the compiler and the runtime in this task.

## Verification

- `common/layout.test.ts` (sizes: 400, 1,000, 500, 2,000, 300, 12, 100; formulas), `tools/gen-mtek.test.ts` (generated equals committed; entity counts; the real compiler checks every program with 0 errors and 0 warnings), `tools/assets.test.ts` (21,600 triangles per mesh, a valid GLB, texture pixels and hashes), `tools/small.test.ts` (picture comparison).
- Measured pixel agreement of the three implementations is in the report (section "Same visible result").
