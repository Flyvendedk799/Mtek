# 0071. Validated suggested edits and the diagnostics audit: one validator, five codes with edits, absence as a tested result, related spans and message rules enforced

- Status: Accepted
- Date: 2026-10-18
- Blueprint origin: M6 (blueprint §11), task M6-02; blueprint §9.4 (diagnostics for repair: validated edits only, complete related spans); `spec/diagnostics.md` §2 (the envelope), §5 (the catalogue), §6 (suggested edits, rewritten by this record), §7 (message rules, extended); `spec/diagnostic.schema.json`; `spec/compiler-architecture.md` §4.2 and §7; decisions 0023 (the parser's candidate edits), 0025 items 9 and 12 (did-you-mean, edits left for M6-02), 0058 (the E7024 rename), 0035/0036 (struct and module identities the related spans rely on).
- Supersedes: nothing. Fulfils the "validation, M6-02" notes of decisions 0023, 0025 and 0058.

## Context

Before this task the pieces of a validated-edit pipeline existed but were not joined. The lexer recorded `FloatFix`es for `E0022`, the parser recorded `CandidateEdit`s for `E1003` and `E1011`, and the asset accessors attached an `E7024` rename straight to the diagnostic after checking only that the accessor would succeed with the new name. `E2003` had a "did you mean" hint and no edit. Nothing re-checked a program with an edit applied, so `spec/diagnostics.md` §6 ("validated edits only") was promised by each reporter and verified by none, and the language server of M6-03 had no documented edit model to build on. The audit part of the task asked for diagnostics that let a human or an agent repair code locally: complete related spans and messages that follow §7, checked mechanically where possible.

## Decision

1. **A stage proposes, one place disposes.** `Diagnostic` gains `candidates: Vec<SuggestedEdit>` (proposals, never serialised) beside `edits` (validated, serialised as `suggestedEdits`); the builder is `Diagnostic::candidate`. `Diagnostic::edit` stays for tests and the validator only: a test (`only_the_edits_module_attaches_edits`) fails if another source file attaches an edit. A second test lists the files that propose (lexer, parser `recover.rs` and `expr.rs`, resolver, asset types) so that a new proposer must be added to the spec and to this record. The parser's and lexer's own records (`CandidateEdit`, `FloatFix`) stay for tools and tests that run them alone; the same edit is built once and used for both.
2. **The validator** is `crates/mtek-compiler/src/edits.rs`, reached through `edits::finish(sink, recheck, sources)`, which replaces `sink.finish()` in `analyze`, `build` and `inspect`: `check`, `build` and `inspect` therefore attach exactly the same edits. For each diagnostic in report order it (a) takes the proposal only if there is exactly one (several proposals are ambiguous: none), (b) checks it is well formed (title, at least one edit, no deletion, in range, on character boundaries, no overlap inside it), (c) drops it if it overlaps an edit attached to an earlier diagnostic, (d) **re-runs the whole front end** (`front_end_with`, the same function `check` runs) on `EditedFs`, an in-memory file system that serves the original project except for the edited files, and (e) attaches it only if the diagnostic has disappeared and the copy has no error that the unedited project lacks. Nothing on disk changes.
3. **The comparison.** Diagnostics are keyed by `(severity, code, file, message)`; byte offsets are left out because the edit moves them. The target must occur fewer times in the copy than in a baseline (the same front end on the unedited files, run once per report and only if a proposal exists), and every error of the copy must occur at most as often in the baseline. An edit may remove other errors too; it must not add one. Warnings of the copy are not compared (a fix may legitimately reveal `W3081`).
4. **Deliberate conservatism, stated in `spec/diagnostics.md` §6.3.** (a) An error the parser's recovery had hidden (one syntax error per three tokens) counts as new when the edit reveals it: two missing semicolons in a row get no edit (fixture `edits_e1003_revealed_error_gets_no_edit`). (b) A baseline with suppressed diagnostics (`W9003`) gets no edits at all. (c) At most `MAX_EDIT_VALIDATIONS` = 32 proposals per report are re-checked, in report order, because each re-check is a whole front-end run (the cap is exercised by a unit test with 37 missing semicolons). (d) Emit-stage errors are not compared: the stage does not run while the front end has errors and `check` never reports them, so a fix that makes the program build and then fails to emit gets its edit (the diagnostic it repairs is repaired). **The scope of the proof is the front end, not `build`**; it is the stage that reports every code that carries an edit.
5. **Which codes carry edits.** `E0022` (the float with its missing digits), `E1003` (insert `;`), `E1011` (parentheses around the descriptor literal), `E2003` (rename to the single visible name within edit distance 2; for `Key.Spce` the member only), `E7024` (rename the string literal to the single name within edit distance 2). The `E2003` proposal is made where the hint is made (`report_unknown`, only for `E2003`: the same function reports `E3003`, which gets no edit), and only if the span is exactly the written name. **No other code carries an edit, deliberately:** `E3003`, `E5001`, `E3023`, `E5042`, `E5003` and the project-file hints are "did you mean" hints that could use the same mechanism but were not in scope and need their own fixtures; `E3001`, `E3102`, `E3041`, `E3040` and every type error would need a conversion or an invented value, which §6.2 forbids; `E1001`, `E1002`, `E1004` have no unambiguous repair. `E1011` does get an edit even when the parenthesised program still has an error (the fixture's `if Flag { ready: true } {` still has `E3070`, an error of the baseline): the edit repairs the syntax, introduces nothing, and the spec's criterion is "removes the diagnostic, adds no error", not "makes the program pass".
6. **The edit data model** (`spec/diagnostics.md` §6.1, for M6-03): a titled (`description`) list of text edits `{file, startByte, endByte, replacement}`, half-open original offsets of the file as stored, applied together in any order (`edits::apply_edits`); an insertion is an empty range; no deletions; one suggestion per diagnostic; the edits of one suggestion do not overlap each other (two insertions at one offset are overlapping, an insertion at the end or start of a replaced range is not); the suggestions of one report never overlap (`edits::spans_conflict`, the one definition, also used by the oracle test). No schema change: `spec/diagnostic.schema.json` already describes `suggestedEdits` and `schemaVersion` stays 1. The human renderer does not print edits (the `help:` notes already carry the hint).
7. **The audit is mechanical where it can be** (`crates/mtek-compiler/tests/diagnostics_audit.rs`, ten tests): over every diagnostic of every golden file (769 of them in `tests/syntax`, `tests/semantics`, `tests/assets`) the message rules (a complete sentence: no leading lowercase word, a full stop, no stray or double whitespace or line break, not just the catalogue title, none of the compiler's own words, "v0.1" for the `x9xx` codes), the note rules, the related-span table (`RELATED_REQUIRED`, with one exception row for the built-in materials), the promise check (every catalogue trigger cell that says "related span" is in the table), the file-naming rule for glTF/image content codes, the anchor of every code a fixture expects; over the sources, that every `E9999`/`E6100` site says "compiler bug" and that edits are attached and proposed only where this record says. Each rule has a self-test with bad input (`the_message_rules_catch_what_they_are_for`). The anchor check of `diagnostics_catalogue.rs` (exactly one anchor per code, in its own row, equal to its `docs` fragment) is the "generated" anchors check: the catalogue is generated from `codes.rs` and the test fails on any difference.
8. **Audit findings, all fixed** (each has a changed golden):
   - *F1, message form.* The `E1040` messages "fields/statements/scene objects cannot appear in …" started with a lowercase word (the plural noun); now capitalised.
   - *F2, message form.* `E7010` ("meshes[0].primitives[0] has no POSITION attribute") and `E7011` (two messages) started with a bare glTF path; they now start "The primitive …" / "The accessor …".
   - *F3, entity not named.* About sixty glTF/image content diagnostics (the goldens of 62 asset fixtures changed) (`E7001`–`E7019`, `E7025`, `E7002` for the JSON chunk) said what was wrong inside a file but not which file (only the path literal at the primary span said). `Issue::at_in` adds the note "the problem is in the file 'models/chair.glb'" when the message does not name it already.
   - *F4, related spans missing* (`spec/diagnostics.md` §2.1 shows the example for `E3102`; §7 now states the rule): `E3102` for a user material or prefab param (the param declaration); `E5003` for a missing material param (the param); `E5042`, three forms (the prefab declaration); `E5051` (the first declaration of the lifecycle function, with a `help:`); `E3021` and `E3023` for a user struct (the struct declaration, or the import for an imported struct; the field-access form only for a struct of the same module, because another module's declarations are not at hand in the interner); `E3001` for a declared type that the value does not fit (the annotation of a constant, state or local), for a `return` (the written result type, `BodyState::ret_span`), and for an argument of a user function (the function declaration, or the import); `E3002` for a user function (the declaration).
   - *Reviewed and left, because there is no source location to point at or the repair does not need one:* `E2001`/`E2002` for built-in names and entity fields, `E3102`/`E5003` for registry schemas and built-in materials, `E3001` arguments of built-ins, `E3090` (the reason's own span is the primary), `E4040` (the captured declaration is not in the resolver's table; a follow-up), `E5004`, `E5013` (only camera inactive), `E5071` velocities, `E5073`, `E5123` without a body, `E9006`.
   - *Not audited by a test:* the run-time messages of `packages/runtime-web` (`E8xxx`, `E7030`, `E7031`, `W80xx`); they were read once against §7 and follow the rules, but a TypeScript audit was not built.

## Fixtures and tests

- `tests/semantics/fail/edits_*` (eight projects, goldens now carry `suggestedEdits` and the runner compares them **whether or not the golden has the key**, so an absent key asserts absence): `edits_e0022_float_forms` (three forms), `edits_e0022_integer_context_gets_no_edit` (`1.` as an `i32`: the fix would be a float, a new error), `edits_e1003_missing_semicolons`, `edits_e1003_revealed_error_gets_no_edit`, `edits_e1011_descriptor_in_condition`, `edits_e2003_single_candidate_renames` (an edit for `lenght` → `length`, `Key.Spce` → `Key.Space`, `SPED` → `SPEED`; none for `lenght` where a vec3 is needed, for `ALPHC` with two candidates, for a name with none), `edits_adjacent_edits_are_all_offered` (an `E1011` insertion and an `E2003` rename that touch at one offset: both attached), `edits_in_an_imported_module` (an edit in another file than the entry). `tests/assets/fail/e7024_ambiguous_names` (two ambiguous mesh names: none); `e7024_unknown_names` keeps its three renames, now validated. Five existing `e2003_*` goldens gained their edits (legitimately, blessed with `MTEK_BLESS=1`).
- `crates/mtek-compiler/tests/suggested_edits.rs` is the acceptance test: for **every fixture project** of `tests/semantics`, `tests/assets`, `tests/modules` and every `tests/syntax/{fail,lex}` file (wrapped in a project) it applies each attached edit with a plain string splice (not the validator's code), runs `analyze` on the copy and asserts that the diagnostic is gone and that no error is new; that no two edits of a report overlap; that no diagnostic has more than one suggestion or a deleting edit; that proposals are consumed; and that every one of the five codes has at least one edit in the corpus (the proof is not vacuous).

## Consequences

- `mtek check --format json` and `mtek build --format json` now contain `suggestedEdits` for the five codes when, and only when, they are proven; an agent can apply them without judgement and a language server (M6-03) can map them to code actions with the documented model. Offsets are bytes of the stored file; the server converts with `SourceFile::lsp_position`.
- A report with edits costs up to 33 extra front-end runs; reports without proposals cost nothing. The dev server pays that on each failed rebuild; the cost was not measured on a large project. If it matters the budget is one constant.
- A fix may be withheld that a human would call obvious (adjacent missing semicolons, a report with more than 200 errors). That is the price of "never attach on a guess"; every such case is in §6.3.
- Because the re-check is the real front end, a later change to any checker that makes an edit invalid is caught by `suggested_edits.rs` without touching the edit code.
- Not done and recorded as follow-ups: edits for `E3003`/`E5001`/`E3023`/`E5042` renames; a related span at the declaration a capture refers to (`E4040`); a TypeScript audit of the run-time messages; printing the edit in the human renderer.
