# 0092. The modular scene: the example, what it uses that the other two demonstrations do not, how its numbers are derived and where its cross-file failure is tested

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M7 (blueprint §11), task M7-01; decision 0002 (the three release demonstrations: the third is `examples/modular-scene/`, "modules, prefabs, parameterised reuse, cross-file diagnostics"); `spec/language.md` §9; `spec/scenes.md` §5; decisions 0036 (modules), 0062 (prefabs), 0064 (spawn), 0059 (compatible instancing), 0074 (`mtek test`), 0069 (the playground this follows).
- Supersedes: nothing.

## Context

Decision 0002 requires that each release demonstration exercises at least one v0.1 feature no other does, and M7-02 checks that from the compiled IR, not from prose. `material-configurator` already imports a constant file, a model file and a material from other modules, and `physics-playground` already has a prefab, `spawn` and `destroy`, so "uses modules" is not what separates this example. What neither does is put the **reusable parts in other files than the scene**: neither declares a prefab in a module it imports. All of this record's choices are **proposals**.

## Decision

1. **Shape.** Five modules: `src/theme.mtek` (constants and one pure function), `src/materials.mtek` (the material `Matte`), `src/props/pillar.mtek` and `src/props/beacon.mtek` (one exported prefab each) and `src/main.mtek`, which declares no prefab and no material and only places things. The import graph is a chain and a fan-in (`theme` is imported by four files; `materials` by three); its shape is asserted from the sources (`m7-modular-scene.test.ts`) and the compiler's load order, `main, theme, materials, pillar, beacon`, from the manifest's `sources`.
2. **What the example uses that the other two do not**, each with the place it is visible in the compiled program: prefabs imported from other modules (`prefabs` and `symbols` of the manifest name them by the declaring file); one prefab instantiated with three different param sets and another with two (`PrefabInstance` in the IR); param defaults that are imported constants (`PILLAR_WIDTH`, `STONE`, `GOLD`); a prefab field computed at instantiation by an imported function (`position: origin + vec3(0.0, half(height), 0.0)`, `Source::Expr` in the IR); `bind` inside a prefab over its params and `frame.time`; prefab state read from the scene file (`Lantern.flashes + Lamp.flashes` in a binding); `spawn` of a prefab declared in another file with run-time params; a user material imported by three modules that compiles to one material and one shader; and, as a consequence of decision 0059, one instanced draw that mixes a prefab instance and a plain entity (`Left` and `Gauge` share a unit box and an equal parameter block). The example has no lights, no host inputs, no physics and no assets: those are the other demonstrations' ground.
3. **The material is a flat colour.** `Matte` returns `tint.rgb * dim` as a linear colour and does not call `lighting.pbr`, so every pixel of the picture is a closed form (`encode(decode(tint) * dim)`) that the independent CPU reference of `tests/browser/support/m1-reference.ts` reproduces exactly, and the example needs neither the PBR oracle of the configurator nor a light. The beacons' pulse is the one place `dim` is not 1. A lit material would test the lighting model again, which decisions 0057 and 0080 already do.
4. **How the numbers are derived.** `tests/browser/support/m7-modular-scene.ts` holds a model of the scene written from the sources: geometry, the formulas of the bob and the pulse, the row that P places, the colours (read from `theme.mtek` by name) and the draw groups. It feeds the CPU reference (`SceneSpec`). The same model drives three checks: the browser spec (`specs/m7/modular-scene.spec.ts`, three pictures compared on a grid, the counters and positions asserted), the unit test that replays the four `mtek test` fixtures without a GPU (`mtek-test/example-fixtures.test.ts`), and the comments at the top of each fixture, which carry the derivation by hand. The draw counters (`drawCalls`, `instancedDraws`) follow from decision 0059's rule that equal meshes with equal `initial` parameter blocks are one draw; the beacons, whose `dim` is bound, are never shared.
5. **The cross-file failure** is `E2033` (`'Pillar' is not exported by 'src/props/pillar.mtek'`), the code `spec/diagnostics.md` and decision 0036 item 5 give for importing a name the target does not export. It is tested the way the playground's `E5071` is: a failing fixture in the compiler's suite, `tests/semantics/fail/e2033_modular_scene_prefab_not_exported/` (the example's shape in three files, exact `expected.diag.json`), and two tests in `crates/mtek-cli/tests/cli.rs` that copy the **real** example, take `export` off `Pillar`, and off `Matte`, and require exactly one `E2033` in `src/main.mtek`, respectively one in each of the three modules that import the material, with the declaration in the other file as related span. A failing build cannot be a `mtek test` fixture (every fixture then fails with kind `build`, decision 0074 item 4), so the example's `tests/` holds only positive fixtures.
6. **Limits met, none fixed here.** `expect_state` cannot address a scale or a spawned entity (decision 0074), so the gauge's length is checked through its centre and its pixels and the placed pillars through pixels in the fixtures and through `app.debug.scene().spawned` in the browser spec. The manifest's `prefabs` table lists only prefabs that something spawns (`Pillar`), not `Beacon`, which is only ever instantiated by name; `symbols` list both. `mtek fmt` separates top-level constants by blank lines. No defect of the compiler or the runtime was found; neither was changed.

## Consequences

- M7-02's coverage matrix can attribute the features of item 2 to this example from its IR; items that the configurator also uses (imports of constants and materials) do not count for it.
- A future change to the example's geometry changes the model in `m7-modular-scene.ts` (its source literals are checked against the files, so a drifted model fails a unit test) and the numbers in the fixtures (checked by the replay test).
