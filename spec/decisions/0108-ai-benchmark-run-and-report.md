# 0108. The AI/token benchmark run: the baseline side of the harness, the spend guard, the recorded conditions, the report from stored records only, and the rule that turns the numbers into better, equivalent or worse

- Status: Accepted
- Date: 2026-10-19
- Blueprint origin: M7 (blueprint §11), task M7-05 ("run the protocol — conditions, at least 5 trials per task per condition per model, recorded settings — compute aggregates, publish the raw JSONL and `benchmarks/results/ai/report.md` with better/equivalent/worse conclusions per decision 0001, holdout reported separately"); blueprint §12.2; `spec/ai-and-benchmarks.md` §§4, 6.3 and 6.4; decisions 0001 (H4 and the three acceptable outcomes), 0003 (no dependency on a provider), 0021 (task format, baseline hooks, holdout rules), 0077 (the harness), 0085 (the holdout), 0104 (release notes from evidence only).
- Supersedes: nothing. Completes decision 0077 item 13 (no aggregator existed; the harness had never met a real service or a baseline).

## Context

Phase 1 of M7-05 had to make the protocol runnable and cheap to scope. At its start `tools/ai-eval` could run the Mtek side of a task only; its `anthropic` adapter had been tested on a fake transport and never on the service; there was no way to run a trial of the three.js baseline (decision 0021 gave the baseline a test hook, but nothing generated, validated and repaired a baseline candidate); nothing computed an aggregate; and decision 0001 says that H4 has the three outcomes "better, equivalent, worse" without saying when a number is which. The user's budget for all of M7-05 is under 10 USD, so the run also needs a guard that makes an overspend impossible rather than unlikely. Every item below is a **proposal** (a design choice) unless it restates a rule of the spec or of a decision named above.

## Decision

1. **A trial belongs to a side (`tools/ai-eval/src/side.ts`).** `mtek` is the harness as decision 0077 left it. `baseline` is the same task as a TypeScript + three.js r186 project (`benchmarks/tasks/<id>/baseline`, decision 0021 item 6). Both sides go through the same loop (`RepairLoop`), the same edit format (exact-match SEARCH/REPLACE, whole files only in cold tasks), the same budgets (`max_repairs`, `max_output_tokens`, `max_wall_seconds` of the task), the same feedback wording after a failure and the same token accounting; they differ only in what is technology-specific: the project's files, the documentation, the system prompt (same rules, other nouns), and the validator. The side is part of the recorded condition (`condition.side`), of the trial id (`<task>--baseline-unconstrained--00`) and therefore of the condition id. A baseline trial has no constrained mode (spec 6.4 lists it for Mtek only) and ends `unavailable` if asked for one.
2. **The baseline's layers are the Mtek layers with the TypeScript tool chain** (`src/baseline-side.ts`, run in one fresh process, `benchmarks/baselines/support/test/run-candidate.ts`, which prints one JSON report):

   | layer | Mtek | baseline |
   |---|---|---|
   | `parse` | `mtek check`: no diagnostic of phase `parse` | the TypeScript compiler reports no syntax error |
   | `check` | `mtek check`: no error | `tsc --noEmit` on the project's `tsconfig.json` (strict): no error at all |
   | `build` | `mtek build --mode test` (emits and validates the shaders) | the esbuild bundle that the task tests use (`test/build.ts`) |
   | `start` / `tests` | one `mtek test` run | the task's own `mtek-tests/*.test.toml` fixtures interpreted against `startTask`'s hooks (decision 0021 item 8: the expectations exist once), each fixture in a fresh page of a fresh Chromium context with the hardware launch arguments of `mtek test`; a console error or warning fails a fixture (as in the Playwright suite); no adapter leaves the fixtures `not-run` (never a pass) |
   | required symbols | `mtek context --symbol S` for each required symbol | the last name of each required symbol that the task's REFERENCE baseline declares as a string literal (a three.js `name`), searched as a string literal in the candidate's sources; a symbol that exists only in Mtek (a scene state) is not demanded of the baseline |

   A failed check skips what follows, as on the Mtek side. The candidate's workspace is made inside `node_modules/.cache/mtek-ai-eval/` of the checkout (so that `three` and the support module resolve), has a `tsconfig.json` that extends the shared base by a relative path, never holds the task's fixtures, and is removed after the trial. Only `src/**/*.ts` can be edited (the counterpart of `mtek.toml` and `src/**/*.mtek`). Diagnostics reach the model in `tsc`'s own words (`src/main.ts(12,5): error TS2322: ...` plus the numbered source lines around the span), the Mtek ones as the compiler's envelope JSON: each side gets what its own tool prints.
3. **The baseline gets version-correct documentation whose tokens are counted** (spec 6.3). `benchmarks/baselines/docs/reference.md` (10.2 kB, the same text for every task) documents the project convention (`startTask`, the frame order, keys, host inputs, names), the support module's signatures (the equivalent helper module of spec 6.3), the three.js r186 API that tasks of this kind use (scene graph, geometry, materials, lights with their physical units, cameras) and the TSL basics. `benchmarks/baselines/support/test/docs.test.ts` checks every name in it against the installed packages (three 0.186.1) and every support-module export against the document. Its size is recorded in the trial (`contextBytes`) and the report attributes its tokens to "documentation" like the Mtek context's. It is a written document, not a generated one: that it is as good as the compiler's context for its purpose is a claim the pilot can test only crudely (decision 0109 items 5 and 6).
4. **Mtek has a second condition, with a document added** (`mtek-guide`, `mtek-getting-started`, `mtek-reference`; `--sides mtek,mtek-guide,baseline`). The pilot showed that the context export of a cold-start task holds no schema, no example and no symbol (decision 0109), so "what does the agent contract alone cost" and "what does Mtek cost when its own guide is in the prompt" are different questions. The condition adds one file of `docs/` (LF, as checked in) after the context, counts it in the documentation bytes, records its hash in `condition.documentation` and has its own trial ids, condition id and report cells and comparison. The default Mtek condition is unchanged and remains the one that the spec's H4 is about.
5. **The `anthropic` adapter met the service and was changed where the service taught something.** The request shape, the usage fields and the finish reasons worked as written (first call, 2026-10-19: `claude-haiku-4-5-20251001`, 17 input and 5 output tokens). Added: (a) `promptCaching` puts one cache breakpoint on the newest message of each call, so a repair round reads the earlier conversation from the cache; Haiku 4.5 caches only prefixes of at least 4 096 tokens, so a first prompt below it is not cached, and a trial that ends after one more call pays the 1.25x write price for nothing (measured: caching cut the cost of the Mtek pilot attempts to 70 % of the uncached figure and the guide attempts to 55 %, the baseline's to 91 %); it is part of the condition (`condition.promptCaching`) because it changes the bill, not the answer; (b) `usage.cacheWriteInputTokens` (reported by the service, kept apart from reads and from plain input, priced apart); (c) `GenerateResult.httpStatus`, so that a call the service rejected (4xx/5xx, not billed) is not charged; (d) `maxRetries: 0` (a retry is a second bill, and decision 0077 item 13 already says a failed generation is recorded, never retried); (e) any API key, by value or by the shape `sk-ant-...`, is removed from an error text before it can be recorded. Replay-based tests are unchanged.
6. **The spend guard** (`src/spend.ts`). A ledger file OUTSIDE the repository (default `<home>/gate-m7/ai-spend.json`, `--spend-ledger FILE`) persists across runs, phases and agents: a total, the reservations of calls in flight, and one entry per call (run id, model, token counts, USD, a note when the charge is not the plain cost). A run that calls a provider is refused without `--spend-cap USD`. The cap is a ceiling on the LEDGER TOTAL, so earlier runs count. Before every call the guard reserves the WORST case of that call — the whole input, estimated as characters / 2.5, at the dearest input price, plus the task's `max_output_tokens` of output at the output price — and refuses the call when total + other reservations + that worst case would exceed the cap. After the call the reservation is replaced by the cost computed from the provider's own usage report. Prices (USD per million tokens, `PRICING`; a model without a price cannot run): Claude Haiku 4.5 `claude-haiku-4-5-20251001`: input 1, cache write 1.25 (5-minute lifetime), cache read 0.10, output 5 — the published list prices; they are deliberately conservative where the service does not say: all input of a call that asked for caching and reported no write count is charged at the write price; a call that returned no usable answer without an HTTP status (aborted, timed out, connection lost) or reported no usage is charged its worst case, as is a call that threw; a call the service answered with an error status is charged nothing. Reservations expire after 15 minutes (a crashed process does not block the money for ever); the ledger refuses to be read if its total is not the sum of its entries; a lock directory serialises read-modify-write across processes. The computed cost is **not reconciled with the provider's invoice**.
7. **When the cap is reached nothing is dropped and nothing is a success.** The refused call is recorded as a `model-call` with generation `budget-exceeded` and budget `spend` (no request, no response), the trial ends **`unfinished`** with the reason `budget-spend` (a new outcome of the record schema: neither success nor failure of the model), and every attempt planned after it starts, finds the cap reached and ends unfinished the same way, so the records say exactly which of the planned attempts did not happen. The run ends `stopped-by-budget`. A later small call that still fits under the cap is allowed to run.
8. **What a run records beyond decision 0077** (`spec/ai-eval-record.schema.json`, version 1, keys only added): `run-start.settings` (date, provider, model, temperature, prompt caching, feedback mode, repair and token budgets, sides, documentation id per side, prompt versions, trial kinds and counts, spend cap, Node and platform), `condition.side` / `.promptCaching` / `.documentation` (all optional, so earlier records stay valid and mean `mtek`), `usage.cacheWriteInputTokens`, `model-call.costUsd` / `.ledgerTotalUsd`, `trial-end.costUsd` and `.totals.cacheWriteInputTokens`, a final **`run-end`** record (status, trials, the spend: cap, ledger total at start and end, this run's spend, calls, refused calls), the diagnostic code pattern widened to `TS…` and `BASELINE-BUILD`, and `unfinished` / `budget-spend` / `spend`. Temperature is explicit and recorded; **the pilot used temperature 1** (the service default), because at 0 repeated trials of a task are nearly the same text and "5 trials per task" would not measure what it is for.
9. **The order of a run** (`--order trial-major|task-major`). The default is trial-major (trial index outermost, then task, side, kind): what exists when the money or the time runs out is balanced between tasks and sides. Task-major runs the trials of a task and side one after another, so the identical first prompts are served from the provider's cache (five minutes), which is cheaper (decision 0109), but a run stopped early lacks whole tasks. The GPU is shared: `--gpu-lock DIR` takes a lock directory (`mkdir`) around every command that opens the browser (the `mtek test` call, the baseline runner) and releases it also on an error or an interrupt.
10. **The report is a function of the stored records** (`src/report.ts`, `report-cli.ts`; `node tools/ai-eval/src/report-cli.ts --run DIR [--run DIR...] --out report.md`). It reads `records.jsonl` and nothing else (and the directory NAMES of `benchmarks/holdout/` to tell holdout attempts apart); the same records give the same text. It states per side, trial kind, model and Mtek condition, and per category and per mode (cold, edit): the attempts and their outcomes; the **completion rate** = completed / attempts that ended by themselves (completed or failed), and, apart, every attempt the harness could not judge (not-run, error, unavailable, unfinished-by-budget), which stays in the token sums, in the lists, and out of the rate; **tokens per completed task = all tokens of all attempts (successes, failures, unjudged) / completed tasks, UNDEFINED, never 0 and never infinity, when nothing completed**; medians and interquartile ranges (linear-interpolation quartiles) of tokens, repairs, seconds and cost; input and output tokens apart, cache reads, cache writes and plain input apart; first-attempt parse, check, start and test success (a first reply that produced no candidate — its edit was rejected, or its generation failed — is a failed first attempt on every layer, not a missing one); the input tokens attributed to instructions, task, documentation, project files, diagnostics, tool results, repair context and generated code, by each part's share of the request's characters (the provider counts per request; these are attributions, the totals are exact); and **every attempt** in a table, failures included.
11. **The rule for better, equivalent, worse** (decision 0001 names the outcomes and leaves the threshold open; this is the threshold). Mtek and the baseline are compared over the tasks that both have attempts at, on two axes. *Success*: the completion rates differ by at most 10 points = "matched", otherwise "higher" or "lower". *Tokens*: the ratio Mtek / baseline of tokens per completed task, with a 95 % percentile interval from a bootstrap over TASKS (a task with its trials is the unit that is resampled; 4 000 resamples; a fixed seed, so the report is reproducible); "fewer" when the whole interval is below 1, "more" when above 1, "same" otherwise; with fewer than 5 tasks there is no interval and no direction is concluded. **better** = success matched or higher and tokens fewer, or success higher and tokens the same; **worse** = success matched or lower and tokens more, or success lower and tokens the same; **equivalent** = success matched and tokens the same; **inconclusive** = nothing completes on either side, the axes oppose each other, or no task has attempts on both sides (a refusal to conclude, not a fourth outcome of H4). If only one side completes anything it is better and the other worse (tokens per completed task is undefined for the other). The same rule is applied per category and per mode. **The research target of spec 6.4** (at matched success at least 30 % fewer tokens per completed task: ratio at most 0.70 with the verdict better) is reported apart; missing it triggers the investigation of spec 6.4 and is not itself "worse". A verdict is **provisional** when a task has fewer than 5 trials on a side, more than 10 % of the attempts could not be judged, token counts are unknown, or tasks have attempts on one side only. The original "about 80 % fewer tokens" stays an unverified hypothesis; the report says so in its first paragraph.
12. **The holdout stays out of the repository.** `benchmark-run --holdout` takes its tasks from `benchmarks/holdout/` and refuses an `--out` inside the repository, because a record holds the prompt, the model's reply and the final candidate; the run directory lives elsewhere. `report-cli` reads such a run and reports its attempts apart, in a section that holds ids, outcomes, reasons (enum values), counts, tokens, cost and layer outcomes only (no message, prompt or candidate text), and `--holdout-summary FILE` writes the same as JSONL — the only form of a holdout result that may be stored in the repository. No file of `tools/` names a holdout id (`check:tasks` scans for them); the tools take the set by directory.
13. **Limits** (said so that nobody reads more into them). One model per run; the temperature is a recorded setting, not a claim about what is best; the baseline's documentation is hand-written and its coverage was checked against the packages, not against what tasks need; the baseline's required-names check is a literal search; a baseline cold starter is a skeleton that calls `startTask` and the helpers (frozen with the task format) while a Mtek cold stub is a comment; the browser layers need a hardware WebGPU adapter and the GPU lock; the attribution of tokens to parts is an estimate by characters; a run's cost is the provider's usage at list prices, not an invoice.

## Fixtures/Tests

## Consequences

- `npm run test:unit` and `npm run check` cover the harness; `tools/ai-eval/README.md` documents the commands. `spec/ai-and-benchmarks.md` §6.4 points here for the rule.
- The full M7-05 run is `benchmark-run` with a `--spend-cap` equal to the ledger total at its start plus its share of the budget, then `report-cli`. The scope is the orchestrator's decision from decision 0109.
- A model whose price is not in `PRICING` cannot be run with a cap; adding a model is adding a price with its source.
