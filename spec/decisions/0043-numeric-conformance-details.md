# 0043. CPU/GPU numeric conformance: details the specification leaves open

- Status: Accepted (items 8 and 9 were answered by decision 0047)
- Date: 2026-10-04
- Blueprint origin: §4.1 (numeric semantics), §12.1 (CPU/GPU tests), §14 (do not weaken tests casually); `spec/testing.md` §5; `spec/language.md` §6.3–§6.5; `spec/compiler-architecture.md` §7.3; decisions 0009, 0012, 0026, 0034, 0035, 0037, 0040, 0041.

## Context

Task M2-08 proves where CPU and GPU agree: the GPU evaluates every case of the CPU table `tests/semantics/numeric/cpu.json` (decision 0037 item 10) and the browser spec compares it with the CPU result, bit-exact for integers, conversions and `+ - *`, within tolerances transcribed from the WGSL "Floating Point Accuracy" section [S5] otherwise. The specification says what to compare but not how the WGSL text becomes numbers: what "inherited from" means for a test, how the rounding, reassociation, fusion and flush-to-zero rules enter, which inputs are outside a stated range, how the probe shader is produced, and what happens when a measured disagreement is a spec issue rather than a bug. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints, except the measurements of items 8–10.

1. **The source.** `tests/semantics/numeric/tolerances.json` (format `mtek-numeric-tolerances/1`) transcribes W3C WGSL, Candidate Recommendation Draft of 21 September 2026 (retrieved 2026-10-04), section 15.7.4.1 "Accuracy of Concrete Floating Point Expressions", plus the domains of §8.8 and §17.5, the conversion rule of §15.7.6 and the rules of §15.7.2–§15.7.5. One entry per Mtek operation of cpu.json, keyed by callee and then argument class (`+ (float)`, `+ (integer)`) or concrete signature (`* (quat, quat)`); each gives the WGSL the lowering emits (decision 0041), the comparison class, the bound in machine form and one or more verbatim quotes with section number and anchor (HTML superscripts written `^`, omissions `[…]`). `scripts/check-wgsl-quotes.mjs` checks every quote, section and anchor against the published spec (137 citations, 0 problems on 2026-10-04); it needs the network and is run by hand when WGSL changes.
2. **Literal reading.** A bound is applied exactly as written, with WGSL's own definitions: ULP is the minimum gap (§15.7.4), "correctly rounded" allows rounding up or down, an absolute bound is absolute, "the worse of" is the union, and "When the accuracy for an operation is specified over an input range, the accuracy is undefined for input values outside that range." Consequently: `sin`/`cos` are compared only on [-π, π] (the binary32 value nearest π is above π); `sqrt(0)` inherits `1.0 / inverseSqrt(0)`, whose divisor is outside [2^-126, 2^126]; `atan2(y, x)` requires y "finite and normal" and zero is not normal (§15.7.1), so `atan2(0, x)`, `asin(0)` and `acos(±1)` (which inherit it) are not compared. Such rows are still evaluated on the GPU and their values written to the report; they are listed with the reason in the generated `tests/semantics/numeric/gpu-not-compared.json` (33 portable rows), next to the 132 rows cpu.json marks non-portable.
3. **Intervals.** `tests/browser/support/numeric-accuracy.ts` computes, for the exact inputs of a case, the interval of binary32 values WGSL allows. An inherited bound evaluates the quoted WGSL expression with each sub-operation bounded by its own entry. The global rules enter as: a correctly rounded operation contributes [round down, round up] of its exact result; a chain of three or more `+`/`-` terms is any association order ("An implementation may reassociate operations"): the exact sum widened by one rounding of at most ULP(sum of the term magnitudes) + 2^-126 per addition; likewise chains of three or more products (relative 2^-23 per rounding); fusion needs nothing (an unrounded product lies inside the rounded interval); an interval that reaches a subnormal value also contains 0 (inputs and outputs of §15.7.4 operations "may be flushed to zero"); an intermediate that may leave the finite range makes the row not compared (§15.7.3, finite math). A numeric constant of an inherited expression is an AbstractFloat converted to f32, either neighbour. WGSL has no accuracy row for matrix products; §8.8 defines each component as a dot product, so they inherit the `dot` bound. Mtek helpers (`mtek_quat_mul`, `mtek_quat_rotate`, `mtek_quat_axis_angle`, `mtek_quat_euler`, `mtek_mat4_rotation`, `mtek_color_srgb`, `mtek_srgb_channel`) are bounded by evaluating their own WGSL bodies (decision 0041 item 8, "the accuracy of the operation is defined as the accuracy of evaluating the given WGSL expression"); the browser spec checks that the compiled helper bodies are exactly the expressions tolerances.json bounds, so a lowering change cannot silently diverge from its tolerance. Endpoint arithmetic is binary64 with exact directed rounding (two-sum) or a stated slack of a few binary64 ULPs where binary64 itself rounds.
4. **CPU rounding.** The interval is widened by `cpuRoundingUlp` = 1 **binary32 step** at each end (`spec/testing.md` §5: "plus 1 ULP for CPU rounding"). A step rather than the minimum-gap ULP, so that the allowance is one representable value on both sides of a power of two. The report also says whether each row is inside the WGSL interval without the step. A unit test (`numeric-tables.test.ts`) requires every portable CPU expectation to lie inside its own interval: 234 of 234 in-domain tolerance rows do, so the intervals and the CPU are consistent before any GPU is involved.
5. **Comparison classes.** Exact: integer operations, comparisons, conversions, bit reinterpretations, constructors and the data-placing helpers (`mat4.translation`, `mat4.scale`), and every float operation WGSL calls correctly rounded whose exact result is representable (`neg`, `abs`, `floor`, `ceil`, `trunc`, `round`, `sign`, `saturate`, `step`, `min`, `max`, `clamp`, `transpose`) plus `+ - *` of finite values. An exact row must match bit for bit except where a quoted rule permits a difference, each counted and listed: **zero sign** (§15.7.2 "may ignore the sign field of a floating point zero value"), **flush to zero** (a row with a subnormal input or result may return the flushed value; constructors are not §15.7.4 operations and must preserve subnormals), **conversion neighbour** (an inexact integer-to-float conversion may pick either neighbour, §15.7.6, `spec/language.md` §6.5). WGSL lets `+ - *` round either way; Mtek requires round-to-nearest on hardware (`spec/testing.md` §5) — a promise stronger than WGSL, which held on both adapters measured. Everything else is a tolerance row.
6. **The probe exercises the compiler.** `tests/browser/support/numeric-probe.ts`, run by Playwright's global setup: a Mtek project made of the function library of the codegen fixture `tests/codegen/numeric_cpu_table` (one pure function per operation and signature of cpu.json, generated by `codegen_cpu_table.rs` and executed against the CPU by M2-07's tests) plus a material `Probe` whose fragment stage calls every function (decision 0041 item 4 lowers only what the stage reaches), built with `mtek build --mode test`. The WGSL of `Probe` is used unchanged; a test-only harness is appended: storage buffers at `@group(3)` (the material module uses groups 0–2) with the arguments as 32-bit words read through `bitcast` (no argument is a constant a GPU compiler could fold), one `probe_case_<n>` per library function calling the compiled `u_fn_<hash8>_<name>`, a fragment entry point that dispatches per pixel and writes the result's words with `bitcast<u32>` to an `rgba32uint` target (a `mat4` result takes four pixels). Only argument decoding and result encoding are hand-written; no row uses hand-written WGSL for the operation under test. All 706 cases run (non-portable ones informationally). The spec writes `$MTEK_RESULTS_DIR/numeric-conformance-<project>.json` with every row, the interval, the CPU and GPU values, and per-entry counts and maximum errors.
7. **Known deviations.** A measured GPU result outside the WGSL interval for a portable row is a lowering bug (fixed with a regression test) or a spec issue. A spec issue may be recorded in tolerances.json `knownDeviations` — row id, decision, observed values and measured cause — and is then reported as `known-deviation` (annotated in the test, counted in the report, listed in gpu-not-compared.json), never as a pass and never by widening an entry. A CPU expectation outside its own interval always fails. Out-of-range f32-to-integer rows where WGSL specifies another value than the CPU (item 8) are compared with the WGSL value and reported as `spec-disagreement`.
8. **Measured: f32 → i32/u32 out of range (open question).** WGSL §15.7.6: "Otherwise, the result is the value in T closest to truncate(X) and also exactly representable in the original floating point type" — `i32(3e9)` is 2147483520 and `u32(5e9)` is 4294967040 (WGSL's own examples). The CPU (`rt.f2i`/`f2u`, decision 0037 item 6), the constant folder and cpu.json clamp to 2147483647 and 4294967295. Both adapters return the WGSL values (`i32_from_f32#9`, `#11`, `u32_from_f32#8`, `#9`). `spec/language.md` §6.5 calls its rule "identical on CPU and GPU" and "WGSL rule", so the CPU deviates from the rule it cites. Proposal: a follow-up task changes `rt`, the folder and the Rust oracle to WGSL's clamp ([-2^31, 2147483520], [0, 4294967040]) and blesses cpu.json and the codegen fixture; alternative: GPU helpers `mtek_f2i`/`mtek_f2u` that saturate to the integer maxima. Until answered the 4 rows are `spec-disagreement`.
9. **Measured: `mix` near overflow (open question).** `mix(3e38, -3e38, 0.5)` (`mix_f32#7`, portable) is 0 on the CPU and inside WGSL's bound ("Inherited from x * (1.0 - z) + y * z"), but -Infinity on both adapters: the backends evaluate `mix` as `x + t * (y - x)` (HLSL `lerp`, SPIR-V `FMix`), and `y - x` overflows. The lowering is correct per WGSL; the platforms do not meet WGSL's bound for this input. Recorded as a known deviation (item 7). Proposal: lower `mix` to a helper `mtek_mix(a, b, t) = a * (1.0 - t) + b * t` (the CPU's order, decision 0037 item 7; a change in `lowering/` and one golden, left out of M2-08 because M2-13 works in `lowering/` concurrently); alternative: document `mix` of operands near F32_MAX/2 as non-portable.
10. **Other measurements (within the bounds, recorded for portability notes).** Both adapters flush subnormals: `add_f32#11`, `sub_f32#5` return 0, `sign` of a subnormal returns 0 (permitted, item 5); `min`, `max` and `saturate` return `+0` where the CPU returns `-0` (zero sign). The GPU's `%` is WGSL's `x - y * trunc(x / y)`, not the CPU's exact remainder: `16777218 % 3` is 3 on the hardware adapter (CPU 0), `0.7 % 0.1` and `1e10 % 0.1` are 0 (CPU 0.09999998 and 0.08839028) — all inside the WGSL interval, which spans both neighbouring quotients when `x / y` is within 2.5 ULP of an integer. Maximum errors per entry are in the report; on hardware every compared tolerance row is within 30 binary32 steps of the CPU (the most: `exp`), or within 2.4e-7 absolute where the result is near zero.
11. **Adapters.** Gate evidence uses the hardware project (`MTEK_REQUIRE_GPU=1`, decision 0012). The software adapter (SwiftShader) runs the same spec and writes its own report; its results are informational (its `sin`/`cos` errors are up to 1.9e-4 absolute, inside 2^-11), but it currently meets every bound, so the spec asserts on both projects.

## Consequences

- No compiler change, no new dependency, no new diagnostic code. The probe follows the compiler: a new operation in cpu.json needs a tolerances.json entry (a unit test fails otherwise), the codegen fixture regenerated, and nothing else.
- `spec/testing.md` §5 and `spec/language.md` §6.4–§6.5 point here; `gpu-not-compared.json` is the explicit list of non-portable and uncompared cases the language reference refers to.
- Answers to items 8 and 9 become their own work items (CPU conversion clamp or GPU helpers; `mtek_mix` or a non-portability note). Removing the `mix_f32#7` known deviation and the `spec-disagreement` status is part of them.
- **M2-12** (and anything that changes `rt` or the shader lowering) re-runs `specs/numeric/`; a changed helper body fails the helper check until tolerances.json transcribes it.
- **M2-GATE** collects `numeric-conformance-hardware.json` and the environment record of a `MTEK_REQUIRE_GPU=1` hardware run as evidence, with the counts of item 10's categories.
