# 0036. Modules: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §4.5 (modules, the entry scene), §9.4 (diagnostics); `spec/language.md` §3.1, §4.2, §9; `spec/compiler-architecture.md` §4.4, §4.6, §5; `spec/gpu-layout.md` §5, §7; `spec/diagnostics.md` §2.1, §5.2; decisions 0018, 0025, 0026, 0028, 0029, 0030.

## Context

Task M2-03 implements multi-file projects: loading every module from the entry, the import specifier rules (`E2030`–`E2036`), exports (`E2033`), duplicate imports (`E2002`), cycles (`E2035`), cross-module name resolution and module-qualified generated names. The specification gives the rules but not every choice an implementation has to make: what "import order" means when imports nest, how a bare specifier is told from a malformed one, which code the reserved `std/` directory gets (decision 0030 item 7 left it to this task), what an imported name means when its import failed, how types cross module boundaries, how the front end's result and the IR hold several modules, and how the construct table records an M2 construct while the build still reports M1. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Load order.** `project::load_modules` parses the entry module and follows its imports in source order **depth first**: a module imported for the first time is read, parsed and has its own imports followed before the next import of the importing module (`main → b → c`, then `main → a`; `main, b, c, a`). A module gets the next `ModuleId` and the next `FileId` when it is first reached, so the two coincide, diagnostics sort in this order (`spec/compiler-architecture.md` §5) and nothing depends on directory enumeration. A path reached again (also through another spelling, `./a.mtek` and `../src/a.mtek`) is the same module.

2. **Specifier rules**, checked in this order, the first that fails reported at the specifier string (`project::resolve_specifier`):
   1. empty, a backslash, or absolute (`/…`, `C:…`): `E2030`;
   2. not starting with `./` or `../`: a **bare specifier** (`E2034`, a package import) unless it starts with `.` (`.hidden.mtek`, `..`), which is `E2030`; `"physics.mtek"` is bare too, with the help to write `"./physics.mtek"`;
   3. a control character or `:`, a file name that is not a non-empty stem plus exactly `.mtek`, or an empty segment: `E2030`;
   4. resolved against the importing file's directory and normalised, climbing above the project root: `E2031`; landing in the top-level directory `std/`, reserved for the embedded standard library: **`E2031` as well**, with its own message ("… inside the directory 'std/', which is reserved …") and a note that standard-library names need no import (decision 0030 item 7). Only the top-level `std/` is reserved (`src/std/x.mtek` is an ordinary module).

3. **Reading.** A file that is not found is `E2036`, unless a path differing only in letter case exists (segment by segment, the first candidate in sorted order), which is `E2032` with the existing spelling as help. A file system that finds the file although the case differs (`read` succeeds, `exact_case_exists` does not) is `E2032` as well. A directory, and any other read failure, is `E2036`. A file the source manager rejects (`E0001`, `E0004`) and a module beyond the limit of 1 024 (`E9002`) have no primary location, as `spec/diagnostics.md` §2.1 specifies for files without a file id, and a related span at the import. A specifier string the lexer rejected is not reported again.

4. **Cycles.** `ModuleGraph::find_cycles` (a depth-first search from the entry in load order, imports in source order) yields one cycle per import that reaches a module still on the search path; each is `E2035` once, at that closing import, with the message `Import cycle: src/a.mtek -> src/b.mtek -> src/a.mtek.` (`Import cycle: 'src/a.mtek' imports itself.` for a cycle of one) and one related span per module of the cycle, in order, at its import of the next module (the last is the closing import). Checking continues: every module is resolved and type-checked. Type checking runs in `ModuleGraph::dependency_order` (post-order over the imports without the closing ones), so a module is checked after the modules it imports, except across the closing import of a cycle, whose imported constants are not known yet and have the type `Error` without a further diagnostic.

5. **Exports** are syntactic: an item is exported when `export` precedes it. `resolve::bind_imports` binds the imported names before the imported module is resolved, from its syntax tree. A name the target does not export is `E2033` at the name, in three wordings: declared without `export` (related span at the declaration, help to add `export`; this includes an entry scene, which may omit `export` only because nothing can import it without a cycle), imported by the target but not declared there (imported names cannot be exported again, as `export import` does not parse), or not there at all ("did you mean" for exactly one exported item within edit distance 1–2, and a note listing the exports). The entry module may export its items.

6. **Duplicates.** A name imported twice in one module is `E2002` "Duplicate import of 'X': the name is already imported in this module." with the first import as related span; an import and a declaration of one name keep the generic `E2002` of decision 0025. Imported names are module-scope declarations (`DefKind::Import`), so the no-shadowing and prelude-reuse rules of `spec/language.md` §4.2 apply to them unchanged.

7. **Failed imports do not cascade.** An imported name whose import was reported still declares the name (so it is not also `E2003`); its uses resolve to `Res::Error` and nothing reports them again. A bound name resolves to its own `DefId` in the importing module; `Resolution::import_target` gives the target (module, declaring node, kind, name span), and kind-dependent rules (a struct is a type, a material is a descriptor type, a constant is a value) use the target's kind. An imported scene, function, struct, material or prefab used as a value is `E3001`, as it would be in its own module.

8. **Types across modules.** Every module keeps its own `TyInterner`. `types::check_module_with_imports` seeds each imported constant with its type, carried into the importing module's interner (`TyInterner::import_from`), and its value, so its uses type and fold exactly like local constants. A user struct type cannot be carried yet (`Ty::Struct` holds a module-local `DefId`; structs are gated in this build) and becomes `Error`; implementing structs needs a module-independent struct identity first.

9. **Results.** `Analysis` keeps the entry module in `module`/`resolution`/`types` (unchanged) and every other module in `dependencies: Vec<ModuleUnit { id, module, resolution, types }>` in load order. The typed IR lists every module in load order (`Program.modules`); imports are not IR items: uses of imported constants are folded, and every declaration appears once, in the module that declares it, under its own symbol (`src/pulse_b.mtek::Pulse`). `inspect` and `build` use all modules; the manifest's `sources` and the build identity cover every module.

10. **Gating.** The construct table rows of `import` and `export` say **M1**: the build implements them although `IMPLEMENTED_MILESTONE` stays M1 until the M2 gate (the same mechanism decision 0026 used for unary minus and arithmetic). This supersedes the two rows of decision 0025 item 2; `gate_import` and `gate_export` are no longer gating fixtures.

11. **Generated names.** `layout::naming` holds every module-qualified name of `spec/gpu-layout.md` §5 and §7, and the emitters take them from there: `material_params_struct` (`MtekParams_<hash8>_<Name>`), `material_writer_qualifier` (`<hash8>_<Name>`, which `emit_js::writer_qualifier` derives from the layout id `material:<path>::<Name>` instead of from the struct name), and `user_struct_name` (`S_<hash8>_<Name>`). A user struct's layout type is named by its symbol (`src/a.mtek::Shape`); `emit_wgsl::blocks::wgsl_struct_name`, used by the block emitter and the shader IR, turns such a name into `S_<hash8>_<Name>`, and keeps `S_<Name>` for the layout fixtures, which have no module.

12. **The `Pulse` criterion.** "Two modules declaring `Pulse` produce distinct WGSL struct and writer names" needs materials compiled from source, which is M2-04 (`material` is `E9010` in this build, decision 0029 keeps the compiler-built `Unlit`). Until then it is asserted at the level that exists: two `Pulse` parameter blocks (each with a nested user struct `Wave`) from two modules give distinct WGSL structs that Naga accepts in one module and writer sets without a common name or table key (`tests/modules.rs`). The material-level project `tests/modules/same_named_materials/` (two modules each declaring `export material Pulse`, one imported directly, the other through an instance constant) must, while `material` is gated, produce exactly the two `E9010`s; the same test switches by itself, when the row is flipped, to building it and requiring `MtekParams_<hash8>_Pulse` and `w_<hash8>_Pulse` of both modules in the shaders, `app.js` and the manifest's layouts.

## Consequences

- No new dependency and no new diagnostic code. `E2030`–`E2036` are reported and covered by fixtures; `E9002` is reachable and covered by `src/project/modules/tests.rs` (a fixture of 1 025 files would not be reviewable).
- M2-01 (structs) must give struct types a module-independent identity before imported struct types and constants of struct type can cross modules (item 8), and should name user-struct layout types by their symbol (item 11).
- M2-04 (materials) flips the `material` row; `same_named_materials_of_two_modules_build_to_distinct_names` then requires the material-level names of item 12. Material layout ids, WGSL structs and writers must come from `layout::naming` with the declaring module's path.
- M2-09 (prelude materials from source) keeps `std/` unimportable (item 2); built-in materials stay reachable without an import.
- M2-10 and later tooling read every module from `Analysis::dependencies` and `Program.modules`; diagnostics in imported modules carry their own file ids.
