# 0033. The development server `mtek dev`: details the specification leaves open

- Status: Accepted
- Date: 2026-10-04
- Blueprint origin: §10 (tooling, "last valid preview"), §13 (never panic); `spec/tooling.md` §1, §3, §4; `spec/runtime-abi.md` §2, §11.1; `spec/compiler-architecture.md` §2, §3; `spec/diagnostics.md` §2; decisions 0007, 0030, 0032.

## Context

Task M1-20 implements `mtek dev` for M1: serve the build output, watch the project, rebuild, and tell the page over Server-Sent Events, with a full page reload on success. The specification fixes the loopback address, `Cache-Control: no-store`, three MIME types, the endpoint `/__mtek/events`, the three event objects and their `data: <JSON>` framing, the exclusions of the watcher, the 50 ms debounce, serialised builds with exactly one follow-up build, the default port 5173 with fallback, that the reload client is part of the compiler's dev `index.html`, and "one line per build with duration and counts". It does not fix what is served before the first successful build, what a client that connects after a failure sees, how request paths are mapped to files, the rest of the MIME table, which file-system events count, the terminal and exit-code details, how shutdown and `--open` behave, or how the overlay of the reload client looks. They are fixed here so that they are visible, testable and changeable by a later record.

## Decision

All of the following are **proposals** (design choices), not external constraints.

1. **Command line.** `mtek dev [--port N] [--open] [PATH]`; `PATH` is found as for every command (decision 0032 item 2). `--port` accepts 1–65535 (0 and anything else are usage errors, exit `2`, like `dev.port`'s range in `mtek.toml`); without it the port is `dev.port` of `mtek.toml`, read directly with the compiler's `parse_config`, or 5173 when the file cannot be read or is invalid (the first build reports why). `--host` is not implemented (usage error): the server listens on `127.0.0.1` only. This supersedes the part of decision 0032 item 1 that lists `mtek dev` as not implemented.
2. **Port fallback.** The requested port and the next 19 are tried in order; the first that binds is used, and if it is not the requested one the terminal says `mtek dev: port 5173 is in use; using port 5174`. If none binds: `error: could not listen on 127.0.0.1, ports A to B: <OS message>` on stderr, exit `3`.
3. **Terminal.** stdout: `mtek dev: serving http://127.0.0.1:<port>/ (Ctrl+C to stop)`, then one line per build — `built 'demo' (dev): 9 files in dist, build 7c4846274cc3a51e; 0 errors, 0 warnings (35 ms)` (the line of decision 0032 item 4 plus the duration) or `build failed: 1 error, 0 warnings (12 ms)` — and `mtek dev: stopping` / `mtek dev: stopped` around shutdown. stderr: the diagnostics of every build (warnings too) in human form, coloured by the rule of decision 0032 item 5, and warnings of the server itself. Writes to a closed stdout or stderr are ignored; the server keeps running.
4. **Exit codes.** `0` after Ctrl+C; `1` when no project is found (`E9004`, as `mtek check`); `2` usage errors; `3` when the server runtime, the socket or the watcher cannot be started; `130` (128 + SIGINT) when a second Ctrl+C ends the process during shutdown. A failing build never ends the server.
5. **Builds.** Every build — the first, at start, and every rebuild — is the build of `mtek build --mode dev` without `--out`: compile, then write `build.out_dir` with replace-on-success (`commands::compile_and_write`, shared with `mtek build`), on the guarded compiler thread (`guard::run_guarded`: 16 MiB stack, `catch_unwind`). A compiler panic is a failed build with the single diagnostic `E9999` (decision 0032 item 7); an output directory that would replace the project (decision 0032 item 8) is a failed build with `E9031` whose message carries the reason, instead of `mtek build`'s exit `2`. A failed build leaves the previous output in place and served ("last valid preview" of `spec/tooling.md` §4, without hot reload in M1). The served and ignored output directory follows `build.out_dir` from build to build.
6. **Events.** Each event is one `data: <JSON>\n\n` frame, compact JSON with keys in this order: `{"type":"build-started"}`, `{"type":"build-failed","diagnostics":[…]}` — `diagnostics` is exactly the `diagnostics` array of the build's report (`spec/diagnostics.md` §2.2, the envelopes of `--format json`) — and `{"type":"build-succeeded","buildId":"<64 hex>","program":"/app.js?build=<buildId>"}`. No `event:`, `id:` or `retry:` fields and no keep-alive comments. Every build publishes `build-started` and then exactly one of the other two.
7. **Replay.** A client that connects while the latest event is `build-failed` receives that event first, then the live events; no other event is replayed (replaying `build-succeeded` would reload every page forever, and `build-started` alone says nothing). So a page opened or reloaded after a failure shows the diagnostics at once. Subscribing and publishing share one lock, so a client never misses an event or receives one twice. A client more than 64 events behind skips the ones it missed. On shutdown every open stream ends (the response completes), so graceful shutdown does not wait for browsers.
8. **Static files.** `/` is `index.html`; any other path must consist of plain segments — ASCII letters, digits, `.`, `_`, `-`, not starting with `.`, not a Windows device name (`con`, `prn`, `aux`, `nul`, `com0`–`com9`, `lpt0`–`lpt9`, with any extension) — which covers every name a build writes; anything else, a missing file or a directory is `404` (`text/plain`). Percent-escapes are not decoded (no build file needs one). The query string is ignored (`/app.js?build=<id>` is `app.js`). `GET` and `HEAD` only; other methods are `405` with `Allow: GET, HEAD`. Every response, the event stream included, has `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. MIME types: `.html` `text/html; charset=utf-8`, `.js`/`.mjs` `text/javascript`, `.json`/`.map` `application/json`, `.wgsl`/`.ts`/`.txt` `text/plain`, `.wasm` `application/wasm`, `.css` `text/css`, `.png`, `.jpg`/`.jpeg`, `.webp`, `.svg`, `.ico`, `.ktx2` (`image/ktx2`), `.glb` `model/gltf-binary`, `.gltf` `model/gltf+json`, anything else `application/octet-stream`.
9. **Before the first successful build** there is no `index.html`; `/` is then the compiler's **waiting page** (`package::html::dev_waiting_page`: the dev page's title, canvas and reload client, no program), so the overlay shows the failure and the first successful build reloads into the real page. The HTML comes from the compiler; the CLI never writes or patches HTML.
10. **Reload client** (amends decision 0030 item 9). On `build-succeeded` it reloads the page (M1). On `build-failed` it logs the diagnostics with `console.error` and shows them in a `<pre id="mtek-dev-overlay">` fixed over the whole page (created once, replaced on every failure): `mtek: build failed`, then per diagnostic `file:line:column: severity[code]: message` (location omitted when `source` is `null`) followed by its notes as `  = note` lines. The text is set with `textContent`, never as markup. `build-started` changes nothing. The full development overlay of `spec/tooling.md` §9 (M4) and candidate hot reload (M3) replace it later.
11. **Watcher.** `notify`'s recommended watcher on the project directory, recursive. A change counts unless its path, relative to the project directory, lies inside the output directory, inside one of its replace-on-success siblings (`<out_dir>.tmp-<id>`, `<out_dir>.old-<id>` — otherwise every build would trigger the next), or inside any directory named `.git` or `node_modules` (at any depth), or is the project directory itself. Access events (open, read, close) never count. Modification events other than renames never count for a path that is a directory: they only say that something inside changed, which arrives as its own event — and Windows reports one when a build merely lists a fresh directory. Paths are compared against the project directory as given and as canonicalised (macOS reports `/private/var/…` for `/var/…`). Excluded directories are still watched and their events dropped (simple and complete for M1; a project with a very large `node_modules` on Linux may need a higher inotify watch limit). Watcher errors are printed as warnings; the server goes on.
12. **Scheduler.** Build once at start. Then wait for a change, then until no change has arrived for 50 ms (trailing debounce), then build. A build always runs to its end; changes that arrive meanwhile are queued and, after it, debounced together into exactly one follow-up build. Builds never overlap.
13. **Shutdown.** The first Ctrl+C (`tokio::signal::ctrl_c`, on Windows too) prints `mtek dev: stopping`, lets a running build finish and write its output (never a half-written `dist/`), stops the watcher, ends the event streams and closes the server (waiting at most 5 s for other connections), prints `mtek dev: stopped` and exits `0`. A second Ctrl+C exits at once with `130`.
14. **`--open`** opens the URL after the first build (successful or not — the waiting page shows the failure) with `cmd /C start "" <url>` on Windows, `open` on macOS and `xdg-open` elsewhere, without waiting for it; a failure to start it is a warning.

## Consequences

- New dependencies `tokio`, `tokio-stream`, `axum`, `notify` and `serde_json` in `mtek-cli` only, as allow-listed in `spec/compiler-architecture.md` §2 and recorded in decision 0007. The compiler gains `package::html::dev_waiting_page` and the overlay in the dev reload client; release and test pages and every golden are unchanged.
- `mtek build`'s output path is shared: `commands::compile_and_write` returns what was written, and `mtek build` formats its outcome from it as before (decision 0032 items 4, 6, 8).
- M3 (candidate hot reload) changes the client's `build-succeeded` handling (`import()` of `program`) and can keep the server, the events and the replay unchanged. M4's overlay replaces item 10's element.
- Browser gate tests (M1-21) can serve a fixture with `mtek dev --port N <fixture>` and read the announced URL from the first stdout line, or keep using `mtek build --mode test --out` as decision 0032 describes; `mtek dev` serves dev builds only.

## Verification

`crates/mtek-cli/tests/dev.rs` runs the binary on temporary projects and speaks HTTP and SSE over `std::net::TcpStream`: MIME types and `no-store` on files, `404` for missing files and traversal attempts, `405`, the event stream's headers, the replayed failure, loopback only (the same port on the machine's own network address refuses connections), the waiting page; without the runtime bundle every build fails with `E9030`; with it, `build-started` → `build-succeeded` with `buildId` and `program`, the new build served at the event's URL, `build-failed` with `E2003` at 3:25 while the previous build stays served, the replay to a new client, recovery, no build triggered by the build's own writes, and a burst of edits that settles on a build whose id equals `mtek build`'s for the final text; on Unix, SIGINT ends the stream, prints `mtek dev: stopped`, exits `0` and closes the port. Unit tests: `src/dev/schedule.rs` (one build per burst, exactly one follow-up build for changes during a build, builds never overlap, shutdown waits for the running build), `src/dev/watch.rs` (exclusions, siblings, nested output directories, paths outside the project, event kinds, a real watcher ignoring output writes and a directory listing), `src/dev/server.rs` (MIME table, request paths, port fallback on loopback), `src/dev/hub.rs` (event JSON, replay rule, delivery), `src/dev/mod.rs` (settings, `E9999` and `E9031` build failures, the browser opener), `src/args.rs` (`--port`, `--open`), `crates/mtek-compiler/src/package/html.rs` (overlay, waiting page).
