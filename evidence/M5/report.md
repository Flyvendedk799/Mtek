**Guardrail — no fake gravity loop presented as the physics subsystem.** The solver is Rapier: `packages/physics-rapier/src/backend.ts` imports `@dimforge/rapier3d-compat` 0.21.0 and calls `world.step(...)`; the runtime holds no solver of its own (`physics/system.ts` only talks to the `PhysicsBackend` interface, `physics/types.ts`). The browser specs measure behaviour no hand-written gravity loop would reproduce: free fall that follows the engine's substepped model (`y₀ − g·dt²·(n²/2 + n/8)`, matched to five digits), resting contact at 0.49993 rather than 0.5, contact and sensor events in the derived ticks, and the tunnelling behaviour below. Unit tests use a fake backend for ordering only; every physical behaviour is asserted against the real engine on hardware.

## Unsupported / remaining

- **High-speed bodies (documented limitation, `spec/physics.md` §7.1).** No continuous collision detection in v0.1, and `setCcdEnabled(true)` was measured to change nothing for two moving bodies. A ball cannot tunnel a thin dynamic plate when `v·dt ≤ t/2 + r + 0.02` (7.2 m/s for a 0.1 m plate and a 0.05 m ball at 1/60 s); above that it tunnels in the share `1 − window / (v·dt)` of the phases. Against a **static** wall nothing ever passed (3 to 100 000 m/s in Node, up to 240 m/s in the browser); why the engine protects that pair is not established and is labelled a hypothesis. Programs should keep thin walls static or clamp speeds.
- **Kinematic movers** against resting bodies are not characterised (a scratch run deviated at 3 m/s in some phases); only dynamic bodies are covered by the tunnelling model.
- **Sensor tick tolerance.** In the sensor spec one delivery arrives one tick after the derived tick (39 against 38, the allowed ±1); the counts and the order are exact.
- **Hot reload** drops velocities and queued commands of a reloaded world (0066 item 16); poses are carried.
- **Entity table** (`liveEntities`, `entitySlots`) still reads 51 after `dispose()` in the waves test: it is CPU bookkeeping, not a GPU or physics resource, and the spec asserts only the resources. The slot table and arenas never shrink (documented above).
- The real-clock pause spec depends on `requestAnimationFrame` running in headless Chrome; its bounds are in elapsed wall-clock time, so a slow frame rate cannot fail it, only a simulated jump can.
- The playground's input is injected through the harness, not real keyboard events; sensor exit is only seen indirectly there (the exit counts are asserted by `physics-sensor.spec.ts`).
- `main` was not pushed and CI was not run on `c4748ac` when this report was written.

## Defects found and fixed during M5

- Merge integration: three invalid manifest examples written for M4-14 carried `physics: true` without the `physicsModule` that M5-05 made required, so they failed for two reasons instead of one (found by `manifest_model`; fixed in the merge, `tests/abi/manifests/invalid/binding-light-dep-bad-field.json`, `light-missing-classes.json`, `light-unknown-class.json`).
- M5-05 reported a new runtime code, `E8104` (a value that is not finite is given to a body), from the range `spec/diagnostics.md` reserved for further physics codes (decision 0066 item 11); the one test that used `E8104` as a placeholder now uses `E8105`.
- The M5-06 engine-level specs found no defect in the M5-05 runtime; the mutation checks recorded in 0068 (a `removeBody` that does not remove, an unchecked second entity, a 40 mm prediction distance, `resume()` keeping the last timestamp) each make a spec fail.
